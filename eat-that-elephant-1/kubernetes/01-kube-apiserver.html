kube-apiserver Deep Dive

The front door of Kubernetes: every request — kubectl, Helm, controllers, kubelets — passes through here before it reaches etcd.

What Is It?

The API Server is the front door of Kubernetes.

Every request enters the cluster through kube-apiserver.

Nothing talks directly to etcd except the API Server.

Examples

  • kubectl
  • Helm
  • Controllers
  • Scheduler
  • Kubelets
  • Operators

All communicate through the API Server.

Responsibilities

  • Accept API requests
  • Validate requests
  • Authenticate users
  • Authorize operations
  • Apply admission controls
  • Persist data into etcd
  • Expose Kubernetes APIs

Responsibilities — Detailed Walkthrough

1. Accept API Requests

  • The Kubernetes API Server is the entry point for all cluster operations.
  • It receives requests from users, kubectl, controllers, and external applications.
  • Requests usually arrive through REST APIs over HTTPS.
  • Every create, update, delete, or read operation starts here.
  • The API server acts as the front door of the control plane.
  • It converts incoming HTTP requests into Kubernetes objects and actions.
  • Without this component, no communication with the cluster is possible.

2. Validate Requests

  • After receiving a request, Kubernetes checks whether the request is correctly formed.
  • Validation ensures required fields are present and data types are correct.
  • It prevents invalid or malformed resources from entering the cluster.
  • Schema validation is based on Kubernetes API definitions.
  • For example, a Deployment without a container image will fail validation.
  • Validation protects cluster consistency and reliability.
  • Only valid objects proceed to the next processing stage.

3. Authenticate Users

  • Authentication verifies the identity of the requester.
  • Kubernetes answers the question, “Who is making this request?”
  • Users can authenticate using certificates, tokens, IAM roles, or OIDC providers.
  • Authentication does not determine permissions.
  • It simply establishes the identity of the user or service account.
  • If authentication fails, the request is immediately rejected.
  • Successful authentication passes the request to the authorization phase.

4. Authorize Operations

  • Authorization determines what an authenticated user is allowed to do.
  • Kubernetes asks, “Can this user perform this action?”
  • It checks permissions using mechanisms like RBAC, ABAC, or Webhooks.
  • Actions include creating pods, deleting deployments, or viewing secrets.
  • Unauthorized operations are denied even if the user is authenticated.
  • RBAC is the most commonly used authorization mechanism.
  • This stage enforces security and least-privilege access.

5. Apply Admission Controls

  • Admission Controllers inspect requests before objects are stored.
  • They can modify, reject, or enforce policies on resources.
  • Examples include setting default values or enforcing security standards.
  • They act after authorization but before persistence.
  • Mutating admission controllers can change requests automatically.
  • Validating admission controllers ensure policies are satisfied.
  • This stage helps maintain compliance and cluster governance.

6. Persist Data into etcd

  • Kubernetes stores cluster state information inside etcd.
  • etcd is a distributed key-value database used by the control plane.
  • Resource definitions such as Pods, Deployments, and Services are saved here.
  • The API server writes changes to etcd after all checks are complete.
  • etcd serves as the single source of truth for the cluster.
  • Controllers continuously read this data to maintain the desired state.
  • Losing etcd data can affect the entire cluster's operation.

7. Expose Kubernetes APIs

  • The API Server provides REST endpoints for Kubernetes resources.
  • Components such as kube-scheduler and kube-controller-manager interact through these APIs.
  • Users access these APIs using kubectl, SDKs, or CI/CD pipelines.
  • APIs support operations like GET, POST, PUT, PATCH, and DELETE.
  • This interface allows automation and integration with external tools.
  • API versioning ensures backward compatibility between releases.
  • By exposing APIs, Kubernetes enables a consistent way to manage cluster resources.

API Groups & Versioning

Every Kubernetes object is addressed by an API group and version, not a single flat namespace of types:

  • The core group (also called the "legacy" group) has no name — Pods, Services, ConfigMaps, Secrets use apiVersion: v1 directly.
  • Named groups use apiVersion: <group>/<version>, e.g. Deployments and ReplicaSets live in apps/v1, Jobs and CronJobs in batch/v1, Roles and RoleBindings in rbac.authorization.k8s.io/v1.
  • Each version carries a maturity level — v1alpha1 (experimental, may change or disappear), v1beta1 (well-tested, minor changes possible), v1 (stable, backward-compatible going forward).

This grouping lets the API surface grow — new resource types, new versions of existing ones — without breaking clients pinned to a stable group/version.

Why It Exists

Without a central API:

  • Scheduler
  • Controller
  • Kubelet
  • etcd

would all need direct communication.

The API Server provides:

  • Single entry point
  • Security boundary
  • Consistent validation
  • Auditability

Failure Impact

If API Server fails:

  • New Deployments Fail
  • Scaling Fails
  • kubectl Fails

Existing Pods usually continue running.

Cluster management becomes unavailable.

Tradeoffs

Advantages

  • Centralized security
  • Validation
  • Auditing
  • Consistent API access

Disadvantages

  • Critical dependency
  • Can become a bottleneck at large scale

Failure Scenario

Symptoms:

  • kubectl commands fail
  • Deployments fail
  • Scaling fails

Existing workloads continue running.

High Availability & Scaling

  • Because kube-apiserver keeps no state of its own — everything lives in etcd — it can run as multiple identical replicas behind a load balancer, and any replica can serve any request.
  • A watch cache lets the API server serve most reads and watches from in-memory state instead of hitting etcd for every request, which is what makes it scale to many clients watching the same objects.
  • API Priority and Fairness classifies and queues incoming requests so that a burst of low-priority traffic (e.g. a runaway controller) can't starve high-priority requests (e.g. node heartbeats) of capacity.
