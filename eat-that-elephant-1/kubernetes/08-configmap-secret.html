ConfigMap & Secret: Separating Config from Sensitive Data

Non-sensitive vs. sensitive configuration, why Base64 isn't encryption, and how Pods consume both without hardcoding values into the image.

ConfigMap vs. Secret: Separating Configuration from the Image

In Kubernetes, ConfigMap and Secret are mechanisms for separating application configuration from the container image and Pod definition.

  • A ConfigMap is designed for non-sensitive configuration, such as database paths, application modes, feature flags, URLs, ports, and environment-specific settings.
  • A Secret is intended for sensitive configuration, such as passwords, API keys, tokens, and certificates.

Both objects can be consumed by Pods as environment variables or mounted as files, allowing the same container image to be deployed across different environments with different configuration.

A Worked Example: app-config and app-secret

A ConfigMap named app-config contains DB_PATH, which tells the application where the SQLite database exists inside the container.

A Secret named app-secret contains GRAFANA_ADMIN_PASSWORD, which is sensitive and therefore separated from normal application configuration.

namespace: microservices means both objects exist specifically inside the microservices namespace and can normally be referenced by Pods in that namespace.

Secrets Are Encoded, Not Encrypted

A Kubernetes Secret is not automatically equivalent to encrypted storage. Kubernetes Secret data is commonly represented as Base64 when using the data field, but Base64 is only encoding, not encryption.

Using stringData instead allows a Secret to be written as normal text in the manifest; Kubernetes converts it into the Secret's internal representation.

Actual protection of Secret data depends on controls such as encryption at rest in the Kubernetes API datastore, RBAC permissions, secure access to the cluster, and avoiding secrets in Git repositories.

Why the Distinction Matters

The ConfigMap is appropriate for values that are safe to expose to application users or developers, while the Secret should be protected because anyone with sufficient Kubernetes permissions may be able to retrieve it.

Pods can receive these values as environment variables — for example, the application can read DB_PATH and GRAFANA_ADMIN_PASSWORD from its environment without hardcoding them into the container image. This separation also allows configuration to change without rebuilding the application image.

What Is a ConfigMap?

A ConfigMap is a Kubernetes resource used to store non-sensitive configuration data separately from application code and container images. It enables applications to be configured dynamically without rebuilding images, supporting the cloud-native principle of separating configuration from code.

ConfigMaps are typically used for:

  • Application settings
  • Feature flags
  • Log levels
  • Service endpoints
  • Configuration files
  • Runtime parameters

ConfigMaps should never be used for passwords, API tokens, certificates, or credentials. Those belong in Kubernetes Secrets.

Why ConfigMaps Exist

Without ConfigMaps, configuration is often baked into container images. Any configuration change requires:

  • Modifying the image
  • Rebuilding the image
  • Pushing the image
  • Redeploying the application

ConfigMaps eliminate this coupling by externalizing configuration. The same application image can be deployed across multiple environments while using different configuration values.

Benefits include:

  • Better portability
  • Simplified deployments
  • Faster configuration changes
  • Environment-specific configuration management
  • Improved CI/CD workflows
  • Reduced image proliferation

Ways Applications Consume ConfigMaps

1. Environment Variables

The application receives ConfigMap values as environment variables during container startup.

Characteristics:

  • Values are loaded once during process startup.
  • Environment variables become part of the process environment.
  • Running processes do not automatically receive updates.

Impact of ConfigMap change:

  • Kubernetes updates the ConfigMap object.
  • Existing Pods continue using old values.
  • Pod restart is required to load new values.

2. Mounted Volumes

ConfigMap data is mounted into the container filesystem as files.

Characteristics:

  • Kubernetes automatically updates mounted files when the ConfigMap changes.
  • No Pod restart is required for the file update itself.
  • The container continues running while files are refreshed.

Impact of ConfigMap change:

  • Kubernetes updates the mounted files.
  • The application may or may not use the new values depending on how it handles configuration reloads.

  • Kubernetes does not control how the application consumes the updated file.
  • Application behavior is independent from ConfigMap behavior.

Possible outcomes:

  • Application automatically reloads configuration.
  • Application requires a manual reload signal.
  • Application requires a full restart.

The behavior depends entirely on application design.

ConfigMap Consumption Tradeoffs

Environment Variables

Advantages:

  • Simple and easy to understand.
  • Widely supported by applications.
  • Clean integration with twelve-factor applications.
  • Easy debugging using standard environment inspection.

Disadvantages:

  • Configuration changes require Pod restarts.
  • Not suitable for frequently changing configuration.
  • Can cause rollout delays during updates.
  • Large configurations become difficult to manage.

Best suited for: stable configuration, infrequently changing settings, small sets of configuration values.

Mounted Files

Advantages:

  • Configuration updates can propagate without restarting Pods.
  • Suitable for large configuration files.
  • Better for applications expecting file-based configuration.
  • Supports dynamic configuration management.

Disadvantages:

  • Application must support configuration reloading.
  • Kubernetes updates files but cannot force application refresh.
  • Behavior varies between applications.
  • More operational complexity than environment variables.

Best suited for: large configuration files, frequently updated configuration, applications supporting runtime reload.

ConfigMap Production Considerations

ConfigMap updates and application updates are two separate concerns.

A successful ConfigMap update only guarantees:

  • Kubernetes stored the new configuration.
  • Mounted files were refreshed if volume-based mounting is used.

It does not guarantee:

  • Application reloaded configuration.
  • Application is actively using new values.
  • Configuration changes are reflected in runtime behavior.

Because of this uncertainty, many production teams intentionally trigger Deployment rollouts after ConfigMap updates.

Benefits of rollout-based updates:

  • Predictable behavior
  • Consistent configuration across replicas
  • Easier troubleshooting
  • Reduced application-specific reload logic
  • Guaranteed configuration synchronization

The tradeoff is temporary Pod replacement and deployment churn.

ConfigMap Key Takeaways

  • ConfigMaps separate configuration from application code.
  • They are intended only for non-sensitive configuration.
  • Environment variable consumption requires Pod restarts after updates.
  • Volume-mounted ConfigMaps update automatically at the filesystem level.
  • Kubernetes updates files, not application memory.
  • Application reload behavior depends on the application itself.
  • ConfigMap updates do not guarantee runtime configuration updates.
  • Environment variables provide simplicity but require restarts.
  • Volume mounts provide flexibility but introduce reload complexity.
  • Many production environments perform Deployment rollouts after ConfigMap changes to ensure consistency and predictability.

Key Distinction

Remember it this way

ConfigMap = configuration that is not sensitive.

Secret = sensitive configuration that needs controlled access, but Base64 alone does not provide encryption.

Protecting Secrets in Production

In production, Secrets should generally be protected with RBAC, encryption at rest, restricted Pod/service-account permissions, secret rotation, and preferably an external secret-management system such as AWS Secrets Manager, HashiCorp Vault, or another dedicated secret manager.
