Persistent Storage & Distributed Databases on Kubernetes

PV/PVC/StorageClass, why each database instance gets its own volume, and where Kubernetes' job ends and the database's replication/failover job begins.

PersistentVolumes, PersistentVolumeClaims & StorageClasses

A PersistentVolume (PV) is a Kubernetes abstraction representing storage that exists independently of a Pod, while a PersistentVolumeClaim (PVC) is a request from an application for a specific amount and type of storage. The Pod normally consumes storage through the PVC rather than directly interacting with the PV.

Kubernetes can either use manually created PVs or dynamically provision PVs through a StorageClass and a storage provisioner such as the AWS EBS CSI driver.

A storage access mode defines how a volume can be mounted:

  • ReadWriteOnce means a volume can be mounted for read/write access by workloads on one node.
  • ReadWriteMany allows simultaneous read/write mounting from multiple nodes, when the underlying storage supports it.

One Volume Per Database Instance

For a distributed database, each database instance generally has its own persistent volume rather than all database instances sharing one filesystem. For example, three database nodes would normally have three Pods, three PVCs, and three underlying volumes.

A Kubernetes StatefulSet is commonly used because database nodes require stable identities, predictable Pod names, and stable storage associations. Its volumeClaimTemplates allow Kubernetes to automatically create a separate PVC for every StatefulSet replica.

The resulting relationship is conceptually:

Pod → PVC → PV → physical storage

If a database Pod is recreated, its StatefulSet identity and PVC allow it to reconnect to its existing storage instead of starting with an empty filesystem.

Storage Provides Durability, Not Distribution

The persistent volume provides durability, but it does not itself make a database distributed or highly available. Replication, sharding, leader election, consistency, failover, and data synchronization are responsibilities of the database system. Kubernetes provides the infrastructure on which those database nodes run.

hostPath vs. Network/Cloud-Backed Storage

A hostPath volume stores data directly on the filesystem of a specific Kubernetes node, so it is simple but tightly coupled to that node. If the Pod moves to another node, the original data does not automatically move with it.

Production Kubernetes clusters therefore commonly use network- or cloud-backed storage, such as AWS EBS through the EBS CSI driver, instead of hostPath. With dynamically provisioned storage, Kubernetes creates an individual persistent volume for each database node, allowing the database to maintain independent storage while the database software manages replication or distribution.

The Theory, in One Line

Where the responsibility line sits

Kubernetes manages workload identity and storage lifecycle; PVCs request storage; PVs represent storage; StorageClasses dynamically provision storage; StatefulSets provide stable identities and per-Pod storage; and the distributed database software manages replication, sharding, consistency, and failover.
