kube-controller-manager Deep Dive

The reconciliation loops that keep actual cluster state converging on desired state.

What Is It?

Controller Manager runs multiple controllers.

Controllers are reconciliation loops.

Their job:

Desired State
       =
Actual State

Desired State vs. Actual State

TermDefinitionExample
Desired StateThe configuration you declare in your YAML manifests. It is stored in etcd (the cluster's database).replicas: 5 in a Deployment YAML.
Actual StateThe real-world status of your cluster at this very moment.Only 3 Pods are currently running because 2 crashed.
ReconciliationThe continuous process of comparing Desired vs. Actual and taking action to correct drift.Kubernetes starts 2 new Pods to bring the count back to 5.

What Is a Controller?

A controller continuously watches cluster state.

Example:

Desired Pods = 3
Actual Pods = 2

Controller detects mismatch:

Create 1 More Pod

      ↓

DaemonSet Controller

Ensures exactly one copy of a Pod runs on every node (or every matching node) — used for node-level agents like log collectors or CNI plugins.

CronJob Controller

Creates a new Job on a schedule, the same way cron creates a new process on a schedule.

Theory: The Watch-Reconcile Loop

The Watch-Reconcile loop is the engine that powers every Kubernetes controller. It's how the controller efficiently watches for changes without overwhelming the API Server.

The Problem It Solves

Kubernetes has thousands of resources (Pods, Services, Deployments, etc.). Polling the API Server every few seconds for changes would crash the API Server due to massive load.

Instead, Kubernetes uses a watch-based event system — the controller "subscribes" to changes and gets notified when something happens.

The Four Core Components

ComponentPurposeAnalogy
InformerWatches the API Server for changes to a specific resource type (e.g., Pods) and caches the data locally.A news subscription — you get notified when something changes.
ListerReads from the local cache (not the API Server) to query resources quickly without network calls.A local copy of the news — you can read it instantly without calling the news agency.
SharedInformerA shared version of Informer where multiple controllers can use the same watch connection to reduce API Server load.A shared newspaper subscription — multiple people read the same copy.
Work QueueA queue that holds events (add, update, delete) that need to be processed. Helps with retries, deduplication, and rate limiting.A to-do list — you put tasks here and process them one by one.

Deep Dive into Each Component

1. Informer (The Watcher)

What it does: An Informer uses the Kubernetes Watch API to establish a persistent connection to the API Server. It listens for events (Add, Update, Delete) on a specific resource type.

How it works:

  • On startup, it performs a List operation to get all existing resources.
  • It then starts a Watch to get incremental changes.
  • It stores all this data in a local cache (called an Indexer).

Why it matters: Without Informers, every controller would need to constantly poll the API Server, causing massive network congestion.

2. Lister (The Reader)

What it does: Lister is a read-only interface to the Informer's local cache.

How it works: Instead of making an API call to GET /api/v1/pods, the controller calls lister.Pods("default").Get("nginx-pod"). This reads from the local cache (memory), which is instantaneous.

Why it matters: Reading from cache is thousands of times faster than making an API call. It also reduces load on the API Server and etcd.

3. SharedInformer (The Efficient Watcher)

What it does: Normally, each controller would have its own Informer and its own watch connection to the API Server. If you have 50 controllers watching Pods, that's 50 watch connections — bad for the API Server.

How it works: SharedInformer allows multiple controllers to share the same watch connection. They all register their event handlers with the same SharedInformer.

Why it matters: It dramatically reduces API Server load. One watch connection vs. 50.

4. Work Queue (The Traffic Controller)

What it does: A work queue holds events (keys/identifiers of resources that changed) until the controller is ready to process them.

How it works:

  • Event handlers push a key (e.g., default/nginx-pod) into the work queue.
  • Worker goroutines pop keys from the queue and call the reconciliation logic.
  • The queue supports retries (if processing fails, the key goes back to the queue), rate limiting (slow down if errors happen), and deduplication (don't process the same key twice if multiple events occur).

Why it matters: It decouples event observation from event processing. If reconciliation takes 5 seconds, the Informer can still collect events during that time without blocking.

Why It Exists

Kubernetes is built on reconciliation.

Users define:

Desired State

Controllers enforce:

Actual State

Failure Impact

If Controller Manager fails:

Existing Workloads Continue Running

But Kubernetes stops correcting problems.

Examples:

  • Failed Pods not recreated
  • Node failures not handled
  • Replica counts not maintained
  • Jobs not managed

Tradeoffs

Advantages

  • Self-healing
  • Continuous reconciliation
  • Automatic recovery

Disadvantages

  • Large clusters generate significant reconciliation activity
  • Misconfigured controllers can cause cascading actions

Failure Scenario

Symptoms:

  • Pods not recreated
  • Nodes not reconciled
  • Replica drift occurs

Cluster loses self-healing capabilities.

High Availability

Like kube-scheduler, kube-controller-manager runs as several replicas but only one is active — it holds a Lease object in etcd and renews it periodically. If the active instance crashes, its lease expires, and a standby replica claims the lease and starts running the reconciliation loops. Only one replica ever reconciles at a time, so controllers never race each other.

For the full mechanics — the election algorithm, lease tuning parameters, failure-recovery timelines, and split-brain prevention — see Leader Election: HA for Controller Manager & Scheduler.
