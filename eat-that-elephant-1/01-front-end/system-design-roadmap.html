System Design Roadmap — DevOps/SRE → System Design Interviews

A sequenced prep path for infra-heavy engineers: move fast through the building blocks you already run in production, slow down on interview framing (requirements → capacity → API → HLD → deep dive → tradeoffs) and the few coding-adjacent pieces (consistent hashing, rate limiters, LRU, tries) that system design rounds lean on.

Context this roadmap assumes about you: ~4 yrs DevOps/SRE, AWS CloudOps certified, hands-on with ECS, Lambda, API Gateway, CloudFront, RDS, OpenSearch, CodePipeline/CodeBuild/CodeDeploy, PostgreSQL, Kubernetes (kubeadm + EKS), SQS/DLQ, PubNub, streaming platforms. You're weak on DSA-style coding, not on infrastructure.

What that means strategically: most people prepping for system design come from the coding side and have to learn infra concepts (load balancers, queues, caching, sharding) from scratch. You already run these in production. Your gap isn't “what is a message queue” — it's translating operational knowledge into the structured interview format (requirements → capacity estimation → API design → HLD → deep dive → tradeoffs) and picking up the handful of algorithmic/data-structure concepts (consistent hashing, rate limiter algorithms, LRU cache, trie for autocomplete) that system design rounds lean on. This roadmap is sequenced accordingly — it moves fast through things you already know operationally and slows down on interview framing and the coding-adjacent pieces.

Phase 0: Interview Framing do this first · 2–3 days

Before terminology, learn the shape of a system design answer — this is what separates “knows AWS” from “passes the interview.”

  • The standard flow: Clarify requirements → Define scale (capacity estimation) → API design → High-level design (boxes and arrows) → Deep dive into 1–2 components → Bottlenecks/tradeoffs → Wrap up
  • Functional vs non-functional requirements — you must explicitly state assumptions (QPS, read:write ratio, data size, latency SLA) before designing
  • Back-of-envelope math: QPS, storage estimates, bandwidth — practice doing this in your head in under 2 minutes
  • Practice resource: Alex Xu's System Design Interview Vol 1 & 2 (read the first 2 chapters now — they teach exactly this framing)

Phase 1: Core Building Blocks fast pass

You know most of this operationally. For each, the goal is: know it well enough to justify choosing it in an interview, not just operate it.

Deliverable for this phase: for each row, be able to say “we use X because Y, and the tradeoff is Z” in one breath.

Phase 2: Distributed Systems Theory the real gap

This is where operational knowledge stops being enough — interviews probe the why behind distributed systems, not just “it works.”

  • CAP theorem — not the buzzword version, the actual tradeoff space (and why it's often mischaracterized)
  • Consistency models: strong, eventual, causal — map these to real systems you've used (Dynamo = eventual, RDS single-region = strong)
  • Consensus basics: what Paxos/Raft solve, not the algorithm internals (interviewers rarely want you to whiteboard Raft, but you should know why leader election matters)
  • Idempotency and exactly-once processing — critical given your SQS/DLQ background, tie this to what you already do
  • Distributed locking (Redis-based, Zookeeper-based)
  • Consistent hashing — this one is worth implementing by hand once, it shows up constantly (load balancers, distributed caches, sharding)
  • Failure detection: heartbeats, gossip protocols
  • Idempotency keys, dedup, and the outbox pattern for reliable event publishing

Practice resource: Designing Data-Intensive Applications (Kleppmann) — chapters 5, 7, 9 specifically cover this phase. Dense but this is the book that separates people who memorized components from people who understand systems.

Phase 3: The Coding-Adjacent Gap targeted, not a DSA grind

You don't need LeetCode-grade DSA for system design rounds, but a handful of concepts get asked as “mini implementations” inside design questions. Learn these specifically, skip general DSA prep:

  • LRU Cache — implement it once (HashMap + doubly linked list). Asked constantly as a standalone or embedded question.
  • Trie — for autocomplete/typeahead design questions
  • Consistent hashing ring — implement a basic version
  • Rate limiter (token bucket / sliding window) — implement in whatever language you're comfortable in (Python is fine, doesn't need to be production-grade)
  • Bloom filter — concept + when to use it (dedup at scale, cache-miss avoidance)
  • Merkle trees — concept only, comes up in “how does DynamoDB detect replica divergence”

You can do all of this in Python without deep coding fluency — these are ~30–50 line implementations, not algorithmic puzzles. Treat it as “write pseudocode that runs,” not LeetCode grinding.

Phase 4: Classic System Design Questions apply everything

Work through these in the standard interview format (Phase 0 flow). Order is easy → hard:

  1. URL shortener (tests: hashing, capacity estimation, DB choice)
  2. Rate limiter (tests: Phase 3 algorithms)
  3. Key-value store / distributed cache (tests: consistent hashing, replication)
  4. Notification system (you have real production experience here — PubNub/FCM/APNs — this should be your strongest answer)
  5. Chat system / WhatsApp-style messaging (tests: WebSockets, message ordering, delivery guarantees)
  6. News feed / Twitter timeline (tests: fan-out on write vs read, caching)
  7. Live streaming platform (you built this — Baseball Scoring platform — walk through it as a real answer)
  8. Distributed job scheduler (tests: queues, idempotency, leader election)
  9. Search autocomplete (tests: trie, ranking)
  10. Ride-sharing / location-based service (tests: geospatial indexing, quadtrees/geohashing)

Practice resource: Alex Xu Vol 1 & 2 cover most of these directly. ByteByteGo YouTube channel for visual walkthroughs.

Phase 5: Advanced / Staff-Level Topics after 1–4 are solid

  • Multi-region architecture, active-active vs active-passive
  • Data pipeline design (batch vs stream — Kafka + Flink/Spark territory)
  • Chaos engineering and failure injection in design (this plays directly to your SRE background — bring it up proactively in interviews)
  • Cost-aware architecture tradeoffs (you already think this way from AWS work — make it explicit in interview answers)
  • Observability as a first-class design concern (metrics/logs/traces at scale) — your CloudWatch/monitoring background is a direct asset here
  • Security in system design: authN/authZ at scale, zero-trust networking

How to use your existing projects

You have real answers for two classic questions already — don't treat them as separate from interview prep, prep with them:

  • Notification system → your PubNub/FCM/APNs/SQS work
  • Live streaming/scoring platform → your 10-service AWS microservices build

Practice narrating these in the Phase 0 structure (requirements → scale → API → HLD → deep dive → tradeoffs). This is usually the strongest material in an interview because it's real and you can defend every decision.
