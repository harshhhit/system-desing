Complete Guide: Web Rendering & Architecture

Rendering Strategies

Core theory, production tradeoffs, failure scenarios, real-world usage, and interview perspective

1. Core Explanation

Rendering strategy answers one question: where does HTML get generated, and when? There are four points on this spectrum: build time, request time, client time, and a hybrid of these.

  • CSR (Client-Side Rendering): Server sends a near-empty HTML shell + a JS bundle. Browser downloads JS, executes it, builds the DOM, fetches data, renders. This is the default for a plain React/Vue SPA (create-react-app, Vite).
  • SSR (Server-Side Rendering): On every request, the server runs your component tree, produces full HTML, and sends that to the browser. The browser shows content immediately, then hydrates (React attaches event listeners to the existing DOM instead of rebuilding it).
  • SSG (Static Site Generation): HTML is generated once, at build time, and pushed to a CDN. Every request just serves a static file — no server compute per request.
  • ISR (Incremental Static Regeneration): Static like SSG, but pages can be regenerated in the background after a TTL or on-demand (via webhook), without a full rebuild.
  • Streaming SSR / RSC (React Server Components): Instead of blocking until the entire page's HTML is ready, the server streams chunks as they resolve — so a slow data-dependent section doesn't block the whole page from painting.

Internally, the mechanism that ties SSR/SSG back to interactivity is hydration: the server-rendered HTML is a visual imposter — it looks interactive but has zero JS behavior attached until React walks the DOM and binds handlers to already-existing nodes (as opposed to CSR, where React builds the DOM from scratch).

Why companies choose what they choose

  • CSR: internal dashboards, admin panels, authenticated apps where SEO is irrelevant and you want to minimize server infra (e.g., a SaaS app behind a login).
  • SSR: e-commerce product pages, news sites — content changes often, SEO matters, and you can't pre-build every URL (e.g., Amazon product pages, personalized feeds).
  • SSG: marketing sites, docs, blogs — content changes rarely relative to traffic volume (e.g., Stripe docs, most landing pages).
  • ISR: e-commerce catalogs with thousands of SKUs — too many pages to SSR on every request, but too dynamic (price/stock changes) for pure SSG (Next.js commerce sites use this heavily).

At low scale: the difference between SSR and CSR barely matters — a few hundred req/s is nothing for a Node server.

At high scale: SSR compute cost scales linearly with traffic (every request = server-side render = CPU cycles), which is why high-traffic sites push as much as possible to SSG/ISR + CDN, and reserve SSR only for genuinely personalized/real-time pages.

3. Failure Scenarios and Debugging

Hydration mismatch — the most infamous SSR bug class

  • Symptom: Console warning "Text content does not match server-rendered HTML," UI flickers or breaks after load.
  • Root cause: Server-rendered HTML differs from what client-side render produces — common causes: Date.now()/Math.random() used during render, typeof window branching, browser extensions mutating the DOM before hydration, or locale/timezone differences between server and client.
  • Detection: React dev console warnings; in production, watch for a spike in client-side error tracking (Sentry) right after deploys touching SSR code.
  • Fix: Move non-deterministic values to useEffect (client-only), or use suppressHydrationWarning sparingly for genuinely-expected mismatches (like timestamps).

SSR server overload

  • Symptom: p99 latency spikes, 502/504s from your Node SSR servers under load.
  • Root cause: Render-per-request is CPU-bound; a traffic spike (e.g., marketing campaign) can exhaust Node's single-threaded event loop if renders are slow (heavy component trees, blocking data fetches in the render path).
  • Detection: CPU utilization metrics on SSR pods, event loop lag metrics (perf_hooks or APM tools like Datadog's Node integration).
  • Fix: Add a caching layer in front of SSR (cache rendered HTML for N seconds per URL), horizontal autoscaling on CPU, or move eligible pages to ISR.

Stale ISR content

  • Symptom: Users see outdated prices/inventory.
  • Root cause: Revalidation window too long, or on-demand revalidation webhook failing silently.
  • Detection: Compare CDN cache age header against expected TTL; alert on revalidation webhook failure rate.
  • Fix: Shorten revalidate interval for volatile data, add on-demand revalidation triggered by your CMS/inventory system on writes.

4. Real-World Example

Amazon-style product page: Uses SSR or ISR — because the page needs to be crawlable (SEO for product discovery) and reflect near-real-time stock/pricing, but pre-rendering millions of SKUs on every deploy is infeasible. ISR lets them regenerate a product page only when it's actually requested and stale, or push updates via webhook when inventory changes.

Stripe docs: Pure SSG — content changes maybe a few times a day via a CMS/git push, traffic is massive, and paying for server compute per doc-page-view would be wasteful when a CDN can serve a static file for fractions of a cent.

Gmail-style inbox: Pure CSR — no SEO need (behind auth), highly interactive, real-time updates via WebSocket — SSR would add hydration overhead with zero SEO benefit.

5. Related Concepts

  • Caching/CDN — directly determines how effective SSG/ISR are in practice.
  • Core Web Vitals (LCP specifically) — the metric that rendering strategy most directly impacts.
  • Edge rendering — running SSR logic at CDN edge nodes instead of a centralized origin server, to cut TTFB globally.
  • Critical rendering path — the browser-side mechanics of turning HTML/CSS/JS into pixels, which hydration interacts with.

6. Interview Perspective

Common question: "Design the frontend architecture for [e-commerce site / social feed / dashboard] — how would you handle rendering?" Expected answer shape: identify which pages need SEO + freshness (product pages → SSR/ISR) vs which don't (checkout flow, user dashboard → CSR), and justify the split with cost/latency tradeoffs — not just naming the technologies.

Common follow-up: "What's a hydration mismatch and how do you debug it?" — expects you to name the root causes (non-deterministic render output) and the fix, not just "clear cache and reload."

7. Best Practices

  • Default to static/ISR wherever content allows it — reserve SSR for genuinely per-request-personalized content.
  • Never do heavy data fetching inside the render-blocking path of SSR — use streaming/Suspense boundaries so slow sections don't block the whole page.
  • Keep server and client render logic deterministic — no Date.now(), Math.random(), or window-dependent branching in shared render code.
  • Cache SSR output at the edge/CDN even for "dynamic" SSR pages, with short TTLs — most traffic doesn't need millisecond freshness.
