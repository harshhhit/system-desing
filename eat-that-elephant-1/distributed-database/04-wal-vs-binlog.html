WAL vs Binlog — Storage Engine vs Server Log

A companion deep-dive to the Distributed Data Roadmap (Phase 0). The junior answer — "WAL is for crash recovery, binlog is for replication" — passes. The principal-engineer answer explains the storage-engine level (physical vs logical), the timing of writes, and the replication topology implications.

The 10-Second TL;DR (the interview hook)

  • WAL (Write-Ahead Log): the database's "insurance policy" against crashes. Lives at the storage-engine level. Logs physical changes to disk pages.
  • Binlog (Binary Log): the database's "tape recorder" for sharing data. Lives at the server level. Logs logical changes (SQL statements or row mutations) for replication and point-in-time recovery.

Part 1 — The Basic Differences

Part 2 — Deep-Dive Mechanics: an UPDATE in MySQL/InnoDB

Interviewers care about the order of operations. The exact choreography:

  1. Buffer pool: the database reads the disk page into memory and modifies the row.
  2. WAL write (InnoDB redo log): before the page is flushed to disk, the physical change is forced to the WAL on disk (fsync). This is the write-ahead guarantee.
  3. Binlog write: the logical change is written to the binlog on disk.
  4. Prepare / commit (XA protocol): MySQL uses a two-phase commit (2PC) between the WAL (storage engine) and binlog (server) to ensure they match.
  5. Data flush: eventually, the memory pages are asynchronously flushed to the actual data files (.ibd files).

The senior insight: the WAL is written during the transaction; the binlog is written at commit time. If the database crashes between step 2 and step 3, the WAL lets InnoDB roll forward committed changes, but the binlog doesn't have the change — so replicas stay safe (they never receive it).

Part 3 — Physical vs Logical (the hidden gold)

This is the distinction that puts you above 90% of candidates.

  • WAL (physical): because it logs physical page offsets, it is extremely compact and fast. No SQL parsing, no figuring out which rows changed — you literally overwrite the bytes on disk. That's why WALs are used for crash recovery: raw, fast byte-shifting.
  • Binlog (logical): because it logs rows/SQL, it is independent of the storage engine. You can use a binlog to replicate from MySQL (InnoDB) to a completely different system — Kafka, Elasticsearch, a data warehouse.
    • Row-based binlog: logs the "before" and "after" image of the row.
    • Statement-based binlog: logs the exact SQL.

The catch: because the binlog is logical, it is larger and slower than the WAL. A massive UPDATE touching 1 million rows produces a tiny WAL entry (a few page changes) but a huge binlog entry (1 million row images).

Part 4 — The Advanced Twist: the MySQL 2PC trap

Interviewer: "What happens if the server crashes right after writing the WAL but BEFORE writing the binlog?"

Junior answer: "The data is lost."

Senior answer: "In MySQL/InnoDB, the WAL and binlog are synchronized using an internal distributed transaction (XA). If the WAL is written but the binlog isn't, the transaction remains in a PREPARE state on crash recovery. During recovery, InnoDB looks at the binlog. Since the binlog has no commit record, InnoDB rolls back the transaction — even though the WAL has the changes. This ensures the master and replicas never diverge."

Part 6 — The PostgreSQL Curveball

If the interviewer mentions PostgreSQL, pivot hard. PostgreSQL has no separate binlog — in Postgres, the WAL is the binlog. It is used for both crash recovery and replication (via streaming replication).

  • MySQL's philosophy: separate the storage engine (InnoDB WAL) from the server (binlog) for flexibility.
  • PostgreSQL's philosophy: tightly couple the log to the storage engine, so you don't need the 2PC overhead — you just ship the physical WAL to replicas. (Logical decoding was added later to mimic a binlog for CDC.)

The Elevator Pitch

"They operate at entirely different layers and times. The WAL is a physical, fixed-size redo log at the storage-engine level, written before data pages are modified, purely to guarantee durability and fast crash recovery.

The binlog is a logical, append-only sequence of row changes at the MySQL server level, written at commit time, designed specifically for cross-cluster replication and point-in-time recovery.

The critical architectural consequence is the 2PC dance between them — if the binlog isn't written, recovery rolls back the WAL changes to keep replication consistent. It also means the binlog grows forever until manually purged, while the WAL is a circular buffer that overwrites itself.

In PostgreSQL, though, I'd note that it combines both jobs into a single WAL to avoid that 2PC overhead entirely."

Why it works: you defined both, contrasted the technical layers, explained the order of operations, called out replication vs crash recovery, and dropped a cross-database comparison — signalling you understand database internals, not just frameworks.
