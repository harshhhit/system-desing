Replication Lag — Causes, Measurement, Mitigation

A companion deep-dive to the Distributed Data Roadmap (Phase 1). Lag is the time difference between when a write commits on the leader and when it becomes visible on a follower. It is never just about network speed.

1. What actually causes replication lag? (The 4 culprits)

Network RTT — the red herring

The least common cause. Modern datacenter networks have sub-millisecond latency. Inter-region (e.g. US → Europe) adds ~100ms, which is trivial next to the real culprits.

The I/O bottleneck — the heavy lifter

The leader writes to its disk sequentially (fast). The replica must apply the change to its existing B-Tree or LSM-Tree indexes — random disk I/O plus updating secondary indexes. If the replica's disk IOPS are lower than the leader's, lag spikes.

The "thundering herd" of reads — the hidden killer

Replicas usually serve analytical queries (heavy SELECT scans). While a replica is crunching a 5-minute report its CPU is maxed out, so it stops applying the replication stream. Lag grows for the duration of the read.

Single-threaded apply — the architectural choke

Most databases (MySQL, PostgreSQL) apply the replication stream on a single CPU core on the replica, to guarantee transactions land in the exact same order as the leader. If the leader handles 10,000 writes/sec across 20 cores, the replica is replaying 10,000 writes/sec on 1 core. It physically cannot keep up.

2. How is replication lag actually measured?

Databases don't use a "stopwatch" — they use transaction timestamps embedded in the replication log.

  • MySQL: Seconds_Behind_Source — the replica compares the Unix timestamp of the last event it applied against its own system clock.
  • PostgreSQL: pg_stat_replication exposes write_lag, flush_lag, and replay_lag, comparing the leader's current LSN (Log Sequence Number) against the LSN the replica reports back.
Operational trap

Seconds_Behind_Source is a lie if the replica is completely stalled (e.g. network partition). If it hasn't received an event in 5 minutes, it reports 0 lag — because the last timestamp it applied is 5 minutes old, matching its clock. The real lag is infinite. Monitor heartbeat timestamps (periodic empty writes) to catch this.

3. Why is lag the #1 operational headache?

Because it breaks the mental model developers have about databases. Three catastrophic failure modes are caused solely by lag:

  • Read-your-writes: a user saves a new profile picture (leader write), refreshes, and their read hits a lagging replica showing the old picture. They think the system is broken.
  • Monotonic reads: a user reads a comment thread on Replica A (up-to-date), refreshes, gets routed to Replica B (lagging), and the comment they just saw disappears. Data goes backward in time for them.
  • The "zombie" backup: if the leader crashes and failover promotes a lagging replica, you either (a) lose all data that hadn't replicated yet, or (b) bring the old leader back as a replica, which then tries to revert the new leader's data — split-brain and corrupted primary keys.

4. Misconception: "just use physical replication to reduce lag"

A common intuitive leap that is actually incorrect. It depends entirely on what "physical" means:

  • Physical (row-based) replication — shipping the exact changed rows: this increases bandwidth but reduces CPU overhead on the replica, because it doesn't have to re-parse complex SQL logic.
  • Physical (disk-block) replication — shipping raw disk pages: this makes lag worse, not better. If you ship a raw page change and the replica is running a heavy analytical query that holds that same page in its cache, the apply process blocks and waits. Physical replication is brittle and stalls easily.

5. The real ways to mitigate lag (the Ops toolkit)

You cannot eliminate lag — you manage it with these four proven mechanisms:

  • Synchronous replication (the nuclear option): make the client wait until the replica applies the change. Fixes lag by definition, but kills write throughput and availability. Only for critical financial data.
  • Read-only routing with bounded staleness: configure the load balancer to route reads only to replicas whose lag is under a threshold (e.g. < 1s). A replica that lags beyond it is pulled from the read pool until it catches up.
  • Session stickiness: pin a single user's session to exactly one replica for its duration. Prevents the "disappearing data" problem (monotonic reads) even if that replica lags.
  • Scale the replica's hardware: since apply is single-threaded, give replicas faster single-core CPU and higher-IOPS NVMe SSDs than the leader. Leaders scale out (more cores); replicas scale up (faster cores).

The ultimate operational truth about lag

Lag is not a bug — it is a thermometer for the health of your entire stack. When lag spikes, 90% of the time it is not a database problem, it is an application problem: someone pushed a schema migration (ALTER TABLE ADD COLUMN) that locks the table, or an analyst ran an unindexed SELECT * that maxed out the replica's CPU.

Treat lag like a pressure gauge: you don't try to stop the pressure, you build alarms for when it exceeds ~10 seconds — and you architect the application to gracefully tolerate temporary staleness (Version Vectors or Hybrid Logical Clocks in the application code itself).
