Database Security and Access Control

Study prompt: Learn authentication, roles, least-privilege permissions, secrets management, TLS, encryption at rest, parameterized queries, SQL-injection prevention, auditing, and data masking for sensitive fields.

Access Control

  • Least privilege: application service accounts get only the grants they need — a reporting job doesn't need DELETE, a write path doesn't need DROP.
  • Roles over per-user grants: assign permissions to roles (read_only, app_writer, migrator), attach users/services to roles, so access changes don't mean re-auditing every account.
  • Row-level security: restrict which rows a role can see (e.g. a tenant can only query its own rows) enforced by the database itself, not just application filters.

Protecting Data in Transit and at Rest

LayerControl
In transitTLS between application and database, certificate verification enabled (not just "encrypted, don't care who").
At restDisk/volume encryption plus, for the most sensitive fields (SSNs, tokens), application- or column-level encryption so a raw disk or backup leak isn't a full data leak.
SecretsDatabase credentials live in a vault/KMS with rotation, never in source control or plain environment files checked into git.

SQL Injection

Always use parameterized queries or an ORM's bound parameters — never string-concatenate user input into SQL. A parameterized query sends the SQL text and the values separately, so user input can never be interpreted as SQL syntax.

Vulnerable pattern

"SELECT * FROM users WHERE email = '" + userInput + "'" lets an input like ' OR '1'='1 change the query's meaning. Use db.query("SELECT * FROM users WHERE email = ?", [userInput]) instead.

Auditing and Masking

  • Log who ran what, when — at minimum for schema changes and access to sensitive tables.
  • Mask or tokenize sensitive fields in non-production copies of data (staging, analytics, developer laptops).
  • Review access grants periodically — accounts and permissions drift and outlive the people who requested them.
