Observability, Capacity, and Operations

Study prompt: Learn database metrics, slow-query logs, tracing, alerting, capacity planning, load testing, maintenance tasks, upgrades, incident response, and how to turn production symptoms into an investigation plan.

What to Watch

SignalWhy it matters
Query latency (p50/p95/p99)Averages hide the slow tail that users actually feel — track percentiles, not just the mean.
Connection count / pool saturationRising toward the max is an early warning of exhaustion, before requests start failing.
Replication lagTells you how stale a read replica's data might be, and how far behind a failover target would start.
Lock waits / deadlocksA rising rate signals growing contention before it becomes visible as timeouts.
Disk usage and IOPSDatabases fail hard when they run out of disk — alert well before capacity, not at it.
Slow query logThe direct list of what to optimize next — see Query Plans and Optimization.

Capacity Planning

  • Track growth trends (data size, QPS, connection count) over weeks/months, not just current load — plan for where the line is heading.
  • Load-test before a known traffic event, not after the first one causes an incident.
  • Know your scaling levers in advance: vertical (bigger instance), read replicas, partitioning/sharding — and which one actually addresses the bottleneck you're hitting (see Scaling and Partitioning).

Operations

  • Routine maintenance (vacuum/analyze, index rebuilds, statistics updates) needs a schedule — deferring it silently degrades query plans over time.
  • Version upgrades need a tested rollback path and a maintenance window plan, not just "run the upgrade."
Turning a symptom into an investigation

Start from the user-visible symptom (timeouts, errors), correlate it against latency/connection/lock graphs at that exact time window, then confirm the suspected cause in the slow query log or EXPLAIN ANALYZE before changing anything in production.
