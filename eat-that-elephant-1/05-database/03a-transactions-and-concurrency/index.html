Transactions and Concurrency

Study prompt: Learn ACID, isolation levels, locks, MVCC, deadlocks, lost updates, optimistic versus pessimistic concurrency, and how to make payment or inventory updates correct under concurrent requests.

ACID

PropertyGuarantee
AtomicityA transaction's writes all happen or none do.
ConsistencyA transaction moves the database from one valid state to another, respecting constraints.
IsolationConcurrent transactions don't see each other's uncommitted intermediate state.
DurabilityOnce committed, a write survives a crash.

Isolation Levels and Anomalies

LevelPreventsStill allows
Read UncommittedNothing extraDirty reads, non-repeatable reads, phantoms
Read CommittedDirty readsNon-repeatable reads, phantoms
Repeatable ReadDirty + non-repeatable readsPhantoms (varies by engine)
SerializableAll of the aboveNothing — behaves as if transactions ran one at a time

Locking and MVCC

  • Pessimistic locking (SELECT ... FOR UPDATE): take a lock before reading, block other writers — safe under high contention, costs throughput.
  • Optimistic concurrency: read without a lock, write with a version check (WHERE version = ?); retry on conflict — better throughput when contention is rare.
  • MVCC (Postgres, MySQL/InnoDB): readers see a consistent snapshot without blocking writers, by keeping multiple row versions.
  • Deadlocks: two transactions each hold a lock the other needs — the database detects the cycle and aborts one; always acquire locks in a consistent order to avoid them.
Lost update

Two transactions read the same row, both compute a new value from it, and the second write silently overwrites the first — e.g. two concurrent UPDATE inventory SET qty = 9 from reads of qty = 10, both decrementing by 1, losing one decrement. Prevent it with row locks, optimistic version checks, or an atomic UPDATE ... SET qty = qty - 1.
