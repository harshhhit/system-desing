Schema Design and Migrations

Study prompt: Learn how to design schemas from access patterns, choose data types and constraints, normalize or denormalize safely, version schema changes, and run backward-compatible migrations with rollback plans.

Designing from Access Patterns

Start from the queries the application actually runs, not from the entities that feel natural to model. A schema optimized for how data is written but never read the way it's queried will need indexes, denormalization, or a rewrite later.

  • List the top read and write paths first (dashboard queries, hot writes, reports).
  • Pick data types that match the domain: use fixed-precision types for money, never floats; use UUID/ULID or auto-increment deliberately, not by default.
  • Add NOT NULL, CHECK, and foreign-key constraints at write time — validating only in application code lets bad data leak in from migrations, scripts, and bugs.

Normalize vs. Denormalize

ChoiceWhen it pays off
NormalizeWrite-heavy data, data that must stay consistent across many readers (e.g. account balances).
DenormalizeRead-heavy, latency-sensitive paths where a join would be too expensive at scale — accept the duplication and own the sync logic.

Migration Strategy

  1. Expand: add the new column/table/index as nullable or with a default, deploy it — nothing depends on it yet.
  2. Backfill: populate the new structure in batches, off the request path, without long locks.
  3. Switch over: deploy application code that reads/writes the new structure.
  4. Contract: once nothing reads the old structure, drop it in a separate migration.
Note

This expand/contract sequence is what makes a migration backward compatible: at every step, both the old and new code can run against the current schema, so a rolling deploy never breaks.

Common pitfalls

Adding a NOT NULL column without a default on a large table (locks it while every row is rewritten), renaming a column instead of add-then-drop, and migrations with no tested rollback path.
