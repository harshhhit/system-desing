Query Plans and Optimization

Study prompt: Learn to read EXPLAIN and EXPLAIN ANALYZE output, identify sequential scans and expensive joins, choose useful indexes, update statistics, avoid N+1 queries, and measure before and after every optimization.

Reading a Query Plan

EXPLAIN shows the planner's chosen steps and estimated cost; EXPLAIN ANALYZE actually runs the query and adds real timings and row counts — use the latter to see where estimate and reality diverge.

Plan nodeMeaning
Seq ScanReads every row in the table. Fine for small tables; a red flag on a large one filtered by a selective condition.
Index ScanUses an index to find matching rows directly, then fetches each from the table.
Index Only ScanAnswers the query entirely from the index — no table fetch needed.
Nested LoopFor each row on one side, scans the other side. Good with a small outer set and an index on the inner.
Hash JoinBuilds a hash table from the smaller side, probes it with the larger — good for large, unsorted, unindexed joins.
Merge JoinBoth sides pre-sorted (often via an index), then merged — efficient for large sorted joins.

Indexing for the Query, Not the Table

  • Index columns used in WHERE, JOIN ... ON, and ORDER BY — not every column that "looks important."
  • A composite index's column order matters: it can serve a query that filters on its leading column(s), not one that only filters on a trailing column.
  • Stale table statistics can make the planner pick a bad plan even with the right index in place — re-run ANALYZE after large data changes.

The N+1 Query Problem

An ORM loop that issues one query per row of an earlier result (fetch 50 orders, then 50 separate queries for each order's line items) turns one round trip into 51. Fix it with a join, a batched WHERE id IN (...), or the ORM's eager-loading feature.

Practice

Take a slow endpoint, run EXPLAIN ANALYZE on its query, change one thing (add an index, rewrite a subquery as a join), and re-measure. Never trust an optimization you haven't measured before and after.
