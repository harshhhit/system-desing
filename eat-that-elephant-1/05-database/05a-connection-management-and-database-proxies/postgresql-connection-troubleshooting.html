PostgreSQL Connection & Query Troubleshooting Guide

Diagnostic queries against pg_stat_activity for connection usage, connection state, per-IP/user/application breakdowns, active and long-running queries, idle and idle-in-transaction sessions, and a step-by-step workflow for "too many connections" incidents.

This page provides a set of PostgreSQL queries for investigating:

  • Current database connection usage
  • Which users/applications/IPs are consuming connections
  • Active and long-running queries
  • Idle connections
  • idle in transaction sessions
  • Old connections
  • Queries running from a specific IP
  • Connection pool problems
  • PostgreSQL connection exhaustion
Important

These queries are primarily diagnostic. Do not terminate database sessions until you understand which application/service owns them.

1. Check Current Connection Usage

Query

SELECT
    count(*) AS current_connections,
    current_setting('max_connections')::int AS max_connections,
    round(
        count(*) * 100.0 / current_setting('max_connections')::int,
        2
    ) AS usage_percent
FROM pg_stat_activity;

What it checks

Shows:

  • Current PostgreSQL connections
  • Configured max_connections
  • Percentage of the connection limit currently being used

Sample Output

 current_connections | max_connections | usage_percent
---------------------+-----------------+--------------
 40                  | 402             | 9.95

Interpretation

In this example:

40 / 402 = ~10%

The database is not currently close to its connection limit.

If you see:

390 / 402 = ~97%

then the database is close to connection exhaustion.

2. Check Connection State

Query

SELECT
    state,
    count(*) AS connections
FROM pg_stat_activity
GROUP BY state
ORDER BY connections DESC;

What it checks

Shows how connections are distributed between:

  • active
  • idle
  • idle in transaction
  • Other PostgreSQL states

Sample Output

 state                   | connections
-------------------------+------------
 idle                    | 35
 active                  | 3
 idle in transaction     | 2

Interpretation

active

The connection is currently executing a query.

idle

The connection is open but currently not executing a query.

A large number of idle connections often indicates connection pooling.

idle in transaction

The application has started a transaction but is currently doing nothing inside it.

This state requires investigation because it can hold locks and prevent database cleanup.

3. Find Which IP Is Using the Most Connections

Query

SELECT
    client_addr,
    count(*) AS total_connections,
    count(*) FILTER (WHERE state = 'active') AS active,
    count(*) FILTER (WHERE state = 'idle') AS idle,
    count(*) FILTER (
        WHERE state = 'idle in transaction'
    ) AS idle_in_transaction
FROM pg_stat_activity
WHERE client_addr IS NOT NULL
GROUP BY client_addr
ORDER BY total_connections DESC;

What it checks

Identifies which client IP is creating the most PostgreSQL connections.

This is particularly useful when applications run on:

  • ECS
  • Kubernetes
  • EC2
  • Application servers
  • Microservices

Sample Output

 client_addr | total_connections | active | idle | idle_in_transaction
-------------+-------------------+--------+------+--------------------
 10.0.1.207  | 15                | 1      | 14   | 0
 10.0.1.84   | 10                | 0      | 10   | 0
 10.0.2.69   |  6                | 0      |  6   | 0
 10.0.2.144  |  3                | 1      |  2   | 0

Interpretation

If one IP has a very high number of connections, investigate which ECS task/server owns that IP.

For example:

10.0.1.207 → 100 connections
10.0.1.84  → 5 connections

The service running on 10.0.1.207 may have an incorrectly configured connection pool.

4. Find All Active Queries

Query

SELECT
    pid,
    usename,
    client_addr,
    application_name,
    state,
    now() - query_start AS query_duration,
    wait_event_type,
    wait_event,
    query
FROM pg_stat_activity
WHERE state = 'active'
  AND query_start IS NOT NULL
  AND pid <> pg_backend_pid()
ORDER BY query_duration DESC;

What it checks

Shows queries that are currently executing.

Important fields:

FieldMeaning
pidPostgreSQL process ID
usenameDatabase user
client_addrClient IP
application_nameApplication/client name
query_durationHow long the current query has been running
wait_event_typeWhat PostgreSQL may be waiting for
wait_eventSpecific wait event
querySQL currently executing

Sample Output

 pid  | usename  | client_addr | state  | query_duration | wait_event | query
------+----------+-------------+--------+----------------+------------+------------------------
 8234 | postgres | 10.0.1.207  | active | 00:18:42       | Lock       | UPDATE orders SET ...
 8121 | postgres | 10.0.2.69   | active | 00:03:12       |            | SELECT * FROM orders...

The first query has been running for approximately 18 minutes.

5. Find the Single Longest-Running Query

Query

SELECT
    pid,
    usename,
    client_addr,
    application_name,
    now() - query_start AS query_duration,
    wait_event_type,
    wait_event,
    query
FROM pg_stat_activity
WHERE state = 'active'
  AND query_start IS NOT NULL
  AND pid <> pg_backend_pid()
ORDER BY query_start ASC
LIMIT 1;

What it checks

Returns the currently running query that started earliest.

Sample Output

 pid  | usename  | client_addr | query_duration | wait_event | query
------+----------+-------------+----------------+------------+-------------------------
 8234 | postgres | 10.0.1.207  | 00:18:42       | Lock       | UPDATE orders SET ...

Important

If this returns no rows, there may be no active application query at that moment.

That does not mean there are no open connections.

6. Find Old Connections

Query

SELECT
    pid,
    usename,
    client_addr,
    application_name,
    state,
    now() - backend_start AS connection_age,
    now() - state_change AS idle_for,
    query
FROM pg_stat_activity
WHERE pid <> pg_backend_pid()
ORDER BY backend_start ASC
LIMIT 20;

What it checks

Shows the oldest database connections.

Sample Output

 pid   | usename  | client_addr | state | connection_age | idle_for
-------+----------+-------------+-------+----------------+----------------
 5431  | postgres | 10.0.1.240  | idle  | 5 days 16:36   | 5 days 16:36
 25357 | postgres | 10.0.1.84   | idle  | 3 days 18:27   | 3 days 18:27
 21294 | postgres | 10.0.1.207  | idle  | 17:27:27       | 17:27:27

Important

A connection being old does not mean a query has been running for that entire time.

For example:

connection_age = 5 days
state = idle

means the connection has been open for five days but is currently not executing a query.

7. Find Idle Connections

Query

SELECT
    pid,
    usename,
    client_addr,
    application_name,
    now() - backend_start AS connection_age,
    now() - state_change AS idle_for
FROM pg_stat_activity
WHERE state = 'idle'
ORDER BY idle_for DESC;

What it checks

Finds connections that are currently idle and shows how long they have been idle.

Sample Output

 pid   | client_addr | state | connection_age | idle_for
-------+-------------+-------+----------------+----------
 5431  | 10.0.1.240  | idle  | 5 days         | 5 days
 25357 | 10.0.1.84   | idle  | 3 days         | 3 days
 21294 | 10.0.1.207  | idle  | 17 hours       | 17 hours

A high number of idle connections can indicate a large application connection pool.

8. Find idle in transaction Sessions

Query

SELECT
    pid,
    usename,
    client_addr,
    application_name,
    now() - xact_start AS transaction_age,
    now() - state_change AS idle_time,
    query
FROM pg_stat_activity
WHERE state = 'idle in transaction'
ORDER BY xact_start ASC;

What it checks

Finds sessions where an application has started a transaction but is currently doing nothing.

Sample Output

 pid  | usename | client_addr | transaction_age | idle_time | query
------+---------+-------------+-----------------+-----------+-------------------
 8211 | appuser | 10.0.1.207  | 00:42:15        | 00:41:58  | UPDATE orders ...

Why this matters

Long-running idle in transaction sessions can:

  • Hold locks
  • Block other queries
  • Prevent vacuum cleanup
  • Cause application requests to hang
  • Increase database resource usage

These should be investigated at the application level.

9. Check Queries From a Specific IP

Replace the IP with the IP you want to investigate.

Example:

SELECT
    pid,
    usename,
    client_addr,
    application_name,
    state,
    now() - query_start AS query_duration,
    wait_event_type,
    wait_event,
    query
FROM pg_stat_activity
WHERE client_addr = '10.0.1.207'
  AND state = 'active'
  AND pid <> pg_backend_pid()
ORDER BY query_start ASC;

What it checks

Shows currently executing queries from a specific client IP.

Sample Output

 pid   | client_addr | state  | query_duration | query
-------+-------------+--------+----------------+----------------------
 12345 | 10.0.1.207  | active | 00:12:35       | SELECT ...
 12346 | 10.0.1.207  | active | 00:02:18       | UPDATE ...

If there are no rows:

No rows returned

then that IP has no active query at that moment.

10. Check Both Active and Idle Sessions From an IP

If the active-query query returns nothing, use this:

SELECT
    pid,
    usename,
    client_addr,
    application_name,
    state,
    now() - backend_start AS connection_age,
    now() - state_change AS idle_for,
    query
FROM pg_stat_activity
WHERE client_addr = '10.0.1.207'
ORDER BY backend_start ASC;

What it checks

Shows every PostgreSQL session belonging to the specified IP, including:

  • Active sessions
  • Idle sessions
  • Idle-in-transaction sessions

Sample Output

 pid   | client_addr | state | connection_age | idle_for
-------+-------------+-------+----------------+----------
 12345 | 10.0.1.207  | idle  | 17 hours       | 17 hours
 12346 | 10.0.1.207  | idle  | 15 hours       | 15 hours
 12347 | 10.0.1.207  | active| 00:02:10        | 00:00:00

11. Identify the Last Query From an Idle Connection

SELECT
    pid,
    usename,
    client_addr,
    application_name,
    state,
    now() - state_change AS idle_for,
    query
FROM pg_stat_activity
WHERE state = 'idle'
ORDER BY idle_for DESC;

Important

For an idle session, the query column represents the last query executed by that session.

It is not currently running.

Do not interpret this:

state = idle
query = SELECT ...

as:

The SELECT is currently running.

The query is only the last query recorded for that connection.

12. Find Connections Grouped by User/Application/IP

Query

SELECT
    usename,
    application_name,
    client_addr,
    state,
    count(*) AS connections
FROM pg_stat_activity
GROUP BY
    usename,
    application_name,
    client_addr,
    state
ORDER BY connections DESC;

What it checks

Shows which combination of:

  • Database user
  • Application
  • Client IP
  • Connection state

is consuming connections.

Sample Output

 usename  | application_name       | client_addr | state | connections
----------+------------------------+-------------+-------+------------
 appuser  | my-service             | 10.0.1.207  | idle  | 50
 appuser  | my-service             | 10.0.1.84   | idle  | 30
 postgres | DBeaver                | 10.0.1.162  | idle  | 2

This is one of the best queries for identifying connection-pool problems.

13. Check PostgreSQL max_connections

SHOW max_connections;

Sample Output

 max_connections
-----------------
 402

This is the maximum number of PostgreSQL client connections allowed by the configuration.

14. Recommended Investigation Workflow

When the application reports:

Too many connections

or:

remaining connection slots are reserved

run these in order.

Step 1 — Check current usage

SELECT
    count(*) AS current_connections,
    current_setting('max_connections')::int AS max_connections,
    round(
        count(*) * 100.0 / current_setting('max_connections')::int,
        2
    ) AS usage_percent
FROM pg_stat_activity;

Step 2 — Check connection states

SELECT
    state,
    count(*) AS connections
FROM pg_stat_activity
GROUP BY state
ORDER BY connections DESC;

Step 3 — Find the IP consuming the most connections

SELECT
    client_addr,
    count(*) AS total_connections,
    count(*) FILTER (WHERE state = 'active') AS active,
    count(*) FILTER (WHERE state = 'idle') AS idle,
    count(*) FILTER (
        WHERE state = 'idle in transaction'
    ) AS idle_in_transaction
FROM pg_stat_activity
WHERE client_addr IS NOT NULL
GROUP BY client_addr
ORDER BY total_connections DESC;

Step 4 — Check active queries

SELECT
    pid,
    usename,
    client_addr,
    application_name,
    state,
    now() - query_start AS query_duration,
    wait_event_type,
    wait_event,
    query
FROM pg_stat_activity
WHERE state = 'active'
  AND query_start IS NOT NULL
  AND pid <> pg_backend_pid()
ORDER BY query_duration DESC;

Step 5 — Check idle in transaction

SELECT
    pid,
    usename,
    client_addr,
    application_name,
    now() - xact_start AS transaction_age,
    now() - state_change AS idle_time,
    query
FROM pg_stat_activity
WHERE state = 'idle in transaction'
ORDER BY xact_start ASC;

Step 6 — Check old connections

SELECT
    pid,
    usename,
    client_addr,
    application_name,
    state,
    now() - backend_start AS connection_age,
    now() - state_change AS idle_for
FROM pg_stat_activity
WHERE pid <> pg_backend_pid()
ORDER BY backend_start ASC
LIMIT 20;

15. How to Interpret the Results

Case A — High active connections

Example:

active = 380
idle   = 10

Possible causes:

  • Heavy database workload
  • Slow queries
  • Missing indexes
  • Lock contention
  • Traffic spike
  • Application requests not completing

Investigate active queries and wait events.

Case B — High idle connections

Example:

active = 5
idle   = 380

Possible causes:

  • Application connection pool is too large
  • Too many ECS tasks
  • Connections are being held for too long
  • Pool idle timeout is too high
  • Application isn't releasing connections correctly

This is usually an application/pool configuration problem, not a slow-query problem.

Case C — High idle in transaction

Example:

active                = 10
idle                  = 20
idle in transaction   = 350

This requires urgent investigation.

Possible causes:

  • Application starts transactions and doesn't commit/rollback
  • Connection leak
  • Application request hangs after starting a transaction
  • Incorrect transaction handling

16. ECS Connection Pool Example

Suppose an ECS service has:

10 ECS tasks

and every task has:

max DB pool = 40

The theoretical maximum becomes:

10 × 40 = 400 connections

If PostgreSQL allows:

max_connections = 402

then the ECS service alone can almost consume the entire database connection capacity.

If ECS scales to 15 tasks:

15 × 40 = 600 connections

PostgreSQL cannot accommodate all of them.

This is why connection pooling must be sized based on the total number of application instances/tasks, not just per application instance.

17. Important Production Rule

Do not immediately solve connection errors by increasing:

max_connections

Increasing the connection limit can increase memory pressure and database contention.

First determine:

  1. Who is opening the connections?
  2. How many connections does each application instance create?
  3. Are connections active, idle, or idle in transaction?
  4. Is ECS scaling creating connection spikes?
  5. Is the application correctly releasing connections?
  6. Is a connection pool configured correctly?

18. Current Example Diagnosis

For the example investigation represented by this README, PostgreSQL reported:

Current connections: 40
Maximum connections: 402
Usage:               9.95%

Most observed application connections were:

state = idle

There were also very old idle connections such as:

10.0.1.240 → approximately 5 days
10.0.1.84  → approximately 3 days
10.0.1.207 → approximately 17 hours

These old connections do not automatically mean queries have been running for those durations.

The evidence points toward investigating:

  • Application connection pooling
  • ECS task count
  • Per-task pool size
  • Connection lifetime
  • Idle connection timeout
  • Connection spikes during the time the application reported the error

19. Safety Notes

Do not blindly run:

SELECT pg_terminate_backend(pid)
FROM pg_stat_activity;

This can terminate legitimate application sessions.

Before terminating a session, identify:

  • PID
  • Application
  • User
  • Client IP
  • State
  • Query
  • Transaction age
  • Business impact

For production systems, prefer fixing the application connection pool or transaction handling instead of repeatedly killing connections.

Key Takeaway

If PostgreSQL shows:

40 / 402 connections

there is no current connection exhaustion.

If the application previously reported a connection error, investigate the database and application at the time of the incident. For AWS/RDS deployments, compare the PostgreSQL connection count with the application's ECS task count and connection-pool configuration.

The most useful first query for identifying the source is:

SELECT
    client_addr,
    count(*) AS total_connections,
    count(*) FILTER (WHERE state = 'active') AS active,
    count(*) FILTER (WHERE state = 'idle') AS idle,
    count(*) FILTER (
        WHERE state = 'idle in transaction'
    ) AS idle_in_transaction
FROM pg_stat_activity
WHERE client_addr IS NOT NULL
GROUP BY client_addr
ORDER BY total_connections DESC;
