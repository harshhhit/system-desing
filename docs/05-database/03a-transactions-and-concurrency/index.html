Transactions and Concurrency

Study prompt: Learn ACID, isolation levels, locks, MVCC, deadlocks, lost updates, optimistic versus pessimistic concurrency, and how to make payment or inventory updates correct under concurrent requests.

Interview Answer — What Is a Database Transaction?

A database transaction is a group of reads and writes that the database treats as one unit: either all of its changes are committed, or none of them are. Transactions provide the ACID guarantees — Atomicity (all or nothing), Consistency (constraints hold before and after), Isolation (concurrent transactions do not see each other's partial work), and Durability (a committed change survives a crash).

Transactions exist because real operations span several writes and many users act at the same time. A money transfer debits one account and credits another; without atomicity, a crash between the two loses money. Without isolation, concurrent requests interfere — the classic lost update: two requests both read qty = 10, both write qty = 9, and one sale disappears. The cause → effect chain the database prevents is: concurrent reads of the same value → decisions based on stale data → one write silently overwrites another.

How much isolation you get is set by the isolation level — Read Committed (the default in PostgreSQL), Repeatable Read, or Serializable — each preventing more anomalies at more cost. Databases implement it with locks and MVCC: MVCC lets readers see a consistent snapshot without blocking writers, while SELECT … FOR UPDATE (pessimistic locking) or a version check on update (optimistic concurrency) protects read-modify-write sequences.

Simple interview version

"A transaction groups several operations so they succeed or fail together, with ACID guarantees: atomicity, consistency, isolation, and durability. Isolation levels trade correctness for concurrency — Read Committed, Repeatable Read, Serializable. Databases like Postgres use MVCC so readers don't block writers. For read-modify-write updates like inventory or balances, I use an atomic update, SELECT FOR UPDATE, or optimistic concurrency with a version column to prevent lost updates, and I acquire locks in a consistent order to avoid deadlocks."

One important interview follow-up

Q: If my inventory update runs inside a transaction, is it safe from concurrent requests?

A: Not by default. Under PostgreSQL's default Read Committed level, two transactions can both SELECT qty (both see 10), both compute 9 in the application, and both UPDATE … SET qty = 9 — the transaction wrapper does not stop the lost update. Fixes: do the arithmetic in one atomic statement (UPDATE inventory SET qty = qty - 1 WHERE id = ? AND qty > 0), lock the row first with SELECT … FOR UPDATE, use a version column and retry on conflict, or run at Serializable and retry the transactions the database aborts.

ACID

PropertyGuarantee
AtomicityA transaction's writes all happen or none do.
ConsistencyA transaction moves the database from one valid state to another, respecting constraints.
IsolationConcurrent transactions don't see each other's uncommitted intermediate state.
DurabilityOnce committed, a write survives a crash.

Isolation Levels and Anomalies

LevelPreventsStill allows
Read UncommittedNothing extraDirty reads, non-repeatable reads, phantoms
Read CommittedDirty readsNon-repeatable reads, phantoms
Repeatable ReadDirty + non-repeatable readsPhantoms (varies by engine)
SerializableAll of the aboveNothing — behaves as if transactions ran one at a time

Locking and MVCC

  • Pessimistic locking (SELECT ... FOR UPDATE): take a lock before reading, block other writers — safe under high contention, costs throughput.
  • Optimistic concurrency: read without a lock, write with a version check (WHERE version = ?); retry on conflict — better throughput when contention is rare.
  • MVCC (Postgres, MySQL/InnoDB): readers see a consistent snapshot without blocking writers, by keeping multiple row versions.
  • Deadlocks: two transactions each hold a lock the other needs — the database detects the cycle and aborts one; always acquire locks in a consistent order to avoid them.
Lost update

Two transactions read the same row, both compute a new value from it, and the second write silently overwrites the first — e.g. two concurrent UPDATE inventory SET qty = 9 from reads of qty = 10, both decrementing by 1, losing one decrement. Prevent it with row locks, optimistic version checks, or an atomic UPDATE ... SET qty = qty - 1.
