Database Security and Access Control

Study prompt: Learn authentication, roles, least-privilege permissions, secrets management, TLS, encryption at rest, parameterized queries, SQL-injection prevention, auditing, and data masking for sensitive fields.

Interview Answer — How Do You Secure a Database?

Database security is the set of controls that ensure only the right people and services can read or change the right data, that data cannot be read if it is intercepted or stolen, and that every sensitive access can be traced afterward. It covers access control (least-privilege roles and row-level security), encryption in transit (TLS) and at rest, credential management, protection against SQL injection, and auditing and masking.

These controls exist because the database is where the valuable data is, so every weakness around it becomes a breach. The cause → effect chains are direct: an application account with DROP and DELETE on every table means one injection bug or leaked password can destroy everything; a password committed to Git means anyone with repository access can connect; an unencrypted backup copied to the wrong bucket means a full data leak; a string-concatenated query means user input can rewrite the SQL. Each control shrinks the blast radius of one specific failure.

In practice: every service gets its own role with only the grants it needs (read_only, app_writer, migrator); multi-tenant data uses row-level security enforced by the database; connections use TLS with certificate verification; disks and backups are encrypted, and the most sensitive columns are encrypted at the application level; credentials live in a secrets manager with rotation; all queries are parameterized; and schema changes and sensitive-table access are logged and reviewed.

Simple interview version

"I secure a database in layers. Each service gets a least-privilege role, and multi-tenant data uses row-level security. Connections use TLS with certificate verification; storage and backups are encrypted, with extra column-level encryption for the most sensitive fields. Credentials live in a secrets manager and are rotated, never in code. Every query is parameterized to prevent SQL injection, sensitive data is masked in non-production copies, and access is audited and reviewed regularly."

One important interview follow-up

Q: If the database uses encryption at rest, is the data protected from a SQL injection attack?

A: No. Encryption at rest protects the files — a stolen disk, snapshot, or backup cannot be read without the key. But a running database decrypts data transparently for any connection that is allowed to query it, so an attacker who injects SQL through your application reads plaintext exactly as the application would. Protection against injection comes from parameterized queries, and damage is limited by giving the application account least privilege (and row-level security); only application-level encryption of specific fields keeps them unreadable even to someone who can run queries.

Access Control

  • Least privilege: application service accounts get only the grants they need — a reporting job doesn't need DELETE, a write path doesn't need DROP.
  • Roles over per-user grants: assign permissions to roles (read_only, app_writer, migrator), attach users/services to roles, so access changes don't mean re-auditing every account.
  • Row-level security: restrict which rows a role can see (e.g. a tenant can only query its own rows) enforced by the database itself, not just application filters.

Protecting Data in Transit and at Rest

LayerControl
In transitTLS between application and database, certificate verification enabled (not just "encrypted, don't care who").
At restDisk/volume encryption plus, for the most sensitive fields (SSNs, tokens), application- or column-level encryption so a raw disk or backup leak isn't a full data leak.
SecretsDatabase credentials live in a vault/KMS with rotation, never in source control or plain environment files checked into git.

SQL Injection

Always use parameterized queries or an ORM's bound parameters — never string-concatenate user input into SQL. A parameterized query sends the SQL text and the values separately, so user input can never be interpreted as SQL syntax.

Vulnerable pattern

"SELECT * FROM users WHERE email = '" + userInput + "'" lets an input like ' OR '1'='1 change the query's meaning. Use db.query("SELECT * FROM users WHERE email = ?", [userInput]) instead.

Auditing and Masking

  • Log who ran what, when — at minimum for schema changes and access to sensitive tables.
  • Mask or tokenize sensitive fields in non-production copies of data (staging, analytics, developer laptops).
  • Review access grants periodically — accounts and permissions drift and outlive the people who requested them.
