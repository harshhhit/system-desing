How to Choose the Database

How to chose the database: a decision procedure, a decision tree and a comparison of the nine database families, so the store is derived from access patterns, consistency, volume and operations instead of popularity, plus the production symptoms that say the choice was wrong.

What you'll learn

By the end of this page you will be able to:

  • Say what "choosing a database" actually decides, and why the decision is expensive to reverse
  • Name the nine database families and state what each is fast at and awkward at
  • Turn a vague feature request into a list of access patterns and hard requirements
  • Run an eight-step selection procedure and a decision tree that ends in a defensible default
  • Fill in a requirements worksheet and a weighted scoring matrix for a real service
  • Recognise the production symptoms that say "the wrong database was chosen", and what to do about each
  • Answer the common interview questions on database selection, including scenarios

What Choosing a Database Means and Why It Is Hard to Undo

Choosing a database means matching a data store's data model (how it organises data) and its guarantees (consistency, durability, transactions, scaling model) to a specific workload. It is not "SQL or NoSQL": it is a set of smaller questions — how will the data be read and written, how fresh must a read be, how much data and traffic will there be, what happens when a node dies — whose answers rule families in or out.

Why the decision matters: every database family is fast at the operations it was designed around and awkward or unsafe at the others. A relational database answers an ad-hoc join in milliseconds but cannot spread writes across twenty nodes without you sharding it by hand; Cassandra spreads writes across twenty nodes effortlessly but cannot answer a query it was not modelled for. Pick the family for the wrong workload and you spend the next two years working around it.

Why it is hard to reverse: data has gravity. Once a few hundred gigabytes and a dozen services depend on one store, moving means dual writes or change-data-capture pipelines, a backfill that must not fall behind live traffic, a cut-over with a rollback plan, and a schema that was shaped around the old store's strengths (see Horizontal Scaling for how painful the sharding half of that is). Changing a web framework is a refactor; changing a database is a migration project.

When you make this decision: at design time for each new service or bounded context (not once for the whole company), and again when a measured bottleneck shows that the current store no longer fits a workload — never because a technology is fashionable.

💡 Important

The decision works backwards from the requirements, never forwards from a product. Write down the access patterns, consistency needs, volume and latency targets first; the database is the last line of the worksheet, not the first.

Core Concepts: The Vocabulary of the Decision

Every family is described below with the same terms, so learn them once here. The terms in this table are reused exactly through the rest of the page.

TermMeaning
Access patternOne concrete way the application reads or writes data, stated as "find X by Y" — e.g. "fetch an order by order id", "list the last 20 posts of a user", "count signups per day". A service usually has 5–15 of them; they are the primary input to the decision.
Data modelThe shape a store organises data in and lets you query by: tables and rows, key → value, JSON documents, partition rows with sorted columns, inverted index, time-ordered samples, nodes and edges, or columns.
WorkloadThe mix of operations the store must sustain: read/write ratio, requests per second, data volume and growth, and whether requests touch one row or scan millions.
OLTPOnline transaction processing: many small, fast reads and writes touching a few rows each (placing an order, loading a profile). Needs indexes and low latency.
OLAPOnline analytical processing: few, heavy queries scanning and aggregating millions of rows (revenue per region per month). Needs column storage and parallel scans, not single-row speed.
ACIDAtomicity, Consistency, Isolation, Durability — a transaction either fully happens or not at all, leaves the data valid, is not corrupted by concurrent transactions, and survives a crash once committed. See Transactions and Concurrency.
BASEBasically Available, Soft state, Eventually consistent — the store stays up and accepts writes, and replicas converge later; a read may return slightly stale data in exchange for availability and scale.
Multi-row transactionA transaction that changes several rows (or several tables / partitions) atomically — "debit account A and credit account B". The single requirement that most often forces a relational database.
Strong vs. eventual consistencyStrong: every read sees the latest committed write. Eventual: a read may lag until replication catches up. See CAP Theorem Questions and PACELC.
Working setThe portion of the data that is touched often. If it fits in memory, reads are served from cache; if not, every miss becomes a disk read.
Hot key / hot partitionOne key or partition receiving a disproportionate share of traffic (a celebrity's profile, today's date as a partition key). It defeats horizontal scaling because one node takes the load.
Schema-on-write vs. schema-on-readSchema-on-write (relational): the database enforces column types and constraints when data is written. Schema-on-read (document, key-value): anything is stored; the application interprets the shape when reading, so inconsistency is possible.
Secondary indexAn index on a column that is not the primary key, letting you query by it efficiently. Cheap and flexible in relational stores; limited or expensive in key-value and wide-column stores.
Source of truthThe one store whose copy of a piece of data is authoritative; every other copy (cache, search index, warehouse) is derived from it and can be rebuilt.
Polyglot persistenceUsing several database types in one system, one per workload. See Polyglot Persistence.
Vertical vs. horizontal scalingVertical: a bigger machine (simple, has a ceiling). Horizontal: more machines sharing the data (no ceiling, but joins and transactions across machines become hard). See Partitioning.
Managed serviceA cloud-operated database (RDS, Aurora, DynamoDB, Cloud Spanner, Atlas) where backups, patching, failover and scaling are the provider's job — at a price and with the provider's limits.

SQL vs. NoSQL — the difference, stated precisely

SQL (relational) vs. NoSQL — the difference is where the data model is decided and what the store promises across rows. A relational database fixes the schema up front, keeps related data in separate normalised tables, and lets you combine them at query time with joins under ACID transactions — so you can ask questions you did not anticipate. A NoSQL store (an umbrella for key-value, document, wide-column, graph and more) organises data around the queries you know you will run, spreads it across nodes by a partition key, and in exchange gives up most joins, ad-hoc queries and (usually) multi-row transactions. "NoSQL" is not one thing: Redis, MongoDB, Cassandra and Neo4j have less in common with each other than each has with PostgreSQL.

OLTP vs. OLAP — the difference

OLTP vs. OLAP — the difference is row-at-a-time versus column-at-a-time. OLTP stores keep each row's bytes together so one order can be fetched or updated in a single disk read; OLAP stores keep each column's bytes together so "sum of all order totals" reads only the totals column, compressed, across billions of rows. Running analytics on the OLTP primary works until the scans evict the working set from cache and slow every checkout; that is the moment to add a separate analytical store fed from the primary.

⚠️ Common mistake

Treating "NoSQL scales, SQL doesn't" as a law. Scaling is a property of the workload fit: a relational database with read replicas and a cache scales reads very far, and a wide-column store with a bad partition key does not scale at all. The right question is "does this family scale for my access patterns?"

One more store that belongs in the decision but is not a database: object storage (Amazon S3, GCS, Azure Blob). Images, videos, PDFs and backups are blobs; they belong in object storage with only their metadata (owner, size, URL, upload time) in a database. Putting a 5 MB image in a database row inflates backups, replication and cache usage for no benefit. This is exactly the split used in the image-share system walkthrough.

🧠 Think about it

Why can a graph database traverse "friends of friends of friends" in roughly constant time per hop while a relational database gets slower with every extra join? Because the graph store stores each edge as a direct pointer from node to node, so a hop is one pointer dereference; the relational store must compute the relationship each time by looking up matching ids in an index — one index probe per row per hop. Same information, different physical layout — and the physical layout is what you are really choosing.

🔥 Production insight

Every arrow leaving the primary in that diagram is a place where two copies of the same data can disagree. Each derived store is therefore a cost — a pipeline to monitor, a lag to alert on, a rebuild procedure to rehearse — before it is a benefit. Add a box only when a measured access pattern cannot be served from the boxes you already have.

How It Works: The Eight-Step Selection Procedure

This is the procedure to run for every new service or new kind of data. Each step narrows the field; by step 7 there is usually one family left, and step 8 checks it against reality before anyone writes production code. Do the steps in order — the first four are about the problem and must be finished before any product name is spoken.

  1. List the entities and every access pattern. Write each as "find / list / count / update X by Y, N times per second, returning ~M rows". Example for an order service: get order by id (2,000/s), list a customer's last 20 orders (500/s), create order with 3–10 line items (300/s), monthly revenue report by region (1/hour). Why first: the data model must make these cheap; everything else is secondary.
  2. Classify the workload: OLTP, OLAP, or both. Many small reads and writes → OLTP. Few heavy scans → OLAP. Both → two stores, with the analytical one derived from the transactional one. Why: no single engine is good at both row-at-a-time and column-at-a-time access (see OLTP vs. OLAP).
  3. Pin down consistency and transaction requirements, pattern by pattern. Ask "can this read ever be stale, and for how long?" and "does this write change several rows that must succeed or fail together?" A balance, an inventory count or a seat reservation cannot be stale and needs multi-row ACID — that alone points to relational (or distributed SQL). A like count, a feed or a search result tolerates seconds of lag. Why: this is the requirement that removes the most families.
  4. Estimate volume and growth. Rows now and in 3 years, bytes per row, writes/s and reads/s at peak, read/write ratio, and how large the working set is. Rule of thumb: a single well-tuned PostgreSQL node comfortably serves a few terabytes and tens of thousands of simple queries per second; a few hundred thousand writes per second or hundreds of terabytes means you are in horizontally-scaled territory from day one. Why: scale decides whether "one relational primary" is a viable answer at all.
  5. Set latency targets per pattern. p99 of 5 ms for a session lookup means in-memory key-value; p99 of 100 ms for an order page is fine for a relational query; a report may take seconds. Why: latency targets decide whether a cache or an in-memory store is required in front of the source of truth.
  6. Decide how much query flexibility you need. Will analysts or new features ask questions nobody listed in step 1? If yes, you need a store that answers unanticipated queries — relational, or a warehouse copy. If the patterns are fixed and few (a URL shortener, a device-event log), a query-first store such as key-value or wide-column is safe. Why: schema-on-read and partition-key stores punish queries they were not designed for.
  7. Apply the operational constraints. Which managed services does your cloud offer? Can the team run and debug this store at 3 a.m.? What does it cost at your volume (per request, per node, per GB)? Licence (Elasticsearch moved to SSPL in 2021, which produced OpenSearch; Redis changed licence in 2024, which produced Valkey)? Backups, point-in-time recovery, multi-region, compliance and data residency? Why: a technically perfect store the team cannot operate is the wrong store.
  8. Pick the default, then prove it with a prototype and a benchmark. Walk the decision tree; if nothing forces a specialised store, choose PostgreSQL (or your organisation's standard relational database). Then load a realistic data volume, run the top access patterns at target rates, and measure p99 latency, write throughput and the cost of the two or three hardest queries. Why: the step most teams skip is the one that catches a wrong choice while it is still cheap.

🎯 Interview tip

In a system design interview, say steps 1–3 out loud before naming any database: "The access patterns are …, the ones that need strong consistency are …, so …". Interviewers mark down candidates who open with "I'd use MongoDB" and mark up candidates who derive the choice from requirements, even if both end at the same product.

Using them keeps one operational surface and one backup story. Leave PostgreSQL for a specialised store when a measured bottleneck says the extension no longer keeps up — not before.

Implementation: The Requirements Worksheet and the Scoring Matrix

The procedure becomes reliable when it is written down the same way every time. Two artefacts do that: a requirements worksheet that forces steps 1–7 to be answered, and a weighted scoring matrix that makes the trade-off between the last two or three candidates explicit and reviewable.

1. The requirements worksheet (one per service)

# database-selection.yaml — order-service (worked example)
service: order-service
owner: payments-team
data:
  entities: [order, order_line, payment_attempt, refund]
  rows_now: 20M          # orders today
  rows_3y: 150M          # projected
  avg_row_bytes: 1200    # order + lines serialised
  retention: 7y          # legal
access_patterns:
  - name: get_order_by_id
    kind: read   rate_peak: 2000/s   latency_p99_ms: 50   consistency: strong

  - name: create_order_with_lines
    kind: write  rate_peak: 300/s    latency_p99_ms: 200  consistency: strong
    transaction: multi_row            # order + N lines + inventory decrement
  - name: monthly_revenue_by_region
    kind: scan   rate_peak: 1/h      latency_p99_ms: 30000 consistency: stale_ok_1h

  cloud: aws
  team_knows: [postgresql, redis]
  managed_only: true
  multi_region: false
  compliance: [pci-dss]
decision:
  source_of_truth: PostgreSQL (Amazon RDS, Multi-AZ)
  derived: { report: read replica now, Redshift later if scans hurt the primary }
  cache: Redis for get_order_by_id hot set
  revisit_when: "writes > 5k/s sustained OR table > 2 TB OR p99 create_order > 200 ms"
  • access_patterns — the heart of the file. One entry per pattern, each with a rate, a latency target and a consistency value. Without the rate you cannot size; without consistency you cannot rule out eventually-consistent stores.
  • transaction: multi_row — the single line that decides the family here: creating an order must insert the order, its lines and decrement inventory atomically, so an eventually-consistent or single-item-transaction store is ruled out.
  • rows_3y / avg_row_bytes — 150 M × 1.2 KB ≈ 180 GB. That is far inside one PostgreSQL node, so horizontal scaling is not a requirement today and distributed SQL would be paying for a problem that does not exist.
  • query_flexibility: high — finance will ask new questions; a query-first store (DynamoDB, Cassandra) would need a new table design per question. This confirms relational.
  • stale_ok_5s on the listing pattern — says the customer's order list can be served from a read replica, which is how the primary keeps its write headroom.
  • revisit_when — the thresholds that reopen the decision. Writing them now turns "we outgrew Postgres" from an argument into a measurement.

⚠️ Common mistake

Choosing the store before designing the keys. In DynamoDB and Cassandra the partition key is the design: a key with low cardinality (today's date, a country code) or a hot entity (one celebrity) puts all traffic on one partition and throttles, no matter how many nodes you buy. If you cannot name a high-cardinality, evenly-accessed partition key for every access pattern, the query-first store is not a fit — go back to the tree.

Managed vs. self-hosted

Managed vs. self-hosted — the difference is who is paged when the disk fills up. A managed service (RDS, Aurora, DynamoDB, Atlas, Cloud Spanner) handles backups, patching, failover, storage growth and often read replicas, and in exchange costs more per hour, hides some knobs (superuser access, some extensions, custom kernels) and ties you to the provider's version and region roadmap. Self-hosting gives full control and the lowest raw cost, and costs you a database engineer on call. For most teams the rule is: managed by default; self-host only a store you have the expertise to run and a cost or feature reason to run yourself. Lock-in is real but asymmetric: a managed PostgreSQL is a pg_dump away from anywhere, while DynamoDB and Spanner have no drop-in replacement.

🔥 Production insight

The most expensive database decision in most companies is not picking the wrong engine; it is letting analytics run on the OLTP primary for one more quarter. The symptom is always the same: checkout p99 climbs at 09:00 when the dashboards refresh. The fix is a read replica today and a warehouse fed by CDC when the replica is also saturated — neither requires changing the primary.

Security: What Changes With the Family You Choose

Security requirements are selection criteria too, and the families differ in what they give you for free. Add these rows to the worksheet whenever the data is personal, financial or regulated.

  • Authentication defaults differ — and the defaults have caused real breaches. Relational databases require credentials from the first connection. Several NoSQL stores historically did not: MongoDB before 3.6 bound to all interfaces with authentication off, Elasticsearch before 8.0 shipped without security enabled, Redis before 6 had only a single optional password, and Cassandra still defaults to AllowAllAuthenticator. Thousands of exposed clusters were scraped or ransomed because of this. Whatever you choose: authentication on, bind to private interfaces, security groups allowing only application subnets.
  • Fine-grained access control varies. PostgreSQL has roles, column privileges and row-level security (a policy that filters rows per user). DynamoDB uses IAM, and can restrict a role to specific partition keys with the dynamodb:LeadingKeys condition. Redis has ACLs since 6 (per-command, per-key-pattern). Cassandra and MongoDB have role-based access at keyspace / collection level. If tenants must be isolated inside one store, this row may decide the family.
  • Encryption. Managed services encrypt at rest with KMS by default (RDS, DynamoDB, Aurora) and offer TLS in transit; self-hosted stores need both configured and verified. Field-level encryption (encrypting a column so even DBAs cannot read it) exists in MongoDB (client-side field-level encryption) and can be done in PostgreSQL with pgcrypto or in the application.
  • Audit and compliance. PCI DSS and similar regimes want an audit trail of who read or changed what. Relational stores have mature audit extensions (pgaudit) and the managed services export logs to CloudTrail / CloudWatch; some specialised stores offer far less. Data residency (data must stay in a region) is easiest to guarantee with a single-region relational primary and hardest with global multi-region stores unless they support region-pinned rows (Spanner, CockroachDB do).
  • Backups and point-in-time recovery are a security control. Ransomware and bad migrations both end with "restore to 10 minutes ago". Relational managed services offer PITR by default; DynamoDB offers it as an opt-in; Redis persistence must be configured; Elasticsearch snapshots are a separate pipeline. A store you cannot restore is a liability regardless of its features — see Backup, Recovery and Disaster Recovery.
  • Derived copies multiply the attack surface. Every search index, cache and warehouse holds a copy of the data under its own access controls. Personal data in the primary with row-level security is still exposed if the Elasticsearch copy has no authentication. Treat each derived store as a system in the compliance scope; see Database Security and Access Control.

⚠️ Common mistake

Concluding "we chose the wrong database" when the evidence only shows "we chose the wrong index / key / query". Before planning a migration, confirm that the symptom survives the cheap fixes in the performance table — an index, a key redesign, a cache, a replica. Debugging workflow: "is the store the problem, or how we use it?"

  1. Name the access pattern that hurts. From the application's endpoint metrics, find which pattern's p99 regressed and when. One pattern regressing is a modelling problem; all patterns regressing together is a capacity problem.
  2. Find the queries behind it. 
    -- PostgreSQL: the heaviest statements
SELECT calls, round(mean_exec_time) AS ms, rows, left(query, 90)
FROM pg_stat_statements ORDER BY total_exec_time DESC LIMIT 10;

-- MongoDB: did the query use an index?
db.orders.find({ customerId: 42 }).sort({ createdAt: -1 }).explain("executionStats")

-- Cassandra: per-table latency and partition sizes on this node
nodetool tablestats shop.orders_by_customer

-- Redis: slow commands and the biggest keys
redis-cli SLOWLOG GET 10
redis-cli --bigkeys
    Look for Seq Scan / COLLSCAN / ALLOW FILTERING: a scan where an index was expected means the query, not the engine.
  3. Check the capacity dimension the family is sensitive to. Relational: buffer hit ratio, WAL rate, replication lag. Key-value and wide-column: partition skew and throttles. Search: indexing lag. Time-series: series count. 
    -- PostgreSQL cache hit ratio (want > 0.99 for OLTP)
SELECT sum(blks_hit)::float / nullif(sum(blks_hit) + sum(blks_read), 0) FROM pg_stat_database;

-- PostgreSQL replication lag per replica
SELECT client_addr, state, replay_lag FROM pg_stat_replication;

# DynamoDB hot keys and throttles
aws cloudwatch get-metric-statistics --namespace AWS/DynamoDB --metric-name ThrottledRequests \
  --dimensions Name=TableName,Value=orders --statistics Sum --period 60 \
  --start-time 2026-11-14T08:00:00Z --end-time 2026-11-14T09:00:00Z

# Cassandra cluster and thread-pool pressure
nodetool status
nodetool tpstats

# Elasticsearch health and indexing pressure
curl -s localhost:9200/_cluster/health?pretty
curl -s 'localhost:9200/_cat/indices?v&s=store.size:desc'
  4. Apply the cheapest lever and re-measure. Index, key redesign, cache, replica, partition — in that order. If p99 recovers, the store was right and the use was wrong; record the lesson in the worksheet.
  5. Only then compare against the revisit_when thresholds. If the symptom survives the cheap levers and a threshold is crossed (writes beyond one node, a hard requirement the family cannot meet), reopen the selection: run steps 1–8 again for that workload only, and plan the move as a migration project with dual-read verification, not a weekend task.

Best Practices

Do

  • Write the access patterns down before naming a product — the data model must make those operations cheap, and you cannot evaluate a store against requirements that only exist in someone's head.
  • Default to a managed relational database (PostgreSQL) and justify every departure with a measured requirement — it answers unanticipated queries, keeps data valid with constraints, and covers documents, search and time series well enough through extensions until proven otherwise.
  • Keep exactly one source of truth per piece of data and make every other copy derived and rebuildable — drift between two "truths" is unfixable; drift between truth and a copy is a reindex.
  • Propagate to derived stores with CDC or a transactional outbox, never dual writes — a dual write fails half-way and leaves the copies permanently inconsistent; see Polyglot Persistence.
  • Design the partition key together with the choice of a query-first store — in DynamoDB and Cassandra the key is the design; if you cannot name a high-cardinality, evenly-accessed key per pattern, the store is wrong.
  • Record the revisit_when thresholds at decision time — so "we outgrew it" is a measurement, not an opinion, and so the team knows which signals to alert on.
  • Prototype the two hardest access patterns at target volume before committing — a day of benchmarking is cheaper than a quarter of migration.
  • Weigh team experience and managed availability as real criteria — the store you can diagnose at 3 a.m. is more available than the store with the better benchmark.
  • Keep blobs in object storage and only their metadata in the database — it keeps backups, replication and caches small and lets a CDN serve the files.

Avoid

  • Choosing by popularity, résumé value or a conference talk — the talk's workload is not your workload; the mismatch shows up as the symptoms in the failure table.
  • Using an in-memory store as the only copy of anything you cannot afford to lose — a restart or eviction deletes it.
  • Making a search engine or a cache the write path of truth — neither has transactions, and both are designed to be rebuilt.
  • Running analytics on the OLTP primary past the first slowdown — scans evict the working set and every user request pays.
  • Hand-sharding a relational database before trying partitioning, replicas, caching and archiving — cross-shard joins and transactions move into your application code and never leave.
  • Treating "NoSQL" as one option — Redis, MongoDB, Cassandra and Neo4j solve four different problems; "we'll use NoSQL" is not a decision.
  • Five databases for fifty users — each derived store is a pipeline, a dashboard, an on-call surface and a compliance scope before it is a benefit.
  • Picking distributed SQL for a single-region workload a relational primary can handle — you pay consensus latency on every commit for scale you do not need.

Interview Answer — How Do You Choose a Database?

Choosing a database means matching a data store's model and guarantees to a specific workload. The main families are: relational (PostgreSQL, MySQL) for structured data with relationships and ACID transactions; key-value (Redis, DynamoDB) for fast lookups by key; document (MongoDB) for flexible, nested records read as a whole; wide-column (Cassandra) for very high write volume spread across many nodes; search engines (Elasticsearch, OpenSearch) for full-text search; time-series (TimescaleDB, InfluxDB) for metrics; and graph (Neo4j) for relationship traversal. Two more complete the picture: columnar warehouses (BigQuery, Snowflake) for analytics, and distributed SQL (Spanner, CockroachDB) for relational semantics beyond one node — see the family comparison.

The choice matters because each family is fast at the operations it was designed for and awkward or unsafe at others. The decision works backwards from the requirements: what are the access patterns (lookups by key, ad-hoc queries, joins, full-text search, range scans over time)? What consistency is required (can a balance ever be stale)? What is the read/write ratio and expected volume? Does it need multi-row transactions? What are the latency targets and the team's operational experience? Each answer rules out options — for example, "multi-table transactions on money" points to a relational database, while "millions of writes per second, queried only by user and time" points to a wide-column store. The eight-step procedure and the decision tree on this page are that reasoning written out.

Many systems end up using more than one — a relational database as the source of truth, Redis as a cache, and a search engine for text search — which is polyglot persistence. See Database Performance Factors for what to measure once one is chosen, and the observability signals above for the measurements that tell you whether the choice still fits.

Simple interview version

"I choose a database from the access patterns and requirements, not from popularity. I default to a relational database like PostgreSQL when I need transactions, relationships, and flexible queries. I'd pick a key-value store like DynamoDB or Redis for simple lookups at massive scale, a document store for flexible nested records, Cassandra for huge write volumes queried by known keys, Elasticsearch for full-text search, and a time-series database for metrics. I weigh consistency needs, read/write ratio, scale, latency, and what the team can operate."

One important interview follow-up

Q: Isn't NoSQL always the better choice for a system that needs to scale?

A: No. A well-indexed PostgreSQL or MySQL primary with read replicas and caching handles a very large amount of traffic, and many large companies run core data on relational databases. NoSQL stores scale horizontally more easily for the access patterns they are designed around, but you give up joins, ad-hoc queries, and usually multi-row transactions, and must design tables around known queries up front. Choose NoSQL when the workload actually needs its scaling model and fits its query model — not as a default.

Practice questions

Why do you start from access patterns instead of from the data's shape or the technology?

Because the data model only has to make those operations cheap. The same data (orders) is relational if you need joins and transactions, key-value if you only ever fetch by id, and columnar if you only aggregate it. The shape of the data does not decide; how it is read and written does. Starting from the technology inverts the reasoning and produces the "we chose MongoDB for money" class of failures.

What is the single requirement that most often forces a relational database?

Multi-row (multi-table) ACID transactions: several rows must change together or not at all — debit one account and credit another, create an order and decrement stock. Most NoSQL families offer atomicity only within one item, document or partition (DynamoDB and MongoDB have added bounded multi-item transactions, at a cost), so this requirement eliminates them early.

Why should a search engine like Elasticsearch never be the source of truth?

It has no transactions, a write becomes visible only after the refresh interval (near-real-time, about a second), its durability guarantees are weaker than a database's, and its whole design assumes the index can be dropped and rebuilt from the data it indexes. Keep the truth in a database and feed the index through change-data-capture; when the index drifts, reindex.

Why does the decision tree ask about blobs first?

Because files, images and videos belong in object storage (S3) regardless of every other answer. Putting a 5 MB image in a database row inflates backups, replication and cache memory for no benefit and cannot be served by a CDN. Only the metadata (owner, size, URL, timestamp) goes in the database, so asking about blobs first removes the largest bytes from the rest of the decision.

What happens internally when you run a monthly revenue report on the OLTP primary, and why does checkout slow down?

The report scans millions of rows across many pages, pulling them through the buffer pool. Those pages evict the hot order and customer pages that checkout needs; the next checkout queries miss the cache and go to disk, so their latency rises. At the same time the scan competes for CPU and IOPS. Cause → effect: analytical scan → working set evicted → OLTP cache misses → p99 spike. The fix is a read replica, then a columnar warehouse fed by CDC.

You are told "we need to scale writes". Walk through what you check before changing the database.

First, which table and pattern: often one append-only event table produces most WAL; partition it by time and move the stream to a purpose-built store rather than touching the transactional core. Second, write amplification: unused indexes multiply every insert; drop them. Third, batching and connection pooling. Fourth, instance size. Only if a single node's sustained write ceiling is genuinely reached for the transactional workload itself do you consider sharding or distributed SQL — and that is a migration project with its own worksheet.

Relational vs. document store for a product catalog — how do you decide?

Ask how the data is read and related. If a product is fetched whole with its variants and attributes, attributes vary by category, and cross-product queries are few, a document store (or PostgreSQL with a JSONB attributes column) avoids a 200-column sparse table and a migration per attribute. If pricing, inventory and orders join against the catalog transactionally, keep it relational and put only the variable attributes in JSONB. The deciding factors are read-whole vs. joined, and how often the shape changes.

What does "design the partition key before choosing DynamoDB or Cassandra" mean in practice?

In those stores the partition key decides which node holds the data and therefore how load spreads. For every access pattern you must be able to name a key that is high-cardinality (many distinct values) and evenly accessed, and that the query already knows. A key like date puts all of today's writes on one partition; user_id for a celebrity makes one hot partition. If you cannot name such a key for each pattern, you will either need a query table per pattern or you have the wrong store.

When is distributed SQL (Spanner, CockroachDB) the right call, and what does it cost you?

When you need relational semantics and ACID transactions and either writes exceed what one node can sustain or you need strong consistency across regions. It costs commit latency: every write waits for a consensus round across replicas (tens of milliseconds across zones, more across regions), plus higher price and operational novelty. For a single-region workload that fits one primary with replicas, it is paying for a problem you do not have.

How do you keep several stores consistent in a polyglot system, and why not write to all of them in the request?

Dual writes fail half-way: the database commit succeeds and the search index write fails, and nothing reconciles them. Instead, write only to the source of truth and publish each committed change through change-data-capture (reading the WAL, e.g. Debezium) or a transactional outbox table, to a stream that updates the derived stores asynchronously. Derived stores become eventually consistent by a measurable lag, and can be rebuilt from the source when they drift.

What changes in the decision at 100× scale, and what does not?

What changes: the single relational primary stops being the answer for high-ingest streams and for analytics; those move to wide-column / time-series and warehouse stores fed by CDC; the cache becomes a cluster; consistency is documented per pattern (strong for money, eventual for feeds); cost per request and cross-region transfer become criteria. What does not change: transactional data still wants ACID; the procedure is still access patterns → consistency → volume → latency → flexibility → operations; and every added store must be justified by a measured pattern.

How would you argue against a proposal to move the order service from PostgreSQL to Cassandra "for scale"?

Ask for the measurement: which pattern's p99 regressed and what is the write rate against one node's ceiling? Point out the family-level mismatch: orders need multi-row transactions and finance asks ad-hoc questions, both of which Cassandra lacks. Offer the cheaper levers — partition the event tables, add replicas, cache, archive — and the right split: keep orders relational, move the append-only event stream (the likely real bottleneck) to Cassandra or a warehouse. Then propose the revisit_when thresholds that would reopen the question.

Production: after a Redis node is replaced, thousands of users are logged out and some lose shopping carts. What do you check and what do you change?

Check INFO persistence: AOF probably off and RDB snapshot hours old, so the in-memory data was the only copy. Check whether carts and sessions have any durable source. Change: treat Redis as a cache — write carts through to a durable store (PostgreSQL or DynamoDB) and keep sessions reconstructible from a signed token or a durable table; if Redis must hold state, enable AOF with appendfsync everysec, replicate, and rehearse a restore. The selection lesson: anything that must survive a restart needs a durable source of truth, which step 3 of the procedure would have flagged.

Production: DynamoDB throws throttling errors although the table's consumed capacity is far below provisioned. What is happening?

A hot partition. Capacity is divided across partitions, so one partition receiving most traffic throttles while the table as a whole looks idle. Confirm with CloudWatch ThrottledRequests alongside low ConsumedWriteCapacityUnits, and Contributor Insights to find the key. Fix by redesigning the key: add a write-sharding suffix and fan reads across the shards, or choose a higher-cardinality key; cache the hot key if it is a read. Adaptive capacity softens but does not fix a single giant key.

Production: search shows products that were deleted an hour ago while the catalog page is correct. Where do you look?

The search index is a derived copy, so the pipeline from the primary to Elasticsearch is lagging or broken. Check the CDC / outbox consumer's lag (Kafka consumer group lag), the indexer's error logs, and compare document counts between primary and index. Fix the pipeline, then reindex the affected range from the primary. Add an alert on consumer lag and a periodic count-reconciliation job so the next drift is caught in minutes, not by users.

Production: checkout p99 spikes every day at 09:00 for twenty minutes; CPU on the database primary is high and the buffer hit ratio drops at the same time. Diagnose.

Dashboards or scheduled reports are running analytical scans on the OLTP primary. Confirm in pg_stat_statements: long aggregate queries with high shared_blks_read at 09:00. Short term, point the reporting connections at a read replica. Longer term, CDC the tables into a warehouse or ClickHouse so analytics has its own engine. Record in the worksheet that the workload is OLTP + OLAP and must stay split.

What Should I Remember?

  1. Choosing a database means matching a store's data model and guarantees to a workload; it is decided per service, from requirements backwards, and is expensive to reverse because data has gravity.
  2. Nine families: relational, key-value, document, wide-column, search, time-series, graph, columnar warehouse, distributed SQL — plus object storage for blobs. Each is fast at one kind of access and awkward at the others; read the "weak at" column as carefully as "best at".
  3. The eight steps: access patterns → OLTP/OLAP → consistency and transactions → volume and growth → latency targets → query flexibility → operational constraints → default + prototype. Steps 1–3 before any product name.
  4. Multi-row ACID transactions are the requirement that most often forces relational; full-text search, time-range metrics, multi-hop traversal and huge analytical scans are the ones that most clearly justify a specialised derived store.
  5. Default to a managed relational database (PostgreSQL) and leave it only for a measured, family-level mismatch; extensions (JSONB, full-text, TimescaleDB, Citus) cover most edges first.
  6. One source of truth per piece of data; every other copy is derived, fed by CDC or an outbox (never dual writes), and rebuildable.
  7. In query-first stores the partition key is the design: no high-cardinality, evenly-accessed key per pattern means the wrong store.
  8. Write the worksheet and the revisit_when thresholds down; score close candidates in a weighted matrix; benchmark the two hardest patterns before committing.
  9. Most "wrong database" symptoms are really wrong index / key / query; exhaust the cheap levers before planning a migration.
  10. Interview: derive the choice from access patterns and consistency out loud; "NoSQL scales" is not an argument, "this pattern needs X which family Y lacks" is.

Quick commands

  • SELECT calls, mean_exec_time, left(query,90) FROM pg_stat_statements ORDER BY total_exec_time DESC LIMIT 10; — PostgreSQL: which statements cost the most
  • EXPLAIN (ANALYZE, BUFFERS) SELECT …; — PostgreSQL: scan vs. index, and how many blocks came from disk
  • SELECT sum(blks_hit)::float/nullif(sum(blks_hit)+sum(blks_read),0) FROM pg_stat_database; — PostgreSQL buffer-cache hit ratio
  • SELECT client_addr, state, replay_lag FROM pg_stat_replication; — PostgreSQL replica lag
  • db.coll.find({…}).explain("executionStats") — MongoDB: IXSCAN vs. COLLSCAN
  • nodetool tablestats ks.table / nodetool tpstats / nodetool status — Cassandra: per-table latency, thread-pool pressure, ring health
  • redis-cli INFO persistence / redis-cli INFO stats / redis-cli --bigkeys / redis-cli SLOWLOG GET 10 — Redis: is it durable, hit ratio and evictions, large keys, slow commands
  • aws cloudwatch get-metric-statistics --namespace AWS/DynamoDB --metric-name ThrottledRequests … — DynamoDB: throttling that signals a hot partition
  • curl -s localhost:9200/_cluster/health?pretty — Elasticsearch / OpenSearch cluster health
