📘 Database & Distributed Systems — Learning Roadmap

Interview Answer — What Is a Database, and Why Does It Get Hard at Scale?

A database is a system that stores data durably and lets applications read and change it concurrently and correctly through a query interface. A single-node database — one PostgreSQL or MySQL server — gives you tables, indexes, SQL, and ACID transactions, and for many applications that is enough.

It gets hard at scale because one node has limits: disk size, write throughput, the number of connections, and being a single point of failure. Each way of removing a limit introduces a new problem. The cause → effect chain is: to survive node failure and scale reads you add replicas → replicas lag, so reads can be stale and failover can lose writes → to scale writes and data size you partition or shard the data → queries and transactions that span partitions become slow or impossible, and a bad partition key creates hot spots → to keep other systems in sync you capture changes (CDC) and index into search engines → now you must reason about ordering, duplicates, and eventual consistency across systems.

This roadmap follows that path in order: single-node foundations → distributed database theory such as CAP and consistency models (see Stage 2) → data distribution → synchronization and change tracking → search and query optimization → putting it together in system design → production operations, security, and reliability.

Simple interview version

"A database stores data durably and lets many clients read and write it correctly, usually with ACID transactions on a single node. At scale one node isn't enough, so we replicate for availability and read scaling, which brings replication lag and consistency trade-offs, and we partition or shard for write throughput and data size, which makes cross-partition queries and transactions harder. Understanding databases for system design means knowing those trade-offs — CAP, consistency models, partitioning strategies, and change data capture — and choosing per workload."

One important interview follow-up

Q: When a single database starts struggling, should you shard it right away?

A: No — sharding is usually the last lever, not the first, because it permanently adds complexity: cross-shard joins and transactions, rebalancing, and a partition key that is hard to change later. Before sharding, fix the queries and indexes, add caching, move reads to read replicas, add connection pooling, archive or partition old data within the same database, and scale the instance vertically. Shard when write throughput or data size genuinely exceeds what one well-tuned primary can handle, and choose the partition key from the access patterns.

Stage 1. Foundations (Single-Node Database Basics)

Why? Before scaling out, you must know how a single database works.

  • Relational (SQL) vs Non-relational (NoSQL)

    • What: SQL (Postgres, MySQL) uses structured schema; NoSQL (MongoDB, Cassandra) stores flexible data.
    • When to use: SQL → banking, orders; NoSQL → social media, logs.
    • Why: Different workloads need different data models.

  • ACID Properties (Atomicity, Consistency, Isolation, Durability)

    • What: Guarantees correctness in transactions.
    • When: Critical systems (banking, inventory).
    • Why: Prevents errors like “double withdrawal.”
    • Isolation Levels: Read Uncommitted → Serializable (trade-off between speed vs. strictness).

  • Indexes & Query Optimization

    • What: Structures (B-Tree, Hash, Bitmap) that speed up reads.
    • When: Queries on large datasets.
    • Why: Without indexes, DB must scan everything.
    • Tool: EXPLAIN query plans.

  • Keys & Constraints

    • What: Rules ensuring data integrity (Primary, Foreign, Composite keys).
    • When: Relational DB design.
    • Why: Avoids duplicates, ensures valid references.

Stage 2. Distributed Database Theory

Why? Single servers can’t handle global scale → we distribute.

  • Why Distribution?

    • Scalability → more users & data.
    • Availability → system keeps running despite failures.
    • Disaster recovery → backup across regions.

  • Vertical vs Horizontal Scaling

    • Vertical: Bigger server → limited.
    • Horizontal: Many servers → scalable.

  • CAP Theorem (Consistency, Availability, Partition tolerance → pick 2)

    • CP: Strong consistency, less availability (e.g., MongoDB strong mode).
    • AP: High availability, eventual consistency (e.g., Cassandra, DynamoDB).
    • Why: Network failures force trade-offs.

  • Consistency Models

    • Strong: Always latest data.
    • Eventual: Updates propagate later.
    • Causal, Read-Your-Own-Writes: Middle ground.
    • When: Choose based on app needs (banking vs social media).

  • BASE (NoSQL Philosophy)

    • What: Basically Available, Soft state, Eventually consistent.
    • Why: Sacrifices strictness for performance at scale.

Deep dive on the site: Distributed Systems, Distributed Database Fundamentals, CAP Theorem Questions, Replication & Distributed Data Roadmap, PACELC — Senior Interview Masterclass.

Stage 3. Data Distribution Techniques

Why? Large systems need splitting & copying data.

  • Partitioning (Sharding)

    • What: Splitting data across servers.
    • How: Key-based, Range-based, Hash-based.
    • Challenge: Rebalancing when data grows.
    • When: Big data apps (e.g., MongoDB sharding).

  • Replication

    • What: Copying data across nodes.
    • Types: Leader-follower, Multi-leader, Leaderless.
    • Trade-off: Sync (safe but slow) vs Async (fast but risk of lag).
    • Why: Improves fault tolerance.

  • Load Balancing

    • What: Spread traffic across servers.
    • How: DNS (Route 53), ALB, Geo-routing.
    • Why: Reduces latency, avoids overload.

Deep dive on the site: Data Distribution, Partitioning, Horizontal Scaling, Replication Mechanism — The 4 Dimensions, Replication Slides (+ Pt. 3, 4, 5, Deep-Dive).

Stage 4. Data Synchronization & Change Tracking

Why? In distributed DBs, data changes must stay in sync.

  • Change Data Capture (CDC)

    • What: Track changes via logs.
    • Tools: Debezium, Kafka Connect, AWS DMS.
    • Why: Keeps downstream systems updated.

  • Full Load + Incremental Updates

    • When: Initial migration (full) + real-time sync (incremental).
    • Why: Efficient for ongoing updates.

  • Conflict Resolution

    • What: Resolve concurrent writes.
    • How: Last-write-wins, Vector clocks, CRDTs.
    • Why: Prevent data corruption.

  • Real-time vs Batch Sync

    • Trade-off: Freshness vs performance.

Deep dive on the site: WAL vs Binlog, Replication Lag — Causes, Measurement, Mitigation.

Stage 5. Search & Query Optimization

Why? Traditional DBs aren’t great for large-scale text or ranking queries.

  • Full-text Search

    • What: Specialized indexing (Elasticsearch, OpenSearch).
    • When: Searching millions of documents.
    • Why: Normal indexes can’t handle it.

  • Ranking & Scores

    • What: TF-IDF, BM25, Vector search.
    • Why: Needed for relevance-based search.

  • Hybrid DB + Search

    • Pattern: Use DB for storage + search engine for queries.
    • Example: E-commerce → DB for orders, Elastic for product search.

Stage 6. System Design Integration

Why? Combine everything for real-world architecture.

  • Scalable DB Design Choices

    • ACID vs BASE → depends on app.
    • Choose consistency model.
    • Multi-AZ & Multi-region deployments.

  • Common Architectures

    • CQRS: Separate read/write paths.
    • Event Sourcing: Store events instead of current state.
    • Polyglot Persistence: Different DBs for different needs.

  • Case Studies

    • Twitter feed: Append-only, high write throughput.
    • E-commerce: Relational for orders, NoSQL cache for products.
    • Analytics dashboard: Real-time streaming DB.

Stage 7. Production Operations, Security & Reliability

Why? Running a database in production is more than the theory above — it also means keeping it safe, connectable at scale, recoverable, and observable.

  • Database Security & Access Control

    • What: Authentication, authorization, roles, row-level security, encryption at rest/in transit.
    • When: Every production database, always.
    • Why: Prevents unauthorized access and data leaks.

  • Connection Management & Database Proxies

    • What: Pooling connections (PgBouncer, RDS Proxy) instead of opening one per client.
    • When: High-concurrency apps, serverless functions hitting the DB.
    • Why: Databases have a hard limit on concurrent connections; pooling avoids exhaustion.

  • Backup, Recovery & Disaster Recovery

    • What: Snapshots, point-in-time recovery, cross-region backups.
    • When: Before you need it — plan and test restores ahead of an incident.
    • Why: Data loss or corruption is a matter of when, not if.

  • Observability, Capacity & Operations

    • What: Query/connection/replication metrics, slow-query logs, capacity planning.
    • When: Continuously, not just when something breaks.
    • Why: You can't fix what you can't see, and capacity problems are cheaper to prevent than to firefight.

🔑 Principles to Remember

  • ACID vs BASE → strict vs scalable.
  • CAP Theorem → can’t have it all.
  • Indexes → fast reads, slower writes.
  • Replication & Sharding → foundation of distributed DBs.
  • Consistency models → choose per use case.
  • Scaling → vertical is limited, horizontal is future.
  • Security, backups & observability → the difference between a database that runs and one that's production-ready.
