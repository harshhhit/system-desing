Lecture 2 — Databases & Distributed Systems

Interview Answer — What Is the Difference Between ACID and BASE?

ACID and BASE describe two philosophies for the guarantees a database gives. ACID — Atomicity, Consistency, Isolation, Durability — means each transaction is all-or-nothing, leaves the data valid, is isolated from concurrent transactions, and survives crashes once committed; relational databases such as PostgreSQL provide it. BASE — Basically Available, Soft state, Eventually consistent — means the system stays available and accepts that replicas may briefly disagree and converge over time; many distributed NoSQL stores such as Cassandra and DynamoDB default to it.

The two exist because of the trade-off the CAP theorem describes. Keeping every replica strictly consistent across a network requires coordination on each write, which costs latency and, during a partition, availability. The cause → effect chain for a BASE system is: a write is accepted by some replicas and acknowledged quickly → other replicas receive it a little later through replication → a read in that window may return an older value → eventually all replicas converge. For an ACID system it is the reverse: the write waits for the coordination it needs, so reads are correct but writes are slower and can be refused during failures.

ACID vs. BASE is not a strict either/or. Many NoSQL databases let you tune consistency per operation — MongoDB's read and write concerns, Cassandra's quorum reads and writes — and the consistency models on this page (strong, near-real-time, eventual, periodic) describe the range in between. Replication method (synchronous, asynchronous, semi-synchronous) and change data capture decide where on that range a system lands.

Simple interview version

"ACID means transactions are atomic, consistent, isolated, and durable — the model of relational databases, ideal for money and inventory. BASE means basically available, soft state, eventually consistent — the model of many distributed NoSQL stores, which stay available and fast but let replicas be briefly out of date. It's a spectrum, not a switch: many NoSQL databases let me tune consistency per request with quorums or read and write concerns, so I pick the guarantee each piece of data actually needs."

One important interview follow-up

Q: Does "eventually consistent" mean the data might be wrong forever?

A: No — it means that if writes stop, all replicas will converge to the same value; it does not say how long that takes or which value wins when writes conflict. In practice convergence is usually milliseconds to seconds, but during that window a user can fail to see their own write or see data go backwards between reads. The design must handle that: route a user's reads to the leader after they write (read-your-writes), use quorum reads when needed, and define how conflicts are resolved — last-write-wins, version vectors, or CRDTs — because "eventually" alone does not decide which concurrent write survives.

  1. CAP Theorem

Definition: In a distributed database, you can only guarantee two out of the following three at any given time:

C – Consistency: Every read gets the latest write or an error.

A – Availability: Every request gets a response, even if it’s not the latest.

P – Partition Tolerance: The system continues operating despite network partitions.

Trade-offs:

CP system: Prioritizes Consistency + Partition Tolerance → sacrifices Availability.

AP system: Prioritizes Availability + Partition Tolerance → sacrifices strict Consistency.

CA system: Possible only in non-partitioned single-node systems.

  1. ACID Properties

    Atomicity: A transaction is all-or-nothing.

    Consistency: Only valid data (meeting constraints) is stored.

    Isolation: Transactions don’t affect each other during execution.

    Durability: Once committed, data is permanent.

Relational DBs: Typically provide full ACID. Non-relational DBs: Often relax Isolation for performance and scalability. 3. Isolation in Non-Relational Databases

Many NoSQL DBs (MongoDB, Cassandra) provide weaker isolation like Read Committed or Eventual Consistency.

Isolation is often tuned via consistency levels:

    Read Concern / Write Concern in MongoDB.

    Quorum reads/writes in Cassandra.
  1. Distributed Systems Concepts

Partition & Replication

Partitioning (Sharding): Splitting data across nodes for scalability.

Replication: Copying data to multiple nodes for availability and durability.

  1. Database Replication Methods

    Synchronous Replication: Writes wait until all replicas confirm.

    Asynchronous Replication: Writes return immediately, replicas update later.

    Semi-Synchronous: Leader waits for at least one replica to confirm.

    Multi-master Replication: Multiple nodes can accept writes.

    Log-based Replication: Replicas replay the leader’s change logs.

  2. Consistency Models in Databases

    Strong Consistency (Real-time): All nodes always return latest value.

    Near Real-time: Small replication delay (milliseconds–seconds).

    Eventual Consistency: Updates propagate eventually, reads may be stale.

    Periodic Consistency: Data syncs at fixed intervals.

  3. CDC (Change Data Capture)

    Captures changes in real-time from DB logs or triggers.

    Useful for replication, streaming, analytics, and sync with search engines.

  4. Full Load

    Initial bulk load of all data into a new system before incremental updates.

  5. Search Optimization in Databases

    Full-text search engines like OpenSearch and Elasticsearch index data for fast keyword queries.

    Confidence score: Indicates relevance of results.

  6. Occurrence in DB Terms

    "Occurrence" often refers to frequency of values in a column (used in statistics and indexing).

  7. Keys in Databases

    Primary Key: Unique identifier for a row.

    Foreign Key: Enforces a link between tables.

    Enforces referential integrity in relational databases.

  8. Load Balancer in Multi-AZ / Multi-Region

    Yes, load balancers (AWS ALB, GCP LB) can distribute traffic across:

    Multiple Availability Zones (for fault tolerance within a region)

Multiple Regions (for disaster recovery & global latency reduction)
