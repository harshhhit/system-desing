Query Plans and Optimization

Study prompt: Learn to read EXPLAIN and EXPLAIN ANALYZE output, identify sequential scans and expensive joins, choose useful indexes, update statistics, avoid N+1 queries, and measure before and after every optimization.

Interview Answer — What Is a Query Plan?

A query plan is the step-by-step strategy the database's query planner (optimizer) chooses to execute a SQL statement — which tables to read, whether to use an index or scan the whole table, in what order to join, and which join algorithm to use. EXPLAIN shows the chosen plan with estimated costs; EXPLAIN ANALYZE actually runs the query and adds real timings and row counts.

Query plans exist because SQL is declarative: you say what you want, and the database decides how. The planner makes that decision using statistics about the data — table sizes and value distributions. The cause → effect chain of a slow query is usually visible in the plan: the statistics are stale or an index is missing → the planner estimates wrongly or has no better option → it picks a sequential scan of a large table or a nested loop over too many rows → the query takes seconds instead of milliseconds. Comparing estimated rows with actual rows in EXPLAIN ANALYZE shows where the planner's picture diverged from reality (see reading a query plan).

Optimization then follows a measure → change → re-measure loop: add an index that matches the query's WHERE, JOIN, and ORDER BY columns, rewrite the query, refresh statistics with ANALYZE, or fix the application pattern — most often the N+1 query problem.

Simple interview version

"A query plan is how the database decides to execute a SQL query — index or full scan, join order, and join algorithm — based on its statistics. I use EXPLAIN ANALYZE to see the real plan with timings and row counts, look for sequential scans on big tables, bad row estimates, and expensive joins, then fix it with the right index, a rewritten query, updated statistics, or by removing N+1 queries in the application — and I always measure before and after."

One important interview follow-up

Q: I added an index on the column in my WHERE clause, but the plan still shows a sequential scan. Is the index broken?

A: Usually not — the planner may be choosing correctly or working from bad information. If the condition matches a large share of the table, reading the table sequentially is genuinely cheaper than thousands of random index lookups. Other common causes: the table statistics are stale (run ANALYZE); the query wraps the column in a function or cast (WHERE lower(email) = … cannot use a plain index on email); it filters only on a trailing column of a composite index; or the table is small. Check the estimated versus actual rows in EXPLAIN ANALYZE before forcing anything.

Reading a Query Plan

EXPLAIN shows the planner's chosen steps and estimated cost; EXPLAIN ANALYZE actually runs the query and adds real timings and row counts — use the latter to see where estimate and reality diverge.

Plan nodeMeaning
Seq ScanReads every row in the table. Fine for small tables; a red flag on a large one filtered by a selective condition.
Index ScanUses an index to find matching rows directly, then fetches each from the table.
Index Only ScanAnswers the query entirely from the index — no table fetch needed.
Nested LoopFor each row on one side, scans the other side. Good with a small outer set and an index on the inner.
Hash JoinBuilds a hash table from the smaller side, probes it with the larger — good for large, unsorted, unindexed joins.
Merge JoinBoth sides pre-sorted (often via an index), then merged — efficient for large sorted joins.

Indexing for the Query, Not the Table

  • Index columns used in WHERE, JOIN ... ON, and ORDER BY — not every column that "looks important."
  • A composite index's column order matters: it can serve a query that filters on its leading column(s), not one that only filters on a trailing column.
  • Stale table statistics can make the planner pick a bad plan even with the right index in place — re-run ANALYZE after large data changes.

The N+1 Query Problem

An ORM loop that issues one query per row of an earlier result (fetch 50 orders, then 50 separate queries for each order's line items) turns one round trip into 51. Fix it with a join, a batched WHERE id IN (...), or the ORM's eager-loading feature.

Practice

Take a slow endpoint, run EXPLAIN ANALYZE on its query, change one thing (add an index, rewrite a subquery as a join), and re-measure. Never trust an optimization you haven't measured before and after.
