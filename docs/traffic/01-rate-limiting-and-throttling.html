Rate Limiting & Throttling

Token bucket, leaky bucket, fixed and sliding window algorithms, distributed rate limiting with Redis, and the client contract (429, Retry-After).

Why rate limit

  • Protect the backend — cap how much load any one client can put on a shared resource, so one noisy caller can't degrade the service for everyone else.
  • Fairness — enforce a per-user/per-key quota so usage is distributed roughly according to plan/tier rather than first-come-first-served.
  • Abuse and cost control — stop credential-stuffing, scraping, or a runaway retry loop from turning into an incident or a surprise bill.
  • Upstream protection — a service calling a third-party API (payment provider, SMS gateway) rate-limits its own outbound calls to stay under that provider's limit and avoid being cut off entirely.

Algorithms

AlgorithmHow it worksAllows bursts?Memory / accuracy
Fixed window counterCount requests in the current clock window (e.g. per-minute); reset the counter when the window rolls overYes — a burst right at the boundary of two windows can let through nearly 2× the limit (all at the end of one window, all at the start of the next)Cheapest — one counter per key
Sliding window logStore the timestamp of every request in the last window; count how many fall inside a rolling window ending "now"No — exact, no boundary problemMost accurate, but memory grows with request volume (one entry per request)
Sliding window counterApproximates the log by weighting the previous fixed window's count by how much of it still overlaps the current rolling windowMostly no — close approximation of the log, without storing every timestampOne or two counters per key — the practical default
Token bucketA bucket holds up to N tokens, refilling at a fixed rate; every request consumes one token, and requests are rejected once the bucket is emptyYes, intentionally — a client that's been idle can burst up to the bucket size, then is limited to the refill rateOne counter + one timestamp per key — cheap, and the standard choice (AWS, Stripe, and most API gateways use it)
Leaky bucketRequests queue into a bucket and are processed ("leak out") at a fixed rate; the bucket overflowing rejects new requestsNo — smooths bursts into a constant output rate rather than allowing them throughSimilar cost to token bucket; used when the goal is a steady outbound rate (e.g. calls to a downstream API), not just gatekeeping inbound
Token bucket vs. leaky bucket, in one line

Token bucket controls how much traffic you let in and is happy to allow bursts; leaky bucket controls how much traffic you send out and actively smooths bursts away. Rate-limiting an API's inbound requests → token bucket. Throttling your own outbound calls to a fragile downstream → leaky bucket.

Where to enforce it

  • Client-side — polite, but not a security boundary; a client can always skip its own throttle. Useful for UX (disable a submit button) not protection.
  • Edge / API gateway — the common place for coarse, per-API-key or per-IP limits, before the request even reaches application servers; cheapest place to reject abusive traffic.
  • Per-service — finer-grained limits close to an expensive specific operation (e.g. "3 password-reset emails per hour," distinct from the general API limit).
  • Distributed rate limiting — once there's more than one instance enforcing the limit, they need a shared counter. The standard approach is Redis: an atomic INCR + EXPIRE (or a single Lua script so the check-and-increment is atomic and race-free) keyed by user:<id>:<window> — see Caching & CDN Fundamentals for why Redis specifically (atomic ops, TTLs built in).
Two instances checking-then-incrementing separately is a race

If "read the counter" and "increment the counter" are two separate calls, two concurrent requests on two different app instances can both read the count just under the limit, both pass, and both increment — quietly letting one extra request through the limit. Use a single atomic operation (Redis INCR, or a Lua script for token-bucket logic) instead of read-then-write.

Talking to the client about it

  • 429 Too Many Requests — the correct HTTP status for a rejected request, distinct from a 4xx client error like malformed input.
  • Retry-After header — tells the client how many seconds (or a date) to wait before retrying, instead of making it guess.
  • X-RateLimit-Limit / -Remaining / -Reset — conventional (non-standard but widely adopted) headers so well-behaved clients can self-throttle before they ever hit 429.
  • A client should back off with jitter on retry, not retry immediately — otherwise every rejected client retries at the same instant, recreating a self-inflicted thundering herd.

Related but distinct terms

  • Throttling — often used interchangeably with rate limiting, but sometimes specifically means slowing a client down (delaying responses) rather than rejecting requests outright.
  • Backpressure — a downstream component that's falling behind signals upstream to slow down (or upstream detects a growing queue and self-limits), as opposed to a rate limiter which enforces a policy regardless of actual downstream health.
  • Circuit breaking — stops calling a dependency at all once it's clearly failing, rather than limiting the rate of calls to a healthy-but-finite one. A different tool for a different failure mode (dependency down vs. dependency at capacity).

Interview checklist

  • Name the algorithm and justify it: token bucket if bursts should be allowed, sliding window counter if precision at the window boundary matters more than a little memory.
  • Say where it's enforced (edge/gateway vs. per-service) and why — coarse abuse protection belongs at the edge, business-rule-specific limits belong near the operation they protect.
  • If there's more than one instance, say explicitly how the counter is shared and kept atomic (Redis + a single atomic op) — this is the detail that separates a real answer from a hand-wave.
  • Mention the client contract: 429 + Retry-After, and clients retrying with jittered backoff, not immediate retry.
