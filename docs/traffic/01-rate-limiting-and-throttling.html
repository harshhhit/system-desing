Rate Limiting & Throttling

Token bucket, leaky bucket, fixed and sliding window algorithms, distributed rate limiting with Redis, and the client contract (429, Retry-After).

What you'll learn

By the end of this page you will be able to:

  • Explain why shared services need per-client limits
  • Compare fixed window, sliding window, token bucket and leaky bucket
  • Decide where to enforce a limit: client, gateway or service
  • Build a race-free distributed limiter on Redis
  • Design the client contract: 429, Retry-After, backoff with jitter
  • Distinguish rate limiting from throttling, backpressure and circuit breaking

Why Rate Limit

Rate limiting caps how many requests one client — an API key, a user, an IP — may make in a time period, and rejects (or delays) the excess. It exists because a shared service has finite capacity, and without a cap one caller can take it all:

  • Protect the backend — cap how much load any one client can put on a shared resource, so one noisy caller can't degrade the service for everyone else.
  • Fairness — enforce a per-user/per-key quota so usage is distributed roughly according to plan/tier rather than first-come-first-served.
  • Abuse and cost control — stop credential-stuffing, scraping, or a runaway retry loop from turning into an incident or a surprise bill.
  • Upstream protection — a service calling a third-party API (payment provider, SMS gateway) rate-limits its own outbound calls to stay under that provider's limit and avoid being cut off entirely.

💡 Important

Adding servers behind a load balancer raises capacity but never makes it unlimited. The load balancer decides where a request goes; the rate limiter decides whether it is allowed at all.

Core Concepts

TermMeaning
KeyWho the limit applies to: API key, user ID, IP, or a combination (e.g. user:42:password-reset).
Limit / windowHow many requests per period (100 per minute).
BurstRequests arriving faster than the average rate for a short time. Some algorithms allow it on purpose.
QuotaA longer-term allowance (per day / per month), usually tied to a pricing tier.

Related but distinct terms

  • Throttling — often used interchangeably with rate limiting, but sometimes specifically means slowing a client down (delaying responses) rather than rejecting requests outright.
  • Backpressure — a downstream component that's falling behind signals upstream to slow down (or upstream detects a growing queue and self-limits), as opposed to a rate limiter which enforces a policy regardless of actual downstream health.
  • Circuit breaking — stops calling a dependency at all once it's clearly failing, rather than limiting the rate of calls to a healthy-but-finite one. A different tool for a different failure mode (dependency down vs. dependency at capacity). See Microservice Resilience Patterns.

Where to Enforce It

flowchart LR C["Client
(self-throttle: UX only)"] --> G["API gateway / edge
coarse per-key / per-IP limits"] G --> S1["Service instance 1"] G --> S2["Service instance 2"] S1 --> R[("Redis
shared counters")] S2 --> R G --> R S1 -->|"leaky-bucket outbound"| P["Third-party API"]

Coarse limits at the edge, operation-specific limits in the service, one shared counter store so every instance sees the same count.

  • Client-side — polite, but not a security boundary; a client can always skip its own throttle. Useful for UX (disable a submit button) not protection.
  • Edge / API gateway — the common place for coarse, per-API-key or per-IP limits, before the request even reaches application servers; cheapest place to reject abusive traffic.
  • Per-service — finer-grained limits close to an expensive specific operation (e.g. "3 password-reset emails per hour," distinct from the general API limit).
  • Distributed rate limiting — once there's more than one instance enforcing the limit, they need a shared counter. The standard approach is Redis: an atomic INCR + EXPIRE (or a single Lua script so the check-and-increment is atomic and race-free) keyed by user:<id>:<window> — see Caching & CDN Fundamentals for why Redis specifically (atomic ops, TTLs built in).

Algorithms

AlgorithmHow it worksAllows bursts?Memory / accuracy
Fixed window counterCount requests in the current clock window (e.g. per-minute); reset the counter when the window rolls overYes — a burst right at the boundary of two windows can let through nearly 2× the limit (all at the end of one window, all at the start of the next)Cheapest — one counter per key
Sliding window logStore the timestamp of every request in the last window; count how many fall inside a rolling window ending "now"No — exact, no boundary problemMost accurate, but memory grows with request volume (one entry per request)
Sliding window counterApproximates the log by weighting the previous fixed window's count by how much of it still overlaps the current rolling windowMostly no — close approximation of the log, without storing every timestampOne or two counters per key — the practical default
Token bucketA bucket holds up to N tokens, refilling at a fixed rate; every request consumes one token, and requests are rejected once the bucket is emptyYes, intentionally — a client that's been idle can burst up to the bucket size, then is limited to the refill rateOne counter + one timestamp per key — cheap, and the standard choice (AWS, Stripe, and most API gateways use it)
Leaky bucketRequests queue into a bucket and are processed ("leak out") at a fixed rate; the bucket overflowing rejects new requestsNo — smooths bursts into a constant output rate rather than allowing them throughSimilar cost to token bucket; used when the goal is a steady outbound rate (e.g. calls to a downstream API), not just gatekeeping inbound
Token bucket vs. leaky bucket, in one line

Token bucket controls how much traffic you let in and is happy to allow bursts; leaky bucket controls how much traffic you send out and actively smooths bursts away. Rate-limiting an API's inbound requests → token bucket. Throttling your own outbound calls to a fragile downstream → leaky bucket.

Token bucket, step by step

  1. State per key: tokens and last_refill timestamp. Capacity 10, refill 1 token/second.
  2. Request arrives: compute elapsed time since last_refill, add elapsed × rate tokens, cap at capacity, set last_refill = now.
  3. Decide: if tokens ≥ 1, subtract one and allow; otherwise reject with 429 and Retry-After ≈ (1 − tokens) / rate.
  4. Effect: an idle client can send 10 requests instantly (burst), then exactly 1 per second (average rate).

🧠 Think about it

Limit 100/minute, fixed window. A client sends 100 requests at 12:00:59 and 100 more at 12:01:00. How many got through in two seconds? (All 200 — the counter reset in between. That's the 2× boundary burst the sliding window removes.)

Implementation

Fixed window in Redis (atomic)

-- KEYS[1] = "rl:user:42:" .. current_minute ; ARGV[1] = limit ; ARGV[2] = window seconds
local n = redis.call("INCR", KEYS[1])
if n == 1 then redis.call("EXPIRE", KEYS[1], ARGV[2]) end
if n > tonumber(ARGV[1]) then return 0 end
return 1
  • INCR — increments and returns the new value in one atomic step, so two instances can never both read "99" and both pass.
  • EXPIRE on the first hit — the key deletes itself when the window ends; no cleanup job.
  • Running it as a Lua script (EVAL) makes increment + expire + compare one atomic unit; doing them as separate client calls reintroduces the race and can leave a key with no TTL if the client dies between calls.
Two instances checking-then-incrementing separately is a race

If "read the counter" and "increment the counter" are two separate calls, two concurrent requests on two different app instances can both read the count just under the limit, both pass, and both increment — quietly letting one extra request through the limit. Use a single atomic operation (Redis INCR, or a Lua script for token-bucket logic) instead of read-then-write.

At the edge: Nginx limit_req

limit_req_zone $binary_remote_addr zone=api:10m rate=10r/s;

location /api/ {
    limit_req zone=api burst=20 nodelay;
    limit_req_status 429;
    proxy_pass http://app;
}
  • limit_req_zone … rate=10r/s — a shared-memory zone keyed by client IP, allowing 10 requests/second (a leaky-bucket implementation).
  • burst=20 nodelay — up to 20 extra requests are accepted immediately instead of queued; beyond that, rejected.
  • limit_req_status 429 — Nginx's default rejection status is 503; set 429 so clients know it's a limit, not an outage.
  • The zone is per Nginx instance — several Nginx nodes each enforce their own copy, so the effective limit is multiplied by the node count.

Talking to the client about it

  • 429 Too Many Requests — the correct HTTP status for a rejected request, distinct from a 4xx client error like malformed input.
  • Retry-After header — tells the client how many seconds (or a date) to wait before retrying, instead of making it guess.
  • X-RateLimit-Limit / -Remaining / -Reset — conventional (non-standard but widely adopted) headers so well-behaved clients can self-throttle before they ever hit 429.
  • A client should back off with jitter on retry, not retry immediately — otherwise every rejected client retries at the same instant, recreating a self-inflicted thundering herd.

Production Usage

Low scaleHigh scale
WhereOne Nginx limit_req or framework middleware.Gateway limits per key/tier + service-level limits on expensive operations + outbound limits to vendors.

Signals to watch

  • 429 rate, per key and overall — a jump for one key is an abusive or buggy client; a jump for everyone means limits are too tight or traffic genuinely grew.
  • Top keys by request volume — who is close to their limit.
  • Limiter latency and Redis errors — the limiter is now on every request's path.
  • Backend latency/error rate after a limit change — confirms the limit is actually protecting capacity.

🔥 Production insight

Decide up front what happens when Redis is unreachable. Fail open (allow everything) keeps the API up but removes protection; fail closed (reject everything) turns a cache outage into a full outage. Most public APIs fail open with a local fallback limit.

Security

  • Login, password reset, OTP and signup endpoints need their own tight limits keyed by account and by IP — the general API limit is far too loose to stop credential stuffing.
  • Key on something the attacker can't rotate cheaply. IP limits are bypassed with botnets/proxies; per-account and per-API-key limits are harder to dodge.
  • Trust the client IP only from your proxy — if the limiter reads a spoofable X-Forwarded-For, every request can claim a new IP (see Web Servers → Security).
  • Client-side throttling is not a control — enforce on the server.
  • Rate limiting reduces volumetric abuse but isn't DDoS protection on its own; large floods must be absorbed upstream (CDN/WAF/provider).

Performance & Scalability

  • Cost per check: one Redis round trip (~sub-millisecond in-region). Reject at the edge so rejected requests cost almost nothing.
  • Hot keys: one very busy API key hammers a single Redis key/shard; shard counters or use local pre-aggregation.
  • Memory: sliding window log grows with traffic; counters and token buckets are O(1) per key.
  • Accuracy vs. cost: exact global limits need a shared store on every request; approximate limits (local counters + periodic sync) scale further.

Debugging workflow

  1. Reproduce: curl -i the endpoint and read the X-RateLimit-* and Retry-After headers.
  2. Inspect the counter: redis-cli GET rl:user:42:<window> and redis-cli TTL rl:user:42:<window>.
  3. Find which layer rejected: gateway logs vs. service logs vs. Nginx (limiting requests in the error log).
  4. Check the key: is the limiter keyed on the real client (user/key) or on a proxy IP?

Best Practices

Do

  • Default to token bucket for inbound APIs — it tolerates normal bursty clients while enforcing an average.
  • Layer limits — coarse at the edge, tight on expensive or sensitive operations.
  • Make every check atomic — one Redis command or one Lua script.
  • Return 429 + Retry-After + remaining-quota headers — so good clients self-throttle.
  • Decide fail-open vs. fail-closed explicitly — per endpoint.

Avoid

  • Per-instance counters for a global limit.
  • Returning 503 or 400 for limits — clients can't tell a limit from an outage or a bug.
  • IP-only limits for authenticated APIs — punishes shared networks, misses rotating attackers.
  • Immediate retries on 429.

Interview Answer — What Is Rate Limiting?

Rate limiting is a control that caps how many requests a single client — identified by an API key, user ID, or IP address — may make to a service in a given period of time, and rejects (or delays) the requests over that limit. A rejected request gets an HTTP 429 Too Many Requests response, ideally with a Retry-After header.

It exists because a shared service has finite capacity. Without a limit, one noisy caller — a buggy retry loop, a scraper, a credential-stuffing attack — can consume that capacity and degrade the service for every other client, or run up the cost of a paid downstream API. With a limit, the cause → effect chain is: a client exceeds its quota → the limiter rejects its extra requests cheaply at the edge → the backend keeps serving everyone else at normal latency.

A rate limiter is defined by its algorithm — token bucket (allows short bursts up to the bucket size), leaky bucket (smooths traffic to a constant rate), or fixed / sliding window counters — and by where it is enforced: coarse limits at the API gateway, operation-specific limits (for example "3 password-reset emails per hour") inside the service. When several instances enforce the same limit, they must share one counter, typically in Redis, updated atomically.

Simple interview version

"Rate limiting caps how many requests a client can make in a time window, so one caller can't overload a shared service or run up costs. I'd usually use a token bucket, which allows short bursts but enforces an average rate, enforced at the API gateway per API key, with Redis holding the counter so every instance sees the same count. Rejected requests get a 429 with a Retry-After header, and clients retry with jittered backoff."

One important interview follow-up

Q: With 10 app servers, can each server just keep its own in-memory counter?

A: No — not if the limit is meant to be global. With 10 independent counters, a client whose requests are spread across all servers gets up to 10× the intended limit, and the effective limit changes every time you scale. The instances need a shared counter, usually in Redis, and the check and the increment must be one atomic operation (a single INCR with expiry, or a Lua script). If "read the count" and "increment the count" are two separate calls, two concurrent requests on different instances can both read a value just under the limit and both pass.

Interview checklist

  • Name the algorithm and justify it: token bucket if bursts should be allowed, sliding window counter if precision at the window boundary matters more than a little memory.
  • Say where it's enforced (edge/gateway vs. per-service) and why — coarse abuse protection belongs at the edge, business-rule-specific limits belong near the operation they protect.
  • If there's more than one instance, say explicitly how the counter is shared and kept atomic (Redis + a single atomic op) — this is the detail that separates a real answer from a hand-wave.
  • Mention the client contract: 429 + Retry-After, and clients retrying with jittered backoff, not immediate retry.

Practice questions

Why does a shared service need rate limiting if it already autoscales?

Autoscaling lags and costs money, and shared dependencies (database, third-party APIs) don't scale with it. A limit stops one client from consuming capacity — or budget — meant for everyone.

What status code and headers should a rejected request get?

429 Too Many Requests with Retry-After, plus X-RateLimit-Limit/Remaining/Reset so clients can self-throttle.

What's the boundary problem with a fixed window?

A client can send the full limit at the end of one window and again at the start of the next, getting nearly 2× the limit in a short span. Sliding windows fix it.

Token bucket vs. leaky bucket — when do you use each?

Token bucket for inbound API limits: allows bursts up to capacity, enforces an average. Leaky bucket for outbound calls to a fragile downstream: smooths bursts into a constant rate.

Where would you enforce a "3 password-reset emails per hour" rule, and why not at the gateway?

In the service that sends the email, keyed by account: it's a business rule tied to one operation and needs the account identity, while the gateway handles coarse per-key/IP limits.

How is rate limiting different from backpressure and circuit breaking?

Rate limiting enforces a policy regardless of downstream health; backpressure reacts to a downstream falling behind; a circuit breaker stops calling a dependency that is failing.

How do you make a distributed limiter race-free?

Shared counter in Redis, with check-and-increment as one atomic operation — INCR + TTL in a Lua script, or a Lua token bucket. Separate read and write calls let concurrent requests on different instances both pass.

Redis is down. Should the limiter fail open or closed?

It depends on what the limit protects. Fail open keeps the API available but unprotected (common for general API limits, ideally with a local fallback limit); fail closed suits security-critical limits like login attempts.

At millions of requests per second, a Redis call per request is too expensive. What then?

Approximate: each instance counts locally and syncs to the shared store periodically, or gets a slice of the global quota. You trade exactness for no per-request network hop.

A customer says they are limited to 100/min but are actually getting ~400/min through. What's wrong?

Probably four instances (or four Nginx nodes) each enforcing 100/min with local counters. Move to a shared atomic counter.

After a short outage, your API is hit by a wave of traffic that trips every limit, then another wave. Why?

Clients retry immediately and in sync (thundering herd), aligned to the same Retry-After. Clients need jittered exponential backoff; server-side, consider spreading Retry-After values.

A whole university complains they get 429s while barely using the API. Why?

The limit is keyed by IP and thousands of users share one NAT address. Key on user or API key; keep IP limits only as a loose outer layer.

What Should I Remember?

  1. Rate limiting decides whether a request is allowed; load balancing decides where it goes.
  2. Fixed window is cheap but lets ~2× through at the boundary; sliding window counter is the practical precise option.
  3. Token bucket (bursts OK) for inbound; leaky bucket (smooth) for outbound.
  4. More than one instance → shared counter in Redis, updated atomically.
  5. Coarse limits at the edge, operation-specific limits in the service.
  6. Contract: 429 + Retry-After; clients back off with jitter.
  7. Choose fail-open vs. fail-closed per endpoint.

Quick commands

  • redis-cli TTL rl:user:42:<window> — seconds until reset (-1 = no TTL bug)
