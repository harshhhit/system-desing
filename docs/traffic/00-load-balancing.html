Load Balancing

L4 vs L7, algorithms (round robin, least connections, consistent hashing), health checks, sticky sessions, and global vs local load balancing.

What you'll learn

By the end of this page you will be able to:

  • Explain why a single server needs a load balancer in front of it
  • Choose between an L4 and an L7 load balancer
  • Pick a balancing algorithm that fits the workload
  • Tune health checks without causing flapping or outages
  • Explain why sticky sessions are a trade-off, not a free feature
  • Separate "which region" (GSLB) from "which instance" (local LB)

Why Load Balancing Exists

A single server has a ceiling — on connections, CPU, memory — and a single point of failure. A load balancer sits in front of a pool of backend instances, spreads incoming traffic across them, and stops sending traffic to any instance that stops responding. That gets you two things at once: horizontal scalability (add more instances, handle more traffic) and availability (one instance dying doesn't take the service down). Almost everything else in this note is either "how do you pick which instance gets this request" or "how do you know an instance is actually healthy."

When you need it: as soon as a service runs on more than one instance — for capacity, for zero-downtime deploys, or simply so one crashed instance isn't an outage.

💡 Important

A load balancer only provides availability if it knows which backends are healthy. Without health checks, a dead backend keeps receiving its share of requests and the balancer simply spreads the outage.

How to Study This Section

Traffic Management answers two questions in order: how do we spread requests across many servers, and how do we stop too many requests from overwhelming them anyway?

  1. Why load balancing exists — one server has a capacity ceiling and is a single point of failure. This unlocks horizontal scaling: add instances behind one address.
  2. L4 vs. L7 — what the balancer can see decides what it can route on. Watch for: L4 vs. L7 — the difference is that an L4 balancer forwards whole connections using only IP and port, while an L7 balancer reads each HTTP request and can route by path, header, or cookie. An L4 balancer therefore cannot send /api and /static to different pools.
  3. Algorithms and health checks — once traffic reaches the balancer, it must pick a backend and must know which backends are healthy. This unlocks real availability: without health checks, a dead backend keeps receiving its share of requests.
  4. Session affinity and global vs. local load balancing — free backend choice depends on stateless backends; if state lives in one server's memory, the balancer loses that freedom. Then the same idea repeats one level up: pick a region first, then an instance.
  5. Rate Limiting & Throttling — adding servers raises capacity but never makes it unlimited. This step unlocks protecting that capacity per client. Watch for: load balancing vs. rate limiting — the difference is that a load balancer decides where a request goes, while a rate limiter decides whether it is allowed at all. A load balancer alone does not stop one abusive client from overloading every backend.

Most real stacks use both, layered: an L4 balancer (or the cloud provider's edge network) absorbs the raw connection volume and hands off to an L7 tier that does the smart, per-request routing.

⚠️ Common mistake

Assuming an L4 balancer spreads requests. It spreads connections. With HTTP/2 or gRPC, one client keeps one long-lived connection and sends every request over it — so an L4 balancer pins all of that client's traffic to one backend. Balancing gRPC evenly needs an L7 (request-aware) balancer or client-side balancing.

"Which region" is decided first (global), then "which instance" (local); health checks keep each pool's membership honest.

Global vs. local load balancing

  • Local (server-side) LB — the classic case above: a dedicated tier/appliance in front of one datacenter's backend pool.
  • Global server load balancing (GSLB) — routes users to an entire region/datacenter, typically via DNS (return the IP of the nearest or healthiest region) or anycast (the same IP is announced from multiple locations; routers deliver the packet to the nearest one) — the same mechanism a CDN uses to route to the nearest PoP (see Caching & CDN Fundamentals).
  • Client-side LB — the client (or a sidecar proxy next to it, as in a service mesh) holds the list of healthy backends itself and picks one directly, skipping a centralized LB hop entirely. Common inside a microservice fleet where the "client" is another internal service, not an end user.

🧠 Think about it

DNS-based GSLB relies on clients re-resolving the name. What happens when a region fails but clients cached the old IP for the full TTL? (They keep hitting the dead region until the TTL expires — which is why GSLB records use short TTLs, and why anycast fails over faster.)

How a Request Is Balanced

  1. Accept. The client connects to the balancer's listener. An L4 balancer forwards the connection as-is; an L7 balancer completes the TCP and TLS handshake itself.
  2. Inspect (L7 only). It parses the request and matches routing rules — host, path, header — to choose a backend pool.
  3. Filter. Only backends currently marked healthy in that pool are candidates.
  4. Pick. The algorithm chooses one candidate (or affinity overrides it with the client's pinned backend).
  5. Forward. The request goes to the backend — over a new or pooled connection for L7, as the same connection for L4.
  6. Observe. Response status and latency feed passive health checking; repeated failures pull the backend out.

How consistent hashing keeps most keys in place when a backend is added or removed is explained in Consistent Hashing.

Health checks

  • Active checks — the load balancer itself polls each backend on an interval (a TCP connect, an HTTP GET /healthz, or a custom check) and pulls it out of rotation on repeated failure.
  • Passive checks — the load balancer watches real traffic; if a backend starts erroring or timing out on actual requests, it's marked unhealthy without a separate probe.
  • Tuning that matters in an interview: check interval (how often), timeout (how long to wait for a response), and threshold (how many consecutive failures/successes before flipping state) — too aggressive and one blip pulls a healthy backend out; too lax and a dead backend keeps eating requests.
  • A deep health check (e.g. "can this instance reach the database") catches more real failures than a shallow one ("process is running"), but couples the LB's routing decision to a dependency's health — a DB blip can then pull every backend out of rotation at once.

Detection time, cause → effect: with a 10 s interval and an unhealthy threshold of 3, a backend that dies is still sent traffic for up to ~30 s before it is removed. Passive checks shorten that window because real requests fail immediately.

Session affinity ("sticky sessions")

If a backend keeps per-user state in local memory (an in-process cache, a WebSocket connection, an uploaded-file-in-progress), every request from that user has to land on the same backend — that's session affinity, usually implemented as a cookie the LB sets on first response, or via IP hash above.

The better fix is usually statelessness

Sticky sessions work, but they reintroduce the single-point-of-failure problem one layer down (that user's traffic all depends on one instance) and complicate scaling down. The alternative — keep backends stateless and put session state in a shared store (JWT in the client, or a session id backed by Redis) — is why Cookies, Sessions & JWT matters for load-balanced systems specifically, not just for auth.

Implementation: An L7 Pool in Nginx

upstream api {
    least_conn;
    server 10.0.1.10:8000 max_fails=3 fail_timeout=30s;
    server 10.0.1.11:8000 max_fails=3 fail_timeout=30s;
    server 10.0.1.12:8000 weight=2;
}

server {
    listen 443 ssl;
    location /api/ {
        proxy_pass http://api;
        proxy_next_upstream error timeout http_502 http_503;
    }
    location /static/ {
        root /srv/www;
    }
}
  • least_conn — least-connections algorithm; without it, Nginx defaults to weighted round robin.
  • max_fails=3 fail_timeout=30s — passive health checking: 3 failed attempts within 30 s mark the server unavailable for 30 s. (Open-source Nginx has no active probes; NGINX Plus, HAProxy, Envoy and cloud LBs do.)
  • weight=2 — this instance gets twice the share (weighted balancing for a bigger box).
  • proxy_next_upstream — retry the request on another backend after a connection error, timeout, 502 or 503. Safe for idempotent requests; for POSTs a retry can duplicate the action.
  • Two location blocks — path-based routing, which only an L7 balancer can do.

On AWS the same shape is an ALB with a listener rule per path, each forwarding to a target group whose health check is configured on the group (path, interval, timeout, healthy/unhealthy thresholds) and whose deregistration delay gives connection draining. Reverse-proxy basics (headers, timeouts) are in Web Servers → Implementation.

Trade-offs

  • Reliability: removes single-instance failure, but the LB tier and its health-check config become critical infrastructure.
  • Performance: L4 adds almost nothing; L7 adds TLS termination and parsing per request but enables connection reuse and smarter routing.
  • Operational complexity: health-check tuning, draining and affinity all interact with deploys.
  • Cost: managed LBs bill per hour plus per traffic/connection unit; client-side LB avoids the hop but moves logic into every client.

🔥 Production insight

Alert on "healthy hosts < N" per pool, not only on error rate. Health-check failures usually start before user-visible errors, and a pool quietly running on one of four hosts is one failure away from an outage.

Security

  • TLS termination at the L7 balancer keeps certificates in one place; re-encrypt to backends if the internal network isn't trusted.
  • Backends accept traffic only from the LB — e.g. a security group that allows the app port only from the LB's security group — so nobody bypasses routing, TLS and WAF rules.
  • Client IP is in a header now (X-Forwarded-For) for L7, or preserved/proxy-protocol for L4; backends must trust it only from the LB (details in Web Servers → Security).
  • A balancer is not DDoS or abuse protection by itself — it spreads load but doesn't cap it; pair it with a WAF and rate limiting.
  • Health endpoints should not leak internals (versions, dependency details) if they're reachable from outside.

Performance & Scalability

  • Horizontal scaling is the point: capacity ≈ instances × per-instance capacity, as long as backends are stateless and the shared dependencies (database, cache) keep up.
  • Connection reuse: L7 balancers keep pooled keep-alive connections to backends, saving a TCP (and TLS) handshake per request.
  • Long-lived connections (WebSockets, HTTP/2, gRPC) make round robin uneven — a backend that got many long connections early stays loaded. Use least connections, and expect rebalancing to happen only as connections close.
  • Autoscaling lag: new instances take time to boot and pass health checks; scale on a leading signal (CPU, request rate) with headroom, not after latency is already bad.
  • Slow start: a freshly added instance with a cold cache can be overwhelmed by least-connections (it has zero connections); some LBs ramp new targets up gradually.

Debugging workflow

  1. Who returned the error? LB-generated vs. backend-generated 5xx (LB access logs record both statuses).
  2. Pool health: how many targets are healthy, and the health-check failure reason.
  3. Hit a backend directly: curl -v http://10.0.1.10:8000/healthz from inside the network — healthy here but not in the LB means the check config or network path is wrong.
  4. Distribution: compare request and connection counts per backend.
  5. Correlate: deploys, autoscaling events, dependency incidents.

Best Practices

Do

  • Keep backends stateless — so the balancer can choose freely and any instance can die.
  • Make health checks cheap and specific to the instance — they should fail when this instance is broken, not when a shared dependency blips.
  • Enable connection draining — so deploys and scale-in don't cut in-flight requests.
  • Spread instances across availability zones — the balancer can only route around failures it has alternatives for.
  • Choose the algorithm from the workload shape — uniform short requests vs. long-lived vs. latency-sensitive.

Avoid

  • Sticky sessions by default — they bring back per-instance failure and uneven load.
  • Retrying non-idempotent requests on another backend — it can execute them twice.
  • A single self-managed LB box — it becomes the single point of failure you were removing.
  • Long DNS TTLs on GSLB records — failover waits for caches to expire.

Interview Answer — What Is a Load Balancer?

A load balancer is a component that sits in front of a pool of backend instances, receives every incoming request or connection, and forwards each one to a healthy backend chosen by an algorithm such as round robin or least connections. To the client, the whole pool looks like one address.

It exists because a single server has a hard ceiling on connections, CPU, and memory, and is a single point of failure. With a load balancer in front, you scale by adding instances behind the same address (horizontal scaling), and you survive instance failures because health checks take a failing instance out of rotation. The cause → effect chain is: an instance stops answering its health check → after the failure threshold the load balancer marks it unhealthy → new requests go only to the remaining instances → clients see no outage, only slightly more load per instance.

Load balancers differ by the layer they work at. A Layer 4 load balancer (for example AWS NLB) sees only IP addresses and ports and forwards connections; a Layer 7 load balancer (for example AWS ALB, Nginx, Envoy) parses the HTTP request and can route by path, header, or cookie and terminate TLS. At global scale, a separate tier — DNS-based or anycast global server load balancing — first picks the region, then a local load balancer picks the instance.

Simple interview version

"A load balancer sits in front of a pool of servers and spreads incoming traffic across them, so I can scale horizontally and survive instance failures. It uses an algorithm like round robin or least connections to pick a backend, and health checks to stop sending traffic to instances that fail. An L4 balancer forwards connections by IP and port; an L7 balancer understands HTTP and can route by path or header and terminate TLS. For multiple regions, DNS or anycast picks the region first, and a local load balancer picks the instance."

One important interview follow-up

Q: Should I just turn on sticky sessions so each user always hits the same server?

A: Only if you must. Sticky sessions make a user's requests depend on one specific instance, so that instance becomes a single point of failure for those users — if it dies, their in-memory session is lost — and it makes load uneven and scale-in harder, because you cannot remove an instance without breaking its users' sessions. The usual better design is to keep backends stateless and move session state to a shared store such as Redis or a signed token, so any instance can serve any request and the load balancer can pick freely.

Interview checklist

  • Say which layer (L4 vs L7) and why — "I need path-based routing" or "this isn't HTTP" both justify the choice.
  • Name an algorithm and justify it against the workload's shape (uniform vs. long-lived vs. latency-sensitive requests), not just "round robin" by default.
  • Mention health checks explicitly — an LB that never removes dead backends isn't actually providing availability.
  • If the design needs sticky sessions, say so and note the trade-off against statelessness — interviewers listen for whether you know that's a trade-off, not a free feature.
  • At global scale, separate "which instance" (local LB, algorithms above) from "which region" (GSLB/DNS/anycast) — they're different problems solved at different layers.

Practice questions

Why does a load balancer improve availability, not just capacity?

Because health checks remove failing instances from rotation: an instance dies → it fails its checks → after the threshold it's marked unhealthy → traffic goes only to the rest. Without health checks it only adds capacity.

When would you choose L4 over L7?

When the traffic isn't HTTP, or raw throughput/latency matters more than content-aware routing. Choose L7 when you need path/host/header routing, TLS termination, cookie affinity or per-request retries.

What's the difference between load balancing and rate limiting?

A load balancer decides where a request goes; a rate limiter decides whether it's allowed. A balancer alone won't stop one abusive client from overloading every backend.

Why is round robin a poor choice for long-lived or uneven requests, and what would you use?

Round robin ignores current load, so a backend still busy with slow requests keeps getting new ones. Least connections (or power-of-two-choices at large scale) sends work to the least-busy backend.

How do health-check interval, timeout and threshold interact?

Detection time ≈ interval × unhealthy threshold. Too aggressive: one blip removes healthy hosts (flapping). Too lax: dead hosts get traffic for a long time. Passive checks on real traffic shorten detection.

What do sticky sessions cost you?

The pinned instance is a single point of failure for its users, load becomes uneven, and scale-in breaks sessions. Prefer stateless backends with session state in Redis or a signed token.

Your gRPC service sits behind an L4 load balancer and one backend is overloaded. Why?

gRPC multiplexes many requests over one long-lived HTTP/2 connection; an L4 balancer balances connections, so each client's whole stream lands on one backend. Use an L7 (HTTP/2-aware) balancer, client-side balancing, or periodic connection recycling.

Why can a "deep" health check cause a total outage?

If every instance's check includes "can I reach the database", a database blip fails all checks at once, the balancer marks every backend unhealthy and returns 503 for everything — even requests that didn't need the database. Keep LB checks instance-local; surface dependency health elsewhere.

How do GSLB and local load balancing divide the work?

GSLB (DNS or anycast) picks the region or datacenter; the local LB picks the instance within it. Different problems at different layers — DNS failover is bounded by TTLs, anycast by routing convergence.

Every deploy causes a burst of 502s. What do you check?

Whether instances are deregistered with connection draining before shutdown, whether new instances receive traffic only after passing readiness/health checks, and the deploy batch size vs. remaining capacity. Fix with draining + health-gated rolling deploys.

Users report being logged out at random after you scaled from 1 to 3 instances. Why?

Sessions live in instance memory; requests now land on instances that don't hold the session. Short-term: sticky sessions. Proper fix: shared session store or stateless tokens.

After adding a new instance, it immediately shows high latency and errors. Why?

Least-connections sends a flood to the empty newcomer while its caches/JIT are cold, or it was added before it was ready. Use readiness checks and slow-start (gradual ramp-up) for new targets.

What Should I Remember?

  1. A load balancer gives horizontal scale and availability — the availability part comes from health checks.
  2. L4 forwards connections by IP/port; L7 reads each HTTP request and routes by path/header/cookie.
  3. Pick the algorithm from the workload: round robin for uniform, least connections for uneven/long-lived, hashing for locality.
  4. Health-check interval × threshold = detection time; deep checks can take down every backend at once.
  5. Sticky sessions are a trade-off; stateless backends + shared session store is the default.
  6. Region choice (GSLB/DNS/anycast) and instance choice (local LB) are separate layers.
  7. Load balancing decides where; rate limiting decides whether.
