Interview Answer — What Is the Browser JavaScript Sandbox?

The browser JavaScript sandbox is the set of restrictions a web browser places on any script that arrives with a web page. JavaScript itself is only a language; what a script can actually do — touch files, open network connections, read other pages — is decided by the host environment that runs it. In a browser, that host deliberately gives the script a small, safe set of APIs: it can change the page, react to the user, talk to servers, and store a little data, but it cannot reach the operating system, the disk, or other sites' data.

The sandbox exists because a browser runs code from strangers. Every time you open a link, you execute a program written by whoever owns that site, without installing it or reviewing it. Without the sandbox, any page could read your files, turn on your camera, or open your bank in a hidden tab and read your balance. The browser's answer is layered: no OS access at all, files and devices only after an explicit user action or permission prompt, and the Same Origin Policy keeping each site's data isolated from every other site's scripts — with CORS as the opt-in way for a server to relax that for specific callers.

The same language runs in other hosts with very different rules. Node.js, Deno and Bun run JavaScript on a server or laptop with full (Node, Bun) or permission-gated (Deno) access to files and the network. Web Workers, Service Workers, extension content scripts and WebAssembly each sit inside the browser with their own, slightly different box. See Other scripts and runtimes that work like this below for the full comparison.

Simple interview version

"JavaScript's power depends on where it runs. In the browser it's sandboxed: it can manipulate the DOM, handle user events, make network requests, set cookies and use localStorage — but it can't read arbitrary files, run programs, or access the OS, and devices like the camera need the user's permission. The Same Origin Policy stops a script from one site reading another site's pages or responses, and CORS headers are how a server explicitly allows cross-origin reads. The same language in Node.js has no sandbox and can read files and open sockets freely."

One important interview follow-up

Q: Does the Same Origin Policy stop my page from sending a request to another domain?

A: No — and this is the most common misconception. The Same Origin Policy mainly restricts reading cross-origin data, not sending requests. A page on http://anysite.com can submit a form or fire a simple fetch (GET/POST with basic content types) to http://gmail.com; the browser sends it, cookies may even be attached, and the server processes it. What the browser blocks is the script reading the response unless the server replies with a matching Access-Control-Allow-Origin header. For "non-simple" requests (e.g. PUT, DELETE, a JSON Content-Type, custom headers) the browser first sends an OPTIONS preflight and only sends the real request if the server approves. This is exactly why CSRF attacks are possible despite the Same Origin Policy, and why servers still need CSRF tokens or SameSite cookies. Also: CORS protects the user in the browser, not the server — curl or a backend service ignores CORS entirely. See Same Origin Policy and CORS below.

What can in-browser JavaScript do?

Modern JavaScript is a “safe” programming language. It does not provide low-level access to memory or the CPU, because it was initially created for browsers which do not require it.

JavaScript’s capabilities greatly depend on the environment it’s running in. For instance, Node.js supports functions that allow JavaScript to read/write arbitrary files, perform network requests, etc.

In-browser JavaScript can do everything related to webpage manipulation, interaction with the user, and the webserver.

For instance, in-browser JavaScript is able to:

  • Add new HTML to the page, change the existing content, modify styles.
  • React to user actions, run on mouse clicks, pointer movements, key presses.
  • Send requests over the network to remote servers, download and upload files (so-called AJAX and COMET technologies).
  • Get and set cookies, ask questions to the visitor, show messages.
  • Remember the data on the client-side (“local storage”).

What CAN’T in-browser JavaScript do?

JavaScript’s abilities in the browser are limited to protect the user’s safety. The aim is to prevent an evil webpage from accessing private information or harming the user’s data.

Examples of such restrictions include:

No arbitrary file or OS access

JavaScript on a webpage may not read/write arbitrary files on the hard disk, copy them or execute programs. It has no direct access to OS functions.

Modern browsers allow it to work with files, but the access is limited and only provided if the user does certain actions, like “dropping” a file into a browser window or selecting it via an <input> tag.

Concretely: <input type="file"> and drag-and-drop give the script a File object for only the file the user picked, never its full path or neighbouring files. The newer File System Access API (showOpenFilePicker(), Chromium-based browsers) can write back to a chosen file or folder, but still only after the user picks it in a native dialog.

Devices need explicit permission

There are ways to interact with the camera/microphone and other devices, but they require a user’s explicit permission. So a JavaScript-enabled page may not sneakily enable a web-camera, observe the surroundings and send the information to the NSA.

The same permission model covers geolocation, notifications, clipboard reading, USB / Bluetooth / Serial (WebUSB, Web Bluetooth, Web Serial) and screen capture. Most of these APIs are also only available on secure (HTTPS) origins, and several require a recent user gesture such as a click.

Tabs and windows are isolated — the Same Origin Policy

Different tabs/windows generally do not know about each other. Sometimes they do, for example when one window uses JavaScript to open the other one. But even in this case, JavaScript from one page may not access the other page if they come from different sites (from a different domain, protocol or port).

This is called the “Same Origin Policy”. To work around that, both pages must agree for data exchange and must contain special JavaScript code that handles it. We’ll cover that in the tutorial.

This limitation is, again, for the user’s safety. A page from http://anysite.com which a user has opened must not be able to access another browser tab with the URL http://gmail.com, for example, and steal information from there.

What an "origin" is: the triple scheme + host + port. All three must match exactly.

The "special JavaScript code" both pages use to agree is usually window.postMessage(): the sender posts a message to the other window, and the receiver listens for message events and must check event.origin before trusting the data. Same-origin tabs can also talk via BroadcastChannel or storage events.

Cross-site network reads need the server's agreement — CORS

JavaScript can easily communicate over the net to the server where the current page came from. But its ability to receive data from other sites/domains is severely limited. Though possible, it requires explicit agreement (expressed in HTTP headers) from the remote side. Once again, that’s a safety limitation.

That agreement mechanism is CORS (Cross-Origin Resource Sharing). Step by step, for a page on https://app.example.com calling https://api.other.com:

  1. The browser adds an Origin: https://app.example.com header to the request.
  2. If the request is "non-simple" (a method other than GET/HEAD/POST, a JSON Content-Type, or custom headers like Authorization), the browser first sends an OPTIONS preflight asking permission.
  3. The server answers with headers such as Access-Control-Allow-Origin: https://app.example.com (and, for preflights, Access-Control-Allow-Methods / Access-Control-Allow-Headers).
  4. If the headers match, the browser hands the response to the script. If not, the script gets a network error — even though the server may already have processed the request.
HTTP/1.1 200 OK
Access-Control-Allow-Origin: https://app.example.com
Access-Control-Allow-Credentials: true
Vary: Origin

CORS vs. security on the server — the difference is who is protected. CORS is enforced by the browser to protect the user's data from other sites; it is not an access control for your API. Any non-browser client (curl, Postman, another backend) ignores it, so the API still needs its own authentication and authorization.

Deep dive: every CORS header, credentials, server configuration and common errors are covered on the dedicated CORS (Cross-Origin Resource Sharing) page.

Other scripts and runtimes that work like this

The key idea from above — the environment, not the language, decides what a script can do — applies to every runtime below. Each one is either another box inside the browser, or JavaScript (or something that compiles to it) running outside the browser with a different set of permissions.

Inside the browser

Web Workers

What: a background thread running a separate script (new Worker("worker.js")). Why: heavy computation on the main thread freezes the page, because the main thread also handles rendering and input. Can: fetch, WebSockets, IndexedDB, timers, postMessage with the page. Can't: touch the DOM, window, or localStorage. Same Origin Policy and CORS still apply — a worker has exactly the page's network rights, not more.

Service Workers

What: a special worker that sits between the page and the network as a programmable proxy. Why: offline support, caching strategies, background sync and push notifications (the basis of PWAs). Can: intercept every fetch from pages in its scope and answer from the Cache API. Can't: access the DOM; it runs only on HTTPS (or localhost), only for its own origin and scope, and the browser kills it when idle. Because it can rewrite responses, it's powerful enough that the HTTPS requirement is non-negotiable.

Worklets (Audio / Paint)

Tiny, even more restricted scripts that hook into the rendering or audio pipeline (e.g. AudioWorklet for real-time audio processing). They get almost no APIs beyond the one pipeline they plug into.

iframes and the sandbox attribute

An <iframe> from another origin is isolated from the parent by the Same Origin Policy; the two talk only via postMessage. The sandbox attribute restricts it further (no scripts, no forms, no top-level navigation) unless you re-enable items like allow-scripts. This is how sites safely embed ads, widgets, and user-generated HTML.

Browser extensions (content scripts vs. background scripts)

What: JavaScript the user installs, which the browser grants more power than a page — but only the permissions declared in its manifest.json and approved at install time.

  • Content scripts are injected into web pages. They can read and change that page's DOM, but run in an "isolated world": they don't share JavaScript variables with the page's own scripts.
  • Background scripts / service workers run with the extension's own origin (chrome-extension://…). With the right host permissions they can make cross-origin requests without CORS and use APIs like chrome.tabs, chrome.storage and chrome.cookies.

Gotcha: an extension with "read and change all your data on all websites" permission effectively bypasses the Same Origin Policy for you — which is why malicious extensions are a real threat.

WebAssembly (Wasm)

What: a compact binary format that C, C++, Rust, Go and others compile to, running at near-native speed in the browser. Why: CPU-heavy work (video editing, games, image processing, databases like SQLite in the browser) that plain JavaScript runs too slowly. This does NOT mean Wasm gets "low-level" access to your machine: it runs inside the same sandbox as JavaScript, sees only its own linear memory block, and can do nothing — no DOM, no network — except call the JavaScript functions the page explicitly imports into it.

TypeScript, JSX and other compile-to-JS languages

TypeScript, JSX (React), CoffeeScript, Elm, Dart (via dart2js) and similar are not separate runtimes in the browser. They are compiled/transpiled to plain JavaScript before the browser sees them, so they have exactly the same capabilities and restrictions as the JavaScript they become. TypeScript's types are erased at build time — they add no runtime security.

Bookmarklets and DevTools console

A bookmarklet (javascript:… URL saved as a bookmark) and code typed into the DevTools console both run as the current page — with that page's origin, cookies (except HttpOnly) and storage. That's why "paste this into your console" is a classic social-engineering attack (self-XSS).

Outside the browser

Node.js

What: JavaScript on the V8 engine, outside a browser, for servers, CLIs and build tools (this site's own scripts/regen-sidebars.js is a Node script). Can: everything the OS user running it can — read/write any file (fs), open raw TCP/UDP sockets (net, dgram), spawn programs (child_process), read environment variables. No DOM, window, or Same Origin Policy, and no CORS on outgoing requests. Newer Node versions add an opt-in permission model (--permission), but it's off by default.

node scripts/regen-sidebars.js --check

Deno

What: a JavaScript/TypeScript runtime by Node's original author, built around a browser-like security model. Why: Node trusts every script and dependency fully; Deno denies everything by default. A script gets file, network, or env access only when granted with flags such as --allow-read, --allow-net=api.example.com or --allow-env. It also ships browser-standard APIs (fetch, Web Workers).

deno run --allow-net=api.example.com main.ts

Bun

A fast Node-compatible runtime (JavaScriptCore engine) with a built-in bundler, test runner and package manager. Security-wise it behaves like Node: full OS access, no sandbox.

Edge / serverless JavaScript (Cloudflare Workers, Vercel Edge, Lambda@Edge)

JavaScript running on CDN edge servers in V8 isolates — the same isolation mechanism browsers use between tabs. They expose browser-style APIs (fetch, Request/Response, Web Crypto) but no file system, strict CPU-time and memory limits, and no persistent in-memory state between requests. A middle ground between the browser sandbox and Node.

Electron and Tauri (desktop apps)

Desktop apps built with web tech (VS Code, Slack, Discord). Electron bundles Chromium + Node: the main process has full Node/OS power, while each window's renderer is a web page that — with the recommended contextIsolation and nodeIntegration: false settings — is sandboxed like a normal browser and reaches OS features only through a narrow preload bridge. Tauri takes the same approach with a Rust backend and an explicit allow-list of commands.

React Native

JavaScript driving native mobile UI (not a web page). It runs in the Hermes engine inside the app, so it has whatever permissions the app has been granted by iOS/Android (camera, files in the app's container) — but no DOM and no Same Origin Policy.

Google Apps Script, userscripts, and other hosted JavaScript

Google Apps Script runs JavaScript on Google's servers with access to Sheets/Docs/Gmail via OAuth scopes you approve. Userscript managers (Tampermonkey, Greasemonkey) are extensions that run your scripts on matching pages, with extra GM_* APIs such as cross-origin GM_xmlhttpRequest if you grant them.

Not JavaScript, but historically "scripts in the page"

Before today's model, browsers ran other in-page languages: VBScript (Internet Explorer only), Java applets, Flash / ActionScript, and Silverlight. Plugins like these ran outside the browser's own sandbox and were a major source of security holes, which is a key reason they were all removed. Today JavaScript (plus WebAssembly) is the only code a browser runs natively.
