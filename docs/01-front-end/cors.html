Interview Answer — What Is CORS?

CORS (Cross-Origin Resource Sharing) is a browser mechanism that lets a server say, through HTTP response headers, which other origins are allowed to read its responses from JavaScript. By default, the browser's Same Origin Policy blocks a script on one origin (for example https://app.example.com) from reading responses from a different origin (for example https://api.example.com). CORS is the controlled exception to that rule.

CORS exists because the Same Origin Policy on its own is too strict for modern apps. A single-page app on one domain routinely calls an API on another subdomain, a third-party payment service, or a CDN-hosted font. Without CORS, every one of those calls would need a same-origin proxy. Without the Same Origin Policy at all, any website you visit could call your bank's API with your cookies and read the result. CORS keeps the safe default (deny) and lets the server that owns the data opt specific origins in.

It works in two modes. For simple requests the browser sends the request with an Origin header and then checks the response's Access-Control-Allow-Origin header before handing the body to the script. For non-simple requests (for example PUT/DELETE, Content-Type: application/json, or an Authorization header) the browser first sends an OPTIONS preflight request and only sends the real request if the server approves. CORS is enforced entirely by the browser, so it protects users in the browser. It is not an authentication or authorization layer for your API. For the wider browser sandbox this fits into, see What In-Browser JavaScript Can & Can't Do.

Simple interview version

"CORS is how a server relaxes the browser's Same Origin Policy. When a page calls an API on a different origin, the browser sends an Origin header, and the server replies with Access-Control-Allow-Origin saying which origins may read the response. For non-simple requests, such as JSON bodies, PUT or DELETE, or custom headers, the browser first sends an OPTIONS preflight to ask permission. It's enforced by the browser, not the server, so it protects users from malicious sites. It doesn't secure your API against curl or other servers."

One important interview follow-up

Q: If I get a CORS error, did the request reach the server?

A: Often yes. For a simple request (for example a POST with Content-Type: application/x-www-form-urlencoded), the browser sends the request, the server runs it (it can write to the database, send an email, and so on) and returns a response. Only then does the browser see there's no matching Access-Control-Allow-Origin and hide the response from your script. So a CORS error does not mean "nothing happened on the server", and CORS does not protect against CSRF. For a preflighted request, a failed preflight means the real request is never sent. The fix for a CORS error is always on the server (or a proxy in front of it). Adding headers to the request in the browser never fixes it. See Simple vs. preflighted requests and Common misconceptions below.

First: what is an origin?

An origin is the combination of scheme + host + port. Two URLs are same-origin only if all three match exactly. The path, query string and fragment are ignored.

Page at https://app.example.com calling…Same origin?Needs CORS?
https://app.example.com/api/notesYesNo
https://api.example.com/notesNo — different host (subdomains count)Yes
http://app.example.com/apiNo — different schemeYes
https://app.example.com:8443/apiNo — different portYes
http://localhost:5173 → http://localhost:3000No — different portYes (the classic dev-setup CORS error)

Origin vs. site — the difference is the subdomain. app.example.com and api.example.com are different origins but the same site (same registrable domain). CORS works on origins. Cookie SameSite rules work on sites. That's why a request can be same-site for cookies but still cross-origin for CORS.

Why CORS exists — what breaks without it

Walk through the attack the Same Origin Policy prevents, step by step:

  1. You're logged in to https://bank.com. Your browser holds its session cookie.
  2. You open https://evil.com in another tab.
  3. evil.com's script runs fetch("https://bank.com/api/balance", { credentials: "include" }).
  4. The browser attaches your bank cookie. The bank sees a valid session and returns your balance.
  5. Without the Same Origin Policy, evil.com's script could read that response and send it to its own server.
  6. With the Same Origin Policy, the browser checks whether bank.com allowed https://evil.com. It didn't, so the script gets an error and never sees the data.

But the same rule also blocks legitimate calls, such as your own front end at app.example.com calling your own API at api.example.com. CORS lets api.example.com say "I trust app.example.com" without opening the door to evil.com.

Simple vs. preflighted requests

The browser decides which flow to use from the request itself. The difference is whether the request could already have been sent by a plain HTML form before CORS existed. If it could, servers were already exposed to it, so the browser just sends it. If it couldn't, the browser asks first.

Simple request

A request is simple only if all of these are true:

  • Method is GET, HEAD or POST.
  • Only "safe-listed" headers are set by the script (Accept, Accept-Language, Content-Language, Content-Type, Range).
  • Content-Type, if set, is application/x-www-form-urlencoded, multipart/form-data or text/plain.
GET /notes HTTP/1.1
Host: api.example.com
Origin: https://app.example.com

HTTP/1.1 200 OK
Access-Control-Allow-Origin: https://app.example.com
Content-Type: application/json

Preflighted request

Anything else, such as PUT, DELETE, PATCH, Content-Type: application/json, or an Authorization / X-Request-Id header, triggers a preflight: an automatic OPTIONS request the browser sends before the real one.

OPTIONS /notes/42 HTTP/1.1
Host: api.example.com
Origin: https://app.example.com
Access-Control-Request-Method: PUT
Access-Control-Request-Headers: content-type, authorization

HTTP/1.1 204 No Content
Access-Control-Allow-Origin: https://app.example.com
Access-Control-Allow-Methods: GET, POST, PUT, DELETE
Access-Control-Allow-Headers: Content-Type, Authorization
Access-Control-Max-Age: 600

Only if that answer matches does the browser send the real PUT, and the real response must also carry Access-Control-Allow-Origin.

Gotcha: sending JSON is the most common reason a request becomes preflighted. It also costs an extra round trip on every call unless the server sets Access-Control-Max-Age so the browser caches the approval. Browsers cap this cache (Chromium at 2 hours).

The full flow

Browser (app.example.com)                     Server (api.example.com)
        |                                                |
        |-- is it a simple request? --no--> OPTIONS ---->|  preflight
        |<------------- 204 + Allow-Origin/Methods/Headers|
        |   approved? no  -> CORS error, real request     |
        |                    is NEVER sent                |
        |   approved? yes                                 |

        |<------------------ response + Allow-Origin -----|

        |                         no  -> CORS error, but  |
        |                         the server already ran  |

The CORS headers

Request headers (set by the browser, never by your code)

HeaderMeaning
OriginThe origin of the page making the request. Sent on cross-origin requests and on non-GET same-origin ones.
Access-Control-Request-MethodPreflight only: the method the real request will use.
Access-Control-Request-HeadersPreflight only: the non-safe-listed headers the real request will send.

Response headers (set by the server)

HeaderMeaningGotcha
Access-Control-Allow-OriginThe one origin allowed to read the response, or * for any.Only a single origin or *. A comma-separated list is invalid. To allow several, check Origin against an allow-list and echo the match back.
Access-Control-Allow-MethodsMethods allowed for the real request (preflight response).Only checked on preflight.
Access-Control-Allow-HeadersRequest headers allowed (preflight response).Authorization must be listed explicitly. * doesn't cover it.
Access-Control-Allow-Credentialstrue lets the browser send cookies/auth and expose the response.Can't be combined with Allow-Origin: *. Must name the exact origin.
Access-Control-Expose-HeadersExtra response headers the script may read (for example X-Total-Count, ETag).Without it, JS can read only a few basic response headers.
Access-Control-Max-AgeSeconds the browser may cache the preflight result.Browsers cap it, so a very large value doesn't help.
Vary: OriginTells caches/CDNs the response differs per Origin.Forget it and a CDN may serve origin A's allowed response to origin B.

Credentials: cookies and CORS

By default, a cross-origin fetch does not send cookies. To send them, both sides must opt in:

  1. The client sets credentials: "include" (or xhr.withCredentials = true).
  2. The server returns Access-Control-Allow-Credentials: true and an explicit Access-Control-Allow-Origin (not *).
  3. The cookie itself must be allowed cross-site: SameSite=None; Secure, and the browser must not be blocking third-party cookies.
fetch("https://api.example.com/me", { credentials: "include" });
Access-Control-Allow-Origin: https://app.example.com
Access-Control-Allow-Credentials: true
Vary: Origin

For how the session cookie itself works, see Cookies, Sessions & JWT.

Configuring CORS on the server

The fix for a CORS error always lives on the server that owns the resource, or on a reverse proxy/API gateway in front of it. The pattern is the same everywhere: check the incoming Origin against an allow-list, echo it back if it matches, and answer OPTIONS preflights.

Node.js / Express

const cors = require("cors");
app.use(cors({
  origin: ["https://app.example.com", "http://localhost:5173"],
  credentials: true,
  methods: ["GET", "POST", "PUT", "DELETE"],
  allowedHeaders: ["Content-Type", "Authorization"],
  maxAge: 600
}));

Nginx

map $http_origin $cors_origin {
    default "";
    "https://app.example.com" $http_origin;
}

location /api/ {
    add_header Access-Control-Allow-Origin $cors_origin always;
    add_header Access-Control-Allow-Credentials true always;
    add_header Vary Origin always;
    if ($request_method = OPTIONS) {
        add_header Access-Control-Allow-Origin $cors_origin;
        add_header Access-Control-Allow-Methods "GET, POST, PUT, DELETE";
        add_header Access-Control-Allow-Headers "Content-Type, Authorization";
        add_header Access-Control-Max-Age 600;
        return 204;
    }
    proxy_pass http://backend;
}

AWS S3 bucket (for example fonts or uploads loaded from another domain)

[
  {
    "AllowedOrigins": ["https://app.example.com"],
    "AllowedMethods": ["GET", "PUT"],
    "AllowedHeaders": ["*"],
    "MaxAgeSeconds": 3000
  }
]

Alternative: avoid CORS entirely. Serve the front end and the API from the same origin (for example app.example.com and app.example.com/api behind one reverse proxy or CDN), or use the dev server's proxy (Vite's server.proxy) locally. With no cross-origin request, there's no CORS and no preflight latency.

Common misconceptions

  • "CORS protects my API." It doesn't. It's enforced by browsers only. curl, Postman, mobile apps and other servers ignore it. Your API still needs authentication, authorization and rate limiting.
  • "CORS stops CSRF." It doesn't. Simple cross-origin requests (form posts) are still sent with cookies; only the response is hidden. Use CSRF tokens and SameSite cookies.
  • "I can fix it in the front end." You can't. Adding Access-Control-Allow-Origin to your request does nothing. mode: "no-cors" doesn't bypass anything either: it gives you an opaque response whose body and status your script can't read.
  • "Reflecting any Origin is a convenient default." Echoing back whatever Origin arrives, together with Allow-Credentials: true, is effectively "every site may read my users' data". Always check against an allow-list. Also never allow the null origin, which sandboxed iframes and file:// pages send.
  • "<img>, <script> and <link> need CORS." Not to load. Cross-origin embedding has always been allowed. CORS matters when a script wants to read the resource: canvas pixel data (crossorigin attribute on <img>), web fonts, ES modules (<script type="module">), and detailed error info from scripts.
