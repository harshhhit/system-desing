Interactive Request Flow

Every method from the Client-Server Model page, walked through as one guided, 13-step request: DNS → TCP/TLS → CDN → load balancer → security gate → API gateway → auth → cache/DB → queue → response → render.

This walks through one real page load end to end, step by step, using the same methods and terms taught on Client-Server Model, End to End. Every stage below maps back to a specific part of that page. Use Next / Previous, click a numbered dot, or just scroll — every step is real content on the page, not hidden behind the interaction.

Step 1 / 13

1DNS Resolution

Network setup

The browser doesn't understand example.com; it needs an IP address. It asks a DNS server "where is example.com?" and gets back something like 192.168.1.1. Nothing else can happen until this resolves.

  • Part 2: The Mechanical Layer

2TCP 3-Way Handshake

Network setup

Browser and server open a reliable connection before any data moves: SYN ("Can we talk?") → SYN-ACK ("Yes, can you hear me?") → ACK ("Yes, let's talk."). This guarantees the bytes that follow arrive intact and in order.

  • Part 2: The Mechanical Layer

3TLS/SSL Handshake

Network setup

If the URL is https://, client and server now negotiate encryption keys cryptographically. Everything sent afterward is ciphertext to anyone intercepting it on the wire.

  • Part 2: The Mechanical Layer

4Browser Sends the HTTP Request

Request

The client sends a request packet: a request line (GET /index.html HTTP/1.1), headers (User-Agent, Accept-Language, any cookie), and an optional body for a POST. Whether this rides over HTTP/1.1, HTTP/2 (multiplexed), or HTTP/3 (QUIC over UDP) changes the transport, not the shape of the message.

  • Part 2: The Mechanical Layer
  • Part 3: The Key Protocols

5Edge Cache / CDN Check

Delivery layer

Before the request reaches the origin server at all, it usually hits a CDN edge node geographically close to the client. If the asset (image, CSS, a cached page) is already there, it's served immediately and the journey ends here. Only a cache miss continues on.

  • Part 6.1: Caching

6Load Balancer (Reverse Proxy)

Delivery layer

On a cache miss, a Load Balancer picks which of many backend servers handles this request — round robin, or "sticky" to whichever server already holds this user's session — and skips any server that's failing its health check.

  • Part 6.2: Load Balancing

7Security Gate: Rate Limiting, WAF & CORS

Security

Before any application logic runs, the request is checked against abuse and origin rules: is this IP over its rate limit (429 if so)? Does a Web Application Firewall flag the payload? If it's a browser-side cross-origin call, does the server's CORS policy even allow this origin to ask?

  • Part 7: Security

8API Gateway Routes to a Microservice

Architecture

In a microservices setup, the request doesn't hit one big application — it hits an API Gateway that decides which small, independent service actually owns this piece of work (Auth-Server, Product-Server, Payment-Server, …) and forwards it there.

  • Part 5, Level 3: Microservices

9Auth Service Validates the Session or JWT

State & identity

The gateway asks "is this user logged in?" Two ways this gets answered: a session cookie triggers a database lookup by Session ID, or a JWT in the Authorization header gets its signature verified locally — no database hit needed, the server just trusts the signed payload.

  • Part 4: State Management
  • Cookies, Sessions & JWT (deep dive)

10Product Service Reads Redis, Then the DB Replica

Data layer

The service handling the actual data first checks an in-memory Redis cache — RAM instead of disk. On a cache miss, it reads from a replica database (writes go to a separate "primary" so reads never block them), possibly a specific shard if the dataset is split by key range.

  • Part 6.1: Caching
  • Part 6.4: Replication & Sharding

11Slow Work Gets Offloaded to a Queue

Data layer

If this request also triggers something slow — sending 10,000 emails, say — the server doesn't make the browser wait. It returns 202 Accepted, drops the job onto a queue (RabbitMQ, SQS), and a separate worker process picks it up later. The browser can poll for completion if it needs to know.

  • Part 6.3: Asynchronous Processing

12Server Assembles and Sends the HTTP Response

Response

Everything gathered from steps 8–11 gets packaged into one response: a status line (200 OK, 404, 500), headers (Content-Type, maybe a fresh Set-Cookie or a rotated refresh token), and the body — HTML or JSON.

  • Part 2: The Mechanical Layer

13Browser Renders the Response

Response

The browser parses the body and paints it. If the app needs live, ongoing updates after this — a chat message, a stock price, a notification — this is where it upgrades to a WebSocket (bidirectional) or opens a Server-Sent Events stream (server → client only) instead of polling with new requests.
