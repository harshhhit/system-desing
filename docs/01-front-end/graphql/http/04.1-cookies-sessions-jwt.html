Cookies, Sessions & JWT

State management deep dive: how cookies work, server-side sessions vs. stateless JWTs, the modern access/refresh hybrid, and the CSRF/XSS trade-offs behind each.

The Fundamental Problem: Why "Stateless" Is a Lie We Tell Ourselves

HTTP was designed in 1991 for academics to fetch static documents. The original spec said: "Each request is independent; the server forgets you immediately."

But modern web applications require:

  • Authentication: "I am John."
  • Continuity: "I have items in my cart."
  • Personalization: "Show me my dashboard."

We cannot change HTTP, so we build state management layers on top of it. There are exactly three strategies to do this. Each is a trade-off between server storage and cryptographic trust.

Strategy 1: Cookies (The Transport Mechanism)

Before we discuss Sessions vs. JWT, we must understand the cookie itself.

A cookie is literally just a key-value pair stored in the browser's memory or hard drive. The server instructs the browser to store it via the Set-Cookie response header:

HTTP/1.1 200 OK
Set-Cookie: cart=shoes; Max-Age=3600; Path=/; Domain=.myshop.com

The critical attributes (security)

AttributePurpose
HttpOnlyCrucial: JavaScript cannot read this cookie. Prevents XSS attacks from stealing it.
SecureThe browser will only send this cookie over HTTPS. Never over plain HTTP.
SameSitePrevents CSRF attacks. Strict means the cookie is only sent if the request originates from the same site.
Max-Age / ExpiresDetermines if it's a "Session Cookie" (deleted when the browser closes) or a "Persistent Cookie" (saved until expiry).

Why cookies over localStorage?

  • The browser automatically attaches cookies to every request to that domain.
  • You don't have to manually inject them into fetch() headers; the browser does it for you.
  • They support HttpOnly, which keeps secrets out of JavaScript's reach.

Strategy 2: Server-Side Sessions (The "Classic" Approach)

This is the traditional way. The server holds the truth. The client holds a "claim check."

How it works

  1. Login: Client sends username/password.
  2. Session creation: Server validates credentials. It generates a random, unguessable string (Session ID), e.g. s7f9g2h1j4k.
  3. Server storage: Server stores { sessionId: s7f9g2h1j4k, userId: 42, cart: ['shoes'], expiresAt: ... } in a database (or an in-memory cache like Redis).
  4. Cookie delivery: Server responds with Set-Cookie: sessionId=s7f9g2h1j4k; HttpOnly; Secure; SameSite=Strict.
  5. Subsequent requests: Browser sends the cookie back automatically. Server looks up sessionId in its storage, retrieves userId: 42, and fulfills the request.

Pros

  • Kill-switch: If a user logs out, the server simply deletes the session from its database. The cookie becomes invalid immediately.
  • Mutable data: You can change user data (e.g., update their email) during a session, and it reflects instantly because the server reads the latest data from the DB on every request.
  • Simpler for traditional MVC: Works beautifully with server-rendered pages (PHP, Ruby on Rails, Django).

Cons

  • Scalability nightmare: If you have 10,000 concurrent users, your session store needs to hold 10,000 entries. If you have 1 million, you need Redis clusters.
  • Sticky sessions: If you deploy 5 servers, you must ensure that User A always hits Server B (where their session is stored), or you must use a shared session store (like a central Redis) that all servers can access. This becomes a single point of failure.
  • Latency: Every request requires a database/cache lookup to fetch the session data.

Strategy 3: JWT (JSON Web Tokens) — The "Stateless" Lie

JWTs are the modern, "scalable" alternative. The server does not store the session. Instead, it gives the client a self-contained passport.

How it works

  1. Login: Client sends username/password.
  2. Token creation: Server validates credentials. It creates a JSON object: 
    {
  "sub": "42",        // User ID
  "name": "John Doe",
  "role": "admin",
  "iat": 1614556800,  // Issued at
  "exp": 1617168800   // Expires in 30 days
}
  3. Signing: The server takes this JSON, base64url-encodes it, and cryptographically signs it using a secret key (HMAC-SHA256) or a public/private key pair (RSA/ECDSA). The signature proves the token was issued by the server and hasn't been altered.
  4. Delivery: The server sends this signed token back — usually in the response body, or in a cookie.
  5. Subsequent requests: The client sends the JWT in the Authorization: Bearer <token> header (or automatically via cookie).
  6. Verification: The server receives the JWT. It recalculates the signature using its secret key. If the signatures match, the server trusts the data inside the JSON. It does not query a database; it just reads userId: 42 and trusts it.

Pros

  • Infinite scalability: No session storage needed. The server does not care which instance handles the request; they all share the same secret key.
  • No database lookup per request: Faster for read-heavy APIs.
  • Cross-domain/service: Great for microservices. Service A can verify the JWT, decode it, and know the user's role without asking Service B.

Cons (the kryptonite)

  1. No kill-switch: Once issued, a JWT is valid until it expires. If a user's account is compromised or they log out, you cannot "invalidate" the token without implementing a token blacklist (which requires... a server-side database, defeating the stateless purpose).
  2. Payload size: JWTs are significantly larger than a Session ID. If your cookie contains a 2KB JWT, and you make 50 API calls, that's 100KB of overhead just in headers.
  3. Refresh token hell: To fix the expiration issue, we issue a short-lived access token (15 minutes) and a long-lived refresh token. The client uses the refresh token to get new access tokens. Now you have two tokens to manage, and the refresh token must be stored securely on the server, often in a database.
  4. Secret rotation: If your private key is leaked, an attacker can issue valid tokens. Rotating keys requires invalidating all issued tokens, which forces all users to re-login.

The "Modern Hybrid" Strategy (The Industry Standard)

No one uses pure Sessions or pure JWTs in production anymore. We use a hybrid:

  • Access token (JWT): Short-lived (5–15 minutes). Stateless. Used for every API request. Stored in memory (not localStorage) to prevent XSS.
  • Refresh token (UUID): Long-lived (7–30 days). Stateful. Stored in an HttpOnly; Secure cookie and in a server-side database (Redis).

Server logic:

  1. Client sends JWT in the Authorization header.
  2. Server verifies the JWT signature. If valid, proceed.
  3. If the JWT is expired, server returns 401 Unauthorized.
  4. Client sends the refresh token (via cookie) to a /refresh endpoint.
  5. Server validates the refresh token against the database. If it exists and isn't revoked, server issues a new JWT and sends it back.
  6. When the user logs out, the server deletes the refresh token from the database.

Why this wins:

  • Performance: 95% of requests (with valid JWTs) are lightning-fast; no DB lookup.
  • Security: The refresh token is HttpOnly, so XSS can't steal it. The JWT is in memory, so CSRF can't steal it.
  • Kill-switch: If a user is compromised, you delete their refresh token from the DB. They can still use the JWT for a few more minutes, but after that, they cannot get a new one.

The Critical Security Debate: JWT vs. Session

Attack vectorServer-side sessionJWT (stateless)
CSRF (Cross-Site Request Forgery)Vulnerable if using cookies; mitigated by SameSite=Strict or CSRF tokens.Immune if using an Authorization: Bearer header (browsers don't auto-send headers). Vulnerable if stored in cookies without SameSite.
XSS (Cross-Site Scripting)Immune if the Session ID is in an HttpOnly cookie (JS can't read it).Vulnerable if stored in localStorage (JS can steal it). Immune if stored in an HttpOnly cookie.
Session hijackingHarder; attacker must steal the Session ID cookie.Harder; attacker must steal the JWT. But since JWTs last longer, the window of exposure is bigger.
Server overheadHigh (DB/Redis lookup per request).Low (CPU for signature verification).

The Developer's Checklist (Production Readiness)

If you are implementing this today:

  1. Never store a JWT in localStorage or sessionStorage (XSS risk).
  2. Never store a Session ID in a non-HttpOnly cookie.
  3. For SPAs (React/Vue), use an HttpOnly; Secure; SameSite=Strict cookie for both Session IDs and refresh tokens.
  4. Use short-lived JWTs (max 15 minutes). Use refresh tokens with a rotation strategy (issue a new refresh token every time it's used, invalidating the old one).
  5. Implement token versioning: store a token_version integer in your user's database row. When the user changes their password or logs out, increment this version. When validating a JWT, check if the version claim matches the DB version — if not, reject it.
  6. Use asymmetric signing (RS256) for JWTs in microservices. The issuer signs with a private key; all other services verify with a public key. No one but the issuer needs the private key.

The Philosophical Conclusion

  • Sessions say: "Trust me, I check the database for everything." (Secure, but expensive.)
  • JWTs say: "Trust me, I did the math." (Fast, but risky.)

There is no "better" one. There is only the right one for your architecture:

  • If you have one monolithic server and render HTML on the backend: use server-side sessions.
  • If you have microservices and an API gateway: use JWTs + refresh tokens in the hybrid model.
  • If you are building a public API for third-party developers: use JWTs (with expirations) because they are portable.

The "hack" isn't about tricking HTTP; it's about choosing where to store the burden of memory — either in your server's RAM or in cryptographic math. Both have a cost; you just choose which bill to pay.
