Web Servers

Which program owns the HTTP connection, which one runs your code, and how a request crosses the boundary between them — Nginx, app servers, and how the pair fails in production.

What you'll learn

By the end of this page you will be able to:

  • Tell a web server from an application server, and say which program does what
  • Explain why production puts a reverse proxy in front of the app
  • Follow one request from browser → Nginx → app server → database and back
  • Read and write a minimal Nginx reverse-proxy config
  • Diagnose 502, 504, 413 and redirect loops from logs and metrics
  • Answer the common web-server interview questions, including scenarios

What This Page Covers

Every web request is received by one program and answered by another. The web server (Nginx, Apache, Caddy) owns the HTTP connection; the application server (Gunicorn, Puma, PHP-FPM, or the runtime itself in Node.js and Go) runs your code. This page explains why the two roles are separated, how a request moves between them, how to configure the boundary, and how it breaks in production.

When you need this: any time you deploy a web application, read a deployment diagram, or debug a 502/504. The same split reappears in Kubernetes, where an Ingress controller or cloud load balancer plays the web-server role.

💡 Important

"Web server" and "application server" are roles, not products. Nginx is almost always the web server; a Go binary can be both at once. Ask "who owns the connection?" and "who runs the code?" — those two answers name the boxes.

How to Study This Section

This section answers one question — which program actually receives an HTTP request, and which one runs my code? Read it in this order:

  1. Web Servers (this page) — the two roles and which languages ship a production server. Unlocks: reading any deployment diagram and naming each box. Watch for: "built-in server" vs. "production-ready setup" — the difference is that a runtime being able to serve HTTP (Node, Go) does NOT mean it should face the internet alone; a reverse proxy usually still sits in front.
  2. Request flow, step by step (below) — one request through proxy, app server and database. Unlocks: knowing where TLS, static files, timeouts and load balancing belong.
  3. WSGI Explained — the contract that lets Nginx + Gunicorn run a Flask or Django app, and ASGI for async apps. Watch for: WSGI vs. ASGI — the difference is that WSGI is synchronous (each request holds a worker process or thread for its whole duration), while ASGI is asynchronous and also supports long-lived connections such as WebSockets.

Web Server vs. Application Server

A web server (HTTP server) is a program that accepts HTTP connections from clients, serves static files, terminates TLS, and forwards dynamic requests — examples are Nginx, Apache, and Caddy. An application server is the process that runs your application code and produces dynamic responses — for example Gunicorn running a Django app, PHP-FPM running a Laravel app, or Tomcat running a Java app.

Web server vs. application server — the difference is responsibility. The web server is good at connections: holding thousands of them open cheaply, speaking TLS, reading files from disk. The application server is good at computation: importing your framework, running business logic, talking to the database. Each is weak at the other's job, which is why production keeps them separate.

Reverse proxy vs. load balancer

Reverse proxy vs. load balancer — the difference is purpose: a reverse proxy sits in front of an application to terminate TLS, serve static files and forward requests; a load balancer spreads requests across several application instances. Nginx can do both, but a single reverse proxy in front of one app server is NOT load balancing — see Load Balancing.

⚠️ Common mistake

"Node/Go has a built-in server, so I don't need Nginx." The built-in server is production-capable, but it still has to handle TLS certificates, slow clients, static assets and multiple instances. Something usually does that job in front of it — Nginx, Caddy, a cloud load balancer or an Ingress controller.

🧠 Think about it

In Kubernetes there is usually no hand-written Nginx next to the app. Which component took over its job? (The Ingress controller — often Nginx itself — or a cloud load balancer, while Gunicorn/Node runs inside the Pod. The layering is unchanged; only who operates it moved.)

Request Flow, Step by Step: Browser → Web Server → App Server → Database

Production stacks put Nginx, Apache or Caddy in front of the application. This is what that looks like for a single request, with each step causing the next (Python example: Nginx + Gunicorn + Django):

sequenceDiagram participant B as Browser participant N as Nginx participant G as Gunicorn worker participant D as Django + DB B->>N: TCP + TLS handshake, GET /api/orders Note over N: static? → serve from disk and stop
dynamic → reverse proxy N->>G: HTTP over Unix socket
+ X-Forwarded-For / -Proto G->>D: WSGI call → view runs, queries DB D-->>G: status, headers, body G-->>N: HTTP response N-->>B: gzip, then send over TLS

One dynamic request. The numbered steps below walk the same path.

  1. Browser → web server. DNS resolves the domain to the server (or load balancer) IP, and the browser opens a TCP connection to port 443. Nginx performs the TLS handshake, so the certificate and private key live in Nginx, not in the application.
  2. Static or dynamic? Nginx checks the path. A request for /static/app.css is answered straight from disk (or a CDN) and never reaches Python. A request for /api/orders is dynamic, so Nginx forwards it — this is reverse proxying.
  3. Web server → app server. Nginx forwards the request over plain HTTP or a Unix socket to Gunicorn, adding headers such as X-Forwarded-For and X-Forwarded-Proto so the app still knows the real client IP and that the original request was HTTPS. Nginx also buffers a slow client's upload, so a Gunicorn worker is not held open waiting on a slow network.
  4. App server → application code. Gunicorn hands the request to one of its worker processes, which calls the Django application through the WSGI interface (see WSGI Explained).
  5. Application → database. The view runs business logic and queries the database, usually through a connection pool.
  6. Response back. The app returns a status, headers and body → Gunicorn sends them to Nginx → Nginx may compress the response and sends it back to the browser over the TLS connection.

How Nginx Handles a Connection

"Nginx handles the request" hides the part that explains most of its behaviour. Nginx runs one master process and a small number of worker processes:

  1. Master starts. It reads and validates the config, opens the listening sockets (:80, :443) and forks the workers — usually one per CPU core (worker_processes auto;). The master never handles traffic itself.
  2. Workers wait on an event loop. Each worker asks the kernel (epoll on Linux, kqueue on BSD/macOS) to notify it when any of its sockets is ready. All I/O is non-blocking, so a worker never sits idle waiting for one client.
  3. A connection becomes readable. The worker reads whatever bytes have arrived, advances that connection's state (TLS handshake → headers → body) and goes straight back to the loop. A slow client costs a little memory, not a blocked process.
  4. Request complete → route it. The worker matches the server block (by Host header) and the location block (by path). A static location reads the file (using sendfile where possible); a proxy_pass location opens or reuses a connection to the upstream.
  5. Upstream response → client. The worker reads the upstream's response into buffers as fast as the app produces it, freeing the app worker, then trickles it out to the client at whatever speed the client can take.

Each worker can hold up to worker_connections connections at once (for example 1024), and a proxied request uses two — one to the client, one to the upstream. That is why one Nginx box can hold tens of thousands of mostly-idle keep-alive connections.

🎯 Interview tip

Nginx worker vs. Gunicorn sync worker — the difference is concurrency model. An Nginx worker multiplexes thousands of connections on one event loop. A Gunicorn sync worker handles exactly one request at a time, start to finish. That asymmetry is the whole reason Nginx sits in front: it absorbs slow, numerous connections and hands the app only complete requests.

What happens on nginx -s reload

The master re-reads and validates the new config → if it is invalid, it logs the error and keeps the old workers running → if it is valid, it starts new workers with the new config → it tells the old workers to stop accepting new connections and exit once their in-flight requests finish. Result: a config change with no dropped connections. This does NOT mean an app server restart is equally safe — that depends on the app server's own graceful-restart support.

Implementation: Nginx in Front of Gunicorn

The minimal production setup for a Django app: Gunicorn listens on a local Unix socket, Nginx owns ports 80/443. Start the app server:

gunicorn myproject.wsgi:application --workers 3 --bind unix:/run/gunicorn.sock --timeout 30
  • myproject.wsgi:application — the WSGI callable Gunicorn will call for every request.
  • --workers 3 — three sync worker processes, so at most three requests run at the same time. Sizing is covered in WSGI Explained.
  • --bind unix:/run/gunicorn.sock — a Unix socket instead of a TCP port, so the app is unreachable from the network; only Nginx on the same host can connect.
  • --timeout 30 — a worker silent for 30 s is killed and restarted. Remember this number: it interacts with Nginx's timeout (see Troubleshooting).

The Nginx side:

upstream app {
    server unix:/run/gunicorn.sock;
    keepalive 16;
}

server {
    listen 80;
    server_name example.com;
    return 301 https://$host$request_uri;
}

server {
    listen 443 ssl;
    server_name example.com;
    ssl_certificate     /etc/letsencrypt/live/example.com/fullchain.pem;
    ssl_certificate_key /etc/letsencrypt/live/example.com/privkey.pem;

    client_max_body_size 10m;
    server_tokens off;

    location /static/ {
        alias /srv/app/static/;
        expires 30d;
    }

    location / {
        proxy_pass http://app;
        proxy_http_version 1.1;
        proxy_set_header Connection "";
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
        proxy_connect_timeout 5s;
        proxy_read_timeout 60s;
    }
}
DirectiveWhat it doesWhat breaks without it
upstream app { … }Names the backend pool. Add more server lines and Nginx load-balances across them (round-robin by default).Nothing for one backend — but scaling out later means editing every proxy_pass.

The app must also be told to trust those headers. In Django: SECURE_PROXY_SSL_HEADER = ("HTTP_X_FORWARDED_PROTO", "https"); in Flask: Werkzeug's ProxyFix middleware. Response caching at the proxy (proxy_cache, micro-caching) is covered in Reverse Proxy & API Gateway Caching.

Production Usage

Production deployments almost always put a web server or reverse proxy in front, for either kind of application server. The cause → effect chain is: the browser connects to Nginx → Nginx terminates TLS, serves static assets directly, and applies limits and buffering → it forwards only dynamic requests to the application server → the application server runs the code and returns the response through Nginx. This keeps slow clients, TLS, and static files off the application processes and lets one proxy load-balance across several of them.

Low scale vs. high scale

🔥 Production insight

Alert on 502 and 504 separately. They have different causes and different first responders: a 502 spike after a deploy points at the app process, a 504 spike with healthy processes points at something slow behind the app — usually the database.

Security at the Web-Server Layer

  • Never expose the app server directly. Bind Gunicorn to a Unix socket or 127.0.0.1. If it listens on 0.0.0.0:8000, anyone who reaches the port bypasses TLS, limits and logging.
  • TLS termination keeps keys in one place. The private key lives on the proxy (or the managed load balancer), readable only by root/Nginx — not inside every app container.
  • Forwarded headers can be forged. A client can send its own X-Forwarded-For: 1.2.3.4; $proxy_add_x_forwarded_for appends the real address. The app must trust only the entries added by its own proxies (the right-most ones), never the left-most value blindly — otherwise per-IP rate limits and audit logs can be bypassed.
  • Limit request size and rate. client_max_body_size stops oversized uploads before they reach the app; limit_req gives basic per-IP rate limiting (see Rate Limiting & Throttling).
  • Reduce what you reveal. server_tokens off hides the Nginx version from error pages and the Server header.
  • Least privilege. Nginx workers run as an unprivileged user (only the master needs root to bind ports 80/443); the Gunicorn socket should be writable only by the Nginx user's group.

Application-level attacks (XSS, SQL injection, CSRF) are not stopped by the web server — see Application Security Fundamentals.

Bandwidth / staticNginxLarge responses dominate egress.gzip, long expires on hashed assets, a CDN (see CDN Caching).

Horizontal vs. vertical: app servers are stateless, so the normal move is horizontal — more instances behind the proxy or load balancer. A single Nginx scales vertically a long way because it is event-driven; when it doesn't, you add more proxies behind DNS or a cloud load balancer.

Buffering is a performance feature. With proxy_buffering on (the default) Nginx reads the whole upstream response quickly and frees the app worker, then feeds a slow mobile client at its own pace. Turning it off makes sense only for streaming responses (server-sent events, long polling), where you want bytes delivered as they're produced.

🧠 Think about it

With three sync Gunicorn workers and requests that take 200 ms, roughly how many requests per second can one instance serve? (About 3 ÷ 0.2 = 15. Doubling Nginx capacity changes nothing; adding workers or instances does.)

⚠️ Common mistake

Answering every 504 by raising proxy_read_timeout. It hides the slow request while each one still holds an app worker, so under load all workers fill up and the 504s return — now joined by 502s. Fix the slow path first.

Debugging workflow

  1. Confirm from outside. curl -I https://example.com/path — which status, and does the Server header show the request reached your Nginx (or a CDN/LB in front)?
  2. Check DNS and network. dig example.com resolves to the right address; the port answers.
  3. Check Nginx. nginx -t, systemctl status nginx, then tail -f /var/log/nginx/error.log while reproducing — the error line names the cause.
  4. Bypass Nginx. Call the app server directly (curl --unix-socket … or curl localhost:8000). Works → the problem is the proxy config. Fails → the problem is the app.
  5. Check the app server. journalctl -u gunicorn for crashes, WORKER TIMEOUT, OOM kills; worker count vs. traffic.
  6. Check dependencies. Database connections and slow queries, external APIs, DNS from inside the app host.
  7. Check metrics. 5xx rate split by code, $upstream_response_time p99, worker saturation, CPU/memory — did it start with a deploy or a traffic change?
  8. Confirm the fix. Re-run the request, watch the error rate return to baseline, and add the alert or check that would have caught it.

Best Practices

Do

  • Put a reverse proxy or load balancer in front of every app, even Node/Go — it is where TLS, limits, buffering and static files belong.
  • Bind the app server to a Unix socket or localhost — so the only way in is through the proxy's controls.
  • Always forward Host, X-Forwarded-For and X-Forwarded-Proto, and configure the app to trust them — otherwise URLs, redirects and client IPs are wrong.
  • Make timeouts shrink as you go inward (LB ≥ Nginx ≥ app ≥ DB query) — so the layer that knows why it's slow is the one that gives up and logs it.
  • Run nginx -t before every reload — a typo should fail in your terminal, not in production.
  • Log upstream timings — without $upstream_response_time you can't tell a slow app from a slow client.

Avoid

  • Running a framework's dev server in production (manage.py runserver, flask run) — single-threaded or unhardened, and not designed to face the internet.
  • Exposing the app server port publicly — it bypasses TLS, limits and logging.
  • Serving static files through the app — each file occupies an expensive worker.
  • Trusting the left-most X-Forwarded-For value — the client controls it.
  • Raising timeouts as the first response to 504s — it hides the slow path and exhausts workers.
  • Disabling proxy_buffering globally — do it only on streaming locations.

Interview Answer — What Is a Web Server vs. an Application Server?

A web server (HTTP server) is a program that accepts HTTP connections from clients, serves static files, terminates TLS, and forwards dynamic requests — examples are Nginx, Apache, and Caddy. An application server is the process that runs your application code and produces dynamic responses — for example Gunicorn running a Django app, PHP-FPM running a Laravel app, or Tomcat running a Java app.

Web server vs. application server — the difference is responsibility. Some languages ship a production-ready HTTP server inside the runtime (Node.js's http module, Go's net/http, ASP.NET Core's Kestrel, Rust's async servers), so the application is its own server. Others do not: Python, Ruby, PHP, and Perl frameworks come with development servers only, and in production they run under a separate application server (Gunicorn/Uvicorn, Puma, PHP-FPM, PSGI) that speaks a language-specific interface such as WSGI or ASGI. See WSGI Explained for the Python case in detail.

Either way, production deployments almost always put a web server or reverse proxy in front — the full chain is walked in Request Flow and Production Usage.

Simple interview version

"A web server like Nginx handles HTTP itself — connections, TLS, static files, reverse proxying, and load balancing — while an application server runs the application code. Node, Go, .NET, and Rust include a production HTTP server in the runtime; Python, Ruby, and PHP need a separate app server like Gunicorn, Puma, or PHP-FPM. In production I put Nginx or a load balancer in front of either kind, so the app processes only handle dynamic requests."

One important interview follow-up

Q: Node.js and Go have built-in HTTP servers — so do they still need Nginx?

A: They do not strictly need it — a Go or Node process can serve HTTP directly — but most production setups still put a reverse proxy or load balancer in front. It terminates TLS and renews certificates, serves static files efficiently, buffers slow clients so they don't tie up application connections, enforces limits, and distributes traffic across multiple application instances. In cloud or Kubernetes deployments that role is often played by a managed load balancer or an Ingress controller instead of a hand-configured Nginx, but the layering is the same.

Practice questions

What problem does a reverse proxy solve that the application can't easily solve itself?

It takes the connection-heavy work off expensive app workers: TLS termination, static files, buffering slow clients, request-size and rate limits, and spreading traffic over several instances. App workers then only ever see complete, ready-to-run requests.

Why does a Django app need Gunicorn, while a Go app doesn't need an app server?

Go's standard library includes a production-grade HTTP server, so the binary is its own server. Django only ships a development server; in production a WSGI/ASGI server (Gunicorn, Uvicorn) owns the sockets and worker processes and calls Django through the WSGI/ASGI interface.

What's the difference between a 502 and a 504?

502 Bad Gateway: the proxy couldn't get a valid response — connection refused or reset, wrong address, crashed worker. 504 Gateway Timeout: the upstream accepted the request but didn't answer within proxy_read_timeout. 502 = broken or unreachable, 504 = too slow.

Is a reverse proxy the same thing as a load balancer?

No. A reverse proxy fronts an application (TLS, static files, forwarding). A load balancer spreads requests across several instances. Nginx can do both, but one proxy in front of one app server is not load balancing.

Why can one Nginx worker hold thousands of connections when a Gunicorn sync worker handles one request at a time?

Nginx workers use an event loop over non-blocking sockets (epoll/kqueue): they only touch a connection when it has data, so an idle or slow client costs memory, not a blocked process. A sync Gunicorn worker runs one request start to finish, including any waiting on the database.

Which headers must a reverse proxy set, and what breaks without each?
  • Host — otherwise the app sees the upstream name; host validation fails or URLs are wrong.
  • X-Forwarded-For / X-Real-IP — otherwise every client looks like 127.0.0.1.
  • X-Forwarded-Proto — otherwise the app thinks it's on HTTP: redirect loops and insecure links.
Why does Nginx buffer requests and responses by default?

So the app worker is held only for the time it takes to compute the response, not for as long as a slow client takes to upload or download. Nginx absorbs the slow network side. Disable response buffering only for streaming (SSE, long polling).

How does nginx -s reload apply a new config without dropping connections?

The master validates the new config, starts new workers with it, then tells the old workers to stop accepting connections and exit after finishing in-flight requests. An invalid config is rejected and the old workers keep running.

Requests that take about 40 seconds return 502, not 504. Why?

Gunicorn's worker --timeout (30 s by default) is shorter than Nginx's proxy_read_timeout (60 s). Gunicorn kills the silent worker first, the connection closes, and Nginx reports "upstream prematurely closed connection" → 502. Fix the slow request and make inner timeouts ≤ outer ones.

How can X-Forwarded-For be spoofed, and how do you get the real client IP?

The client can send its own X-Forwarded-For; proxies append to it. Trust only the right-most entries added by proxies you control (configure the number of trusted hops, e.g. ProxyFix(x_for=1) or Nginx's real_ip module with set_real_ip_from), and never the left-most value.

Why enable upstream keepalive, and what does it require?

Without it, Nginx opens a new connection to the upstream for every request — extra latency and, over TCP, piles of TIME_WAIT sockets and ephemeral-port exhaustion at high rates. It needs keepalive N in the upstream block plus proxy_http_version 1.1 and proxy_set_header Connection "".

In Kubernetes, where does the web-server role go?

To the Ingress controller (often Nginx-based) or a cloud load balancer, which terminates TLS and routes by host/path to Services. The app server (Gunicorn, Node) runs inside the Pod. The layering is the same; the proxy is now shared cluster infrastructure configured through Ingress resources.

After every deploy, users see 502s for about 10 seconds. What's happening and how do you fix it?

The app server is restarting, and Nginx forwards requests to a socket nobody is listening on yet (connection refused → 502). Fix: graceful restarts (Gunicorn reloads workers on HUP), or run several instances and do a rolling deploy behind health checks so traffic only reaches ready instances; proxy_next_upstream lets Nginx retry another upstream for idempotent requests.

Uploads larger than 1 MB fail, and the app logs show nothing. What do you check?

Nginx's client_max_body_size (1 MB default) — Nginx returns 413 before the request ever reaches the app, which is why the app logs are empty. Raise it for the upload location only.

You enabled "force HTTPS" in the app and now the site redirect-loops. Why?

TLS terminates at Nginx, so the app receives plain HTTP and keeps redirecting to HTTPS. Send X-Forwarded-Proto $scheme from Nginx and tell the app to trust it (SECURE_PROXY_SSL_HEADER in Django, ProxyFix in Flask).

p99 latency jumps during peak traffic, but app CPU is only 30%. What do you suspect and check?

Worker saturation: all sync workers are busy waiting on I/O (database, external APIs), so new requests queue. Compare $request_time with $upstream_response_time, check worker utilisation and DB pool waits, and look for slow downstream calls in traces. Fix with timeouts on outbound calls, more workers/instances, or async workers.

What Should I Remember?

  1. The web server owns the connection (TLS, static files, buffering, limits); the application server runs the code.
  2. Languages with built-in servers: Node.js, Go, ASP.NET Core, Rust, Elixir. Languages needing app servers: Python, Ruby, PHP, Perl, traditional Java.
  3. Production best practice: Even if a language has a built-in server, most real-world deployments put Nginx or Apache (or Caddy) in front for SSL, caching, and load balancing.
  4. Nginx is event-driven (master + per-core workers on epoll); sync app workers handle one request each — that asymmetry is why the proxy sits in front.
  5. Forward Host, X-Forwarded-For, X-Forwarded-Proto — and configure the app to trust them, only from your own proxy.
  6. 502 = upstream broken or unreachable; 504 = upstream too slow; the Nginx error log says which and why.
  7. Timeouts must shrink inward (LB ≥ Nginx ≥ app ≥ DB), or a slow request shows up as the wrong error.
  8. Reverse proxy ≠ load balancer: one forwards, the other spreads across instances.
