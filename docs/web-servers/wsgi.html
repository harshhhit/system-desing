WSGI Explained

What you'll learn

By the end of this page you will be able to:

  • Explain what WSGI is and why Python needs it
  • Follow a request from browser → Nginx → Gunicorn → Django and back
  • Compare WSGI and ASGI, and Gunicorn, uWSGI and Uvicorn
  • Write a minimal WSGI app and run it under Gunicorn
  • Size and tune Gunicorn workers
  • Debug worker timeouts and saturation

The Problem WSGI Solves

When you build a web app in Python (using Django, Flask, FastAPI, etc.), the app cannot directly talk to the internet. Browsers send HTTP requests, but your Python app only understands function calls and objects.

👉 This is where WSGI (Web Server Gateway Interface) and ASGI (Asynchronous Server Gateway Interface) come into play. They act as translators between your Python app and the outside world (browsers, clients, APIs, etc.).

This page zooms in on the Python step of the stack described in Web Servers: the contract between the application server (Gunicorn, Uvicorn) and your framework.

💡 Important

WSGI is a specification, not a program. Gunicorn implements the server side; Django and Flask implement the application side. Because both follow the same spec, any WSGI server can run any WSGI framework.

WSGI – Web Server Gateway Interface

  • Definition: A standard protocol that defines how a Python web app communicates with a web server.
  • Introduced: PEP 3333 (Python standard).
  • Nature: Synchronous (one request per worker at a time).

The whole contract is one callable: the server calls application(environ, start_response), where environ is a dictionary describing the request (method, path, headers, body stream) and start_response is a function the app calls with the status and headers; the app returns an iterable of body bytes.

ASGI – The Modern Successor

  • Definition: Asynchronous Server Gateway Interface.
  • Purpose: Designed for async frameworks (FastAPI, Django Channels).
  • Supports: WebSockets, HTTP/2, long-lived connections.

📌 Key Difference:

  • WSGI → Handles synchronous apps (blocking).
  • ASGI → Handles asynchronous + synchronous apps.

WSGI vs. ASGI — the difference is what a worker does while waiting. A WSGI worker is blocked for the whole request, including time spent waiting on the database. An ASGI app is an async callable (app(scope, receive, send)), so one event loop can interleave thousands of waiting requests and hold WebSocket connections open.

General-purpose HTTP servers

These are not Python-specific but widely used to serve static files and act as reverse proxies:

  • Apache HTTP Server (httpd): Oldest, feature-rich, but heavier.
  • Nginx: Lightweight, high-performance, handles load balancing & reverse proxy.
  • Caddy: Auto HTTPS, modern.
  • LiteSpeed: Optimized for hosting environments.

⚠️ Common mistake

Calling Gunicorn "the web server." It's an application server: it speaks enough HTTP to run Python workers, but it isn't built to face the internet, terminate TLS or serve static files efficiently. That's Nginx's job — see why use both.

The browser only ever talks to the HTTP server; the Python app only ever sees a function call from the app server.

HTTP Server – The Gateway to the Web

An HTTP Server is a program that:

  1. Listens for incoming HTTP requests (usually on port 80 or 443).
  2. Parses the request (method, path, headers, body).
  3. Processes it:
    • If the request is for static content (HTML, CSS, JS, images) → fetch from disk.
    • If it’s for dynamic content (Python app) → forward to a WSGI/ASGI app server.
  4. Builds a response and sends it back to the browser.

Example deployment stacks

For a Django application:

  • Nginx → Handles incoming HTTP/HTTPS requests, serves static files.
  • Gunicorn → Runs Django as a WSGI application.
  • Django → Your Python web framework.
  • PostgreSQL/MySQL → Database.

For a FastAPI application:

  • Nginx → Reverse proxy + SSL termination.
  • Uvicorn → Runs FastAPI as an ASGI app.

Workflow of WSGI

  1. Browser sends an HTTP request.
  2. Web server (like Nginx) forwards it to a WSGI server (like Gunicorn).
  3. WSGI server calls your Python app using a standard interface (application(environ, start_response)).
  4. Python app returns a response.
  5. WSGI server sends it back to the HTTP server → browser.

Inside Gunicorn: the pre-fork worker model

  1. Arbiter starts. The Gunicorn master ("arbiter") binds the socket and forks N worker processes. With --preload, the app is imported once in the master before forking, saving memory.
  2. A worker accepts a connection. Workers share the listening socket; whichever is free accepts the next connection.
  3. Translate. The worker parses the HTTP request into environ and calls the WSGI callable.
  4. Block. A sync worker is now busy until the app returns — including every millisecond spent waiting on the database or an external API.
  5. Supervise. The arbiter restarts any worker that crashes or stays silent longer than --timeout (default 30 s).

Cause → effect: concurrency equals the number of workers (× threads for gthread workers). Three sync workers = at most three requests in flight; the fourth waits in the socket backlog. Async worker classes (gevent, or uvicorn.workers.UvicornWorker for ASGI apps) let one worker interleave many waiting requests.

Why Use Both Nginx and Gunicorn?

👉 Many Django/Flask deployments use Nginx + Gunicorn together.

  • Gunicorn (WSGI Server): Runs the Python app.
  • Nginx (HTTP Server): Handles static files, SSL termination, reverse proxy.

Flow: Browser → Nginx → Gunicorn → Django App → Gunicorn → Nginx → Browser (the same path as the diagram above).

✅ Benefits of Nginx in front:

  • Serves static content efficiently.
  • Manages SSL certificates.
  • Provides load balancing.
  • Protects Gunicorn from direct internet exposure.

The deeper reason is the worker model above: a sync worker held open by a slow mobile client for 10 seconds serves nobody else for those 10 seconds. Nginx buffers the slow client and hands Gunicorn a complete request. How Nginx itself handles thousands of connections is explained in Web Servers → How Nginx Handles a Connection.

🧠 Think about it

A FastAPI app runs under Uvicorn, which is async. Does it still benefit from Nginx in front? (Yes for TLS, static files, request limits and load balancing across instances — but the slow-client argument is weaker, because an async server doesn't block a worker per connection.)

Implementation

A complete WSGI application

def application(environ, start_response):
    path = environ["PATH_INFO"]
    body = f"Hello from {path}".encode()
    start_response("200 OK", [("Content-Type", "text/plain"), ("Content-Length", str(len(body)))])
    return [body]
  • environ — request data as a dict: PATH_INFO, REQUEST_METHOD, QUERY_STRING, headers as HTTP_* keys, body as wsgi.input.
  • start_response(status, headers) — tells the server the status line and headers.
  • return [body] — an iterable of bytes; Django's and Flask's application objects are just more elaborate versions of this function.

Running it

gunicorn app:application --workers 3 --bind 127.0.0.1:8000
gunicorn myproject.wsgi:application --workers 5 --threads 2 --worker-class gthread --timeout 30 --max-requests 1000 --max-requests-jitter 100
uvicorn main:app --host 127.0.0.1 --port 8000 --workers 4
  • app:application — module app, callable application.
  • --workers — process count; a common starting point from Gunicorn's docs is (2 × CPU cores) + 1, then adjust by measuring.
  • --threads 2 --worker-class gthread — each process handles 2 requests concurrently (helps I/O-bound apps).
  • --timeout 30 — kill workers silent for 30 s; must be shorter than Nginx's proxy_read_timeout or slow requests show up as 502s (see Web Servers → Troubleshooting).
  • --max-requests 1000 --max-requests-jitter 100 — recycle each worker after ~1000 requests, containing slow memory leaks; jitter stops all workers restarting at once.
  • uvicorn main:app --workers 4 — the ASGI equivalent for FastAPI.

The Nginx side of this stack (proxy_pass, forwarded headers, static files) is shown in Web Servers → Implementation.

Production Usage

  • WSGI is still the standard for Django & Flask.
  • ASGI is the future for FastAPI, async Django apps.
  • Most production setups use Nginx + Gunicorn/Uvicorn.

Signals to watch

  • Busy vs. idle workers — all busy means requests are queuing; latency rises even with low CPU.
  • Worker restarts / WORKER TIMEOUT in Gunicorn logs — slow requests or hangs.
  • Memory per worker — growth over time means a leak (contained by --max-requests).
  • Upstream response time from Nginx's log vs. total request time.

🔥 Production insight

Each worker opens its own database connections. 4 instances × 9 workers × a pool of 5 = 180 connections — more than a default PostgreSQL max_connections of 100. Scaling the web tier can take the database down.

Security

  • Bind Gunicorn to localhost or a Unix socket so only the proxy can reach it.
  • Trust forwarded headers only from the proxy — Gunicorn's --forwarded-allow-ips, Django's SECURE_PROXY_SSL_HEADER, Flask's ProxyFix.
  • Never run DEBUG=True or the dev server (runserver, flask run) in production — they leak stack traces and settings.
  • Run workers as an unprivileged user.

Performance & Scalability

  • Throughput ≈ concurrent workers ÷ average request time. 9 sync workers at 100 ms ≈ 90 req/s per instance.
  • CPU-bound apps: more processes (up to cores × ~2); threads don't help because of the GIL.
  • I/O-bound apps: threads (gthread) or async (gevent / ASGI) raise concurrency cheaply.
  • Memory limits worker count: each process holds the whole framework; --preload shares the imported code pages via copy-on-write.
  • Horizontal scaling works because workers are stateless — keep sessions and caches in Redis, not process memory.

Debugging workflow

  1. Is the app server up? systemctl status gunicorn, ss -ltnp | grep 8000.
  2. Bypass Nginx: curl -i http://127.0.0.1:8000/health.
  3. Read the app server log: journalctl -u gunicorn -f for timeouts, tracebacks, worker boots.
  4. Check saturation: busy workers vs. configured; DB connection count.
  5. Profile the slow endpoint with traces before touching worker counts.

Best Practices

Do

  • Put Nginx (or an LB/Ingress) in front for TLS, static files and slow-client buffering.
  • Start with (2 × cores) + 1 workers and measure — the right number depends on CPU vs. I/O mix.
  • Use async (ASGI) when you need WebSockets or massive I/O concurrency.
  • Recycle workers with --max-requests + jitter.
  • Budget database connections across all workers and instances.

Avoid

  • Exposing Gunicorn directly to the internet.
  • Long blocking work in a request — use a task queue.
  • Raising --timeout to hide slow endpoints.
  • Calling blocking libraries inside async ASGI handlers — it stalls the whole event loop.

Interview Answer — What Is WSGI?

WSGI (Web Server Gateway Interface) is the Python standard, defined in PEP 3333, for how a web server passes an HTTP request to a Python web application and gets the response back. The application exposes a single callable — application(environ, start_response) — and any WSGI server (Gunicorn, uWSGI, Waitress) can run any WSGI framework (Django, Flask).

WSGI exists so that servers and frameworks can be mixed freely. Without a shared interface, every framework would need its own server integration and every server would need to support each framework separately. With it, the cause → effect chain for a request is: the browser sends an HTTP request → Nginx terminates TLS, serves static files itself, and forwards the dynamic request to Gunicorn → Gunicorn converts the request into the environ dictionary and calls the Django application → Django returns the status, headers, and body → Gunicorn sends them back through Nginx to the browser.

WSGI is synchronous: each worker handles one request at a time, so concurrency comes from running multiple worker processes or threads. ASGI (Asynchronous Server Gateway Interface) is its async successor, used by FastAPI and Django Channels with servers such as Uvicorn and Daphne; it supports long-lived connections such as WebSockets. See why use both Nginx and Gunicorn above.

Simple interview version

"WSGI is the Python standard interface between a web server and a Python web application. A WSGI server like Gunicorn receives the request, calls the app's application(environ, start_response) callable, and returns the response, so any WSGI server can run any WSGI framework such as Django or Flask. In production, Nginx sits in front for TLS, static files, and proxying. WSGI is synchronous, one request per worker at a time; ASGI is the async successor used by FastAPI and for WebSockets."

One important interview follow-up

Q: Is Gunicorn a web server that replaces Nginx?

A: No. Gunicorn is a WSGI application server: it understands HTTP well enough to run Python workers, but it is not designed to face the internet directly. Its synchronous workers are tied up for as long as a client takes to send a request or receive a response, so slow clients can exhaust them; it is also not built for serving static files efficiently or managing TLS certificates. Nginx in front buffers slow clients, terminates TLS, serves static files, and load-balances across Gunicorn workers or instances — the two do different jobs.

Practice questions

What is WSGI, and why do we need it?

A Python standard (PEP 3333) for how a server calls a web app: application(environ, start_response). It decouples servers from frameworks, so any WSGI server runs any WSGI framework.

How does an HTTP server differ from a WSGI server?

The HTTP server (Nginx) owns client connections, TLS and static files and forwards dynamic requests; the WSGI server (Gunicorn) manages Python worker processes and translates HTTP into WSGI calls.

Can Django run without WSGI?

Django needs some server interface: it ships both a WSGI entry point (wsgi.py) and, since Django 3.0, an ASGI one (asgi.py), so it can run under Uvicorn/Daphne instead. The runserver dev server is for development only.

Explain the request flow from a browser to a Django app.

Browser → DNS/TCP/TLS to Nginx → Nginx serves static or proxies to Gunicorn → a Gunicorn worker builds environ and calls Django's WSGI app → middleware, URL routing, view, DB queries → response back through Gunicorn and Nginx.

Why do we use Nginx in front of Gunicorn?

Sync Gunicorn workers would be held by slow clients; Nginx buffers them, terminates TLS, serves static files, enforces limits and load-balances, and keeps Gunicorn off the internet.

Difference between Gunicorn and uWSGI.

Gunicorn: pure-Python pre-fork server, few options, easy to run. uWSGI: written in C, extremely configurable (its own uwsgi protocol, many plugins), but complex, and the project has been in maintenance mode. Gunicorn is the usual default.

What is ASGI, and how is it different from WSGI?

ASGI is the async interface (async app(scope, receive, send)). WSGI blocks a worker per request; ASGI lets one event loop interleave many requests and supports WebSockets and long-lived connections.

How would you scale a Django app running on Gunicorn?

Tune workers/threads per instance by measuring; run more stateless instances behind a load balancer; move slow work to a task queue; cache; put a connection pooler in front of the DB; serve static from a CDN.

How does Nginx handle SSL termination in a Django deployment?

Nginx holds the certificate and does the TLS handshake, then proxies plain HTTP to Gunicorn with X-Forwarded-Proto: https. Django must trust that header (SECURE_PROXY_SSL_HEADER) or it will think requests are HTTP — breaking secure cookies and redirects.

Can a single server handle both static and dynamic content? Pros/cons?

Yes (Django can serve static via WhiteNoise; Nginx can do both with a proxy). One process is simpler, but serving static through Python workers wastes expensive workers; Nginx or a CDN serves static far more efficiently.

Users see 502s only on the report-export endpoint, which takes ~45 s. Why?

Gunicorn's 30 s worker timeout kills the worker before Nginx's 60 s timeout; Nginx sees a closed connection → 502. Make export asynchronous (queue + download link) rather than raising timeouts.

After scaling from 2 to 8 instances, the site gets slower and the DB logs connection errors. Why?

Total DB connections = instances × workers × pool size, now above the DB limit. Add PgBouncer or shrink pools; scale the web tier only within the DB's connection budget.

What Should I Remember?

  1. WSGI is a spec (PEP 3333): application(environ, start_response); servers and frameworks are interchangeable.
  2. WSGI is synchronous — concurrency = workers × threads; ASGI is async and supports WebSockets.
  3. Nginx in front protects sync workers from slow clients and handles TLS/static.
  4. Gunicorn workers: start at (2 × cores) + 1, measure, recycle with --max-requests.
  5. Gunicorn --timeout < Nginx timeout, or slow requests become 502s.
  6. Workers × instances × pool size must fit the database's connection limit.
