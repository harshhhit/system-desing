Domain-Driven Design — Eric Evans

Tackling Complexity in the Heart of Software (2003). The book's four parts and seventeen chapters, with the key topics each chapter covers.

What This Book Is About

Domain-Driven Design: Tackling Complexity in the Heart of Software (Eric Evans, 2003) is a book about one problem: in most serious software, the hardest part is not the technology — it is the domain, the business area the software serves (shipping, banking, insurance, healthcare). Evans argues that the design of the software should be driven by a model of that domain, built together by developers and domain experts, expressed in a shared language, and kept in sync with the code.

Without that, two things go wrong. The code fills up with business rules hidden in conditionals that nobody can find or explain, and developers and business people talk past each other because each side uses its own vocabulary. Every change then gets slower and riskier as the system grows. DDD is the set of practices and patterns that keeps the model, the language and the code aligned so the system stays changeable.

💡 Important

The book has two halves that people often confuse. Tactical design (Parts I–III) is about building a good model inside one area — Entities, Value Objects, Aggregates, Repositories. Strategic design (Part IV) is about how many models coexist in a large system — Bounded Contexts, Context Maps, the Core Domain. Microservice boundaries usually come from the strategic half.
