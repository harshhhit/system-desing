Domain-Driven Design, Ch 2 — Communication and the Use of Language

The Ubiquitous Language: one vocabulary built on the model and used everywhere — modeling out loud, one team one language, and the role of diagrams, documents and explanatory models.

What you'll learn

By the end of this chapter's notes you will be able to:

  • Say what a Ubiquitous Language is and the problem it solves
  • Explain why translating between "business words" and "developer words" damages a design
  • Use "modeling out loud" to test and improve a model
  • Decide what role diagrams and written documents should play — and what they shouldn't
  • Tell the implementation model apart from an explanatory model

What a Ubiquitous Language Is and Why It Exists

A Ubiquitous Language is a single vocabulary, built from the domain model, that developers and domain experts both use — in conversation, in diagrams, in documents, and in the code itself. "Ubiquitous" means it is used everywhere on the project, not just in meetings. It is the central pattern of Chapter 2 and one of the most quoted ideas in the whole book.

It exists because, without it, every project grows two languages. Domain experts speak their business jargon; developers speak in tables, classes, services and design patterns. Someone has to translate between them, and every translation loses precision. Experts describe a rule vaguely because they can't see how the software works; developers implement their own interpretation because they can't see the business; and different developers invent different names for the same concept. The result is a design that nobody can fully explain and bugs that come from misunderstandings rather than from coding errors.

Chapter 1 built a model through knowledge crunching. Chapter 2 is about making that model the backbone of how the team talks, so that the model is used — and therefore tested and improved — every day.

💡 Important

The language and the model are tied together: a change in the Ubiquitous Language is a change to the model. If the team starts calling something by a new name, or discovers that one word is being used for two things, the model (and the code) must change too. Language is not documentation sitting next to the model — it is the model, spoken.

What belongs in the language

The Ubiquitous Language is more than a list of class names. Evans lists what it draws on:

  • The names of classes and their main operations — Cargo, Itinerary, RoutingService.findItinerary().
  • Terms for rules that have been made explicit in the model — like the overbooking policy from Chapter 1.
  • Names of patterns applied to the model — if the team says "this is a Strategy", that is part of the shared vocabulary.
  • Terms from the high-level organising structure of the system (covered much later, in Part IV).

Two kinds of words stay out: purely technical words that experts never need (thread pools, ORM mappings), which developers can keep among themselves, and expert jargon about parts of the business the software doesn't model.

Ubiquitous Language vs. a project glossary — the difference

The difference is whether the words are used and tied to the model. A glossary is a document listing definitions; it can be correct while the code, tickets and meetings all use other words. A Ubiquitous Language is enforced by use: the same terms appear in class names, method names, test names, user stories and conversation, and when a term turns out to be wrong, the code is refactored to match.

⚠️ Common mistake

Thinking the Ubiquitous Language means "use the business people's words exactly as they are". It is built on the model, which developers and experts shape together. Experts' existing jargon is often vague, overloaded or inconsistent; part of the work is agreeing on precise terms — sometimes new ones — that both sides then adopt.

Architecture — Where the Language Lives

The book's running example is a cargo shipping application. Its routing part uses a handful of model concepts, and those same words appear in every channel the team uses.

How It Works — From Translation to a Shared Language

Evans illustrates the effect with two versions of the same conversation between a user and a developer, about what happens when a cargo's customs clearance point changes. The dialogue below is a paraphrase of the book's example.

Scenario 1 — minimal abstraction of the domain

The developer talks in database and implementation terms: "When the customs point changes, we delete the rows for that cargo in the routing table, pass the origin, destination and new customs point to the routing service, and it repopulates the table. We need a flag in the cargo record that says whether there's routing data." The user follows only vaguely and has to trust that this matches what the business needs. Every new case needs another round of translation.

Scenario 2 — the model enriched to support the discussion

The developer and user share the model: "When any constraint in the Route Specification changes — including the customs clearance point — we check whether the current Itinerary still satisfies it. If it doesn't, we ask the Routing Service for a new Itinerary based on the new Route Specification." The user can now spot mistakes directly ("what about cargo that's already loaded?"), and the developer's sentence describes both the business and the code.

🧠 Think about it

In Scenario 2 the concept Route Specification may not have existed before the conversation. It was added because talking about "the origin, destination, customs point and deadline" every time was clumsy. Clumsy speech is a signal that a concept is missing from the model.

Modeling out loud

Modeling out loud means describing scenarios aloud in the model's terms and listening for sentences that sound awkward. People are good at noticing when a spoken sentence is convoluted, so speech works as a cheap test of the model. Evans shows a sequence of ways to describe the routing step, each sharper than the last (paraphrased):

  1. Vague: "If we give the Routing Service an origin, destination and arrival time, it looks up the stops the cargo has to make and… puts them in the database." — the model is barely involved; the database is doing the explaining.
  2. Better: "The origin, destination and the rest all go into the Routing Service, and we get back an Itinerary with everything we need." — a real model object (Itinerary) appears.
  3. Precise: "A Routing Service finds an Itinerary that satisfies a Route Specification." — two model concepts and one relationship say the whole thing, and the sentence maps directly to code.

Cause → effect: the awkward sentence (step 1) leads the team to ask what concept is missing → they name the bundle of constraints a Route Specification → the sentence becomes short and exact (step 3) → the code gains a RouteSpecification class with a clear job. The language improved the model.

One team, one language

Technical people sometimes assume domain experts should be shielded from the model ("they don't need to understand our design"). Evans argues the opposite: if sophisticated domain experts cannot understand the model, something is wrong with the model. The experts' role is to object to terms or structures that are awkward or that don't capture the domain; the developers' role is to watch for ambiguity and inconsistency that would break the design. When both sides use the same words, each side can catch the other's mistakes.

🔥 Production insight

A cheap way to see the problem in your own team: listen to a planning meeting for the phrase "so in our system that's…". Each time it's said, someone is translating, and that translation is a place where requirements and code can drift apart.

Implementation — The Language in Code

The Scenario 1 vs. Scenario 2 difference shows up directly in code. The first version, written in implementation terms, could look like this:

void onCustomsPointChanged(long cargoId, String newCustomsPoint) {
    routingDao.deleteStopsForCargo(cargoId);
    CargoRecord rec = cargoDao.load(cargoId);
    List<Stop> stops = routingService.lookUp(rec.origin, rec.destination, newCustomsPoint);
    routingDao.insertStops(cargoId, stops);
    cargoDao.setHasRouting(cargoId, true);
}
  • deleteStopsForCargo, insertStops, setHasRouting — storage operations. A domain expert can't confirm this is right because it says nothing about the business rule.
  • The rule "re-route when the requirements change" is only implied by the sequence of calls; it has no name.

The same behaviour written in the Ubiquitous Language:

void changeCustomsClearancePoint(Cargo cargo, Location point) {
    cargo.specifyNewRoute(cargo.routeSpecification().withCustomsPoint(point));

    if (!cargo.routeSpecification().isSatisfiedBy(cargo.itinerary())) {
        Itinerary itinerary = routingService.findItinerary(cargo.routeSpecification());
        cargo.assignToRoute(itinerary);
    }
}
  • routeSpecification().isSatisfiedBy(itinerary()) — reads almost exactly like the spoken sentence from Scenario 2; an expert can check it line by line.
  • routingService.findItinerary(routeSpecification) — the "precise" sentence from modeling out loud, now as a method call.
  • Storage details are gone from this method; they move to infrastructure code (Chapter 4's layered architecture explains where).

💡 Important

Renaming is a real design change here, not cosmetics. When the team agrees a better term, refactor the class and method names to match. Code that keeps old names after the language has moved on silently reintroduces translation.

In Real Projects — Documents and Diagrams

A shared language raises the question of what to write down. Evans takes a clear position: the model is carried mainly by conversation and code; diagrams and documents support them but cannot replace them.

Diagrams

Diagrams (including UML) are good at showing structure — which objects exist and how they relate — and are a great aid to discussion. They are poor at conveying meaning (what a concept really is) and behaviour (what objects actually do). Trying to put the whole model into a complete UML diagram produces a picture too detailed to read that still misses what matters. Evans's advice: use simple, informal diagrams of the important part of the model, and pair them with text that explains them.

Written design documents

Documents are useful when they complement code and speech rather than duplicate them. Two guidelines from the chapter:

  • Documents should complement code and speech. Code already states the details precisely; a document should explain what code cannot — the meaning of concepts, the reasons behind design decisions, the big picture.
  • Documents should work for a living and stay current. A document nobody uses drifts out of date and then actively misleads. Keep documents few, focused and involved in the team's real work; if a document isn't used, it doesn't help the language.

Executable bedrock

Code is the only artifact guaranteed to describe what the software does. Well-written code that uses the Ubiquitous Language can communicate the design directly — but only if names are honest. A method called isSatisfiedBy that secretly also modifies data misleads more than no name at all.

Explanatory models

Not every model has to be the one in the code. An explanatory model is a separate view built only to teach the domain — for example, the book shows cargo shipping as a timeline of handling events and transfers between parties, which explains how shipping works more clearly than the class diagram does. Explanatory models are free to be informal and to emphasise different things, as long as everyone knows they are teaching aids, not the implementation model.

Best Practices

Do

  • Use the model as the backbone of the language, and use it relentlessly — in speech, tickets, diagrams, tests and code — because a language used only in meetings doesn't protect the code.
  • Say scenarios out loud — awkward sentences reveal missing or wrong concepts cheaply.
  • Treat a change in the language as a change in the model — refactor names in code when terms change.
  • Expect domain experts to object to terms that don't fit — their objections are model bugs found early.
  • Keep diagrams small and informal, with explanatory text — they show structure, text gives meaning.
  • Keep documents few and current, and use explanatory models to teach the domain.

Avoid

  • Translation layers between people — every translation loses precision.
  • Synonyms for one concept — readers assume different words mean different things.
  • Shielding experts from the model — if experts can't understand it, the model is wrong.
  • Exhaustive UML diagrams — too detailed to read, and still missing meaning and behaviour.
  • Documents that duplicate the code — they go stale and mislead.

🎯 Interview tip

When you mention Ubiquitous Language, give a before/after: "the ticket said update stops table, the code now says routeSpecification.isSatisfiedBy(itinerary)". A concrete example shows you've applied it, not just read the term.

Interview Answer — What Is a Ubiquitous Language?

A Ubiquitous Language is a shared vocabulary, built on the domain model, that developers and domain experts use in every form of communication — conversation, tickets, diagrams, documents and the code itself. Class names, method names and the terms for business rules all come from it, so a sentence spoken in a meeting maps directly onto the code.

It exists because projects otherwise split into two languages — business jargon and technical jargon — with translation in between. Translation loses precision, so requirements are misunderstood, the same concept gets several names, and experts can't check whether the design is right. With one language, experts can catch modeling mistakes and developers can catch ambiguity, and awkward phrasing ("modeling out loud") points to missing concepts.

The language and the model are the same thing seen from two sides: a change in the language is a change in the model and must be reflected in code. It is "ubiquitous" within one model — in larger systems each Bounded Context has its own language, which Part IV of the book covers.

Simple interview version

"A Ubiquitous Language is one shared vocabulary, based on the domain model, that developers and business experts both use — in meetings, tickets, diagrams and directly in code names. It removes the translation between business and technical terms, which is where requirements get lost. If the team changes a term, that's a model change, so the code gets renamed too. In a large system each bounded context has its own language."

One important interview follow-up

Q: Does Ubiquitous Language mean one vocabulary for the entire company?

A: No. It is ubiquitous within one model — one team or one area of the system. Different parts of a large business genuinely use the same word differently ("customer" in billing vs. in shipping), and forcing one company-wide definition produces a vague, compromised model. DDD instead gives each Bounded Context its own precise language and makes the translation between contexts explicit at their boundaries.

Practice questions

Why is translating between business terms and technical terms harmful?

Each translation loses precision. Experts can't verify the design because it's described in terms they don't use, developers implement their own interpretation, and different people invent different names for the same concept — so misunderstandings become bugs.

Where should the Ubiquitous Language appear?

Everywhere the team communicates: conversation, tickets and acceptance criteria, diagrams, documents, test names, and class and method names in code.

What is "modeling out loud" and why does it work?

Describing scenarios aloud in model terms. People quickly notice when spoken sentences are convoluted; an awkward sentence usually means a concept is missing or misnamed. Refining the sentence (e.g. to "a Routing Service finds an Itinerary that satisfies a Route Specification") refines the model.

Why does Evans say a change in the language is a change in the model?

The language is built on the model, so renaming or splitting a term changes what concepts exist and how they relate. If the code keeps the old names, the team is back to translating between how it talks and how the code is written.

What role should UML diagrams and design documents play in DDD?

A supporting one. Diagrams show structure well but not meaning or behaviour, so keep them small and pair them with text. Documents should complement code and speech (explain concepts and decisions) and stay current by being used; the code is the precise, executable statement of the design. Explanatory models can teach the domain without matching the code.

What does it mean if domain experts can't understand your model?

Evans treats it as a sign the model is wrong — it is probably expressed in technical terms or doesn't capture the domain's real concepts. Sophisticated experts should be able to follow and challenge the model.

Billing and shipping teams keep arguing about what a "customer" is, and integration bugs follow. What do you do?

Recognise that the word has two legitimate meanings in two models. Don't force one definition; give each area its own precise term within its own context (a Bounded Context, Ch 14) and make the mapping between them explicit at the integration point.

A new developer finds Shipment, Consignment and CargoRecord classes that seem to be the same thing. What's the fix?

Ask the domain experts which term they use and whether these are truly one concept. If they are, pick the agreed term and rename across code, tests and tickets. If they aren't, define the difference precisely and make it visible in the model.

What Should I Remember?

  1. A Ubiquitous Language is one vocabulary, built on the model, used by developers and experts everywhere — including code.
  2. Translation between business and technical words loses precision; the shared language removes it.
  3. A change in the language is a change in the model — rename the code too.
  4. Modeling out loud: awkward sentences reveal missing concepts (e.g. Route Specification).
  5. One team, one language: if experts can't understand the model, the model is wrong.
  6. Diagrams show structure, not meaning — keep them small and add text.
  7. Documents should complement code and speech and stay current; code is the executable bedrock.
  8. Explanatory models can teach the domain without matching the code.
  9. The language is ubiquitous within one model; large systems have one per Bounded Context.
