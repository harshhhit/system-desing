Network Reconnaissance During Penetration Testing

Map the network before you test it: ip addr, ip route, ping, getent hosts and nc -vz — what each tells you, what a failure does not prove, and why ARP stops at Docker bridges.

What you'll learn

By the end of this page you will be able to:

  • Say what network reconnaissance is and why it comes before vulnerability testing
  • Read ip addr and ip route output and know which networks your machine can reach
  • Interpret ping, getent hosts and nc -vz results — including what a failure does not prove
  • Explain why ARP-based tools like Netdiscover stop at Docker bridge / Layer 2 boundaries
  • Chain the commands into a repeatable recon workflow and troubleshoot when one works and another fails

What Network Reconnaissance Is and Why It Exists

The commands:

ip addr
ip route
ping TARGET
getent hosts TARGET
nc -vz TARGET PORT

are part of Network Reconnaissance and Connectivity Enumeration, which is one of the first stages of penetration testing.

Before testing a server for vulnerabilities, you need to understand how the machine communicates with other machines, which networks it can access, which services are reachable, and where network boundaries exist.

Think of it this way:

You cannot effectively test a network if you don't understand how the network is connected.

Let's understand the theory, the internal working, and what each command tells you from a penetration tester's perspective.

Definition and the ten questions it answers

Network reconnaissance is the process of collecting information about a target's network infrastructure before attempting vulnerability assessment or exploitation.

During reconnaissance, we try to answer these questions:

  1. What IP address does my machine have?
  2. Which network am I connected to?
  3. What is my default gateway?
  4. Which other machines can I communicate with?
  5. Can I resolve domain names into IP addresses?
  6. Which ports are accessible on the target?
  7. Which network services are exposed?
  8. Are there network segmentation or firewall restrictions?
  9. Is the target accessible directly or through another network?
  10. Are there unexpected services exposed internally?

Why it matters: an example target

Imagine you are performing an authorized penetration test against a company infrastructure.

The infrastructure looks like this:

                  Internet
                     |
                  Firewall
                     |
                Public Subnet
                     |
                Load Balancer
                     |
                Private Subnet
                 /        \
             EC2-1        EC2-2
               |            |
               +----- RDS --+

Your job is to identify weaknesses.

But before testing anything, you need to understand:

  • Can you reach the public load balancer?
  • Can you reach private EC2 instances?
  • Can you access the database directly?
  • Is the database exposed to an unauthorized network?
  • Can one EC2 instance communicate with another?
  • Are unnecessary ports open?

This is why network reconnaissance is important.

💡 Important

The objective is to understand the attack surface, not immediately attack the target.

Core Concepts — Terminology

Each command answers one question about the network. The terms below are used throughout the page with exactly these meanings.

TermMeaning
IP addressA logical address assigned to a network interface; identifies where that interface sits in an IP network.
CIDRClassless Inter-Domain Routing notation (/24) — how many leading bits are the network portion.
Routing tableThe kernel's list of rules deciding which interface and next-hop gateway a packet uses.
Default gatewayThe next hop used when no more specific route matches — usually your router.
ICMPInternet Control Message Protocol — network-layer diagnostics and errors; has no ports.
TTLTime To Live — an IP packet's remaining lifetime, decremented by each router.

IP Addressing — ip addr

Theory: What is an IP address?

An IP address is a logical address assigned to a network interface.

It identifies a machine or network interface within an IP network.

For example:

192.168.1.10

This address tells us where a particular network interface exists in an IPv4 network.

A machine can have multiple network interfaces, and each interface can have a different IP address.

For example:

Linux Machine
     |
     |--- eth0: 192.168.1.10
     |
     |--- docker0: 172.17.0.1
     |
     |--- lo: 127.0.0.1

Each interface serves a different purpose.

InterfacePurpose
eth0Physical or virtual network connectivity
docker0Docker bridge networking
loLoopback communication
tun0VPN tunnel
wlan0Wireless networking

Command

ip addr

Short version:

ip a

Example output:

2: eth0:
    inet 192.168.1.10/24

3: docker0:
    inet 172.17.0.1/16

4: lo:
    inet 127.0.0.1/8

What does /24 mean?

This is called CIDR notation (Classless Inter-Domain Routing).

Consider:

192.168.1.10/24

The /24 means:

  • 24 bits are reserved for the network portion.
  • 8 bits are available for host addresses.
  • Subnet mask: 255.255.255.0.
  • Total IPv4 addresses: 256.
  • Traditionally usable host addresses: 254.

The network is:

192.168.1.0/24

Typical usable host range:

192.168.1.1 - 192.168.1.254

What do we check during pentesting?

When you run:

ip addr

You are trying to identify:

CheckWhy it matters
IP addressesIdentify your machine's network location
Network interfacesIdentify available network paths
CIDR/subnet maskUnderstand the local network range
VPN interfacesIdentify VPN connectivity
Docker interfacesIdentify container network boundaries
Multiple interfacesIdentify possible multi-network access

Practical pentesting example

Suppose your output shows:

eth0: 192.168.1.10/24
docker0: 172.17.0.1/16
tun0: 10.10.10.5/24

You have three network environments:

192.168.1.0/24  → Local network
172.17.0.0/16   → Docker network
10.10.10.0/24   → VPN network

This is useful because you can identify which networks are potentially reachable from your machine.

⚠️ Common mistake

Important: An assigned IP address does not automatically mean you can reach every machine in that subnet. Routing, firewall rules, network namespaces, and access controls determine actual connectivity.

Routing — ip route

Theory: What is routing?

IP addressing tells us where our machine is located.

Routing tells us where network traffic should go.

When your machine wants to communicate with another IP address, Linux needs to determine which network interface and next-hop gateway should be used.

This decision is made using the routing table.

For example:

192.168.1.10 → 192.168.1.50

Both machines are in the same /24 network.

Linux can communicate directly using the local network.

But consider:

192.168.1.10 → 8.8.8.8

The destination is outside the local subnet.

Linux generally sends the packet to its default gateway, which forwards it towards the destination.

IP addressing vs. routing — the difference is that addressing says where an interface is, while routing says which way a packet leaves to reach a destination.

Command

ip route

Example:

default via 192.168.1.1 dev eth0

172.17.0.0/16 dev docker0

192.168.1.0/24 dev eth0

Let's understand each entry.

A. Default route

default via 192.168.1.1 dev eth0

Meaning:

  • default: Used when no more specific route matches.
  • via 192.168.1.1: Send traffic to this gateway.
  • dev eth0: Use the eth0 interface.

The default gateway is generally your router.

B. Docker route

172.17.0.0/16 dev docker0

Meaning:

Traffic destined for the Docker subnet should use the Docker bridge interface.

C. Local subnet route

192.168.1.0/24 dev eth0

Meaning:

Traffic destined for this subnet is directly reachable through eth0, subject to network and host restrictions.

What do we check during pentesting?

CheckSecurity significance
Default gatewayUnderstand the upstream network path
Multiple routesIdentify multiple reachable network segments
VPN routesIdentify networks accessible through VPN
Docker routesIdentify container network connectivity
Unexpected routesInvestigate unintended network access
Missing routesUnderstand why a target is unreachable

Important additional command

ip route get 8.8.8.8

This is particularly useful.

It tells you which interface and gateway Linux would use to reach a specific destination.

Example:

8.8.8.8 via 192.168.1.1 dev eth0 src 192.168.1.10

This tells you:

  • Destination: 8.8.8.8
  • Gateway: 192.168.1.1
  • Interface: eth0
  • Source IP: 192.168.1.10

🧠 Think about it

Pentesting perspective: Before scanning a target, understand the route your traffic will take. Otherwise, you might interpret routing problems as firewall restrictions or target downtime.

ICMP Reachability — ping

Theory: What is ICMP?

ICMP stands for Internet Control Message Protocol.

It is a network-layer protocol used by devices to communicate network errors, operational information, and diagnostic information.

Unlike TCP and UDP, ICMP does not use port numbers.

One of its most common uses is checking whether a destination can respond to network requests.

When you execute:

ping 192.168.1.20

Your machine sends an ICMP Echo Request packet to the destination.

If the destination allows it, it responds with an ICMP Echo Reply.

The communication looks like this:

Your Machine                 Target Machine
192.168.1.10                 192.168.1.20
     |                            |
     |------ Echo Request ------->|
     |                            |
     |<----- Echo Reply ----------|
     |                            |

Command

ping 192.168.1.20

Send only four packets:

ping -c 4 192.168.1.20

Set packet interval:

ping -i 2 192.168.1.20

Set timeout:

ping -W 2 -c 4 192.168.1.20

What does the output tell us?

Example:

64 bytes from 192.168.1.20:
icmp_seq=1 ttl=64 time=0.45 ms

Understand the fields:

FieldMeaning
64 bytesSize of the response
192.168.1.20Responding IP address
icmp_seq=1ICMP packet sequence number
ttl=64Remaining IP packet lifetime
time=0.45 msRound-trip time

What is TTL?

TTL stands for Time To Live.

It prevents IP packets from circulating indefinitely in a network.

Every router that forwards an IP packet normally decreases its TTL by one.

When TTL reaches zero, the packet is discarded.

TTL can sometimes provide clues about the operating system or network path, but it is not a reliable OS identification method.

What do we check during pentesting?

  1. Is the target responding to ICMP?
  2. Is there packet loss?
  3. Is latency unusually high?
  4. Is the target reachable from our network?
  5. Is a firewall filtering ICMP?

Important security concept

Suppose you run:

ping 192.168.1.50

And receive:

100% packet loss

Does this mean the server is down?

No.

There are several possibilities:

  • The server is offline.
  • The server is online but ICMP is disabled.
  • A firewall blocks ICMP.
  • A network ACL blocks ICMP.
  • A routing problem prevents communication.
  • The server is reachable through TCP but not ICMP.

This is why penetration testers should never rely only on ping to identify live systems.

For example:

nc -vz 192.168.1.50 22

The SSH port might still be accessible even when ping fails.

🎯 Interview tip

"Ping failed, so the host is down" is the classic wrong answer. Say: ICMP may be filtered while TCP services remain reachable — confirm with a TCP check on a likely port.

Name Resolution — getent hosts

Theory: What is DNS?

DNS stands for Domain Name System.

Computers communicate using IP addresses, but humans generally use domain names.

For example:

google.com

A DNS resolver translates this hostname into an IP address.

Conceptually:

Application
     |
     | Request: example.com
     |
DNS Resolver
     |
     | Returns IP address
     |
93.184.216.34
     |
     |
Connect to destination

Without DNS, you would need to remember IP addresses for every service.

DNS is particularly important in production environments because applications frequently communicate through service names rather than hardcoded IP addresses.

Examples:

api.internal.company.com
database.internal.company.com
redis.internal.company.com

Command

getent hosts example.com

Example:

2606:2800:220:1:248:1893:25c8:1946 example.com

You might also receive an IPv4 address, depending on the resolver configuration.

Why use getent instead of only nslookup?

This is an important Linux concept.

Linux uses the Name Service Switch (NSS) to determine how different types of names should be resolved.

The configuration is generally available in:

cat /etc/nsswitch.conf

Look for:

hosts: files dns

This means Linux checks:

  1. /etc/hosts
  2. DNS

Other NSS modules can also participate depending on the configuration.

getent hosts uses the system's configured name-resolution mechanisms, making it useful for testing how applications on that machine resolve hostnames.

getent vs. nslookup/dig — the difference is that getent follows the NSS order (so it sees /etc/hosts entries, exactly like an application on the box would), while nslookup/dig query a DNS server directly and ignore /etc/hosts.

Useful commands

Check hostname resolution:

getent hosts example.com

Check local hostname mappings:

cat /etc/hosts

Check DNS resolver configuration:

cat /etc/resolv.conf

Check NSS configuration:

grep '^hosts:' /etc/nsswitch.conf

Check DNS records using dig:

dig example.com

Check only IPv4:

dig A example.com

Check IPv6:

dig AAAA example.com

What do we check during pentesting?

CheckWhy it matters
DNS resolutionDetermine whether target names resolve
Internal DNSIdentify internal naming infrastructure
/etc/hostsFind manually configured hostname mappings
DNS recordsUnderstand publicly exposed infrastructure
DNS misconfigurationIdentify potential security weaknesses
Internal domainsUnderstand internal service architecture

Real-world security example

Suppose an organization uses:

api.company.com
admin.company.com
staging.company.com
database.internal.company.com

During an authorized assessment, you might discover that:

getent hosts staging.company.com

Returns an IP address belonging to a publicly reachable server.

This gives you an additional asset to investigate.

However, DNS resolution does not prove that the service is reachable or vulnerable. You must perform additional checks.

TCP Port Connectivity — nc -vz

This is one of the most important commands for network reconnaissance.

Theory: What is TCP?

TCP stands for Transmission Control Protocol.

It is a transport-layer protocol that provides reliable, ordered communication between applications.

Applications use TCP ports to identify services.

For example:

PortCommon service
22SSH
80HTTP
443HTTPS
3306MySQL
5432PostgreSQL
6379Redis
8080Alternative HTTP
27017MongoDB

Imagine a server has this IP:

192.168.1.50

And you want to check whether SSH is accessible.

You need to test:

192.168.1.50:22

An IP identifies the destination machine, while a port identifies a particular service endpoint.

What is Netcat?

Netcat (nc) is a network utility used to establish TCP or UDP connections, transfer data, and perform basic network diagnostics.

Command:

nc -vz 192.168.1.50 22

Understand each argument:

ArgumentMeaning
ncNetcat utility
-vVerbose output
-zZero-I/O mode; check connectivity without sending application data
192.168.1.50Destination IP
22Destination port

Example successful output:

Connection to 192.168.1.50 22 port [tcp/ssh] succeeded!

This indicates that the TCP connection was established.

It does not prove that SSH authentication will succeed.

Different possible results

Scenario A: Port is open

nc -vz 192.168.1.50 22

Output:

Connection succeeded

Interpretation:

  • Target is reachable through the tested path.
  • TCP handshake succeeded.
  • Something is accepting TCP connections on that port.

Scenario B: Port is closed

Output:

Connection refused

Interpretation:

  • The destination was reachable enough to return a rejection.
  • Usually, no service is listening on that port, or a firewall actively rejected the connection.

Scenario C: Port is filtered

Output:

Connection timed out

Interpretation:

  • No successful connection was established within the timeout.
  • A firewall may be silently dropping traffic.
  • Routing problems or an unavailable target are also possible.

⚠️ Common mistake

Important: A timeout does not conclusively prove that a firewall is blocking the port. Refused vs. timed out — the difference is that "refused" means something answered with a rejection (the host is reachable), while "timed out" means nothing answered at all.

Useful commands

Check SSH:

nc -vz 192.168.1.50 22

Check HTTP:

nc -vz 192.168.1.50 80

Check HTTPS:

nc -vz 192.168.1.50 443

Check PostgreSQL:

nc -vz 192.168.1.50 5432

Check multiple ports:

nc -vz 192.168.1.50 22 80 443 3306 5432

Check with timeout:

nc -vz -w 3 192.168.1.50 443

What do we check during pentesting?

This is where you start identifying the target's network attack surface.

For example:

Target: 192.168.1.50

22    SSH         Open
80    HTTP        Open
443   HTTPS       Open
3306  MySQL       Closed
5432  PostgreSQL  Open
6379  Redis       Open

This gives you several investigation opportunities.

  • Is SSH exposed unnecessarily?
  • Is the PostgreSQL port accessible from an unauthorized network?
  • Is Redis exposed without appropriate authentication and network restrictions?
  • Is HTTP redirecting to HTTPS?
  • Is HTTPS using a secure TLS configuration?

Notice that an open port is not automatically a vulnerability.

You must understand what service is listening, whether it is intended to be exposed, and whether it has security weaknesses.

Layer 2 Discovery — ARP and Netdiscover

A common observation:

Netdiscover relies on ARP and may not discover peers across Docker bridge boundaries.

This is an important concept, particularly when working with Docker-based pentesting labs.

Theory: What is ARP?

ARP stands for Address Resolution Protocol.

It is used in IPv4 local networks to discover the MAC address associated with an IPv4 address.

Remember:

  • IP address identifies a network-layer destination.
  • MAC address identifies a link-layer interface.

Suppose:

Your machine: 192.168.1.10
Target:       192.168.1.20

Your machine wants to send an Ethernet frame to the target.

But it needs the target's MAC address.

It sends an ARP request:

Who has 192.168.1.20?

Tell 192.168.1.10

The target responds:

192.168.1.20 is at AA:BB:CC:DD:EE:FF

Your machine can now send Ethernet frames to that MAC address.

ARP communication

Your Machine                  Target
192.168.1.10                  192.168.1.20
     |                             |
     |------ ARP Request ---------->|
     |                             |
     |<----- ARP Reply -------------|
     |                             |
     |      MAC Address Known      |

What is Netdiscover?

Netdiscover is a network discovery utility that uses ARP requests to identify devices on a local IPv4 network.

Example:

netdiscover -r 192.168.1.0/24

This attempts to identify devices on that local subnet.

Why doesn't it always work across Docker networks?

Understand Docker networking first.

Suppose you have:

Host Machine
     |
     | docker0
     |
     +-------------------+
     |                   |
 Container A         Container B
 172.17.0.2          172.17.0.3

Docker creates a virtual bridge connecting containers.

ARP broadcasts are generally confined to their Layer 2 network segment.

A container on one bridge cannot automatically use ARP broadcasts to discover devices attached to a different bridge.

Also, Docker containers have their own network namespaces, which isolate interfaces, routing tables, and network stacks.

Therefore:

  • ARP discovery works within the relevant Layer 2 segment.
  • It does not automatically cross routers.
  • It does not automatically cross separate Docker bridges.
  • Host networking and bridge networking behave differently.

ARP vs. DNS — the difference is that ARP maps an IPv4 address to a MAC address on the local Layer 2 segment, while DNS maps a hostname to an IP address (or other records) and works across networks.

Check your Docker network

docker network ls

Inspect a network:

docker network inspect bridge

Check container IP addresses:

docker inspect CONTAINER_NAME

Check the container's network configuration:

docker exec -it CONTAINER_NAME ip addr

💡 Important

Pentesting significance: Network segmentation is a security boundary. Your assessment should establish whether systems that should be isolated can communicate with each other.

Architecture — Where Each Command Sits in the Network Stack

Each recon command tests a different layer. Knowing the layer tells you what a failure can and cannot mean: an ARP tool cannot see past a router, and a successful ICMP reply says nothing about a TCP port.

CommandLayer / protocolQuestion it answersScope
netdiscover, ip neighLayer 2 — ARPWhich hosts (MAC addresses) share my segment?Local Layer 2 segment only
ip addrLayer 3 — interface addressingWhich IPs and subnets do I have?This machine
ip route, ip route getLayer 3 — routing tableWhich interface and gateway will a packet use?This machine's forwarding decision
pingLayer 3 — ICMPDoes the host answer Echo Requests?Any routed destination that allows ICMP
nc -vzLayer 4 — TCPDoes a three-way handshake complete on this port?Any routed destination + port
getent hostsApplication — NSS (/etc/hosts, DNS)Which IP does this name resolve to here?This machine's resolver configuration
flowchart TB L7["Application: getent hosts (NSS → /etc/hosts, DNS)"] --> L4["Transport (TCP): nc -vz"] --> L3["Network (IP / ICMP): ip addr · ip route · ping"] --> L2["Link (ARP / MAC): netdiscover · ip neigh"]

Recon commands mapped to the layer they test — a failure only tells you about its own layer and the ones beneath it.

How It Works — the TCP Three-Way Handshake Behind nc -vz

A basic TCP connectivity test is checking whether this handshake completes. TCP establishes connections using a process called the three-way handshake.

Your Machine                     Target Server
     |                                |
     |---------- SYN ---------------->|
     |                                |
     |<--------- SYN-ACK --------------|
     |                                |
     |---------- ACK ---------------->|
     |                                |
     |        Connection Established  |

Let's understand:

  1. SYN: Your machine requests a TCP connection.
  2. SYN-ACK: The target acknowledges the request and indicates that it is willing to establish the connection.
  3. ACK: Your machine acknowledges the response. The TCP connection is established.

This is what a basic TCP connectivity test is checking.

The Recon Workflow — How the Commands Fit Together

Now let's connect all the concepts.

Imagine you have been given access to an authorized pentesting lab.

Your Kali Linux machine is running inside a Docker container.

You need to identify the network and test connectivity to another machine.

Follow this sequence.

  1. Step 1: Identify your network interfaces — ip addr. Questions: What is my IP? Which interface is active? What is my subnet? Am I connected through a VPN? Am I inside Docker?
  2. Step 2: Identify routing — ip route. Questions: What is my default gateway? Which network is directly connected? Which interface handles external traffic? Are there multiple network paths?
  3. Step 3: Identify the route to the target — ip route get 172.17.0.2. Questions: Is the target covered by a known route? Which interface will Linux use? What source IP will be selected?
  4. Step 4: Check whether ICMP works — ping -c 4 172.17.0.2. Questions: Is the target responding? Is there packet loss? Is ICMP being filtered?
  5. Step 5: Check hostname resolution — getent hosts target.local. Questions: Does the hostname resolve? Which IP address does it resolve to? Is it resolving through /etc/hosts or DNS?
  6. Step 6: Check TCP connectivity — nc -vz -w 3 172.17.0.2 22. Questions: Is SSH reachable? Does the TCP handshake succeed? Is the connection refused or timing out?
  7. Step 7: Perform service enumeration — once you have identified a reachable target, use Nmap within the authorized scope, for example nmap -sV 172.17.0.2. This attempts service and version detection on discovered open ports.

Important debugging commands

These are commands worth learning alongside the original five.

  1. Check listening ports — ss -tulnp. -t: TCP; -u: UDP; -l: Listening sockets; -n: Numeric addresses and ports; -p: Process information. This tells you which services are listening on your own machine.
  2. Check the ARP/neighbour table — ip neigh. This shows cached neighbour information, including IP-to-MAC mappings.
  3. Trace the network path — traceroute 8.8.8.8 or tracepath 8.8.8.8. These help identify where packets travel and where responses stop.
  4. Capture network packets — tcpdump -i any. Packet capture is particularly important because it lets you see what is actually happening on the network instead of relying only on command output.

Do / Avoid — Fundamentals Before Commands

There is a significant difference between someone who knows:

nmap -sV 192.168.1.10

and someone who understands:

  • How the packet leaves their machine.
  • Which interface sends it.
  • Which gateway forwards it.
  • How ARP resolves the next-hop MAC address.
  • How TCP establishes a connection.
  • How a firewall affects the packet.
  • Why Nmap classifies a port as open, closed or filtered.

The second person can troubleshoot real infrastructure, understand scan results and identify security misconfigurations.

Do

  • Run ip addr / ip route / ip route get before scanning — so you don't mistake a routing problem for a firewall or a dead host.
  • Confirm liveness with a TCP check, not only ping — ICMP is often filtered while services stay reachable.
  • Use -w timeouts with nc — so filtered ports don't hang your workflow.
  • Watch the wire with tcpdump when results disagree — packet capture shows what actually happened instead of what a tool reported.

Avoid

  • Treating every open port as a vulnerability — first establish what is listening and whether it is meant to be exposed.
  • Relying on ARP tools (Netdiscover) across bridges, VLANs or routers — ARP stops at the Layer 2 segment, so an empty result there proves nothing.
  • Testing outside the authorized scope — recon is only legitimate against systems you are permitted to assess.

Interview Answer — What Is Network Reconnaissance?

Network reconnaissance is the first stage of a penetration test: collecting information about how the target network is connected — your own addresses and subnets, the routes your traffic takes, which hosts respond, how names resolve, and which TCP ports accept connections — before any vulnerability assessment or exploitation. It exists because results from later tools are meaningless without that map: a scan that "finds nothing" might be a routing problem, an ICMP filter, or a Layer 2 boundary rather than an empty network.

On Linux the core toolkit is small. ip addr shows interfaces and their CIDR ranges (local, Docker, VPN). ip route and ip route get show which interface and gateway a packet will use. ping tests ICMP reachability, getent hosts resolves names the way applications on the box do (following NSS: /etc/hosts then DNS), and nc -vz tests whether a TCP three-way handshake completes on a port. ARP-based discovery such as Netdiscover only works within one Layer 2 segment.

In an assessment, the point is to compare actual reachability with the intended security architecture — for example, whether an unrelated server can reach the database port — rather than to treat every open port as a finding. See the step-by-step workflow and the troubleshooting table.

Simple interview version

"Network reconnaissance is mapping the network before testing it. I check my interfaces and subnets with ip addr, where my traffic goes with ip route, whether hosts answer with ping, how names resolve with getent hosts, and whether ports complete a TCP handshake with nc -vz — then move on to Nmap service enumeration. The goal is to understand the attack surface and see whether real network access matches what the architecture intends, not to attack straight away."

One important interview follow-up

Q: If ping gets 100% packet loss, is the server down?

A: No. The server may be offline, but it may equally be online with ICMP disabled, or ICMP may be blocked by a firewall or network ACL, or a routing problem may prevent communication. The server can be reachable over TCP while ICMP fails, so confirm with a TCP check such as nc -vz TARGET 22 — and never rely only on ping to identify live systems.

Practice questions

For a DevSecOps, Network Security or Penetration Testing interview, prepare these questions:

What is the difference between IP addressing and routing?

IP addressing identifies a network interface. Routing determines where packets should be forwarded to reach their destination.

Does a failed ping mean the server is down?

No. ICMP may be blocked while TCP services remain accessible.

What is the difference between ARP and DNS?

ARP resolves IPv4 addresses to MAC addresses on a local network. DNS resolves hostnames to IP addresses or other DNS records.

What happens when you execute nc -vz 192.168.1.10 443?

Netcat attempts to establish a TCP connection with port 443. It reports whether the connection succeeds, is refused, or times out.

What is the difference between an open and filtered port in Nmap?

An open port has an application accepting connections. A filtered port cannot be reliably classified because packet filtering prevents Nmap from determining whether it is open or closed.

Why might Netdiscover fail inside Docker?

Because ARP operates within Layer 2 broadcast domains. Separate Docker bridge networks isolate broadcast traffic, and network namespaces provide additional isolation.

Why use getent hosts instead of only nslookup when checking resolution on a target box?

getent follows the Name Service Switch order in /etc/nsswitch.conf (e.g. hosts: files dns), so it sees /etc/hosts entries exactly as applications on that machine do; nslookup only queries DNS.

From a compromised-in-scope app server, nc -vz -w 3 10.0.3.25 5432 succeeds against the database. Is that a finding?

Only if that server should not reach the database. The backend that owns the database is expected to connect; an unrelated server reaching 5432 suggests an overly permissive security group, incorrect segmentation, excessive database access, or a violation of least-privilege network architecture.

nc to a port reports "Connection timed out" while another port reports "Connection refused". What does each tell you?

Refused means the destination was reachable enough to return a rejection — usually nothing is listening, or a firewall actively rejected it. Timed out means no reply within the timeout — a firewall may be silently dropping traffic, but routing problems or an unavailable target are also possible, so it is not conclusive.

What Should I Remember?

  1. You cannot effectively test a network if you don't understand how it is connected — recon maps the attack surface, it doesn't attack.
  2. ip addr shows interfaces and CIDR ranges; an assigned IP does not mean every host in that subnet is reachable.
  3. ip route / ip route get show the interface, gateway and source IP — check them before blaming a firewall.
  4. A failed ping does not mean the host is down; ICMP is often filtered while TCP works.
  5. getent hosts resolves names like applications do (NSS: /etc/hosts then DNS); resolution doesn't prove reachability.
  6. nc -vz: succeeded = handshake completed; refused = reachable but closed/rejected; timed out = dropped or unreachable (not conclusive).
  7. ARP and Netdiscover stay within one Layer 2 segment — they don't cross routers or separate Docker bridges.
  8. An open port is not automatically a vulnerability; the finding is when actual access doesn't match the intended architecture.

Quick commands

  • ip -br addr — interfaces and addresses, one line each
  • ip route get TARGET — interface, gateway and source IP for one destination
  • ping -W 2 -c 4 TARGET — ICMP reachability with a timeout
  • getent hosts NAME — resolve via NSS like an application would
  • nc -vz -w 3 TARGET PORT — TCP handshake test with a timeout
  • ss -tulnp — listening sockets on this machine
  • ip neigh — ARP/neighbour cache
  • tcpdump -i any host TARGET — see what is actually on the wire
  • netdiscover -r 192.168.1.0/24 — ARP discovery on the local segment
  • nmap -sV TARGET — service and version detection (in scope only)
