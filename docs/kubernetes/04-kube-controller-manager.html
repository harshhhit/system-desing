kube-controller-manager Deep Dive

The reconciliation loops that keep actual cluster state converging on desired state.

Interview Answer — What Is kube-controller-manager?

kube-controller-manager is a Kubernetes control-plane process that bundles together the built-in controllers — Deployment, ReplicaSet, Node, Job, and the rest — and runs each of them as a background reconciliation loop inside a single binary.

It sits in the control plane alongside kube-apiserver, etcd, and kube-scheduler. Where the Scheduler makes a one-time placement decision for a Pod, kube-controller-manager is what keeps enforcing every other kind of desired state after that decision — replica counts, Node health, Job completion, Service endpoints, and so on — for as long as the cluster runs.

Mechanically, every controller inside kube-controller-manager runs the same watch → detect → correct loop: it watches the API Server (via an Informer, backed by a local cache and a work queue — see the "Theory: The Watch-Reconcile Loop" section below), detects when actual state has drifted from the desired state stored in etcd, and issues the corrective API calls (create a Pod, evict a Node's workloads, mark a Job complete) back through the API Server.

One nuance worth stating plainly: kube-controller-manager never talks to a kubelet or a worker node directly, and it never touches etcd directly either. Every read and every corrective write goes through the API Server — that's the same gateway/persistent-store split etcd's own page describes for the whole control plane, and it applies just as much to this component.

Simple interview version

"kube-controller-manager is the Kubernetes control-plane component that runs the built-in controllers — Deployment, ReplicaSet, Node, Job, and more — as a single process. Each controller watches the API Server, compares desired state (from etcd) against actual cluster state, and takes corrective action when they diverge. It only ever talks to the API Server — never directly to a kubelet, a worker node, or etcd."

One important interview follow-up

Q: Does kube-controller-manager talk to worker nodes or kubelets directly?

A: No. kube-controller-manager only ever reads and writes through the API Server — which is itself backed by etcd — and it never opens a direct connection to a kubelet or a worker node. Even the Node Controller, which is the controller most directly "about" nodes, doesn't reach out to a Node itself to check on it: it watches the Node's status object as reported to the API Server by that Node's own kubelet via periodic heartbeats, and if those heartbeats stop arriving for longer than the grace period, the Node Controller marks the Node object NotReady and evicts its Pods — all through API Server calls, never a direct connection to the Node. This is the same watch → detect → correct loop described in "Internal Architecture" above, and it's what keeps kube-controller-manager stateless and restartable: it holds no direct channel to any Node that would need to be re-established after a crash.

What Is kube-controller-manager?

kube-controller-manager is the Kubernetes control-plane component that runs the reconciliation loops. It doesn't run one controller — it bundles a whole set of independent controllers (Deployment Controller, Node Controller, Job Controller, and more) into a single process. Every one of those controllers does the same basic job, just applied to a different kind of resource: continuously compare the desired state you declared against the cluster's actual state, and take action whenever the two disagree.

That compare-and-correct loop is what "reconciliation" means everywhere on this page, and it's the mechanism every controller described below runs.

Desired State vs. Actual State

The three terms below are used throughout this page — the table spells out exactly what each one means and where it lives.

TermDefinitionExample
Desired StateThe configuration you declare in your YAML manifests. It is stored in etcd (the cluster's database).replicas: 5 in a Deployment YAML.
Actual StateThe real-world status of your cluster at this very moment.Only 3 Pods are currently running because 2 crashed.
ReconciliationThe continuous process of comparing Desired vs. Actual and taking action to correct drift.Kubernetes starts 2 new Pods to bring the count back to 5.

What Is a Controller?

A controller is one instance of that watch-and-correct loop, scoped to one kind of resource. Concretely: if a ReplicaSet declares Desired Pods = 3 but only 2 are currently running, the controller detects that mismatch and reacts by creating one more Pod — no human intervention required. Every controller below runs this same pattern against a different resource type.

Common Controllers

Deployment Controller

The Deployment Controller keeps a Deployment's Pod count and version in line with its spec by managing a chain of objects underneath it: a Deployment owns one or more ReplicaSets, and each ReplicaSet owns the individual Pods. When you change a Deployment's image or replica count, this controller creates a new ReplicaSet (or scales an existing one) and lets the old one scale down — that hand-off between ReplicaSets is what makes rolling updates and rollbacks possible without touching Pods directly.

flowchart TD A["Deployment"] --> B["ReplicaSet"] B --> C["Pods"]

ReplicaSet Controller

The ReplicaSet Controller is the layer below Deployments: it only cares about keeping a fixed number of Pod replicas running, regardless of why a Pod disappeared (crash, node failure, manual deletion). If a ReplicaSet declares Desired = 5 but only 4 Pods are currently running, the controller creates one more Pod to close the gap — the same watch → detect → correct pattern from the "What Is a Controller?" example above, just running continuously in the background for every ReplicaSet in the cluster.

Node Controller

The Node Controller watches the health of every Node via periodic heartbeats (the kubelet on each Node reports its status back to the API Server). When a Node stops reporting for longer than the configured grace period, the Node Controller marks it NotReady and, after a further timeout, evicts the Pods that were scheduled on it — which is what lets the Deployment/ReplicaSet controllers notice the resulting shortfall and reschedule those Pods onto healthy Nodes.

flowchart TD A["Node Failure"] --> B["Pod Recovery"]

Job Controller

The Job Controller manages one-off and batch workloads: it creates Pods to run a Job to completion, retries a Pod if it fails (up to the Job's configured retry limit), and marks the Job Completed once the required number of Pods have finished successfully. Unlike a Deployment, a completed Job's Pods are meant to exit, not be restarted indefinitely.

flowchart TD A["Job Running"] --> B["Job Completed"]

Service Account Controller

The Service Account Controller makes sure every Namespace has a default ServiceAccount, and creates the API credentials (tokens) Pods use to authenticate to the API Server when they don't specify a ServiceAccount of their own.

Namespace Controller

Handles namespace deletion: when a Namespace is deleted, this controller cleans up every object inside it before the Namespace itself is removed. That cascading delete is what keeps a deleted Namespace from leaving orphaned Pods, Services, or ConfigMaps behind in etcd.

Endpoint / EndpointSlice Controller

Keeps the list of Pod IPs behind a Service up to date, so kube-proxy always routes traffic to currently-running Pods.

flowchart TD A["Service selector matches 3 Pods"] --> B["EndpointSlice updated with 3 Pod IPs"] B --> C["kube-proxy programs routing rules"]

PersistentVolume Controller

Binds PersistentVolumeClaims to matching PersistentVolumes, and reclaims (or deletes) the volume once its claim is released — request (the PVC) meets supply (the PV), with a reclaim policy deciding what happens afterward. See Persistent Storage & Distributed DBs for the full binding and reclaim mechanics.

HorizontalPodAutoscaler Controller

Watches metrics (CPU, memory, or custom metrics) and adjusts a Deployment's or ReplicaSet's replica count to match a target. For example, if a Deployment targets 50% average CPU utilization and observed usage climbs to 80%, the HPA Controller increases the replica count to spread load back down toward the target — and scales back down once utilization drops, within whatever min/max replica bounds you've configured.

flowchart TD A["Observed CPU > target"] --> B["Increase replicas"]

StatefulSet Controller

Maintains StatefulSets — Pods with stable identities, stable network names, and stable storage — creating and updating them one at a time, in order (pod-0, then pod-1, then pod-2, and so on), and never reusing another Pod's name or PersistentVolumeClaim. That ordering and stable identity is what makes StatefulSets suitable for workloads like databases, which assume a fixed identity and fixed storage per replica.

DaemonSet Controller

Ensures exactly one copy of a Pod runs on every node (or every matching node) — used for node-level agents like log collectors or CNI plugins. It reacts to cluster membership directly: a new Node joining automatically gets a copy scheduled onto it, and a Node being removed automatically has its copy cleaned up, with no replica count to update.

CronJob Controller

Creates a new Job on a schedule, the same way cron creates a new process on a schedule. Each time the schedule fires, it creates a new Job — which the Job Controller above then drives to completion — and it keeps a configurable number of past successful/failed Jobs around afterward for inspection rather than deleting them immediately.

Internal Architecture

flowchart TD A["Controller"] --> B["Watch API Server"] B --> C["Detect Drift"] C --> D["Correct Drift"]

Every controller in kube-controller-manager runs this same watch → detect → correct loop independently and continuously. There's no fixed polling interval; a controller reacts as soon as it observes a relevant change, with a periodic full resync as a safety net against any event it might have missed.

Theory: The Watch-Reconcile Loop

The Watch-Reconcile loop is the engine that powers every Kubernetes controller. It's how the controller efficiently watches for changes without overwhelming the API Server.

The Problem It Solves

Kubernetes has thousands of resources (Pods, Services, Deployments, etc.). Polling the API Server every few seconds for changes would crash the API Server due to massive load.

Instead, Kubernetes uses a watch-based event system — the controller "subscribes" to changes and gets notified when something happens.

The Four Core Components

ComponentPurposeAnalogy
InformerWatches the API Server for changes to a specific resource type (e.g., Pods) and caches the data locally.A news subscription — you get notified when something changes.
ListerReads from the local cache (not the API Server) to query resources quickly without network calls.A local copy of the news — you can read it instantly without calling the news agency.
SharedInformerA shared version of Informer where multiple controllers can use the same watch connection to reduce API Server load.A shared newspaper subscription — multiple people read the same copy.
Work QueueA queue that holds events (add, update, delete) that need to be processed. Helps with retries, deduplication, and rate limiting.A to-do list — you put tasks here and process them one by one.

Deep Dive into Each Component

1. Informer (The Watcher)

What it does: An Informer uses the Kubernetes Watch API to establish a persistent connection to the API Server. It listens for events (Add, Update, Delete) on a specific resource type.

How it works:

  • On startup, it performs a List operation to get all existing resources.
  • It then starts a Watch to get incremental changes.
  • It stores all this data in a local cache (called an Indexer).

Why it matters: Without Informers, every controller would need to constantly poll the API Server, causing massive network congestion.

2. Lister (The Reader)

What it does: Lister is a read-only interface to the Informer's local cache.

How it works: Instead of making an API call to GET /api/v1/pods, the controller calls lister.Pods("default").Get("nginx-pod"). This reads from the local cache (memory), which is instantaneous.

Why it matters: Reading from cache is thousands of times faster than making an API call. It also reduces load on the API Server and etcd.

3. SharedInformer (The Efficient Watcher)

What it does: Normally, each controller would have its own Informer and its own watch connection to the API Server. If you have 50 controllers watching Pods, that's 50 watch connections — bad for the API Server.

How it works: SharedInformer allows multiple controllers to share the same watch connection. They all register their event handlers with the same SharedInformer.

Why it matters: It dramatically reduces API Server load. One watch connection vs. 50.

4. Work Queue (The Traffic Controller)

What it does: A work queue holds events (keys/identifiers of resources that changed) until the controller is ready to process them.

How it works:

  • Event handlers push a key (e.g., default/nginx-pod) into the work queue.
  • Worker goroutines pop keys from the queue and call the reconciliation logic.
  • The queue supports retries (if processing fails, the key goes back to the queue), rate limiting (slow down if errors happen), and deduplication (don't process the same key twice if multiple events occur).

Why it matters: It decouples event observation from event processing. If reconciliation takes 5 seconds, the Informer can still collect events during that time without blocking.

Why It Exists

Without controllers, Kubernetes would only be a static record-keeper: you could declare that you want 5 replicas of a Pod, but nothing would act on that declaration, and nothing would notice or recover when reality drifted away from it — a crashed Pod would just stay crashed, and a failed Node would silently drop capacity. Controllers exist to close that gap: users declare desired state once, and controllers continuously enforce it, so the cluster keeps converging back toward what was asked for without further input.

Failure Impact

If kube-controller-manager itself fails or becomes unreachable, already-running workloads are not affected immediately — existing Pods keep serving traffic, since the data plane (kubelet, kube-proxy, and the Pods themselves) doesn't depend on the controller manager to keep running. What stops is Kubernetes' ability to correct problems going forward. Examples:

  • Failed Pods not recreated
  • Node failures not handled
  • Replica counts not maintained
  • Jobs not managed

Tradeoffs

Advantages: the reconciliation model is self-healing and runs continuously, so most failures recover automatically without operator intervention.

Disadvantages: at large scale, the constant reconciliation activity is itself a real cost, and a misconfigured controller can trigger cascading, hard-to-diagnose actions across many resources at once.

Failure Scenario

Operationally, a controller-manager outage shows up as a cluster that stops self-correcting rather than one that immediately breaks — which is exactly why it's worth monitoring controller-manager health directly instead of waiting for user-facing symptoms. Symptoms:

  • Pods not recreated
  • Nodes not reconciled
  • Replica drift occurs

The net effect is the same as the "Failure Impact" section above: the cluster loses its self-healing capability, even while existing traffic keeps flowing.

High Availability

Like kube-scheduler, kube-controller-manager runs as several replicas but only one is active — it holds a Lease object in etcd and renews it periodically. If the active instance crashes, its lease expires, and a standby replica claims the lease and starts running the reconciliation loops. Only one replica ever reconciles at a time, so controllers never race each other.

For the full mechanics — the election algorithm, lease tuning parameters, failure-recovery timelines, and split-brain prevention — see Leader Election: HA for Controller Manager & Scheduler.
