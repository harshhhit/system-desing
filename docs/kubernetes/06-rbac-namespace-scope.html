RBAC: Scoping a Namespace-Only User

A worked example: give a user access to one namespace only, why RBAC can't restrict specific nodes, and where SSH/OS access takes over.

Interview Answer — What Is RBAC Namespace Scoping?

RBAC namespace scoping is the practice of granting Kubernetes permissions with a Role and RoleBinding that both live inside one namespace, so the access they grant only applies to objects in that single namespace — not the whole cluster.

RBAC (Role-Based Access Control) is Kubernetes' authorization mechanism: it's the step that decides, once a request is authenticated, whether that identity is allowed to perform the requested verb on the requested resource. Namespace scoping is what lets a single cluster be shared safely by multiple teams or users — a frontend developer can be given full control over the frontend namespace without that access silently extending to backend, kube-system, or any namespace created later.

Mechanically, this is exactly the worked example above: a Role object carries a metadata.namespace field (e.g. namespace: frontend) naming the resources and verbs it allows, and a RoleBinding — also namespaced — links a subject (like the user alice) to that Role. kube-apiserver's RBAC authorizer only consults RoleBindings that live in the namespace a namespaced request is targeting, so a RoleBinding sitting in frontend is never consulted when alice runs kubectl get pods -n backend.

The one caveat worth stating plainly: a namespaced Role/RoleBinding pair grants access in that namespace only — it does not compose across namespaces, and it cannot express cluster-scoped resources like Nodes at all. Reusable or cluster-wide permission sets need a ClusterRole, covered in "Role vs. ClusterRole, RoleBinding vs. ClusterRoleBinding" below.

Simple interview version

"RBAC namespace scoping means the Role and RoleBinding you create both belong to one namespace, so the permissions they grant only apply inside that namespace. kube-apiserver's RBAC authorizer only looks at RoleBindings in the namespace a request targets, so a RoleBinding in `frontend` has no effect on requests against `backend`. If you need the same permissions everywhere, or need to grant access to cluster-scoped resources like Nodes, you reach for a ClusterRole and ClusterRoleBinding instead of duplicating namespaced Roles."

One important interview follow-up

Q: If I create a Role and RoleBinding in the default namespace, does that grant the same access in other namespaces too?

A: No. A Role and its RoleBinding are scoped to the single namespace they're created in — permissions granted in default have zero effect on frontend, backend, or any other namespace, exactly like the worked example above where alice's RoleBinding lives in frontend and her access to backend stays denied by default (RBAC has no implicit "allow everywhere" fallback). To get the same permissions in other namespaces, you have two options: create a separate Role/RoleBinding pair in each namespace, or define one ClusterRole once and bind it per-namespace with ordinary (namespaced) RoleBindings — which grants that ClusterRole's rules only in the namespace each RoleBinding lives in, not cluster-wide. A ClusterRoleBinding is the third option, but it's a different, broader tool: it grants the ClusterRole's permissions in every namespace at once, including ones created later, which is usually more than "the same access in other namespaces" calls for. See "Role vs. ClusterRole, RoleBinding vs. ClusterRoleBinding" for the full comparison table.

Create a User Who Can Access Only Frontend Pods (or Nodes)

The important distinction is:

  • “Frontend pods” and “frontend nodes” are different authorization targets.
  • If you want a user to manage/view pods belonging to the frontend workload, use a namespace/RBAC design.
  • If you literally want the user to access Kubernetes Node objects, that's a different permission.

Also, Kubernetes RBAC does not natively say “this user can access only pods scheduled on these particular nodes.” RBAC primarily controls API resources such as Pods, Deployments, Nodes, etc.

A good design is:

flowchart TD API["Kubernetes API"] --> Auth["Authentication"] Auth --> User["User: alice"] User --> RBACz["RBAC Authorizer"] RBACz --> FE["frontend namespace"] RBACz --> Other["other namespaces"] FE --> Allow["ALLOW"] Other --> Deny["DENY"] Allow --> Res["Pods / Deployments
Services / ConfigMaps
etc."]
flowchart TD Alice["👤 alice"] --> RB["🔗 RoleBinding"] RB --> Role["📜 Role: frontend-user"] Role --> NS["📦 namespace: frontend"] NS --> Pods["Pods ✓"] NS --> Svc["Services ✓"] NS --> Dep["Deployments ✓"] Alice -. denied .-> Other["other namespaces ✗"] Alice -. denied .-> Nodes["Nodes ✗"]

Example: frontend-only user

Create a namespace:

kubectl create namespace frontend

Then create a Role allowing the user to work with frontend resources:

apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  name: frontend-user
  namespace: frontend
rules:
  - apiGroups: [""]
    resources: ["pods", "services", "configmaps"]
    verbs: ["get", "list", "watch"]
  - apiGroups: ["apps"]
    resources: ["deployments", "replicasets"]
    verbs: ["get", "list", "watch"]

Then bind that role to the user:

apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata:
  name: frontend-user-binding
  namespace: frontend
subjects:
  - kind: User
    name: alice
    apiGroup: rbac.authorization.k8s.io
roleRef:
  kind: Role
  name: frontend-user
  apiGroup: rbac.authorization.k8s.io

Now alice can do things like:

kubectl get pods -n frontend
kubectl get deployments -n frontend
kubectl get services -n frontend

but not:

kubectl get pods -n backend
kubectl get secrets -n frontend
kubectl get nodes

assuming there aren't other Roles/ClusterRoles granting her those permissions.

If You Want Her to Access Only the Frontend Nodes

This is different.

Suppose you label nodes:

kubectl label node node-1 workload=frontend
kubectl label node node-2 workload=frontend

and schedule frontend pods onto them using a node selector:

spec:
  nodeSelector:
    workload: frontend

That controls where pods run, but it does not give alice access to those nodes.

For example:

flowchart TD N1["node-1 workload=frontend"] --> N1A["frontend-pod-1"] N1 --> N1B["frontend-pod-2"] N2["node-2 workload=frontend"] --> N2A["frontend-pod-3"] N3["node-3 workload=backend"] --> N3A["backend-pod-1"] N3 --> N3B["backend-pod-2"]

RBAC can give:

flowchart TD Alice2["alice"] --> FE2["frontend namespace"] FE2 --> P["pods ✓"] FE2 --> S["services ✓"] FE2 --> D["deployments ✓"] BE["backend namespace"] --> BEAll["everything ✗"] NodesG["Nodes"] --> NodesAll["everything ✗"]

But if you grant:

resources: ["nodes"]
verbs: ["get", "list"]

the permission is cluster-wide; you can't use an ordinary namespace Role to limit get nodes to only node-1 and node-2.

If “Access Nodes” Means SSH Access

That's outside Kubernetes RBAC.

For example, if you want:

flowchart TD Alice3["alice"] --> S1["SSH → frontend-node-1 ✓"] Alice3 --> S2["SSH → frontend-node-2 ✓"] Alice3 --> S3["SSH → backend-node-1 ✗"]

you need operating-system/cloud/network controls such as:

  • Linux users/groups
  • SSH configuration
  • sudo policy
  • cloud IAM
  • bastion/access gateway
  • firewall/security groups
  • network segmentation

Kubernetes RBAC alone cannot provide that isolation.

Role vs. ClusterRole, RoleBinding vs. ClusterRoleBinding

The Role and RoleBinding used above are namespaced — they only grant access within the frontend namespace. Kubernetes also has cluster-scoped equivalents:

ObjectScopeGrants access to
RoleOne namespaceNamespaced resources (Pods, Services, ConfigMaps, …) in that namespace
ClusterRoleWhole clusterNamespaced resources across every namespace, or cluster-scoped resources (Nodes, PersistentVolumes, Namespaces themselves)
RoleBindingOne namespaceBinds a Role — or even a ClusterRole — to a user/group/ServiceAccount, but only within that one namespace
ClusterRoleBindingWhole clusterBinds a ClusterRole to a user/group/ServiceAccount across every namespace

Binding a ClusterRole with a per-namespace RoleBinding is a common pattern: define one reusable ClusterRole (e.g. a generic "edit" role) and grant it namespace-by-namespace via separate RoleBindings, instead of duplicating the same Role in every namespace.

Built-in Aggregated ClusterRoles

Kubernetes ships four ClusterRoles out of the box:

  • view — read-only access to most objects in a namespace, excluding Secrets and RBAC objects.
  • edit — read/write access to most objects in a namespace, but not Roles/RoleBindings and not resource quotas.
  • admin — full access within a namespace, including managing Roles and RoleBindings inside it, but not the namespace object itself.
  • cluster-admin — full access to every resource in every namespace, plus cluster-scoped resources. Effectively root.

These are aggregated ClusterRoles: other ClusterRoles (including ones you define) can add rules to view/edit/admin automatically by carrying the matching aggregation label, without editing the built-in object directly.

Testing Permissions

Before wiring up a Role — or when debugging why a user's kubectl command fails — check what they're actually allowed to do:

kubectl auth can-i get pods --namespace frontend --as alice
kubectl auth can-i delete deployments --namespace backend --as alice
kubectl auth can-i '*' '*' --as alice

The last form asks whether alice has blanket access to everything — a quick sanity check that she isn't accidentally bound to cluster-admin.

Common RBAC Pitfalls

  • Wildcard verbs/resources (verbs: ["*"], resources: ["*"]) in a custom Role silently grant far more than intended — list exact verbs and resources instead.
  • The default ServiceAccount in every namespace is auto-mounted into every Pod unless automountServiceAccountToken: false is set; binding broad permissions to it exposes that token to any workload in the namespace.
  • A ClusterRoleBinding is easy to reach for when a namespaced RoleBinding would have been enough — it silently widens access to every namespace, including ones created later.
  • RBAC is additive only — there is no explicit “deny” rule. Access is the union of every Role/ClusterRole bound to a user, so removing access means removing bindings, not adding a deny.

Recommended Architecture

For most teams, separate the requirements like this:

RequirementKubernetes mechanism
Identify userAuthentication/OIDC/certificates
Allow frontend API accessRBAC Role
Restrict to frontend namespaceRoleBinding
Restrict specific resourcesRBAC resources
Restrict operationsRBAC verbs
Restrict pod placementNode labels + affinity/nodeSelector
Restrict access to physical/VM nodesOS/cloud IAM/network controls
Prevent dangerous objectsAdmission controls
Store cluster stateetcd

A requirement like “create a developer account that can deploy and troubleshoot only the frontend application, while having zero access to backend workloads, secrets, and nodes” maps directly onto the Authentication → Role → RoleBinding → namespace → Deployment chain described above.
