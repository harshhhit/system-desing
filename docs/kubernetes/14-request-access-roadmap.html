Request & Access Flow Roadmap

A concept-first map of how a request reaches the Kubernetes API and clears authentication, authorization, and admission control before it's allowed to change cluster state. Tick each stage as you cover it; progress is saved in this browser.

A concept-first map of how a single request — a kubectl command, a controller's API call, anything — reaches the Kubernetes API server and gets cleared to actually change cluster state. Every request, no matter who sends it, walks the same sequential pipeline: prove who you are, prove you're allowed to do this, survive admission control, then get validated and persisted. Follow top to bottom — each stage assumes the one before it. Tick a stage's box once you've genuinely covered it; progress is saved in this browser.

Stage 0 — The Big Picture: One Pipeline, Every Request

The kube-apiserver is the only component that talks to etcd, and it is the single front door for every request in the cluster — whether that request comes from a human running kubectl, a CI pipeline, a controller reconciling desired state, or kubelet reporting node status. Every one of those requests, without exception, passes through the same sequential pipeline before it's allowed to touch anything:

flowchart TD A["Request arrives
(kubectl / controller / kubelet / …)"] --> B["Authentication
Who are you?"] B --> C["Authorization
Are you allowed to do this?"] C --> D["Admission Control
Should this specific change be allowed?"] D --> E["API validation
Is the object well-formed?"] E --> F["etcd
Persist the new state"]

Why it matters that this is a strict, sequential pipeline rather than one big permission check: each stage answers a different question and fails independently. An expired certificate fails at Authentication with an HTTP 401, before Kubernetes has even considered what you were trying to do. A validly-authenticated user asking for something they don't have a Role for fails at Authorization with an HTTP 403, before any object is inspected. A well-authorized request for a Pod that violates a resource quota fails at Admission Control, after Kubernetes already knows who you are and that you're generally allowed to create Pods. Knowing which stage rejected a request is usually enough to know what to fix.

  • Read requests (get, list, watch) still pass through Authentication and Authorization, but skip Admission Control — admission only acts on requests that create, modify, delete, or proxy an object.
  • Write requests (create, update, patch, delete) pass through all four gates before the API server ever writes to etcd.

This roadmap is a checklist framing of three existing deep-dive pages, not a replacement for them: 05. API Request Flow walks a concrete kubectl call through this pipeline end to end, 06. RBAC: Namespace Scoping works through a real namespace-restricted user, and 10. API Request Lifecycle: The Four Gates gives the short diagram-only version of Stages 1, 2, 4, and etcd below.

Stage 1 — Authentication: Who Are You?

Authentication answers exactly one question — which identity is making this request? Kubernetes does not store "user" objects the way it stores Pods or Deployments; a normal user is just a name that some external system (a certificate authority, an identity provider) vouches for. The API server runs its configured authenticator modules in sequence, and the first one that successfully authenticates the request wins — the rest are skipped. If none of them succeed, the request fails immediately with HTTP 401 and never reaches Authorization.

MethodHow identity is establishedTypical use
X.509 client certificatesClient presents a certificate signed by the cluster's CA; the username comes from the certificate's CN (subject Common Name) and groups from its O fields.Admin/operator access, kubectl via kubeconfig.
Bearer tokens (static/bootstrap)An opaque token string sent in the Authorization: Bearer <token> header, matched against a configured token file.Simple setups, cluster bootstrap.
Service account tokens (JWT)A JSON Web Token, automatically mounted into every Pod as a Secret/projected volume, identifying the Pod as a specific ServiceAccount.In-cluster processes (controllers, apps) calling the API server from inside a Pod.
OIDC tokensA JWT issued by an external OpenID Connect provider (e.g. your company SSO), verified against that provider's public keys.Human users authenticating with existing corporate identity.
Webhook token authenticationThe API server delegates the token-validity check to an external HTTP service instead of validating it itself.Integrating a custom or third-party identity system.
Anonymous / unauthenticatedIf no method succeeds and anonymous auth is enabled, the request is attributed to system:anonymous in the system:unauthenticated group instead of being rejected outright.Usually disabled in production (--anonymous-auth=false).

On success, the request carries a fixed bundle of attributes into every later stage: a username, a UID, a list of groups (every authenticated identity is also automatically added to system:authenticated), and optional extra fields. Authorization in Stage 2 never re-derives identity — it only ever consumes this bundle.

Concrete worked example of a service-account token authenticating an in-cluster client, and of a client certificate authenticating kubectl, in 05. API Request Flow.

Stage 2 — Authorization: Can You Do This?

Authorization takes the identity Stage 1 established and answers a second, separate question — is this specific identity allowed to perform this specific action on this specific object? A request only reaches this stage already knowing who is asking; it still has to earn the right to act. Kubernetes evaluates every configured authorization module in sequence against the request's attributes (user, group, verb, resource, namespace, API group, subresource):

  • If any module explicitly allows the request, it proceeds immediately — later modules are not consulted.
  • If any module explicitly denies it, the request is rejected immediately with HTTP 403.
  • If every module has no opinion, the request is denied by default — access is deny-by-default, not allow-by-default.
ModeWhat it does
RBACGrants permissions via Roles/ClusterRoles bound to users, groups, or ServiceAccounts. The modern default — see Stage 3.
ABACAttribute-based rules in a static policy file evaluated per-request (e.g. "user bob can read pods in namespace projectCaribou"). Largely superseded by RBAC — inflexible to update without restarting the API server.
NodeA special-purpose authorizer that grants each kubelet permission only for the API objects it needs for the Node it runs on (its own Pods, Secrets, ConfigMaps, etc.) — the mechanism that stops one compromised kubelet from reading every Secret in the cluster.
WebhookDelegates the allow/deny decision to an external HTTP service, for integrating a custom policy engine.
AlwaysAllow / AlwaysDenyTrivial modules that allow or deny everything — testing only, never production.

A production cluster commonly configures more than one mode together, e.g. --authorization-mode=Node,RBAC — Node handles kubelet's own narrow needs, RBAC handles everyone and everything else. One caveat worth stating plainly: identities in the system:masters group bypass authorization entirely and are treated as full cluster admins — that group should never be handed out casually.

RBAC is covered as its own stage next because it's the mode almost every real cluster actually runs, and because "namespace scoping" — restricting a user to one namespace — is entirely an RBAC-shaped answer to this stage's question.

Stage 3 — RBAC Mechanics: Namespace vs. Cluster Scope

RBAC grants permissions through two pairs of objects that differ only in scope. Getting the scope of each one right is the entire game — the most common real-world RBAC mistake is reaching for the cluster-wide pair when the namespaced pair would have been enough, silently widening access to every namespace including ones created later.

ObjectScopeWhat it does
RoleOne namespaceDefines a set of permission rules (apiGroups + resources + verbs) that only apply inside the namespace it's created in.
ClusterRoleWhole clusterThe same kind of rules, but not tied to a namespace — can grant access to cluster-scoped resources (Nodes, PersistentVolumes, Namespaces themselves) or to a namespaced resource across every namespace at once.
RoleBindingOne namespaceAttaches a Role — or even a ClusterRole — to a user/group/ServiceAccount, but the grant only takes effect within that one namespace.
ClusterRoleBindingWhole clusterAttaches a ClusterRole to a subject across every namespace, with no boundary.

A rule inside a Role or ClusterRole is always the same three-part shape:

rules:
- apiGroups: [""]                     # "" = the core API group
  resources: ["pods"]
  verbs: ["get", "list", "watch"]

apiGroups picks the API family the resource belongs to, resources picks the resource type within it, and verbs picks the allowed actions (get/list/watch/create/update/patch/delete/deletecollection). RBAC rules are purely additive — there is no "deny" rule type. A subject's effective permissions are the union of every Role/ClusterRole bound to it, so revoking access means removing a binding, never adding a negative rule.

flowchart TD Alice["👤 alice"] --> RB["RoleBinding
(namespace: frontend)"] RB --> Role["Role: frontend-user
(namespace: frontend)"] Role --> Allowed["Pods / Services / Deployments
— frontend namespace only"] Bob["👤 bob"] --> CRB["ClusterRoleBinding"] CRB --> CRole["ClusterRole: viewer"] CRole --> AllowedAll["Same resources —
every namespace"]

Binding a ClusterRole with a per-namespace RoleBinding is a common, deliberate pattern — define one reusable ClusterRole (e.g. a generic "edit" role) once, then grant it namespace-by-namespace via separate RoleBindings, instead of duplicating an identical Role in every namespace. Kubernetes also ships four built-in aggregated ClusterRoles — view, edit, admin, and cluster-admin — of increasing scope, the last of which is effectively root.

Full worked example — creating a namespace, a Role, a RoleBinding, testing the result with kubectl auth can-i, and the common pitfalls (wildcard rules, the auto-mounted default ServiceAccount, reaching for ClusterRoleBinding too eagerly) — in 06. RBAC: Namespace Scoping.

Stage 4 — Admission Control: Should This Change Be Allowed?

By the time a request reaches Admission Control, Kubernetes already knows who's asking (Stage 1) and that they're generally permitted to do this kind of thing (Stages 2–3). Admission control asks a narrower, more specific question: should this particular object, exactly as submitted, be allowed to exist? It runs only on write operations (create, update, delete, connect) — never on reads — and it sits after authorization but before the object is validated and persisted to etcd.

flowchart LR Authn["Authentication"] --> Authz["Authorization"] Authz --> M["Mutating admission
(may rewrite the object)"] M --> V["Validating admission
(accept or reject, no changes)"] V --> Persist["API validation → etcd"]

Admission runs in two ordered phases, and the order is deliberate — anything mutation adds must still pass validation afterward:

  • Mutating admission controllers/webhooks run first and can rewrite the incoming object — inject a sidecar container, set a default StorageClass, stamp on a label, apply a default resource request. Examples: MutatingAdmissionWebhook, the ServiceAccount controller, DefaultStorageClass.
  • Validating admission controllers/webhooks run second, see the already-mutated object, and can only accept or reject it — never change it further. Examples: ResourceQuota (rejects if a namespace's aggregate limits would be exceeded), LimitRanger (enforces min/max per-object resource constraints), PodSecurity (enforces Pod Security Standards), ValidatingAdmissionWebhook.

Any single rejection at either phase fails the whole request immediately — admission controllers are evaluated in a chain, and one "no" is final. This is also the layer that makes custom policy enforcement possible without forking Kubernetes itself: writing your own mutating or validating webhook (or, on newer clusters, a declarative CEL-based ValidatingAdmissionPolicy / MutatingAdmissionPolicy) is the standard extension point for organization-specific rules that RBAC has no vocabulary for — RBAC can say "alice may create Pods," but only admission control can say "no Pod may run as root" or "every Pod must carry a team label."

This is the same admission layer referenced from the RBAC page's "Recommended Architecture" table — 06. RBAC: Namespace Scoping — as the mechanism for "prevent dangerous objects," a job RBAC's identity/verb model was never meant to do.

Stage 5 — The Full Request Lifecycle, End to End

Putting all four gates together against one concrete request — kubectl create -f pod.yaml -n frontend — makes the sequencing and the short-circuit behavior of each stage concrete:

sequenceDiagram participant U as kubectl participant A as kube-apiserver participant E as etcd U->>A: POST /pods (namespace=frontend) A->>A: Authenticate — client cert → user "alice" (401 if it fails) A->>A: Authorize — RBAC checks alice can create pods in frontend (403 if denied) A->>A: Mutating admission — inject defaults/sidecars A->>A: Validating admission — enforce quotas/policy (rejected if it fails) A->>A: API validation — schema/object rules A->>E: Persist Pod object E-->>A: Ack A-->>U: 201 Created

Two details worth stating plainly, because they're easy to blur together:

  • A read request (kubectl get pods -n frontend) walks Authentication and Authorization exactly the same way, but skips Admission Control entirely and returns the current state straight from the API server — no etcd write, and for a --watch, no per-request etcd read either (served from the API server's in-memory watch cache instead).
  • Rejection at any gate is final and immediate — a request that fails Authentication never reaches Authorization; a request that fails Authorization never reaches Admission Control. There's no partial credit and no fallback to a "looser" stage.

The full step-by-step walkthrough of this exact example — including the List+Watch pattern controllers use to stay in sync after the write lands — lives in 05. API Request Flow; the condensed four-box version of just this diagram lives in 10. API Request Lifecycle: The Four Gates.

Suggested Learning Order

  1. Stage 0 (the big picture) — get the shape of the pipeline fixed first; every later stage is "zoom in on one box" from this diagram.
  2. Stage 1–2 (Authentication, Authorization) — the two questions every request must clear before Kubernetes even looks at what it's asking for: who are you, and are you generally allowed to do this.
  3. Stage 3 (RBAC mechanics) — once Authorization's shape makes sense, go deep on the mode that actually matters day to day: Role vs. ClusterRole, RoleBinding vs. ClusterRoleBinding.
  4. Stage 4 (Admission Control) — the layer that catches everything RBAC's identity/verb model structurally can't express.
  5. Stage 5 (full lifecycle) — put it all back together against one real request, then read the three linked deep-dive pages for the parts you want more detail on.

Each stage answers a why before a how — that's intentional. See also Control Plane Overview for where the API server sits relative to etcd, the scheduler, and the controller manager.
