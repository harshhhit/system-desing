Workload Config & Storage Roadmap

A concept-first map of how workloads get configuration and storage without baking either into the container image — Volumes, PersistentVolumeClaims, ConfigMaps, and Secrets. Tick each stage as you cover it; progress is saved in this browser.

A concept-first map of how a workload gets its configuration and its storage without either one being baked into the container image: plain Volumes, the PersistentVolume/PersistentVolumeClaim supply-and-demand model, StorageClass-driven dynamic provisioning, ConfigMap and Secret, and finally how the worker-node data plane actually turns all of that into files inside a running container. Stage 0 — Why Config & Storage Can't Live in the Image

A container image is meant to be an immutable, portable artifact: the same built image should run unmodified in dev, staging, and production. If a database hostname, a feature flag, or an API key is baked into that image, then every environment needs its own image — and every configuration change means rebuilding, re-pushing, and redeploying an image just to flip one value. This is the same idea the twelve-factor app methodology calls "config" as a first-class concern, kept strictly out of the codebase and out of the build artifact.

Without externalized configuration, teams end up with:

  • One image per environment, multiplying build/CI work and drifting out of sync over time.
  • Secrets (passwords, API keys, certificates) sitting in source control or inside image layers, where anyone who can pull the image can read them.
  • No way to change a runtime value without a full rebuild-and-redeploy cycle.

Storage has the same root problem in a different shape: a container's own filesystem is tied to that one container's lifetime. Kubernetes' answer to both problems is to keep configuration, secrets, and storage as separate API objects that get attached to a Pod at runtime — the image itself never needs to know its environment's specific values or where its data physically lives. Stages 1–4 below are exactly those separate objects; Stage 5 is how they actually land inside the running container.

(code only)"] -->|"+ Volume / PVC"| Pod["Running Pod"] Img -->|"+ ConfigMap"| Pod Img -->|"+ Secret"| Pod

The image stays identical across environments; only what gets attached to the Pod at deploy time changes.

Stage 1 — Volumes: Ephemeral vs. Persistent

A Volume in Kubernetes is, at its core, a directory that containers in a Pod can access through the filesystem — but unlike a container's own writable layer, a Volume's data survives a container restart within the same Pod. That distinction exists because a plain container filesystem is ephemeral: if the container crashes and is restarted, it comes back with a clean filesystem and everything it wrote is gone. A Volume attached to the Pod fixes exactly that, for as long as the Pod that owns it is alive.

Kubernetes splits Volumes into two lifecycles:

  • Ephemeral volumes (e.g. emptyDir) exist only as long as the Pod exists — created when the Pod is created, destroyed when the Pod is deleted. Useful as scratch space or for sharing files between containers in the same Pod, but not for data that must outlive the Pod.
  • Persistent volumes (backed by a persistentVolumeClaim volume type) outlive the individual Pod — the underlying storage keeps existing even after that Pod is deleted, which is what Stage 2 is built around.

Why a plain Volume isn't enough on its own: it is still declared inline inside the Pod spec and its lifecycle is still tied to that Pod object being deleted or recreated by hand. A database, a queue, or any workload that must not lose data across a Pod being rescheduled to a different Node needs storage whose lifecycle is decoupled from any one Pod — that's exactly the gap PersistentVolumes and PersistentVolumeClaims close in Stage 2. Both configMap and secret (Stage 4) are themselves just other Volume types under this same mechanism — they get mounted into a container exactly like any other volume, just sourced from a ConfigMap/Secret object instead of disk.

flowchart TD subgraph Pod["Pod"] C1["Container A"] C2["Container B"] V["emptyDir volume
(scratch / shared space)"] C1 --- V C2 --- V end Pod -->|"Pod deleted"| Gone["Volume data destroyed with it"]

An emptyDir is perfect for sharing files between two containers in one Pod — but it dies the moment the Pod does.

Stage 2 — PersistentVolume & PersistentVolumeClaim

A PersistentVolume (PV) is a piece of storage in the cluster that has been provisioned, and it exists as a Kubernetes API object independently of any Pod that might use it. A PersistentVolumeClaim (PVC) is a request for storage made by a user or an application — it asks for a certain amount of space and certain access characteristics, without needing to know which physical disk will back it. This is deliberately a supply-and-demand model: PVs are the supply (provisioned by an administrator or dynamically, see Stage 3), and PVCs are the demand (declared by whoever is deploying the workload). A Pod never talks to a PV directly — it always goes through a PVC.

The binding lifecycle has four stages:

  1. Provisioning — a PV is created, either statically by an administrator ahead of time, or dynamically on demand from a StorageClass when no static PV matches a new PVC (Stage 3).
  2. Binding — a control loop in the control plane watches for new PVCs, finds a PV that satisfies its request, and binds the two together exclusively via a bidirectional claimRef — one PVC to exactly one PV.
  3. Using — a Pod references the PVC (not the PV) in its volumes block; Kubernetes resolves that to the bound PV and mounts it into the Pod.
  4. Reclaiming — once the PVC is deleted, the PV's reclaim policy decides what happens next.
flowchart LR Pod["Pod"] --> PVC["PersistentVolumeClaim
(demand: how much, what mode)"] PVC -->|bound 1:1| PV["PersistentVolume
(supply: real storage)"] PV --> Disk[("Physical / cloud disk")]

Access modes describe how a PV can be mounted at once:

Access modeMeaning
ReadWriteOnce (RWO)Mounted read-write by a single node at a time.
ReadOnlyMany (ROX)Mounted read-only by many nodes simultaneously.
ReadWriteMany (RWX)Mounted read-write by many nodes simultaneously — needs storage that supports it (e.g. NFS), not all backends do.
ReadWriteOncePod (RWOP)Mounted read-write by a single Pod in the whole cluster, a stricter, newer mode for cases where even a second Pod on the same node must be prevented from mounting it.

Reclaim policies decide what happens to the PV once its PVC is deleted:

PolicyWhat happens
RetainThe PV and its data are kept for manual cleanup — nothing is deleted automatically. Default for manually created PVs.
DeleteThe underlying storage asset (e.g. an EBS volume) is deleted along with the PV. Default for dynamically provisioned volumes.
RecycleDeprecated: performs a basic scrub (rm -rf-style) and makes the volume available again. Dynamic provisioning (Stage 3) is the recommended replacement approach.

See Persistent Storage & Distributed DBs for why a distributed database typically gets one PV/PVC pair per instance rather than one shared volume, and how a StatefulSet's volumeClaimTemplates automates that.

Stage 3 — StorageClass & Dynamic Provisioning

Statically pre-provisioning PVs — an administrator creating each one by hand ahead of time — does not scale. Every new workload that needs storage would require someone to first go create a matching PV with the right size and backend before the PVC could ever bind. A StorageClass removes that manual step: it's an API object that describes a class of storage (which provisioner to use, what parameters to pass it, its reclaim policy) so that a PV can be created automatically, on demand, the moment a PVC asks for that class.

  • provisioner — which plugin/CSI driver actually creates the storage (e.g. an AWS EBS CSI driver, a GCE persistent disk provisioner).
  • parameters — provisioner-specific settings, such as disk type or IOPS tier.
  • reclaimPolicy — same meaning as on a PV (Stage 2); a StorageClass sets the default for volumes it dynamically creates.
  • volumeBindingMode — Immediate provisions as soon as the PVC is created, while WaitForFirstConsumer delays provisioning until a Pod using the PVC is actually scheduled, so the volume can be created in the right zone/node topology.

With dynamic provisioning, a PVC that names a StorageClass (or relies on the cluster's default one) never needs a pre-existing PV at all — the provisioner named in that StorageClass creates one automatically, sized and configured per the PVC's request, and the ordinary binding flow from Stage 2 continues from there.

flowchart TD PVC["New PVC
(requests a StorageClass)"] --> SC["StorageClass
(provisioner + parameters)"] SC -->|"provisions on demand"| PV["New PersistentVolume"] PV -->|bound| PVC

Static provisioning still has a place — e.g. pre-existing storage an admin wants to hand out deliberately — but dynamic provisioning via StorageClass is the default path on virtually every cloud-hosted cluster today.

Stage 4 — ConfigMap & Secret

Stages 1–3 solve storage; this stage solves the other half of Stage 0's motivation — configuration and sensitive values. A ConfigMap holds non-confidential configuration as key-value pairs (database paths, feature flags, log levels). A Secret holds the same shape of data but is meant for confidential values — passwords, API keys, tokens, certificates. Kubernetes treats them as distinct object kinds specifically so that access-control and handling can differ: Secrets get tighter default handling (e.g. volume-mounted Secrets use an in-memory tmpfs, never written to the node's disk), while ConfigMaps carry no such assumption.

Both are consumed by a Pod the same two ways:

  • Environment variables — values are injected into the container's environment at startup. Simple and universally supported, but the values are read once at process start: updating the ConfigMap/Secret does not change a running container's environment — the Pod must be restarted.
  • Volume mount — each key becomes a file in a mounted directory. Kubernetes refreshes the files on disk automatically when the source object changes, with no Pod restart required — but whether the running application notices and reloads that file is entirely up to the application itself.

Base64 is encoding, not encryption. A Secret's data field is Base64 text, which is trivially reversible by anyone who can read it — it is not a security control by itself. Kubernetes Secrets are stored unencrypted in etcd by default, and anyone with API access to read Secrets in a namespace, or direct access to etcd, can read their plaintext values; anyone allowed to create a Pod in that namespace can also read any Secret available to it. Real protection comes from enabling encryption at rest for the API server's etcd store, tight RBAC on who can read Secret objects, and — for higher-sensitivity data — an external secret manager such as HashiCorp Vault or AWS Secrets Manager instead of relying on Secret objects alone.

flowchart TD CM["ConfigMap
non-sensitive"] -->|env var or volume mount| Pod["Pod"] Sec["Secret
sensitive, Base64-encoded only"] -->|env var or tmpfs volume mount| Pod Pod --> App["Application"]

See ConfigMap & Secret for the full env-var-vs-volume tradeoff table and why many teams trigger a rollout after a ConfigMap/Secret change instead of trusting an in-place reload.

Stage 5 — How the Data Plane Actually Mounts All of This

Every object above (Volume, PV/PVC, ConfigMap, Secret) is just an API record until something on the worker node turns it into real files a container process can open. That "something" is the kubelet, working with the container runtime (via the CRI) and, for persistent storage specifically, a CSI (Container Storage Interface) driver:

  • Kubelet reads the Pod spec assigned to its Node and sees which volumes, ConfigMaps, and Secrets it declares.
  • For a ConfigMap/Secret volume, kubelet materializes the keys as files in a directory on the node (Secrets specifically under tmpfs, i.e. RAM-backed, never touching disk).
  • For a PVC-backed volume, kubelet calls the CSI driver named by the PV's provisioner, which attaches the real remote disk (e.g. an EBS volume) to the Node and mounts it to a plugin directory on the host filesystem.
  • The container runtime, invoked through the CRI, then bind-mounts that host path into the container's own filesystem namespace at the path given in the Pod's volumeMounts — the container sees an ordinary directory/file, with no awareness that it came from a ConfigMap, a Secret, or a cloud disk.

This is why a container never needs any Kubernetes-specific code to read its configuration or write its data: from inside the container, a Secret-backed file and a PVC-backed data directory both just look like paths on the local filesystem — the translation from "Kubernetes object" to "mounted path" is entirely the data plane's job, not the application's.

sequenceDiagram participant K as Kubelet participant CSI as CSI driver participant CRI as Container runtime (CRI) participant C as Container K->>CSI: Attach & mount PVC's disk to Node CSI-->>K: Disk mounted at host path K->>K: Materialize ConfigMap/Secret keys as files K->>CRI: Start container with volumeMounts CRI->>C: Bind-mount host paths into container filesystem C->>C: Reads config/secret/data as ordinary files

See Data Plane Deep Dive for the full kubelet / CRI / CNI / CSI / kube-proxy picture, including the CSI-driver step in a live end-to-end walkthrough.

Suggested Learning Order

  1. Stage 0 (why this separation exists) — the motivation that makes every later stage feel necessary instead of arbitrary API surface.
  2. Stage 1 (Volumes) — the base primitive; understand ephemeral-vs-persistent before anything else clicks.
  3. Stage 2–3 (PV/PVC, then StorageClass) — the supply/demand model first as a static picture, then how it's automated at scale via dynamic provisioning.
  4. Stage 4 (ConfigMap & Secret) — the configuration half; pairs naturally with Stage 1 since both are "just another volume type" mechanically.
  5. Stage 5 (the data plane) — ties everything together into one mechanism once the individual objects make sense on their own.

Each stage answers a why before a how — that's intentional. Once this checklist feels solid, the three deep-dive pages linked throughout (Persistent Storage & Distributed DBs, ConfigMap & Secret, Data Plane Deep Dive) go considerably further into each piece.
