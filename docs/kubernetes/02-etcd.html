etcd Deep Dive

Kubernetes' distributed key-value store and single source of truth for cluster state.

Interview Answer — What Is etcd?

etcd is a distributed, consistent key-value database used by Kubernetes to store the cluster's state and configuration.

In Kubernetes, etcd acts as the persistent source of truth for the control plane. It stores information such as Pods, Deployments, Services, ConfigMaps, Secrets, Nodes, namespaces, RBAC objects, and the desired state of the cluster.

When you create or modify a Kubernetes resource using kubectl, the request goes to the API Server, and the API Server persists the relevant state into etcd. Other control-plane components such as the Scheduler and Controllers observe changes through the API Server and take actions to make the actual cluster state match the desired state stored in Kubernetes.

etcd is designed to provide strong consistency and high availability using the Raft consensus algorithm. In a production cluster, etcd commonly runs with multiple members so that the cluster can continue operating if one member fails.

One important point is that etcd is not a complete history database of everything that has happened in Kubernetes. It primarily stores the current Kubernetes state; etcd does maintain revisions of key changes internally for consistency, watches, and limited historical reads, but Kubernetes audit logs and application/control-plane logs are what you use when you need a longer-term record of what happened.

Simple interview version

"etcd is a distributed, strongly consistent key-value store used by Kubernetes as the source of truth for cluster state. The Kubernetes API Server stores resources such as Pods, Deployments, Services, Secrets, and ConfigMaps in etcd. Controllers and the Scheduler use the API Server to observe that state and continuously reconcile the actual cluster with the desired state. etcd uses the Raft consensus algorithm to provide consistency and high availability."

One important interview follow-up

Q: Does etcd store the entire history of the Kubernetes cluster?

A: No. etcd stores the current value of each Kubernetes object, not a permanent log of every value it has ever had — if a Deployment's replica count changed from 2 to 4 to 6, etcd only holds 6. Internally, etcd uses MVCC and assigns each write a monotonically increasing revision, so it can serve slightly-old reads for a while, but production clusters run periodic compaction that permanently discards old revisions to keep the data store bounded — so that revision history is short-lived, not an audit trail. If you need to know who changed what and when, or want a durable history, reach for Kubernetes Audit Logs, the old ReplicaSets a Deployment retains for rollbacks, or your own GitOps history — not etcd. See "Does etcd Store the Entire History From Start to End?" below for the full breakdown.

What Is It?

etcd is Kubernetes' distributed key-value database. It stores the entire cluster state.

Think of it as the source of truth.

Kubernetes is a desired-state system: when you create or modify an object — a Deployment, Service, ConfigMap, Secret, or raw Pod spec — the API Server needs somewhere durable to persist that object so the cluster still knows about it after any component restarts. That "somewhere" is etcd. The API Server does not keep the cluster's state in its own process memory; if it did, an API Server restart would forget every object that existed before the restart. Instead the API Server is a gateway, and etcd is the persistent storage behind it — a distinction worth naming explicitly, since it's easy to think of the API Server itself as "where Kubernetes lives":

flowchart TD K["kubectl"] --> A["API Server"] A --> AUTH["Authentication"] AUTH --> AUTHZ["Authorization"] AUTHZ --> V["Admission & Validation"] V --> E[("etcd")] E --> S["Persistent Kubernetes state"]

The API Server never writes to disk itself and never trusts an in-memory cache as the source of truth — every write that must survive a restart goes through etcd first.

What Is Stored?

  • Pods
  • Deployments
  • ConfigMaps
  • Secrets
  • Services
  • Nodes
  • Namespaces
  • RBAC Rules

Everything Kubernetes knows is stored in etcd.

Concretely, Kubernetes objects are stored as keys under a /registry/ prefix, one key per object, namespaced where the object itself is namespaced:

/registry/pods/default/my-app-7c9f8d-abcde
/registry/deployments/default/my-app
/registry/services/default/my-app-svc
/registry/secrets/default/db-password
/registry/configmaps/default/app-config

You normally never touch these keys yourself — kubectl get pod my-app goes through the API Server, which knows how to translate the request into the right etcd key and deserialize the value back into a Pod object. Reading or writing etcd directly (with etcdctl) bypasses authentication, authorization, and admission control entirely, which is exactly why production clusters lock down direct etcd access to the control plane's own certificates.

Example

Deployment created:

replicas: 3

Stored in etcd:

Desired Replicas = 3

Controllers continuously compare:

Desired State
vs
Actual State

using data from etcd.

Why It Exists

Kubernetes is a declarative system. The cluster must remember: What should exist?

etcd stores that desired state.

That single fact — "the desired state lives in etcd" — is what lets every other control-plane component behave the way it does. Controllers don't push changes at the workload directly; they run a continuous loop that reads the desired state out of etcd (via the API Server), compares it against what's actually running, and acts only on the difference:

flowchart LR D[("Desired state
in etcd")] --> C["Controller reads state"] C --> CMP{"Desired == Actual?"} CMP -- no --> ACT["Take action to reconcile"] ACT --> ACTUAL["Actual cluster state"] ACTUAL --> C CMP -- yes --> WAIT["Idle / watch for changes"] WAIT --> C

For example, if a Deployment's etcd record says replicas: 3 but only 2 Pods are currently running (one node crashed), the ReplicaSet controller notices the gap on its next reconciliation pass and creates one more Pod. It does not need to be told "a node crashed" — it only ever asks "does actual state match the etcd record?", which is what makes the reconciliation loop resilient to almost any kind of failure: the controller doesn't need a special code path per failure type, just the same compare-and-act loop every time.

Does etcd Store the Entire History From Start to End?

Not in the way it's easy to assume. This is one of the most common misconceptions about etcd, and the distinction matters for anyone reasoning about backups, audits, or "what changed."

etcd is not an unlimited historical log of every state the cluster has ever been in. If a Deployment's replica count changes three times —

Version 1: replicas = 2
Version 2: replicas = 4
Version 3: replicas = 6

— the Kubernetes object stored in etcd holds only the current value, replicas = 6. Kubernetes does not rely on etcd to keep an infinite audit trail of every prior value forever.

MVCC: etcd does keep short-lived revisions

Here's the part that makes the picture more interesting: etcd internally uses MVCC (Multi-Version Concurrency Control). Every write to a key is assigned a monotonically increasing revision number, and etcd can serve reads "as of" an old revision for a while after the write that produced it:

flowchart LR R100["Revision 100
replicas = 2"] --> R101["Revision 101
replicas = 4"] R101 --> R102["Revision 102
replicas = 6 (current)"] R102 -.-> COMPACT["Compaction"] COMPACT --> GONE["Revisions 100-101
discarded"]

This is why etcd feels like it has "history" — for a while, it genuinely does. But that history is not permanent: etcd supports (and production clusters schedule) compaction, which discards old revisions below a chosen point to keep the data file from growing without bound. Once a revision is compacted, it is gone — there is no way to read "what replicas was set to at revision 100" afterward. This is the same compaction mentioned under "Operating etcd" below; skip it and etcd's storage grows until it hits its quota and refuses writes.

So the accurate mental model is: etcd is a strongly consistent store of current state, with versioned revisions available for a limited window — not an unlimited event-history database. If you need "what was this object's value an hour ago," don't reach for etcd; reach for one of the mechanisms below.

Where Kubernetes' Other Kinds of "History" Actually Live

Several different Kubernetes concepts get lumped together as "history." They're easy to confuse because they all answer some version of "what changed," but each is a distinct mechanism with a distinct storage location — naming them side by side avoids the mix-up:

Question you're actually askingWhere the answer lives
"What revision is this object on right now?" (used for optimistic concurrency — an update fails if resourceVersion is stale)Object metadata: resourceVersion, generation, uid, creationTimestamp — stored with the current object, not a separate log
"What did this Deployment look like before the last few rollouts, and can I roll back?"Old ReplicaSets that the Deployment keeps around (bounded by spec.revisionHistoryLimit, default 10) — a Kubernetes-level mechanism, not an etcd feature
"Who ran kubectl delete on this Secret, and when?"Kubernetes Audit Logs — a dedicated API Server feature that records every request (who, what verb, what resource, when, from where), written to its own log sink
flowchart TD Q["What changed?"] --> Q1["Concurrency check"] Q --> Q2["Rollout history"] Q --> Q3["Who did it, and when"] Q1 --> A1["resourceVersion / generation
(on the object itself)"] Q2 --> A2["Old ReplicaSets
kept by the Deployment"] Q3 --> A3["Kubernetes Audit Log
(separate log sink)"]

None of these three routes through etcd's MVCC revisions as their primary interface — the Deployment rollout history is itself just more current-state objects (old ReplicaSets), and audit logs are written by the API Server as a side effect of handling a request, independent of what etcd does with the revision internally.

etcd vs. Application Logs, Metrics, and Traces

etcd stores Kubernetes API objects — it does not store application stdout, HTTP access logs, CPU/memory metrics, or distributed traces. This distinction matters because "where do I look when something's wrong" depends entirely on which of these you're debugging:

flowchart LR subgraph CP["Control Plane State"] E[("etcd")] end subgraph AL["Application Logs"] L["Loki / Elasticsearch / CloudWatch Logs"] end subgraph MT["Metrics"] M["Prometheus / CloudWatch Metrics"] end subgraph TR["Traces"] T["Jaeger / Tempo / OpenTelemetry"] end

If a Pod is crash-looping, etcd can tell you the Pod's spec and the last-observed status the kubelet reported back — it cannot tell you why the container exited, because that's in the container's stdout/stderr, which lives in your logging stack, not etcd.

How etcd Achieves Consensus (Raft)

etcd is distributed across several members and uses the Raft consensus algorithm to keep them in agreement:

  • One member is elected leader; all writes go through it. The leader replicates each write to the other members as a log entry.
  • A write is only acknowledged once a majority (quorum) of members have persisted it — not just the leader — which is what makes etcd survive a member crashing without losing data.
  • A cluster of N members tolerates the loss of up to (N-1)/2 members while still having a quorum. That's why clusters use odd sizes — typically 3 or 5: a 3-member cluster tolerates 1 failure, a 5-member cluster tolerates 2, and adding an even-numbered member (e.g. going from 3 to 4) raises cost without raising fault tolerance.
  • If the leader fails, the remaining members hold a new election and pick a new leader before accepting writes again.
flowchart TD L["👑 Leader"] -- replicate write --> F1["Follower 1"] L -- replicate write --> F2["Follower 2"] F1 -- ack --> L F2 -- ack --> L L -- majority acked --> Done["✅ Write Committed"]

Why Not Just Use a Normal Database?

The control plane needs strong consistency because the API Server, the Scheduler, and every controller must all act on the same view of cluster state — not "eventually the same," but the same right now. A database that only offers eventual consistency (many NoSQL stores optimized for availability over consistency) would let two control-plane components briefly disagree about a fact as basic as how many replicas a Deployment wants.

Concretely: if the Scheduler believes replicas = 3 while a controller (reading a stale replica) believes replicas = 7, the two components make conflicting decisions — the Scheduler stops placing Pods while the controller keeps creating them — and the cluster oscillates until the inconsistency resolves. etcd's Raft-based consensus (described above) is what rules this out: a write is only visible as committed once a quorum agrees on it, so any component reading committed state reads the same value every other component would read at that moment.

Why etcd Is So Critical

Losing worker nodes is usually recoverable — Kubernetes can reschedule the workloads that were running there onto healthy nodes, because the desired state for those workloads still exists. Losing etcd's data permanently, with no usable backup, is a different category of failure: the control plane no longer knows what Deployments, Services, Secrets, or RBAC rules were supposed to exist in the first place. There's nothing left to reconcile toward.

That's why production Kubernetes treats etcd as critical infrastructure, but who is responsible for it depends on how the cluster is run — worth naming explicitly since it changes what you're on the hook for operationally:

flowchart TD subgraph SM["Self-managed cluster (e.g. kubeadm)"] A1["API Server"] --- SC1["Scheduler"] --- CM1["Controller Manager"] --- E1[("etcd - you back it up,
you monitor it, you own it")] end subgraph EKS["Managed control plane (e.g. Amazon EKS)"] A2["API Server"] --- SC2["Scheduler"] --- CM2["Controller Manager"] --- E2[("etcd - managed by AWS,
not visible or accessible to you")] end

On a self-managed cluster, etcd backups and disaster-recovery drills are your responsibility. On Amazon EKS, AWS manages the control plane — including etcd — so you don't run etcdctl snapshot save yourself; this does not mean cluster data can never be lost, only that the operational burden of keeping etcd healthy moves to AWS. You still own backing up your own Kubernetes object definitions (e.g. via GitOps) if you want a recovery path independent of the managed control plane.

Request Lifecycle: What Actually Happens on kubectl apply

Tying the pieces above together, here's the full path a single kubectl apply takes, and why each stage exists:

flowchart TD K["kubectl apply -f deploy.yaml"] --> A["API Server receives request"] A --> AUTH["Authentication (who are you?)"] AUTH --> AUTHZ["Authorization (are you allowed to do this?)"] AUTHZ --> ADM["Admission control"] ADM --> VAL["Validation (is the object well-formed?)"] VAL --> P["Persist object"] P --> E[("etcd")] E --> STORED["Object stored"] STORED --> OBS["Controllers & Scheduler observe the change (watch)"] OBS --> MOVE["Cluster moves toward the new desired state"]

The critical point: the API Server does not just acknowledge "I received your YAML" and move on. It only reports success back to kubectl after the object is durably persisted in etcd — if the API Server crashed between validation and the etcd write, the object would not exist, and reporting success early would have lied to the caller.

Restarts don't lose state — because state doesn't live in the restarting component

This is the payoff of separating "gateway" (API Server, Scheduler, Controller Manager) from "persistent store" (etcd): any control-plane component can restart without losing cluster state, because none of them hold the authoritative copy in their own process memory.

sequenceDiagram participant API as API Server participant E as etcd participant Sch as Scheduler API->>E: (before restart) reads/writes objects Note over API: API Server crashes and restarts API->>E: What's the current cluster state? E-->>API: Kubernetes objects Note over API: View reconstructed, no data lost Note over Sch: Scheduler crashes and restarts Sch->>API: What's pending scheduling? API-->>Sch: current unscheduled Pods (from etcd) Note over Sch: Resumes scheduling, no gap in desired state

The same logic applies to the Scheduler and Controller Manager: when either restarts, it doesn't need to remember anything from before the crash — it re-reads the current state through the API Server (backed by etcd) and resumes the reconcile loop from there. This is the general Kubernetes control-plane principle worth naming: control-plane components are stateless and restartable; only etcd holds the persistent state they all depend on.

Production Considerations

etcd is the most critical component in Kubernetes.

Best practices:

  • Regular backups
  • Multi-node quorum
  • Fast SSD storage
  • Encryption at rest
  • Disaster recovery testing

Each of those bullet points is shorthand for a specific failure mode. Spelled out:

  • Availability — if etcd loses quorum (more than (N-1)/2 members down), the API Server can no longer persist or reliably read cluster state, which means kubectl apply, Pod scheduling, and controller reconciliation all stall — the cluster doesn't crash, it freezes. This is why quorum size (odd numbers, 3 or 5 members) is a production decision, not an implementation detail.
  • Consistency — covered above: Raft's quorum-commit is what lets every control-plane component trust that a read reflects the latest write. Weakening this (e.g. reading from a partitioned minority member) would reintroduce exactly the "two components disagree" problem etcd exists to prevent.
  • Performance — etcd sits on the write path of every API Server mutation. Slow etcd disk I/O directly shows up as slow kubectl apply, slow Pod scheduling, and slow controller reconciliation — it does not stay contained to etcd's own metrics.
  • Storage — etcd is latency-sensitive to disk fsync time, which is why it's typically run on local SSD rather than network-attached storage with variable latency. This does not mean any SSD works equally well — high fsync latency under load is one of the most common causes of etcd leader flapping in production.
  • Backups — a backup here means an etcdctl snapshot save (or equivalent for a managed control plane), taken on a schedule and tested by actually restoring it. A backup you've never restored is not a verified backup — see "Operating etcd" below for the exact commands.
  • Security — etcd stores Kubernetes Secrets, which by default are only base64-encoded, not encrypted, inside etcd's data. Anyone with filesystem or network access to etcd can read every Secret in the cluster, so etcd access must be as tightly controlled as the Secrets themselves — enable encryption at rest and restrict etcd's client certificates to the control plane.

Operating etcd

Take a point-in-time snapshot and restore from one using etcdctl:

etcdctl snapshot save backup.db
etcdctl snapshot restore backup.db --data-dir /var/lib/etcd-restore

etcd also needs periodic compaction (removing old key revisions that write-ahead history no longer needs) and defragmentation (reclaiming disk space after compaction) — skipping these lets the data file grow until etcd hits its storage quota and stops accepting writes.

Tradeoffs

Advantages

  • Strong consistency
  • Reliable cluster state
  • Distributed architecture

Disadvantages

  • Operationally sensitive
  • Backup and recovery are critical
  • Performance directly affects cluster responsiveness

The Mental Model to Keep

It's tempting to think of etcd as "the Kubernetes history database," because it does keep short-lived MVCC revisions and it clearly matters for auditing. That framing is wrong enough to cause real mistakes — like assuming a fresh etcd cluster preserves last month's Deployment revisions, or that etcd alone is a sufficient audit trail. The accurate framing:

flowchart TD ETCD[("etcd")] --> CUR["Current state: What is true right now?"] ETCD --> REV["Limited revisions: What changed recently? (until compaction)"] CUR --> KEEP["Kept indefinitely, as long as the object exists"] REV --> COMP["Compaction removes old revisions"]

etcd is Kubernetes' strongly consistent persistent state store: it keeps the cluster's current control-plane state and maintains versioned revisions for a limited period, but it is not an unlimited historical database. For anything that needs to outlive compaction — who changed what and when, rollout history, application behavior over time — reach for the purpose-built mechanism instead: Kubernetes Audit Logs, Deployment/ReplicaSet history, GitOps history, or your observability stack.
