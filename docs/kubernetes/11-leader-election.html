Leader Election: HA for Controller Manager & Scheduler

How Lease objects in etcd let multiple replicas of kube-controller-manager and kube-scheduler run without fighting over the same resources — election process, tuning, and failure scenarios.

Interview Answer — What Is Leader Election, and Why Do kube-scheduler & kube-controller-manager Need It?

Leader election is the mechanism by which multiple replicas of a Kubernetes control-plane component agree on exactly one of themselves to be "active" at any given moment, while the rest sit as passive standbys, ready to take over the moment the active one stops responding.

kube-scheduler and kube-controller-manager need it because production clusters run multiple replicas of each for high availability, but unlike a stateless web server, both of these components run a continuous reconciliation loop — the Scheduler decides which node each pending Pod lands on, and the Controller Manager runs controllers (Deployment, ReplicaSet, Node, and more) that create, update, and delete cluster objects. If more than one replica of either ran that loop at the same time, they'd make independent, conflicting decisions about the same objects — exactly the race conditions and split-brain scenarios described above under "The Problem It Solves."

Mechanically, it's implemented with a Lease object (coordination.k8s.io/v1) stored in etcd, as covered in detail below. The leader periodically renews the Lease's renewTime to prove it's still alive; if it stops renewing and leaseDurationSeconds passes, a follower detects the expiration and races to atomically acquire the Lease with a compare-and-swap write. Whichever follower's write lands first (matching the Lease's current resourceVersion) becomes the new leader; every other candidate's write is rejected as a conflict, and that candidate falls back to following.

One nuance worth naming: leader election guarantees "at most one active replica," not "zero downtime." During the window between the old leader's failure and a follower's successful acquisition — bounded by leaseDurationSeconds plus the retry period, roughly 15-20 seconds with the defaults — no scheduling and no controller reconciliation happens at all. That gap is the deliberate cost of avoiding split-brain, not a flaw in the mechanism.

Simple interview version

"Leader election lets Kubernetes run multiple replicas of kube-scheduler and kube-controller-manager for high availability without letting them step on each other. Only one replica — the leader — actually performs reconciliation work at a time; the rest are followers that just watch. It's implemented with a Lease object in etcd: the leader periodically renews it, and if it stops renewing, a follower detects the expired Lease and does an atomic compare-and-swap to become the new leader — so leadership changes safely on a crash, without ever having two leaders active at once."

One important interview follow-up

Q: Do kube-scheduler and kube-controller-manager run active-active across all their replicas, the same way kube-apiserver does?

A: No — conflating the two is a common mistake. kube-apiserver is stateless: it doesn't hold cluster state in its own memory (etcd does that) and doesn't run any reconciliation loop, so every replica can serve reads and writes simultaneously behind a load balancer — that's active-active. kube-scheduler and kube-controller-manager are different: each runs a continuous reconciliation loop, and running that loop from more than one replica at the same time produces exactly the race conditions, duplicate work, and split-brain described under "The Problem It Solves". The fix isn't letting more replicas serve traffic — it's electing exactly one active replica via the Lease mechanism described in "How Leader Election Works in Kubernetes": the leader renews its Lease every retry period, and only if it stops renewing does a follower take over. So: kube-apiserver is active-active by design, while kube-scheduler and kube-controller-manager are active-standby by design — and the Lease's acquire/renew/expire cycle is exactly what makes it safe to leave the standby replicas running at all.

The Problem It Solves

Kubernetes control plane components (kube-controller-manager and kube-scheduler) are designed to be stateless. This means you can run multiple replicas for high availability.

The problem: if you run 3 replicas of the controller-manager and all 3 are active simultaneously:

  • Deployment Controller: all 3 replicas would try to scale Deployments simultaneously → race conditions.
  • ReplicaSet Controller: all 3 would try to create/delete Pods simultaneously → conflicts.
  • Node Controller: all 3 would try to mark nodes as NotReady simultaneously → split-brain.

The solution: Leader Election — only one replica (the leader) actively performs work. The other replicas (followers) stand by, ready to take over if the leader fails.

How Leader Election Works in Kubernetes

Kubernetes uses leases (a custom resource in the coordination.k8s.io/v1 API group) to implement leader election. It's based on the distributed lock pattern.

Lease Object Structure

The Lease object is stored in etcd and looks like this:

apiVersion: coordination.k8s.io/v1
kind: Lease
metadata:
  name: kube-controller-manager
  namespace: kube-system
spec:
  # Who is the current leader?
  holderIdentity: "controller-manager-7d8f9-abcde"

  # How many seconds before the lease expires?
  leaseDurationSeconds: 15

  # When was the lease last renewed?
  renewTime: "2024-01-15T10:30:45Z"

  # When did the current leader acquire the lease?
  acquireTime: "2024-01-15T10:30:45Z"

  # How many times has leadership changed?
  leaderTransitions: 42

The Election Algorithm (client-go's leaderelection)

Leader election is implemented in the client-go library. Here's the pseudocode each component runs:

// Each component runs this loop
func runLeaderElection() {
    // Create a lease lock
    lock := &resourcelock.LeaseLock{
        LeaseMeta: metav1.ObjectMeta{
            Name:      "kube-controller-manager",
            Namespace: "kube-system",
        },
        Client: clientset.CoordinationV1(),
        LockConfig: resourcelock.ResourceLockConfig{
            Identity: "controller-manager-7d8f9-abcde",
        },
    }

    // Start leader election
    leaderelection.RunOrDie(ctx, leaderelection.LeaderElectionConfig{
        Lock:            lock,
        LeaseDuration:   15 * time.Second,
        RenewDeadline:   10 * time.Second,
        RetryPeriod:     2 * time.Second,
        Callbacks: leaderelection.LeaderCallbacks{
            OnStartedLeading: func(ctx context.Context) {
                // This is the leader! Start controllers
                startControllers()
            },
            OnStoppedLeading: func() {
                // Lost leadership; stop controllers gracefully
                stopControllers()
            },
            OnNewLeader: func(identity string) {
                // A new leader was elected (not us)
                log.Printf("New leader elected: %s", identity)
            },
        },
    })
}

Set up a highly available Kubernetes control plane with 3 controller-manager replicas and 3 scheduler replicas, one on each of Node 1, Node 2, Node 3 (each also running an API server and an etcd member).

Why Leader Election Is Critical

Problem Without Leader ElectionConsequenceHow Leader Election Solves It
Duplicate ControllersMultiple replicas create/delete resources simultaneously → corruption.Only the leader runs controllers; followers are passive.
Race ConditionsTwo controllers try to update the same resource → conflicts.Only one controller makes changes; no conflicts.
Split-BrainDifferent nodes have different views of the cluster state.A single leader ensures a consistent view.
Thundering HerdAll replicas react to events simultaneously → API Server overload.Only the leader reacts; followers don't process events.
Resource WasteAll replicas use CPU/memory for active work.Followers use minimal resources (only watch for leadership).
