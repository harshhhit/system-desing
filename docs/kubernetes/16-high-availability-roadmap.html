Control Plane High Availability Roadmap

A concept-first map of how the control plane itself survives failures — HA kube-apiserver, HA etcd, and Lease-based leader election for the scheduler and controller manager. Tick each stage as you cover it; progress is saved in this browser.

A concept-first map of how the control plane itself survives failure — not the workloads it schedules, but the brain doing the scheduling. This roadmap covers HA kube-apiserver, HA etcd, and Lease-based leader election for kube-scheduler and kube-controller-manager. Follow top to bottom — each stage assumes the one before it. Tick a stage's box once you've genuinely covered it; progress is saved in this browser. Interview Answer — What Is Control Plane High Availability?

Control plane high availability (HA) is running multiple copies of each control-plane component, usually across three or more control-plane Nodes, so that the cluster can still accept changes and heal itself when one of them fails. It exists because a single control-plane Node is a single point of failure: running Pods would keep running, but nothing could be deployed, scaled, rescheduled, or repaired until it came back (Stage 0).

Each component becomes highly available in a different way. kube-apiserver is stateless, so every replica serves traffic at once (active-active) behind a load balancer (Stage 1). etcd is stateful, so it runs as a Raft cluster that needs a quorum — a majority of members — to accept writes; three members tolerate one failure and five tolerate two (Stage 2). etcd can be stacked (an etcd member runs on each control-plane Node) or external (etcd runs on its own dedicated machines) — stacked is simpler, external isolates failures (Stage 2). If etcd loses quorum, the API server cannot serve writes (and generally not consistent reads), so the control plane is effectively down — while Pods already running on worker Nodes keep running. kube-scheduler and kube-controller-manager run as several replicas but only one is active at a time (active-passive); they use a Lease object in the API for leader election (Stage 3).

The cause → effect chain when a leader dies is: the leader stops renewing its Lease (a healthy leader renews every retryPeriod of 2s and gives up leadership if it cannot renew within renewDeadline of 10s) → the Lease expires once leaseDuration (15s by default) passes without a renewal → a standby replica, which retries every 2s, acquires the Lease and becomes leader → it resumes scheduling or reconciling. Because Lease updates use optimistic concurrency (resourceVersion) on top of etcd's consistent writes, only one replica can win the update, which prevents two schedulers from making conflicting decisions (split-brain) (Stage 4).

Simple interview version

"Control plane HA means running the control plane on several Nodes, typically three. The API servers are stateless, so they all run active-active behind a load balancer. etcd runs as a Raft cluster and needs a majority quorum, so three members survive one failure. The scheduler and controller manager run multiple copies but use Lease-based leader election so only one is active, and a standby takes over when the leader's Lease expires."

One important interview follow-up

Q: Does adding more etcd members (for example going from 3 to 4) make the cluster more available?

A: No. Quorum is a majority of members, so 3 members need 2 and tolerate 1 failure, while 4 members need 3 and still tolerate only 1 failure — the fourth member adds no fault tolerance, adds one more machine that can fail, and makes every write wait for one more acknowledgement. That is why etcd clusters use an odd size (3 or 5). Adding members also does not scale write throughput, because every write still goes through the single Raft leader. See Stage 2 — HA etcd.

Stage 0 — Why Control-Plane HA Matters at All

The data plane (the Nodes actually running your Pods) keeps serving traffic even if the entire control plane disappears — kubelet, the running containers, and kube-proxy's already-programmed rules don't need to talk to kube-apiserver every second to keep existing Pods alive. The control plane is different: it is the single place where scheduling decisions, API reads/writes, and reconciliation loops happen. If it goes down as a whole, the cluster doesn't crash outright, but it freezes — no new Pods get scheduled, no failed Pod gets replaced, no kubectl command works, and no controller notices or fixes drift, cluster-wide, until it comes back.

Why this matters: a single-node control plane is a single point of failure for the entire cluster's ability to change state, even though existing workloads on the data plane keep running for a while. That's the gap this whole roadmap closes — not by making any one component "unbreakable," but by making sure enough replicas of each control-plane piece exist that losing one (a crashed process, a rebooted node, a lost zone) never leaves zero working copies behind. Background on the components themselves is in Control Plane Overview.

The data plane's short-term resilience is exactly why control-plane HA is worth the extra infrastructure — it buys you the same "keeps working through a failure" property for the part of the cluster that otherwise has none.

Stage 1 — HA kube-apiserver: The Easy Part

kube-apiserver is stateless — every request it handles is either read from or written to etcd, and the API server itself keeps no durable state of its own between requests. That statelessness is what makes this stage the easiest piece of control-plane HA: you simply run multiple identical replicas of kube-apiserver (typically one per control-plane node) behind a load balancer, and any replica can answer any request. There's no leader election here and no coordination needed between replicas — unlike Stage 3, API server replicas run active-active.

  • The load balancer's job is simple but essential: distribute traffic across all healthy replicas and TCP-health-check port 6443 so a crashed or unreachable replica is taken out of rotation automatically.
  • Every other control-plane component (scheduler, controller manager, kubelets) and every kubectl user talks to the load balancer's stable address — never to one API server node directly — so an individual replica's failure is invisible to clients.
  • kubeadm HA setups make this explicit via --control-plane-endpoint, which must point at a stable DNS name resolving through the load balancer, not at any one node's own IP.

Because every replica is interchangeable and none holds unique state, losing any one of them just means the load balancer stops sending it traffic — nothing else in the cluster needs to know or care which replica served a given request. Since v1.26, each running API server also publishes its own identity as a Lease object in kube-system (the same Lease mechanism used for leader election in Stage 3), purely so clients and tooling can discover how many API server instances are currently up — it plays no role in routing.

How kubelets and clients reach an HA API server. Kubelets, kubectl, and in-cluster components must not point at one API server's own address, or losing that Node would disconnect them even though other replicas are healthy. Instead they use one stable endpoint — a load balancer or a virtual IP (for example, keepalived + HAProxy on-prem, or a cloud load balancer) — configured as controlPlaneEndpoint in kubeadm. Every API server's serving certificate must list that endpoint's DNS name and IP in its Subject Alternative Names (SANs); otherwise TLS verification fails for clients connecting through the load balancer. During upgrades, the version-skew policy sets the order: upgrade the API servers first (they may be at most one minor version apart during the rollout), then kube-controller-manager and kube-scheduler, then the kubelets — a kubelet must never be newer than the API server it talks to (it may be up to three minor versions older, since v1.28).

Stage 2 — HA etcd: Clustered Quorum

etcd is where Stage 1's statelessness stops applying — it's the cluster's single source of truth, so making it durable is the hard part of control-plane HA. etcd achieves this by running as a cluster of its own (typically 3 or 5 members) that replicates every write via the Raft consensus protocol and requires a quorum — a strict majority of members — to agree before any write is committed. That's a deliberate trade-off: a write isn't acknowledged until most members have it durably, so the cluster can lose a minority of members and keep serving both reads and writes with zero data loss.

Why an even number of members is a bad idea: the table above shows the pattern directly — a 4-member cluster needs 3 votes for quorum and still only tolerates 1 failure, exactly like a 3-member cluster, but for the cost of a 4th machine that adds no extra fault tolerance at all. A 6-member cluster tolerates the same 2 failures as a 5-member one, again for a wasted extra member. Odd-sized clusters get the same tolerance for less infrastructure, which is why the official guidance is explicit: run etcd with an odd number of members, and a 5-member cluster is the standard production recommendation.

There are two ways to place the etcd cluster relative to the rest of the control plane:

  • Stacked etcd — each etcd member runs on the same machine as a control-plane node (co-located with that node's kube-apiserver). Simpler, needs fewer machines (3+ control-plane/etcd nodes total), but couples the two failure domains: losing a control-plane node also removes one etcd member.
  • External etcd — the etcd cluster runs on entirely separate machines from the control-plane nodes (3+ control-plane nodes plus 3+ dedicated etcd nodes). More infrastructure, but the two layers fail independently — losing a control-plane node doesn't touch etcd's quorum, and vice versa.

Same odd-number-and-quorum math applies to control-plane node counts too: kubeadm's own HA guidance notes that an odd number of control-plane nodes similarly helps with leader-selection behavior on node or zone failure — the same underlying majority-vote reasoning as etcd's quorum.

Stage 3 — Leader Election: kube-scheduler & kube-controller-manager

Stage 1 showed why kube-apiserver can safely run active-active: it's stateless, so two replicas answering requests simultaneously never conflict. The scheduler and controller manager are different — both run reconciliation loops that make decisions and take action (assigning a Pod to a Node, creating a replacement Pod, issuing a certificate). If two copies of either ran active-active, they could both act on the same object at once — e.g. two schedulers racing to bind the same Pod to two different Nodes. So instead they run active-standby: several replicas are started, but only one is ever active as leader at a time; the rest sit idle, watching, ready to take over.

The mechanism behind "only one leader at a time" is a Lease object (API group coordination.k8s.io) — a small, general-purpose distributed-locking primitive stored in etcd like any other API object. Leader election reduces to a simple cycle:

  • Acquire — every replica races to create (or claim) the same named Lease; whichever one succeeds first writes its own identity into spec.holderIdentity and becomes leader.
  • Renew — the leader periodically refreshes spec.renewTime on that Lease, well before it would expire, as a heartbeat proving it's still alive and still wants to hold leadership.
  • Expire — if the leader stops renewing (crash, node loss, network partition), the Lease's leaseDurationSeconds eventually runs out with no fresh renewal.
  • Re-acquire — every standby replica is watching the same Lease; once it observes the lease has expired, one of them wins the next race to acquire it and becomes the new leader.

Why it matters, concretely: whichever replica is currently the leader is the only one actually scheduling Pods or running controllers at that moment — the standby replicas of kube-scheduler/kube-controller-manager are running processes that are deliberately doing nothing but watching a Lease. This is the same trade-off as etcd's quorum in Stage 2, just applied to decision-making instead of storage: correctness (never two conflicting actors) is chosen over throughput (only one of N replicas is doing useful work at any instant). The full mechanics — exact default timing parameters, tuning trade-offs, and a step-by-step failure timeline — live in the deep dive: Leader Election: HA for Controller Manager & Scheduler; this stage is the concept-first summary of the same mechanism.

Stage 4 — Failure-Recovery Timeline & Split-Brain Prevention

Putting Stages 1–3 together end-to-end: what actually happens, in order, when a leader control-plane process dies.

  1. The leader (say, kube-controller-manager replica A) crashes or its node is partitioned from the network. It stops renewing its Lease.
  2. Every standby replica is already watching that same Lease object via the API server (Stage 1's HA API server is what makes this watch reliable even while individual nodes fail) — they simply see no new renewTime come in.
  3. Once leaseDurationSeconds elapses past the last renewal with no update, the standbys treat the leader as dead and race to acquire the Lease themselves.
  4. One standby (replica B) wins the race, writes its own identity as holderIdentity, and becomes the new leader — it immediately begins scheduling Pods / running controller loops from wherever cluster state (in etcd) says things stand.
  5. There is a real, bounded gap between step 1 and step 4 — no scheduling or reconciliation for that component happens during it. This is the cost of active-standby: it trades a short recovery pause for the guarantee that two leaders are never active simultaneously.

Split-brain prevention — the guarantee that step 5's trade-off protects — is why this design leans on quorum-backed storage rather than, say, a simple timeout each replica judges for itself. The Lease lives in etcd, and etcd itself only ever commits a write when a quorum (Stage 2) agrees on it; a minority partition of etcd members (and anything talking only to them) can't accept new writes at all, so it cannot also elect and run a rogue "leader" writing conflicting state. Two control-plane replicas can only both believe they're leader if they each hold a Lease acquired against a quorum-agreeing store — and quorum guarantees at most one side of any partition has that majority. That's the same principle protecting etcd's own data from Stage 2, reused to protect leadership state too.

Caveat worth stating plainly: none of this makes recovery instantaneous. Tuning the Lease's duration and renewal timing shorter shrinks the failover gap but raises the risk of a false failover from a merely slow (not dead) leader under load or network jitter — see the deep dive's tuning-parameters section in Leader Election: HA for Controller Manager & Scheduler for the actual trade-off numbers.

Backup & disaster recovery: etcd snapshot/restore

An etcd snapshot is a point-in-time copy of etcd's entire keyspace — every Kubernetes object in the cluster — written to a single file. Backups exist because HA and backup solve different problems. HA protects against losing a member: if one of three etcd Nodes dies, the other two still hold every write. HA does NOT protect against bad data: if someone runs kubectl delete namespace prod, or a buggy controller overwrites objects, or the data is corrupted, Raft faithfully replicates that write to every member within milliseconds. The only way back to the state before the bad write is a snapshot taken before it.

Taking a snapshot (run against one healthy member, with the etcd client certificates):

ETCDCTL_API=3 etcdctl --endpoints=https://127.0.0.1:2379 --cacert=/etc/kubernetes/pki/etcd/ca.crt --cert=/etc/kubernetes/pki/etcd/server.crt --key=/etc/kubernetes/pki/etcd/server.key snapshot save /backup/etcd-snap.db

Restoring is done offline with etcdutl (older docs use etcdctl snapshot restore, now deprecated):

etcdutl snapshot restore /backup/etcd-snap.db --data-dir /var/lib/etcd-restored

For a multi-member cluster, run the restore on every member with that member's own --name, --initial-cluster, --initial-cluster-token and --initial-advertise-peer-urls, so all members form the same new cluster.

The cause → effect chain of a restore is: stop the API servers (so nothing writes during the restore) → restore the snapshot on each member into a new data directory → point etcd at that directory and start it → restart the API servers. A restore does not rejoin the old cluster; it creates a new etcd cluster (new cluster ID and member IDs) whose content is the snapshot. Everything written after the snapshot is lost, and controllers then reconcile the real Nodes back toward the restored desired state.

What the backup must also include: the snapshot alone is not enough. You also need the cluster's PKI (/etc/kubernetes/pki: CA and etcd certificates) and, if encryption at rest is enabled, the EncryptionConfiguration key — without that key, every Secret in the restored snapshot is unreadable ciphertext.

Space quota and defragmentation: etcd keeps old revisions until they are compacted, and compaction frees space logically but does not shrink the database file — defragmentation (etcdctl defrag) does. etcd also enforces a storage quota (2 GiB by default, configurable with --quota-backend-bytes). If the database reaches it, etcd raises a NOSPACE alarm and rejects writes with mvcc: database space exceeded — the cluster becomes effectively read-only until you compact, defragment, and disarm the alarm.

Suggested Learning Order

  1. Stage 0 (why HA matters) — grounds every later stage in a concrete failure mode instead of abstract "best practice."
  2. Stage 1 (HA API server) — the simplest case, and a useful contrast for Stage 3's active-standby model later.
  3. Stage 2 (HA etcd) — the hard state-durability problem underneath everything else; understand quorum here before Stage 4 leans on it again.
  4. Stage 3 (leader election) — the mechanism for the two components that can't run active-active; read the linked deep dive (Leader Election) alongside this stage for the full tuning detail.
  5. Stage 4 (failure timeline + split-brain) — ties Stages 1–3 together into one end-to-end story and names the guarantee the whole design is protecting.

Each stage answers a why before a how — that's intentional. See also Control Plane Overview for how these HA'd components fit into the control plane as a whole, and Networking Roadmap for the equivalent concept-first map of the cluster's networking layer.
