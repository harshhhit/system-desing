Non-sensitive vs. sensitive configuration, why Base64 isn't encryption, and how Pods consume both without hardcoding values into the image.

ConfigMap vs. Secret: Separating Configuration from the Image

In Kubernetes, ConfigMap and Secret are mechanisms for separating application configuration from the container image and Pod definition. A ConfigMap is designed for non-sensitive configuration — database paths, application modes, feature flags, URLs, ports, and environment-specific settings — while a Secret is intended for sensitive configuration, such as passwords, API keys, tokens, and certificates.

Both objects can be consumed by Pods as environment variables or mounted as files, allowing the same container image to be deployed across different environments with different configuration.

Secrets Are Encoded, Not Encrypted

A Kubernetes Secret is not automatically equivalent to encrypted storage. Kubernetes Secret data is commonly represented as Base64 when using the data field, but Base64 is only encoding, not encryption.

Using stringData instead allows a Secret to be written as normal text in the manifest; Kubernetes converts it into the Secret's internal representation.

Actual protection of Secret data depends on controls such as encryption at rest in the Kubernetes API datastore, RBAC permissions, secure access to the cluster, and avoiding secrets in Git repositories.

Why the Distinction Matters

The ConfigMap is appropriate for values that are safe to expose to application users or developers, while the Secret should be protected because anyone with sufficient Kubernetes permissions may be able to retrieve it.

Pods can receive these values as environment variables — for example, the application can read DB_PATH and GRAFANA_ADMIN_PASSWORD from its environment without hardcoding them into the container image. This separation also allows configuration to change without rebuilding the application image.

What Is a ConfigMap?

A ConfigMap is a Kubernetes resource used to store non-sensitive configuration data separately from application code and container images. It enables applications to be configured dynamically without rebuilding images, supporting the cloud-native principle of separating configuration from code.

ConfigMaps are typically used for:

  • Application settings
  • Feature flags
  • Log levels
  • Service endpoints
  • Configuration files
  • Runtime parameters

ConfigMaps should never be used for passwords, API tokens, certificates, or credentials. Those belong in Kubernetes Secrets.

Why ConfigMaps Exist

Without ConfigMaps, configuration is often baked into container images. Any configuration change requires:

  • Modifying the image
  • Rebuilding the image
  • Pushing the image
  • Redeploying the application

ConfigMaps eliminate this coupling by externalizing configuration. The same application image can be deployed across multiple environments while using different configuration values.

Benefits include:

  • Better portability
  • Simplified deployments
  • Faster configuration changes
  • Environment-specific configuration management
  • Improved CI/CD workflows
  • Reduced image proliferation

Ways Applications Consume ConfigMaps

1. Environment Variables

The application receives ConfigMap values as environment variables during container startup. These values are loaded once, when the process starts; they become part of the process environment, and a running process does not automatically receive any later update. That is exactly why a ConfigMap change behaves the way it does here: Kubernetes updates the ConfigMap object right away, but existing Pods keep running on the old values they already loaded, and a Pod restart is required before the new values take effect.

2. Mounted Volumes

ConfigMap data can also be mounted into the container filesystem as files. Kubernetes automatically updates the mounted files as soon as the ConfigMap changes, and no Pod restart is required for that file update — the container keeps running while the files are refreshed underneath it. The catch is that Kubernetes only guarantees the file on disk gets updated; whether the running application notices and actually uses the new values depends entirely on how it handles configuration reloads.

Possible outcomes: the application may automatically reload the configuration on its own, it may require an explicit manual reload signal, or it may require a full restart before the new values are picked up. The behavior depends entirely on application design.

ConfigMap Consumption Tradeoffs

Environment Variables

Advantages: environment variables are simple and easy to understand, widely supported by applications, integrate cleanly with twelve-factor applications, and are easy to debug using standard environment inspection.

Disadvantages: configuration changes require Pod restarts, which makes them unsuitable for frequently changing configuration, can cause rollout delays during updates, and becomes harder to manage as configurations grow large.

Best suited for: stable configuration, infrequently changing settings, small sets of configuration values.

Mounted Files

Advantages: configuration updates can propagate without restarting Pods, which suits large configuration files, applications that already expect file-based configuration, and dynamic configuration management generally.

Disadvantages: the application must support configuration reloading itself — Kubernetes updates the files but cannot force an application refresh, so behavior varies between applications and there is more operational complexity than with environment variables.

Best suited for: large configuration files, frequently updated configuration, applications supporting runtime reload.

ConfigMap Production Considerations

ConfigMap updates and application updates are two separate concerns. A successful ConfigMap update only guarantees that Kubernetes stored the new configuration and, if volume-based mounting is used, that the mounted files were refreshed. It does not guarantee that the application reloaded its configuration, is actively using the new values, or that the change is reflected in runtime behavior.

Because of this uncertainty, many production teams intentionally trigger Deployment rollouts after ConfigMap updates. Benefits of rollout-based updates: predictable behavior, consistent configuration across replicas, easier troubleshooting, less application-specific reload logic to maintain, and guaranteed configuration synchronization. The tradeoff is temporary Pod replacement and deployment churn.

ConfigMap Key Takeaways

ConfigMaps separate configuration from application code, and are intended only for non-sensitive configuration. How that configuration reaches the application changes what an update actually does: environment variable consumption requires a Pod restart after updates, since Kubernetes updates files, not application memory, while volume-mounted ConfigMaps update automatically at the filesystem level — whether the application itself reloads depends on the application, and a ConfigMap update never guarantees that runtime behavior actually changed.

Environment variables provide simplicity but require restarts; volume mounts provide flexibility but introduce reload complexity. Because an update alone doesn't guarantee the running application picked up the new values, many production environments perform Deployment rollouts after ConfigMap changes to ensure consistency and predictability.

Key Distinction

Remember it this way

ConfigMap = configuration that is not sensitive.

Secret = sensitive configuration that needs controlled access, but Base64 alone does not provide encryption.

Protecting Secrets in Production

In production, Secrets should generally be protected with RBAC, encryption at rest, restricted Pod/service-account permissions, secret rotation, and preferably an external secret-management system such as AWS Secrets Manager, HashiCorp Vault, or another dedicated secret manager.
