Kubernetes Control Plane Roadmap

A concept-first map of the four control-plane components — kube-apiserver, etcd, kube-scheduler, kube-controller-manager — how they fit together and why each one exists. Tick each stage as you cover it; progress is saved in this browser.

Stage 0 — What Is the Control Plane, and Why Does It Exist?

A Kubernetes cluster is two tiers: a control plane that makes global decisions about the cluster (scheduling, detecting and responding to cluster events), and a set of worker nodes that actually run your containers. Every one of the four components on this page runs on the control plane; none of them run your application code directly.

Why it exists: without a control plane, "desired state" would just be a YAML file sitting on someone's laptop — nothing would compare it against what's actually running, and nothing would act when a Pod crashed or a Node died. The control plane's entire job is to close that loop continuously: read what you declared you want, compare it to what's actually running, and take action to close the gap. This is the reconciliation model, and it is the single most important idea in Kubernetes — every one of the next four stages is a piece of the machinery that makes reconciliation possible.

flowchart LR D["Desired state
(what you declared)"] --> CMP{"Compare"} A["Actual state
(what's really running)"] --> CMP CMP -->|"gap found"| ACT["Take action"] ACT -.->|"loop forever"| A

Kubernetes never "finishes" — it doesn't reach a stable end-state and stop. It keeps watching and reconciling indefinitely; that's a deliberate design choice, not a limitation.

  • kube-apiserver — the single door every read and write goes through (Stage 1).
  • etcd — where "desired state" and "actual state" both actually live (Stage 2).
  • kube-scheduler — decides where a new Pod should run (Stage 3).
  • kube-controller-manager — runs the loops that notice a gap and act on it (Stage 4).

Kubernetes also ships an optional cloud-controller-manager for cloud-provider-specific integration (provisioning load balancers, labeling Nodes with cloud metadata, etc.). It isn't one of this page's four core components, but you'll see it named alongside them in the official docs.

Stage 1 — kube-apiserver: The Single Entry Point

The official reference describes it plainly: kube-apiserver "validates and configures data for the api objects... and provides the frontend to the cluster's shared state through which all other components interact." In plain terms: it is a REST API server sitting in front of etcd, and it is the only component allowed to read or write cluster state directly. kubectl, Helm, the scheduler, every controller, every kubelet on every Node — none of them ever talk to etcd themselves; they all go through kube-apiserver.

Why it exists: if every component could write to etcd directly, there would be no single place to enforce authentication, authorization, validation, or admission rules — any client with network access to etcd could corrupt cluster state with no checks at all. Centralizing all reads and writes behind one API server is what makes it possible to apply one consistent set of gates (authn → authz → admission → validation) to every single change, no matter which client made it. See API Request Lifecycle: The Four Gates and API Request Flow for that gate sequence in detail.

flowchart TD K["kubectl"] --> API["kube-apiserver"] H["Helm"] --> API C["Controllers"] --> API S["Scheduler"] --> API KL["kubelets"] --> API API --> ETCD[("etcd")]

Concrete example: run kubectl apply -f pod.yaml and the YAML goes to kube-apiserver, not to etcd. Only after the API server has authenticated you, authorized the action, run it through admission control, and validated the object does it get persisted to etcd. Full depth: kube-apiserver Deep Dive.

Stage 2 — etcd: The Source of Truth

etcd is the "consistent and highly-available key-value store used as Kubernetes' backing store for all cluster data," in the official description. Every object you've ever created — every Pod spec, every Service, every ConfigMap, every Secret, the current status of every Node — lives here as a key-value entry. Nothing in Kubernetes is "remembered" anywhere else; if it isn't in etcd, as far as the cluster is concerned it doesn't exist.

Why it exists: the reconciliation loop from Stage 0 needs both halves of its comparison — desired state and actual state — to persist somewhere durable and consistent, or a control-plane restart would simply forget the cluster. etcd is that durable store, and because it's built on the Raft consensus algorithm, it stays consistent even when several of its own nodes are running as a replicated cluster (see Consensus Algorithms: Raft & Paxos). What breaks without it: no etcd means no cluster state at all — kube-apiserver would have nothing to read or write, and every other component would have nothing to watch.

  • Only kube-apiserver talks to etcd directly (Stage 1) — no other component, and no user, is meant to touch it.
  • etcd exposes a watch API: a client can subscribe to a key prefix and get streamed every change to it, instead of polling. This is exactly the mechanism kube-controller-manager and kube-scheduler build on in Stages 3 and 4.
flowchart LR API["kube-apiserver"] -->|"read / write"| ETCD[("etcd
(key-value store)")] ETCD -->|"watch stream"| API

Because etcd is the single source of truth, its backup and restore practices are one of the highest-stakes operational concerns in running Kubernetes. Full depth: etcd Deep Dive.

Stage 3 — kube-scheduler: Placing Pods

kube-scheduler watches kube-apiserver for Pods that exist in etcd but have no Node assigned yet, and picks a Node for each one. It does not run anything itself — its entire output is one decision, written back through the API server: "this Pod belongs on that Node."

Why it exists: without it, a newly created Pod would sit forever with an empty nodeName field — nothing else in the system is responsible for choosing placement. The scheduler's decision has to account for resource requests, hardware and policy constraints, and affinity/anti-affinity rules, which is enough combinatorial complexity that it needs a dedicated component rather than being folded into, say, kube-apiserver itself.

The official mechanics are a two-step pipeline per unscheduled Pod:

  1. Filtering — find the set of feasible Nodes: ones that satisfy the Pod's resource requests and constraints. If this set comes up empty, the Pod stays unscheduled until something changes (e.g. another Pod is evicted, or a new Node joins).
  2. Scoring — rank every feasible Node and pick the highest-scoring one; ties are broken randomly.

Once a Node is chosen, the scheduler performs binding: it writes that decision back to kube-apiserver (never to the Node directly). Only then does the kubelet on the winning Node notice the assignment and actually start the containers — placement and execution are two separate concerns, handled by two separate components.

flowchart TD Pod["Unscheduled Pod
(nodeName empty)"] --> Filter["Filtering:
which Nodes are feasible?"] Filter --> Score["Scoring:
rank feasible Nodes"] Score --> Bind["Binding:
write decision to API server"] Bind --> Kubelet["kubelet on chosen Node
starts the containers"]

The scheduler decides placement, not execution — a distinction worth stating explicitly, since it's easy to assume the scheduler itself "runs" the Pod. Full depth: kube-scheduler Deep Dive.

Stage 4 — kube-controller-manager: The Watch-Reconcile Loop

A controller, per the official docs, is "a control loop that watches the state of your cluster, then makes or requests changes where needed... trying to move the current cluster state closer to the desired state." kube-controller-manager is the process that bundles many of these built-in controllers together and runs them as one binary — the Deployment controller, the ReplicaSet controller, the Node controller, the Endpoint/EndpointSlice controller, and others, each responsible for one narrow slice of cluster behavior.

Why they're bundled rather than shipped as one monolithic loop: the docs are explicit that "it's useful to have simple controllers rather than one, monolithic set of control loops that are interlinked" — if one controller has a bug or crashes, the others keep running unaffected, and each one stays easy to reason about because it only watches and reconciles one type of object.

The pattern every controller follows is the same three-step loop:

  1. Watch — subscribe (via kube-apiserver, never etcd directly) to one resource type's spec field, e.g. "all Deployments."
  2. Reconcile — compare that spec (desired state) against the current state (e.g. "spec says 3 replicas, only 2 Pods exist") and request whatever change closes the gap — here, asking the API server to create one more Pod.
  3. Report — write the resulting status back through the API server so it's visible in kubectl get/describe.

Concrete example: delete a Pod that belongs to a Deployment with replicas: 3. The ReplicaSet controller's watch fires almost immediately (it's watching Pods and ReplicaSets), notices only 2 Pods now match the label selector against a desired count of 3, and asks the API server to create a replacement — which then goes through kube-scheduler (Stage 3) exactly like any other new Pod.

flowchart LR Watch["Watch (via API server)
Deployment: 3 replicas"] --> Cmp{"Current = 2 Pods.
Gap found?"} Cmp -->|yes| Act["Request: create 1 Pod"] Act --> Report["Report new status"] Report -.->|loop| Watch

This watch-reconcile loop is what people mean by "Kubernetes self-healing" — nobody manually restarts the crashed Pod; the controller loop already noticed and fixed it. Full depth: kube-controller-manager Deep Dive.

Stage 5 — How It All Fits Together: A Request's Full Round Trip

Each earlier stage looked at one component in isolation. This stage traces one concrete action — kubectl apply on a new 3-replica Deployment — end to end, through all four, to show how they depend on each other in practice.

  1. kubectl sends the Deployment YAML to kube-apiserver (Stage 1) — never to etcd, never to any other component directly.
  2. kube-apiserver authenticates the request, authorizes it, runs admission control, validates the object, then persists it to etcd (Stage 2) as the new desired state.
  3. kube-controller-manager's Deployment/ReplicaSet controllers (Stage 4), which are watching kube-apiserver for Deployments, notice the new object, see the current Pod count (0) doesn't match the desired count (3), and request 3 new Pod objects through the API server — again written to etcd.
  4. Those 3 Pods exist in etcd with no nodeName set yet. kube-scheduler (Stage 3), watching for exactly that condition, runs filtering and scoring for each one and binds each Pod to a chosen Node — once more, by writing back through the API server.
  5. The kubelet on each chosen Node — a data-plane component, not part of the control plane — is itself watching kube-apiserver for Pods assigned to its own Node, sees the new assignment, and tells the container runtime to actually start the containers.
flowchart TD U["kubectl apply"] --> API["kube-apiserver
(authn/authz/admission/validate)"] API --> ETCD[("etcd — desired state
written")] ETCD -->|watch| CM["kube-controller-manager
notices 0 of 3 Pods exist"] CM -->|"create 3 Pods"| API API --> ETCD2[("etcd — 3 unscheduled
Pods written")] ETCD2 -->|watch| SCHED["kube-scheduler
filters + scores Nodes"] SCHED -->|"bind decision"| API API --> ETCD3[("etcd — nodeName set")] ETCD3 -->|watch| KL["kubelet on chosen Node"] KL --> RUN["Container runtime starts containers"]

Notice the pattern repeats three times: write through the API server → land in etcd → get picked up by a watcher. That single pattern, reused by every component, is the entire mechanism behind "declarative" Kubernetes — you never tell any component what to do directly, you only ever declare desired state and let the watch-reconcile loops (Stages 3 and 4) discover and close the gap.

A caveat worth stating plainly: this whole chain depends on every step succeeding. If kube-apiserver is unreachable, nothing above can even start. If etcd loses quorum, kube-apiserver can't durably persist anything, even though it may still serve reads from a stale cache. If the scheduler is down, Pods pile up unscheduled but Deployments and existing Pods keep running — the control plane degrades in pieces, not all at once. See Leader Election: HA for Controller Manager & Scheduler for how a production cluster avoids any one of these being a single point of failure — multiple kube-apiserver replicas sit behind a load balancer, etcd runs as a Raft quorum, and the scheduler and controller manager each run several replicas that use a Lease object in etcd to elect exactly one active leader at a time, with a standby ready to take over the moment the leader's lease isn't renewed.

Suggested Learning Order

  1. Stage 0 (the reconciliation model) — the idea every other stage is in service of; skip it and the other four components look like arbitrary trivia.
  2. Stage 1–2 (kube-apiserver, etcd) — the read/write path everything else depends on: one gatekeeper, one durable store behind it.
  3. Stage 3 (kube-scheduler) — the narrowest, most self-contained component: one decision (which Node), made once per unscheduled Pod.
  4. Stage 4 (kube-controller-manager) — the broadest component conceptually, since it's really dozens of independent loops sharing one process; understand the watch-reconcile pattern once and it explains all of them.
  5. Stage 5 (the full round trip) — come back to this only once Stages 1–4 are individually solid; it's the payoff stage that shows why the split into four components exists at all, rather than one big program.

See also Control Plane Overview for the same material at a glance, and API Request Flow plus API Request Lifecycle: The Four Gates for a deeper look specifically at Stage 1's gatekeeping.
