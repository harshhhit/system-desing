kube-scheduler Deep Dive

How Kubernetes decides which node an unscheduled Pod should run on.

Interview Answer — What Is kube-scheduler?

kube-scheduler is the control-plane component that decides which node a newly created Pod should run on. When a Pod is created without a node already assigned, it's the scheduler's job to pick one.

It's one of the four core control-plane components (alongside kube-apiserver, etcd, and kube-controller-manager), and it only handles placement decisions — it has no role in actually running containers, which belongs to the kubelet and container runtime on the worker node.

Mechanically, the scheduler watches the API server for Pods with no node assigned, then runs each one through two phases: filtering (eliminate nodes that can't run the Pod at all — insufficient CPU/memory, a required label that doesn't match, an untolerated taint) and scoring (rank the remaining feasible nodes and pick the best one). Once a node is chosen, the scheduler doesn't touch the node directly — it writes a binding back to the API server recording the decision.

One nuance worth being precise about: "the scheduler scheduled the Pod" means the placement decision was made and recorded — it does not mean the Pod is running yet. See the follow-up below for exactly where that responsibility hands off.

Simple interview version

"kube-scheduler is the control-plane component that decides which node an unscheduled Pod should run on. It filters out nodes that can't fit the Pod, scores the remaining candidates, and writes the winning node's name back to the API server as a binding. It never runs anything itself — the kubelet on the chosen node is what actually pulls the image and starts the containers."

One important interview follow-up

Q: Does the scheduler actually start or run the Pod on the chosen node?

A: No. The scheduler's job stops at the decision: once filtering and scoring pick a node, its Binding Phase writes that decision back to kube-apiserver as a binding (see "Scheduler Components You Must Understand" above) — it never contacts the node directly and never starts a container. From there, the kubelet running on the chosen node — which is watching the API server, not the scheduler — notices the new binding and is what actually pulls the container image and starts the containers. This split matters operationally: a Pod stuck in Pending is a scheduler problem (no feasible node was found), but a Pod that's been scheduled and yet never reaches Running is a kubelet/runtime problem on that specific node, not a scheduling problem.

Node Selection

Node selection is the simplest scheduling mechanism in Kubernetes. It allows a Pod to run only on nodes that have specific labels — the scheduler checks node labels and matches them against the Pod's requirements. If a node contains the required label, it becomes a candidate for scheduling; if no node matches, the Pod remains in a Pending state.

Node selection is usually implemented using nodeSelector. It provides hard constraints, meaning the scheduler must satisfy them — there is no "soft" nodeSelector. Organizations commonly use it to separate workloads such as production, development, GPU, storage-heavy, or compliance-specific applications. It's simple but not flexible for complex placement requirements (that's what affinity is for, below).

Major things to understand: node labels, nodeSelector, hard scheduling constraints, Pending Pods due to no matching nodes, label management strategy.

Resource Placement

Resource placement refers to scheduling Pods based on available node resources. The scheduler evaluates CPU, memory, ephemeral storage, and extended resources. Pod resource requests determine the minimum resources required — nodes lacking sufficient available resources are filtered out. This prevents overcommitment and node exhaustion.

Kubernetes schedules based on requested resources, not actual usage. Proper resource requests help achieve predictable scheduling behavior; resource placement directly impacts cluster utilization and workload performance, and poor resource sizing often leads to scheduling failures or resource waste.

Major things to understand: CPU requests and limits, memory requests and limits, ephemeral storage, extended resources (GPU, FPGA), resource accounting, scheduler filtering phase.

Capacity Evaluation

Capacity evaluation is the process of determining whether a node can accommodate a Pod. The scheduler compares requested resources against a node's allocatable resources — allocatable capacity excludes resources reserved for system components (kubelet, OS, eviction thresholds), so it's always ≤ the node's raw capacity.

Nodes are continuously evaluated as workloads are added or removed, and capacity evaluation happens before scoring candidate nodes. It helps prevent resource contention and node instability — insufficient capacity causes Pods to remain unscheduled. Kubernetes maintains a view of cluster resource availability through the API server, and accurate capacity information is critical for efficient scheduling.

Major things to understand: node capacity vs. allocatable resources, scheduler cache, resource reservation, cluster utilization, node pressure conditions, scheduling failures.

nodeSelector vs. Affinity/Anti-Affinity — Intuition

Affinity and anti-affinity let you constrain which nodes your Pod is eligible to be scheduled on, based on labels of nodes or labels of other Pods.

1. What is nodeSelector?

Think of nodeSelector like a simple filter:

  • You put labels on nodes (e.g. disk: ssd, size: large).
  • In your Pod spec, you say: "Only run me on nodes that have label disk: ssd."

✅ Simple — either the node matches all labels, or it doesn't.
❌ Limited — no "or" logic, no "soft" rules, no "I prefer but don't require."

2. What do affinity/anti-affinity add?

They give you more powerful rules:

a. More expressive matching — with nodeSelector, only AND (all labels must match). With affinity, you can say "node must have disk=ssd or disk=nvme." You can also say "avoid nodes with disk=hdd" (anti-affinity).

b. Soft rules (preferences) — a hard rule (required): the Pod must go to a matching node, otherwise it won't be scheduled. A soft rule (preferred): "try to put me on an SSD node, but if none exists, put me anywhere." That's huge for reliability — your Pod can still run even if the ideal node type is unavailable.

c. Look at other Pods, not just node labels — node affinity looks at node labels; inter-pod affinity/anti-affinity looks at labels on Pods already running on a node. Example: "schedule me on a node where there's already a Pod with label app=frontend" (affinity), or "don't schedule me on a node where a Pod with label app=backend is running" (anti-affinity). This helps with keeping related Pods together (affinity) for low latency, and spreading Pods apart (anti-affinity) for high availability.

3. Two types of affinity

TypeLooks at…Example
Node affinityLabels on the node itself"Run me on a node in us-east-1 zone, preferably with GPU."
Inter-pod affinity/anti-affinityLabels on other Pods running on the same node (or same zone, etc.)"Don't run two database Pods on the same node."

4. Real-world analogy

Imagine you're assigning people to seats in a bus:

  • nodeSelector: "Only sit in seats labeled 'window'." — strict, simple.
  • Node affinity: "I prefer a window seat, but if none available, an aisle is okay." — soft.
  • Inter-pod anti-affinity: "I don't want to sit next to anyone who is eating fish." — based on other passengers, not seat labels.
  • Inter-pod affinity: "I want to sit next to my coworker (same project label)."

Summary for memory:

  • nodeSelector → simple, hard, node-labels-only.
  • Node affinity → hard or soft, expressive logic on node labels.
  • Inter-pod affinity/anti-affinity → hard or soft, based on other Pods.

This makes Kubernetes scheduling much more flexible and intelligent for production environments.

Affinity Rules

Affinity rules tell Kubernetes where Pods prefer or must run. Affinity provides more advanced scheduling than node selectors — it allows matching based on node labels and the placement of other, already-running Pods. Affinity can be mandatory (a hard rule) or preferred (a soft rule that influences scoring):

  • Required (requiredDuringSchedulingIgnoredDuringExecution) — acts as a hard rule; the Pod must go to a matching node or it won't be scheduled at all.
  • Preferred (preferredDuringSchedulingIgnoredDuringExecution) — acts as a soft rule; e.g. "try to put me on an SSD node, but if none exists, put me anywhere." It influences scoring rather than filtering.

It enables workload placement near specific hardware or services, improving performance, locality, and regulatory compliance — large clusters often use affinity to optimize application architecture.

Node Affinity

Matches node labels. Unlike nodeSelector (which is a strict AND of all labels), node affinity supports richer boolean logic — e.g. "node must have disk=ssd OR disk=nvme."

Pod Affinity

Places Pods close to other Pods, matched via label selectors over a topology domain (e.g. "schedule me on a node in the same zone as Pods labeled app=cache").

Major things to understand: hard vs. soft affinity, label selectors, node affinity, Pod affinity, scheduler scoring.

Anti-Affinity Rules

Anti-affinity is the opposite of affinity — it prevents Pods from being scheduled together. It improves fault tolerance and availability: applications can avoid placing replicas on the same node, reducing the impact of a single node failure. Anti-affinity is commonly used for databases and stateful applications.

The scheduler evaluates existing Pod locations before placement. Hard anti-affinity can make scheduling difficult in small clusters, and excessive anti-affinity can lead to resource fragmentation.

Pod Anti-Affinity

podAntiAffinity:
  requiredDuringSchedulingIgnoredDuringExecution:
    - labelSelector:
        matchLabels:
          app: my-db
      topologyKey: "kubernetes.io/hostname"

Use cases: spread replicas, high availability, fault isolation, multi-tenant environments.

Key concepts: topology domains, label selectors, required anti-affinity, preferred anti-affinity.

Taints and Tolerations

Taints work from the node side, while tolerations work from the Pod side. A taint marks a node as unsuitable for certain workloads — Pods must explicitly tolerate the taint to run there. Taints provide workload isolation and are commonly used for dedicated nodes: GPU nodes often use taints to prevent accidental scheduling and reserve expensive infrastructure. Multiple taints can exist on a node, and the scheduler checks tolerations before placement.

EffectBehavior
NoScheduleNew Pods without a matching toleration won't be scheduled here; existing Pods are left alone.
PreferNoScheduleSoft version — the scheduler tries to avoid the node but will use it if there's no alternative.
NoExecuteNew Pods won't be scheduled here and already-running Pods without a matching toleration are evicted.

Major things to understand: node taints, Pod tolerations, dedicated workloads, node eviction, NoSchedule vs. NoExecute, system taints.

Topology Awareness

Topology awareness helps Kubernetes make scheduling decisions based on physical or logical infrastructure boundaries. A topology domain can be a node, rack, zone, region, or data center. Kubernetes can spread workloads across topology domains to improve application availability during failures and reduce single points of failure.

The scheduler uses topology labels to understand infrastructure layout — modern clusters heavily rely on topology-aware scheduling, especially in multi-zone cloud environments, to balance resiliency, latency, and resource utilization.

Examples: node, rack, availability zone, region.

Major things to understand: topology labels, availability zones, failure domains, topology spread constraints, Pod distribution, cross-zone traffic costs.

Scheduling Process

Scheduler evaluates:

  • CPU
  • Memory
  • Storage
  • Affinity Rules
  • Node Labels
  • Taints
  • Policies

Then chooses a node.

How the Scheduler Picks a Node

Choosing a node happens in two phases:

  • Filtering (predicates) — eliminates every node that can't run the Pod at all: not enough CPU/memory, a required label doesn't match nodeSelector/affinity rules, or the node has a taint the Pod doesn't tolerate. What's left is the set of feasible nodes.
  • Scoring (priorities) — ranks the feasible nodes and picks the highest-scoring one. Scoring plugins balance goals like spreading Pods evenly across nodes, bin-packing onto fewer nodes to save resources, or preferring nodes that already have the Pod's image cached.

If no node survives filtering, the Pod stays Pending until one becomes available.

Priority & Preemption

A PriorityClass gives Pods a priority value. When the cluster is full and a high-priority Pod can't be scheduled, the scheduler can preempt — evict — one or more lower-priority Pods from a node to make room, rather than leaving the high-priority Pod pending indefinitely.

Multiple & Custom Schedulers

A Pod can request a specific scheduler with spec.schedulerName. This means multiple schedulers can run side by side in the same cluster — the default kube-scheduler alongside a custom or specialized scheduler (e.g. for batch/ML workloads with different bin-packing goals) — each only picking up Pods addressed to it.

Scheduler Components You Must Understand

To master Kubernetes scheduling, focus on these building blocks end to end:

  1. Scheduling Queue — stores unscheduled Pods waiting for placement.
  2. Filtering Phase — removes nodes that cannot run the Pod (resource shortage, missing labels, untolerated taints, affinity mismatch). See "How the Scheduler Picks a Node" above.
  3. Scoring Phase — ranks remaining nodes (least loaded node, preferred affinity, resource balance). See "How the Scheduler Picks a Node" above.
  4. Binding Phase — assigns the Pod to the selected node, writing the binding back to the API server.
  5. Scheduler Cache — maintains cluster state (nodes, assumed Pods, resource usage) in memory for fast decisions without re-querying the API server on every cycle.
  6. Scheduling Framework Plugins — the extension points the scheduler runs at each phase. Important plugins: NodeResourcesFit, NodeAffinity, PodTopologySpread, TaintToleration, InterPodAffinity.
  7. Preemption — the scheduler evicts lower-priority Pods when higher-priority Pods need resources. See "Priority & Preemption" above.
  8. Priority Classes — determine which workloads are more important via PriorityClass. See "Priority & Preemption" above.
  9. Topology Manager — coordinates NUMA-aware resource placement (aligning CPU, memory, and device assignment on the same NUMA node for latency-sensitive workloads).
  10. Cluster Autoscaler Interaction — when no node fits a Pod, the scheduler leaves it Pending, the Cluster Autoscaler adds a node, and the scheduler retries placement:
    flowchart TD A["Scheduler → Pod Pending"] --> B["Cluster Autoscaler → Add Node"] B --> C["Scheduler → Retry Placement"]
