Kubernetes Data Plane Roadmap

A concept-first map of the worker-node layer that actually runs workloads — kubelet, CRI, CNI, CSI, kube-proxy, and how the control plane knows a Node is still healthy. Tick each stage as you cover it; progress is saved in this browser.

A concept-first map of the worker-node layer that actually runs your workloads: the kubelet, the container runtime (via CRI), Pod networking (via CNI), storage attachment (via CSI), kube-proxy, and how the control plane knows a Node is still healthy at all. Follow top to bottom — each stage assumes the one before it. Tick a stage's box once you've genuinely covered it; progress is saved in this browser. For the full narrative walkthrough of one Pod's journey through all of these pieces, see Data Plane Deep Dive — this roadmap is the checklist companion to it, not a replacement.

Interview Answer — What Is the Kubernetes Data Plane?

The Kubernetes data plane is the set of worker Nodes, and the agents running on each of them, that actually run containers and carry their traffic. It exists because the control plane only makes decisions and records state — something on every machine has to turn "this Pod is bound to this Node" into running processes, network interfaces, and mounted disks (Stage 0).

The central agent is the kubelet, which watches the API server for Pods bound to its Node and makes them real (Stage 1). It does not do the low-level work itself; it works through three plug-in interfaces. The kubelet uses the CRI (Container Runtime Interface) to have a runtime such as containerd pull images, create the Pod sandbox, and start containers (Stage 2) — the runtime in turn invokes the CNI (Container Network Interface) plugin to give the Pod an IP address (Stage 3) — and the kubelet uses the CSI (Container Storage Interface) node plugin to mount volumes the control plane has already attached to the Node (Stage 4). Alongside it, kube-proxy programs each Node's iptables/IPVS (or nftables) rules so Service IPs reach the right Pods (Stage 5).

The kubelet also reports back: it updates the Node's status and renews a Node heartbeat Lease. If those heartbeats stop, the node controller marks the Node NotReady, taints it, and after a grace period the Pods on it are evicted and recreated elsewhere by their controllers (Stage 6, Stage 7).

Simple interview version

"The data plane is the worker Nodes that actually run workloads. On each Node the kubelet watches for Pods assigned to it and runs them by calling the container runtime through CRI, setting up networking through CNI, and mounting storage through CSI. kube-proxy makes Service IPs route to the right Pods. The kubelet sends heartbeats back to the control plane, and if a Node stops reporting, its Pods are eventually evicted and rescheduled elsewhere."

One important interview follow-up

Q: If a worker Node loses contact with the control plane, are its Pods immediately moved to another Node?

A: No. First the node controller must notice missed heartbeats (node-monitor-grace-period, about 40–50 seconds by default — 40s before v1.32, 50s since) and mark the Node NotReady/Unreachable, which adds a taint; Pods by default tolerate that taint for 300 seconds, so eviction starts roughly 5–6 minutes later. Meanwhile the containers on that Node usually keep running, because the kubelet and runtime do not need the control plane to keep them alive. Also, "moved" is not quite right: Pods are never migrated — the old Pod objects are deleted and the owning controller (for example a ReplicaSet) creates brand-new Pods that the scheduler places elsewhere. Bare Pods with no controller are not recreated at all. See Stage 6 — Node Health.

Stage 0 — Data Plane vs. Control Plane

One sentence, since the deep-dive page covers this in full: the control plane decides what should run and where; the data plane is every component that actually carries that decision out, running once per worker node, not once per cluster.

  • kubelet, the container runtime, and kube-proxy are the three components every Node runs (per the official Kubernetes docs' Node-components list).
  • CNI and CSI plugins are also per-node, invoked by the kubelet rather than running as independent control-plane-facing services.
  • None of these make cluster-wide scheduling or reconciliation decisions — that's the control plane's job (see the Control Plane Roadmap).

Stage 1 — kubelet: The Node Agent

The kubelet is the agent that runs on every Node and, in the Kubernetes project's own words, "ensures that Pods are running, including their containers." It watches the API Server for Pods assigned to its own Node, and continuously works to make sure the containers described in each Pod's spec actually exist and are healthy — restarting a container that crashes, for example.

Why it matters: the kubelet is the only data-plane component with a direct line back to the API Server for Pod state. It doesn't create containers, wire up networking, or mount storage itself — it delegates each of those to a separate interface (CRI, CNI, CSI respectively, covered next), which is what lets Kubernetes support many different runtimes, network plugins, and storage backends without changing the kubelet's own code.

Probes: liveness vs. readiness vs. startup

A probe is a periodic health check that the kubelet runs against a container — an HTTP GET, a TCP connect, a gRPC health call, or a command run inside the container. Probes exist because "the process is running" is not the same as "the application is working": a web server can be deadlocked with its process still alive, or still warming a cache and not yet able to answer requests. Kubernetes defines three probes, and the difference between them is what the kubelet does when one fails:

  • Liveness probe — "is this container broken beyond recovery?" On failure (after failureThreshold consecutive failures), the kubelet kills and restarts the container. If it keeps failing, the restarts back off exponentially and the Pod shows CrashLoopBackOff.
  • Readiness probe — "should this container receive traffic right now?" On failure, the kubelet marks the Pod not Ready, so the EndpointSlice controller removes it from its Services' endpoints and kube-proxy stops sending it traffic. The container is not restarted; once the probe passes again, the Pod is added back.
  • Startup probe — "has this slow-starting container finished starting?" While it is configured and has not yet succeeded, the liveness and readiness probes are held off. This lets a legacy app take, say, two minutes to boot without a short liveness timeout killing it mid-start.

Concrete example: a Java service with a readiness probe on /ready and a liveness probe on /healthz. During a rolling update, the new Pod receives no traffic until /ready returns 200; if the JVM later deadlocks and /healthz times out three times in a row, the kubelet restarts that one container.

Gotcha — liveness vs. readiness is not interchangeable: a liveness probe that checks a shared dependency (for example, "can I reach the database?") is dangerous. If the database has a brief outage, every Pod's liveness probe fails at once, the kubelet restarts every container at the same moment, and a short DB blip becomes a full outage plus a restart storm. Dependency checks belong in the readiness probe (or nowhere); the liveness probe should check only the container's own health.

Stage 2 — Container Runtime & CRI

The Container Runtime Interface (CRI) is a gRPC API that lets the kubelet talk to any compliant container runtime — containerd, CRI-O, and others — without Kubernetes itself needing to know which one is installed. The kubelet acts as a CRI client with two endpoints: a Container Service (start/stop containers) and an Image Service (pull/manage images); the runtime on the other end actually pulls the image layers and starts the container processes using Linux namespaces and cgroups.

Why it matters: before CRI existed, Kubernetes had specific runtimes wired directly into its own code. Standardizing this interface is what let the ecosystem move away from one runtime (Docker) without forking Kubernetes itself — cluster operators can pick containerd, CRI-O, or a sandboxed runtime like Kata Containers or gVisor, and the kubelet talks to all of them the same way.

Stage 3 — CNI: Pod Networking

Once a container exists, it still has no network identity — that's what the Container Network Interface (CNI) provides. When the kubelet (via the CRI) creates a new Pod sandbox, it calls the configured CNI plugin (Calico, Flannel, Cilium, etc.), which creates a virtual network interface, assigns the Pod an IP address, and adds the routing rules needed for that IP to be reachable from other Pods and Nodes.

Why it matters: this is the mechanism that actually implements the flat, NAT-free Pod network model every Kubernetes networking concept assumes — see Stage 0–1 of the Networking Roadmap for the rules CNI plugins are required to uphold.

Stage 4 — CSI: Storage Attachment

The Container Storage Interface (CSI) is the storage equivalent of CNI: a standard interface that lets storage vendors (AWS EBS, GCE Persistent Disk, NetApp, and others) ship their own drivers instead of Kubernetes maintaining "in-tree" support for every storage backend itself. When a Pod's volume is backed by a PersistentVolumeClaim, the kubelet calls the CSI driver to attach the underlying disk to the Node and mount it, which the kubelet then bind-mounts into the container's filesystem.

This is the mechanical "last mile" of the PV/PVC binding covered conceptually in the Workload Config & Storage Roadmap — that roadmap explains the supply/demand binding model; this stage is about what physically happens on the Node once a claim is bound.

Stage 5 — kube-proxy: Service Traffic

Unlike the kubelet/CRI/CNI/CSI chain, kube-proxy doesn't run as part of that delegation flow — it watches the API Server directly for Services and EndpointSlices, on every Node independently, and programs that Node's own packet-forwarding rules so traffic sent to a Service's virtual IP gets redirected (DNAT'ed) to one of the real Pod IPs behind it.

  • iptables mode — the long-time default: a chain of iptables rules per Service, picking a backend Pod essentially at random per new connection.
  • IPVS mode — uses the Linux kernel's IPVS load balancer for O(1) lookup and more load-balancing algorithm choices, built for clusters with very large numbers of Services.
  • nftables mode — the newer kernel subsystem Kubernetes is migrating toward as the eventual default, replacing iptables.

Stage 6 — Node Health: Status, Heartbeats & Eviction

A Node reports its own health back to the control plane rather than being polled — the kubelet periodically updates the Node object's status (conditions like Ready, MemoryPressure, DiskPressure, plus capacity/allocatable resources), and separately renews a lightweight Lease object in the kube-node-lease namespace as a fast, cheap heartbeat — the same Lease mechanism used for leader election (see the High Availability Roadmap), applied here per-Node instead of per-controller.

When a Node stops renewing its lease and updating its status, the Node Controller (part of kube-controller-manager, not the data plane itself) waits out a grace period, marks the Node NotReady, and eventually evicts its Pods so they can be rescheduled elsewhere. This eviction is deliberately rate-limited (a fraction of nodes per unit time, slowing down further if a large share of the cluster looks unhealthy at once) specifically so a control-plane blip or a network partition doesn't cause a mass eviction stampede across the whole cluster.

This is the data-plane-facing half of a fact from the Control Plane Roadmap: the Node Controller is a control-plane component, but everything it's reacting to — the kubelet's own status/lease updates — originates here, on the data plane.

Resource requests/limits, QoS & node-pressure eviction. A container's request is the amount of CPU/memory the scheduler reserves for it — it is used for placement. Its limit is the ceiling the kubelet enforces through Linux cgroups at run time. Requests vs. limits is the distinction: requests decide where a Pod can run, limits decide how much it may use once running. Exceeding the limit has different effects per resource: over the memory limit, the kernel kills the process and the container shows OOMKilled; over the CPU limit, the container is only throttled (slowed down), never killed. From requests and limits, Kubernetes derives a QoS class: Guaranteed (every container has requests equal to limits for CPU and memory), Burstable (some requests or limits set), and BestEffort (none set). When a Node runs low on a resource and crosses an eviction threshold such as memory.available<100Mi, the kubelet evicts Pods to protect the Node, ranking them first by whether their usage exceeds their requests, then by Pod priority, then by how far usage is above requests — in practice BestEffort and over-request Burstable Pods go first, and Guaranteed Pods (whose usage can never exceed their requests) go last. Related, and often confused: cordon vs. drain — kubectl cordon only marks a Node unschedulable (existing Pods keep running), while kubectl drain cordons it and then evicts its Pods through the Eviction API, which respects PodDisruptionBudgets (a drain waits rather than violate a PDB).

Stage 7 — Putting It Together: A Pod's Full Journey

Tying every stage above into one sequence: a Pod gets assigned to a Node → the kubelet asks the CRI to pull the image and start the container → the kubelet asks the CNI plugin to attach networking and assign an IP → the kubelet asks the CSI driver to mount any requested storage → independently, kube-proxy notices any Service pointing at this Pod and updates its own forwarding rules → the kubelet keeps reporting Node/Pod status and renewing its Lease the whole time, which is what lets the control plane trust that everything above is still actually running.

Precision note: the sequence above says "the kubelet asks the CNI plugin" as shorthand. Strictly, the kubelet asks the container runtime (via CRI) to create the Pod sandbox, and it is the runtime (e.g. containerd) that invokes the CNI plugin to set up networking and assign the IP. Likewise, remote disks are attached by the control plane (attach/detach controller + CSI external-attacher) first; the kubelet then asks the CSI node plugin to mount them.

For the fully worked example — an actual kubectl create deployment and kubectl expose walked step by step, plus a sequence diagram — see Data Plane Deep Dive.

Suggested Learning Order

  1. Stage 0–1 (the framing + kubelet) — the non-negotiable foundation; every later stage is something the kubelet delegates to.
  2. Stage 2–4 (CRI, CNI, CSI) — the three delegation interfaces, in the order the kubelet actually calls them when starting a new Pod.
  3. Stage 5 (kube-proxy) — a parallel, independent path rather than part of that delegation chain, so it's worth learning as its own piece.
  4. Stage 6 (Node health) — how the control plane finds out any of this stopped working.
  5. Stage 7 (the full journey) — only after the individual pieces are solid, since it assumes you already know what each one does.

Each stage answers a why before a how — that's intentional. See also Control Plane Overview for how the control plane and this data plane divide responsibility.
