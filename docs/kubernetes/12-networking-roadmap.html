Kubernetes Networking Roadmap

A concept-first map of Pod networking, Services, kube-proxy, cluster DNS, Ingress, and NetworkPolicy — the ideas, why they exist, and how they connect. Tick each stage as you cover it; progress is saved in this browser.

A concept-first map of Kubernetes networking: how a Pod gets an IP, how that IP stays reachable cluster-wide, how a stable Service hides an unstable set of Pods, how traffic gets into the cluster from outside, and how you restrict who can talk to whom. Follow top to bottom — each stage assumes the one before it. Tick a stage's box once you've genuinely covered it; progress is saved in this browser.

Stage 0 — The Kubernetes Networking Model

The non-negotiable rules every other stage builds on. Kubernetes doesn't implement these itself — it delegates them to a CNI plugin (Stage 1) — but every plugin must honor them.

  • Every Pod gets its own IP address — no port-mapping, no shared host ports between Pods.
  • Every Pod can reach every other Pod's IP directly, without NAT, regardless of which Node either is on.
  • A Node can reach every Pod's IP without NAT (used for health checks, kubelet probes, etc.).
  • Containers within the same Pod share one network namespace — they talk to each other over localhost, and share the same IP and port space.

Why this matters: because every Pod IP is directly routable, application code never has to think about NAT traversal or port juggling to reach another Pod — it just connects to that Pod's IP as if it were on the same flat network. That flatness is what every higher layer below (Services, DNS, Ingress, NetworkPolicy) is built on top of.

flowchart TD subgraph N1["Node 1"] P1["Pod A — 10.244.1.5"] P2["Pod B — 10.244.1.6"] end subgraph N2["Node 2"] P3["Pod C — 10.244.2.7"] end P1 <--> P2 P1 <--> P3 P2 <--> P3

Pod IPs are directly reachable across Nodes, with no NAT in between — that's the flat network the rule set above guarantees.

Stage 1 — Pod Networking & CNI Plugins

Kubernetes itself does not implement Pod networking — it defines the rules from Stage 0 and delegates the actual implementation to a CNI (Container Network Interface) plugin. When kubelet creates a Pod, it calls the configured CNI plugin to create that Pod's network namespace, assign it an IP, and wire it into the cluster network — Kubernetes never touches a network interface directly.

  • Overlay networks (e.g. Flannel's VXLAN mode) wrap Pod-to-Pod traffic in an extra packet header so it can cross Nodes over the existing physical network, at the cost of some encapsulation overhead.
  • Native/BGP routing (e.g. Calico's default mode) advertises each Node's Pod IP range as a normal route, so packets travel unmodified — faster, but requires the underlying network to support the routing.
  • eBPF-based plugins (e.g. Cilium) implement routing, Services, and NetworkPolicy in the Linux kernel via eBPF instead of iptables, which is where kube-proxy's job (Stage 3) is heading on modern clusters.

Why it matters: the CNI choice is usually invisible to application code — Stage 0's guarantees hold no matter which plugin you run — but it directly affects performance, and whether advanced features like NetworkPolicy (Stage 6) or encryption between Pods are even available at all.

Stage 2 — Services: Stable Access to Unstable Pods

Pod IPs from Stage 0 are not stable — a Pod that crashes and gets recreated by a controller (see kube-controller-manager) comes back with a brand-new IP. A Service solves that by giving a group of Pods (selected by label) one stable virtual IP and DNS name that never changes, while the Pods behind it come and go freely. The Endpoint/EndpointSlice Controller keeps the live list of matching Pod IPs up to date automatically.

The Service IP never changes even as the Pods behind it are replaced — clients only ever need to know that one stable address.

Stage 3 — kube-proxy: How a Service IP Becomes Real Traffic

A Service's virtual IP isn't attached to any real network interface — nothing is "listening" on it. kube-proxy, running on every Node, is what makes it work: it watches the API Server for Services and EndpointSlices, and programs each Node's packet-forwarding rules so that any packet sent to a Service IP gets rewritten (DNAT) to one of the real Pod IPs behind it.

  • iptables mode (the long-time default): programs a chain of iptables rules per Service; picks a backend Pod at random per new connection. Simple, but rule evaluation is effectively linear in the number of Services, so it degrades on very large clusters.
  • IPVS mode: uses the Linux kernel's IPVS load balancer instead of iptables chains, giving O(1) lookup and more load-balancing algorithm choices — built for clusters with thousands of Services.

Why it matters: this is the layer where a Service's "stable IP" claim actually gets enforced in practice — if kube-proxy is down or hasn't synced yet on a Node, Pods on that Node simply can't reach any Service IP, even though the Service object itself looks perfectly healthy in the API.

Stage 4 — Cluster DNS (CoreDNS)

Remembering Service IPs isn't practical, so every cluster runs CoreDNS as a cluster-internal DNS server. Every Service automatically gets a DNS name of the form <service>.<namespace>.svc.cluster.local, which resolves to that Service's stable ClusterIP — so application code connects to a name like db.default.svc.cluster.local instead of hardcoding an IP that could be recreated with a different address if the Service itself were ever deleted and recreated.

flowchart LR App["App in a Pod"] -->|"lookup db.default.svc.cluster.local"| DNS["CoreDNS"] DNS -->|"10.96.0.55"| App App -->|connects to| SVC["Service VIP 10.96.0.55"]

Pods within the same Namespace can also reach a Service by its short name alone (e.g. just db) — the Pod's DNS search path fills in the rest.

Stage 5 — Ingress & Ingress Controllers

A LoadBalancer Service (Stage 2) gets you one external IP per Service — fine for one or two Services, expensive and unwieldy for dozens of HTTP services that all need their own public endpoint. Ingress solves this for HTTP(S) traffic specifically: it's a single set of host/path routing rules ("api.example.com → Service A", "example.com/blog → Service B") that one shared load balancer can enforce, instead of one load balancer per Service.

An Ingress object is only a set of rules, though — it does nothing by itself. An Ingress Controller (e.g. NGINX Ingress, Traefik) is the actual running proxy that watches Ingress objects and enforces them; without a controller installed, creating an Ingress object has no effect at all.

flowchart TD Internet["Internet"] --> LB["One external LoadBalancer"] LB --> IC["Ingress Controller"] IC -->|"host: api.example.com"| SvcA["Service A"] IC -->|"path: /blog"| SvcB["Service B"]

Worth knowing as a term, not a stage to necessarily master right away: the newer Gateway API is Kubernetes' in-progress successor to Ingress, aiming to cover more than just HTTP and fix several of Ingress's long-standing limitations.

Stage 6 — NetworkPolicy: Restricting Traffic

Stage 0's flat network means that, by default, every Pod can reach every other Pod — there is no isolation between Namespaces or workloads unless you add it yourself. A NetworkPolicy is how you add it: a label-selector-based rule that says which Pods a given set of Pods is (or isn't) allowed to send/receive traffic from.

  • NetworkPolicies are additive and default-deny once any policy selects a Pod: the moment one NetworkPolicy targets a Pod, all traffic not explicitly allowed by some policy is dropped for that Pod.
  • NetworkPolicy enforcement is not built into core Kubernetes — it requires a CNI plugin that implements it (Calico and Cilium do; some minimal CNI plugins don't). Creating a NetworkPolicy on a cluster whose CNI doesn't support it silently does nothing.

Why it matters: this is the mechanism behind "the frontend namespace can't reach the database namespace directly" — the same kind of namespace-boundary enforcement covered from the RBAC angle in RBAC: Namespace Scoping, but for network traffic instead of API access.

Stage 7 — Advanced & Emerging Topics

  • Service Mesh (Istio, Linkerd): injects a sidecar proxy into every Pod to add mutual TLS between services, fine-grained traffic shifting/canarying, and detailed traffic metrics — capabilities that sit above what Services + NetworkPolicy + Ingress provide on their own, at the cost of real operational complexity.
  • Gateway API: the evolving, more expressive successor to Ingress (see Stage 5), designed to also cover TCP/UDP and cross-namespace routing cleanly.
  • Dual-stack networking: running Pods and Services with both IPv4 and IPv6 addresses simultaneously, rather than choosing one.
  • Multi-cluster networking: connecting Pods/Services across separate clusters (e.g. Cilium Cluster Mesh, Istio multi-cluster) — relevant once a single cluster stops being enough.

Suggested Learning Order

  1. Stage 0–1 (the networking model + CNI) — the non-negotiable foundation; skipping this makes every later stage feel like memorized trivia instead of a mechanism.
  2. Stage 2–4 (Services, kube-proxy, DNS) — how Kubernetes turns "a bunch of ephemeral Pod IPs" into something an application can actually depend on.
  3. Stage 5 (Ingress) — the layer most people meet first in practice (it's how traffic gets in from the internet), but it only makes sense once Services are solid.
  4. Stage 6 (NetworkPolicy) — security/isolation, once you understand what's reachable by default.
  5. Stage 7 (advanced/emerging) — only after the rest is solid; service mesh in particular is easy to over-adopt before you need it.

Each stage answers a why before a how — that's intentional. See also Control Plane Overview for how the control plane and data plane (where all of this networking actually runs) fit together.
