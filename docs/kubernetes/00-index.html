Kubernetes Control Plane: Overview

The brain of the cluster — architecture, the reconciliation loop, and how kube-apiserver, etcd, the scheduler, and the controller manager depend on each other.

What Is the Control Plane?

The Kubernetes Control Plane is the brain of the cluster. It is responsible for managing cluster state, making scheduling decisions, maintaining desired state, and coordinating all cluster operations.

Every Kubernetes action eventually passes through the Control Plane.

Example operations

  • Creating a Deployment
  • Scaling Pods
  • Updating ConfigMaps
  • Scheduling workloads
  • Recovering failed Pods
  • Managing Nodes

The Control Plane continuously works to ensure the actual cluster state matches the desired state defined by users.

Control Plane vs. Data Plane

Everything on this page runs on the control plane. The actual workloads — your containers — run on separate worker nodes, which make up the data plane. Worker nodes talk to the control plane exclusively through kube-apiserver; they never touch etcd, the scheduler, or the controller manager directly.

Worker node components

  • kubelet — the agent on every worker node. It watches the API server for Pods assigned to its node, tells the container runtime to start/stop containers to match, and reports node and Pod status back.
  • kube-proxy — maintains the network rules (iptables/IPVS) on each node so traffic sent to a Service's virtual IP gets routed to one of the matching Pods.
  • Container runtime (containerd, CRI-O, etc.) — pulls container images and actually runs the containers, driven by kubelet through the Container Runtime Interface (CRI).

High Availability of the Control Plane

A production cluster doesn't run a single copy of each control-plane component:

  • kube-apiserver runs as multiple stateless replicas behind a load balancer — any replica can serve any request, since all state lives in etcd.
  • etcd runs as a clustered quorum, typically 3 or 5 members, tolerating the loss of a minority of nodes without losing data or availability.
  • kube-scheduler and kube-controller-manager run as several replicas each, but only one is active at a time per component — the others stand by. They use a Lease object in etcd for leader election: the active replica renews its lease periodically, and if it stops, a standby claims the lease and takes over.

Key Takeaways

  • The Control Plane is the brain of Kubernetes.
  • kube-apiserver is the single entry point to the cluster.
  • etcd stores the entire cluster state and acts as the source of truth.
  • kube-scheduler decides where Pods should run.
  • kube-controller-manager continuously reconciles desired and actual state.
  • Controllers provide Kubernetes self-healing behavior.
  • Scheduler handles placement, not execution.
  • API Server is the communication hub for all Kubernetes components.
  • etcd is the most critical data component and requires strong backup practices.
  • Kubernetes operates through a continuous reconciliation loop driven by controllers and desired state.
