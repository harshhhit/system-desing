Kubernetes API Request Flow: Auth, AuthZ, Admission

Walking a single kubectl get pods -n frontend call through authentication, authorization, admission control, validation, and etcd — read vs. write paths.

Interview Answer — What Happens When a Request Reaches the Kubernetes API Server?

Every Kubernetes API request — whether it's typed as kubectl, sent by a controller, or issued by another Pod's service-account token — is handled by kube-apiserver through the same ordered pipeline: authentication, authorization, admission control, and API validation, before the request is either persisted (a write) or served back from current state (a read).

kube-apiserver is the single front door to the cluster: it's the only control-plane component that talks to etcd directly, and every other component (Scheduler, Controller Manager, kubelet) reads and writes cluster state by calling it, not by touching etcd themselves. That's why this pipeline matters — it's the one gate every request passes through, regardless of who sent it or what tool they used.

Mechanically, the request first goes through Authentication ("who are you?" — via client certificate, bearer token, OIDC, or a service-account token), then Authorization ("can you do this?" — RBAC is the common mechanism), then Admission Control ("should this request be accepted, or should it be modified first?" — Pod Security, resource quotas, mutating/validating webhooks), then API validation against the object schema. Only after all of that does a write get persisted to etcd; a read is served from current state instead, as the page's own "A concrete example: kubectl get pods -n frontend" section walks through step by step.

One nuance: not every stage does equal work on every request. Authentication and authorization run for literally every call, but admission control's job is to inspect or modify an object being written — so its work is concentrated on create/update/patch/delete calls, not on reads. See the follow-up below for the full reasoning.

Simple interview version

"Every request to the Kubernetes API server goes through the same pipeline: authentication figures out who you are, authorization (usually RBAC) checks whether you're allowed to do what you're asking, admission control can modify or reject the request, and API validation checks the object against the schema. If it's a write, the API server then persists the object to etcd and controllers react to the change; if it's a read, the API server just returns current state without touching etcd for a new write."

One important interview follow-up

Q: Does every request — including simple reads like kubectl get pods — go through all the same stages (authentication, authorization, admission control, validation)?

A: Authentication and authorization apply to every request, full stop — the API server always needs to know who's calling and whether they're allowed to perform that verb on that resource, whether it's a get or a delete. Admission control is different: mutating and validating admission webhooks, and most built-in admission plugins, exist to inspect or modify an object that's about to be written, so they generally only run on requests that create, update, patch, or delete an object. A plain read/get/list has no object being written, so there's nothing for those plugins to mutate or validate, and they're skipped. This lines up with the page's own concrete example: the ordered steps list "Admission control can modify or reject the request" right before "API validation checks the object," and the very next step notes that a read simply returns current state "rather than writing a new object to etcd" — there's no object-write step for admission to act on in that path.

Request Flow, Step by Step

This is the kube-apiserver request path — the sequence every API call follows before the desired state is enforced.

A simplified flow

flowchart TD A["User / kubectl / application"] --> B["Authentication
#quot;Who are you?#quot;"] B --> C["Authorization
#quot;Can you do this?#quot;"] C --> D["Admission Control
#quot;Should this request be accepted?#quot;"] D --> E["API validation
#quot;Is the request valid?#quot;"] E --> F["API processing"] F --> G["etcd
#quot;Persist cluster state#quot;"] G --> H["Kubernetes controllers / scheduler / kubelet"]

A concrete example: kubectl get pods -n frontend

More precisely, for a request such as:

kubectl get pods -n frontend

the request goes roughly:

  1. kubectl sends HTTPS request to kube-apiserver.
  2. Authentication identifies the caller:
    • client certificate
    • bearer token
    • OIDC
    • service-account token
    • etc.
  3. Authorization checks whether that identity is allowed to perform the requested operation.
    • RBAC is the common mechanism.
  4. Admission control can modify or reject the request.
    • Pod Security
    • resource quotas
    • validating/mutating admission policies/webhooks
    • etc.
  5. API validation checks the object/request against the Kubernetes API schema and rules.
  6. If it is a write operation, the API server persists the resulting object in etcd.
  7. Controllers/watchers receive the change and Kubernetes reconciles the desired state.
  8. For a read such as get pods, Kubernetes normally reads the current state rather than writing a new object to etcd.

A->>A: Authorize ("can you do this?") A->>A: Admission Control A->>A: API Validation alt read A-->>U: Return current state (no etcd write) else write A->>E: Persist object E-->>A: Ack A-->>U: Response end

Watches: How Controllers Stay in Sync

Controllers and kubectl get pods --watch don't poll the API server in a loop. They use the List + Watch pattern:

  1. List — fetch the current set of objects once, which comes back with a resourceVersion marking that point in time.
  2. Watch — open a long-lived HTTP connection starting from that resourceVersion, over which the API server streams ADDED / MODIFIED / DELETED events as they happen.

The API server serves these watches from its in-memory watch cache rather than re-querying etcd per client, which is how thousands of controllers and kubectl sessions can watch the same objects without overwhelming etcd.
