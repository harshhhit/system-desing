Data Plane Deep Dive

Kubelet, CRI, CNI, CSI, and kube-proxy — the worker-node layer that actually runs containers, wires up networking and storage, and forwards Service traffic.

Interview Answer — What Is the Kubernetes Data Plane?

The data plane is the set of components that actually run your workloads and move traffic on each worker node — as opposed to the control plane, which makes the cluster-wide decisions about what should run and where. If the control plane is the "brain" deciding desired state, the data plane is the "muscle" that carries that decision out on the ground, node by node.

In Kubernetes, the data plane lives entirely on worker nodes and is made up of the kubelet (the node agent that watches the API Server for Pods assigned to its node), the container runtime reached through the CRI (which actually pulls images and starts containers), the CNI plugin (which wires up Pod networking), the CSI driver (which attaches and mounts storage), and kube-proxy (which programs the node's packet-forwarding rules for Services). None of these components make cluster-wide scheduling or reconciliation decisions — they execute what the control plane already decided.

Mechanically, this shows up as a chain of delegation on every node: the kubelet doesn't create containers itself, it calls the CRI; it doesn't wire up networking itself, it calls a CNI plugin; it doesn't mount cloud disks itself, it calls a CSI driver. Kube-proxy runs on the same node but outside that delegation chain — it watches the API Server directly for Services and EndpointSlices and updates the node's iptables/IPVS rules on its own.

The nuance worth stating plainly: every one of these — kubelet, CRI, CNI plugin, CSI driver, kube-proxy — runs once per worker node, not once per cluster. A 50-node cluster runs 50 kubelets and 50 kube-proxies, each only aware of its own node. That per-node replication is exactly why the data plane keeps working even if the control plane is briefly unreachable — already-running Pods and already-programmed iptables rules don't disappear just because the API Server is temporarily unavailable.

Simple interview version

"The data plane is the worker-node layer that actually executes what the control plane decides — it's made up of the kubelet, the container runtime reached via CRI, the CNI plugin for Pod networking, the CSI driver for storage, and kube-proxy for Service traffic forwarding. All of these run per-node, not per-cluster, and none of them make scheduling or cluster-wide decisions — they carry out what was already decided, and keep running even if the control plane is briefly unavailable."

One important interview follow-up

Q: Is kube-proxy part of the control plane, since it's one of Kubernetes' "core" components?

A: No — kube-proxy is part of the data plane. It runs on every worker node, exactly like the kubelet and container runtime described in "5. Kube-proxy (Network Forwarding)" above, rather than as a single cluster-wide process the way kube-scheduler or kube-controller-manager run. Its job is purely local and mechanical: watch the API Server for Services and EndpointSlices, and program that one node's iptables/IPVS rules so packets aimed at a Service IP get DNAT'ed to a real Pod IP. It doesn't decide which node a Pod should run on (that's kube-scheduler's job) and it doesn't reconcile cluster-wide desired-vs-actual state (that's kube-controller-manager's job) — being "core" to how Kubernetes networking works doesn't put a component in the control plane; only running as a cluster-wide singleton (or HA pair) that makes cluster-wide decisions does that.

What Is the Data Plane?

The Data Plane is the "muscle." It is the actual execution layer where your applications (containers) run. It is responsible for moving data (network traffic) and managing resources (storage and compute) on the worker nodes.

Major Theory to Understand

1. Kubelet (The Node Agent)

Theory: The Kubelet is the "captain" of the worker node. It is the primary interface between the Control Plane and the node. It watches the API Server for Pod specifications (PodSpecs) assigned to its node. Its primary job is Pod Lifecycle Management — ensuring that the containers described in the PodSpec are running and healthy. If a container crashes, the Kubelet restarts it (if configured to do so).

Key detail: It does not create containers directly; it delegates that task to the CRI.

2. CRI (Container Runtime Interface)

Theory: The CRI is an abstraction layer (a standard API) that allows Kubelet to use different container runtimes without changing its own code. Think of it as a universal translator.

Why it exists: Kubernetes needs to run containers, but there are many runtimes (Docker, containerd, CRI-O). Instead of hardcoding support for each, Kubernetes defined the CRI. The Kubelet calls the CRI gRPC endpoints, and the runtime (e.g., containerd) actually pulls the image and starts the containers using Linux namespaces and cgroups.

3. CNI (Container Network Interface)

Theory: The CNI is another abstraction layer, but this time for networking. When a Pod is created, it needs an IP address and a virtual network interface. The CNI is a set of specifications and libraries that define how a container runtime should set up the network.

How it works: The Kubelet/CRI calls the CNI plugin (e.g., Calico, Flannel, Cilium) to add a network interface to the Pod's network namespace. The CNI plugin is responsible for assigning an IP, routing traffic between Pods across different nodes, and enforcing network policies.

4. CSI (Container Storage Interface)

Theory: The CSI is the abstraction layer for storage. Before CSI, storage drivers were baked into the Kubernetes core (in-tree), making it hard for vendors to release new features. CSI allows storage providers (e.g., AWS EBS, Google Persistent Disk, NetApp) to write drivers that run as Pods in the cluster.

How it works: When a Pod requests a Persistent Volume, the Kubelet uses the CSI driver to mount a remote disk (SAN/NAS) onto the local filesystem of the worker node, making it available to the container.

5. Kube-proxy (Network Forwarding)

Theory: Kube-proxy is a network daemon that runs on every node. It does not proxy traffic for Pods to the internet; instead, it implements the Service abstraction. A Service gives a single, stable IP (ClusterIP) to a group of Pods whose IPs change frequently.

How it works: Kube-proxy watches the API Server for new Services and EndpointSlices. It then programs the node's kernel packet-filtering rules (using iptables or IPVS) so that when a Pod tries to talk to a Service IP, the kernel intercepts that packet and load-balances it to one of the actual backend Pod IPs.

Practical Usage Example: Deploying a Web Application

Let's put this into a real-world scenario. You are a developer, and you run this command:

kubectl create deployment nginx --image=nginx

Here is the step-by-step journey through the Data Plane:

Step 1: The Control Plane assigns the Pod to Worker Node A.
The Kubelet on Worker Node A sees the API Server update and realizes it must run an nginx container.

Step 2: Kubelet talks to CRI (containerd).
The Kubelet sends a request via the CRI interface: "Pull the 'nginx' image and start a container." Your chosen CRI (e.g., containerd) downloads the Docker image layers and creates the container processes (using cgroups for resource limits). The container is now running, but it has no network and no disk yet.

Step 3: Kubelet asks CNI (Calico) for an IP.
The CRI triggers the CNI plugin. The CNI plugin (e.g., Calico) creates a virtual Ethernet pair (veth), attaches one end to the Pod's network namespace, and assigns an IP address (e.g., 10.244.1.5). The CNI also adds a routing rule on the node so that packets destined for 10.244.1.5 go to this specific Pod. The Pod can now communicate with other Pods across the cluster.

Step 4: Kubelet asks CSI (e.g., AWS EBS) for a disk (Optional).
If your YAML file specified a Persistent Volume Claim, the Kubelet would call the CSI driver. The CSI driver would communicate with the AWS API to attach a physical EBS volume to Worker Node A, then mount it to a specific directory on the host (e.g., /var/lib/kubelet/plugins/...), and finally bind-mount that directory into the nginx container so it can save files persistently.

Step 5: Kube-proxy enables external access.
Now, you want to access this nginx from your browser. You run:

kubectl expose deployment nginx --type=NodePort --port=80

Kube-proxy (watching the API) sees this new Service. It runs iptables commands on Worker Node A.

  • Rule 1: "If a packet enters this node on port 30000 (NodePort), send it to the ClusterIP (e.g., 10.96.0.1)."
  • Rule 2: "If a packet is destined for ClusterIP 10.96.0.1, randomly forward it to the Pod's actual IP (10.244.1.5) using DNAT."

When you type http://<Node-IP>:30000 in your browser, the packet hits the node's kernel, iptables modifies the destination to 10.244.1.5:80, and the CNI routes it directly to your nginx container.
