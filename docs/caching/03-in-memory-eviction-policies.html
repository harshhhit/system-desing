In-Memory Eviction Policies

LRU, LFU, FIFO, MRU, Random, CLOCK, SLRU/2Q, ARC and W-TinyLFU, TTL expiration, and Redis maxmemory-policy — what a full cache throws out, and why.

What you'll learn

By the end of this page you will be able to:

  • Explain eviction vs. expiration
  • Compare LRU, LFU, FIFO, MRU, random, CLOCK, SLRU/2Q, ARC and W-TinyLFU
  • Implement an O(1) LRU cache
  • Explain how Redis approximates LRU/LFU and expires keys
  • Choose a Redis maxmemory-policy and avoid OOM surprises

Why Eviction Policies Matter

A cache is deliberately smaller than the data behind it. When it fills, something must go — and the eviction policy's guess about what will be needed next decides the hit ratio. A good guess keeps the hot set in memory; a bad one (or a scan) flushes it and sends traffic to the database.

💡 Important

No policy fixes a cache that's too small for its working set. If the hot keys don't fit, every policy thrashes — add memory before tuning the policy.

Terms used on this page

  • Victim — the entry the policy chooses to remove.
  • Hit ratio — hits ÷ total lookups. The metric every policy is judged by.
  • Working set — keys actively read in a time window. If the working set is larger than the cache, every policy performs badly (thrashing) — add memory rather than tuning the policy.
  • Scan — a one-time sequential read of many keys (a batch job, a crawler, a report). Scans are the classic way to destroy a naive LRU cache.
  • Belady's optimal (MIN) — the theoretical best policy: evict the key whose next use is farthest in the future. It needs knowledge of the future, so it is unimplementable, but it is the benchmark real policies are compared against.

1. LRU — Least Recently Used

What it is: evict the entry that has gone the longest without being read or written. Why it works: temporal locality — a key read a moment ago is likely to be read again soon. It is the default in most caching libraries and in memory-limited systems.

Example (capacity 3): access A, B, C → cache [C, B, A] (most recent first) → access A → [A, C, B] → insert D → the least recent is B → evict B → [D, A, C].

  • Pros: simple, O(1), adapts quickly when popularity shifts.
  • Cons: scan pollution — a batch job that reads 1 million cold keys once pushes out every genuinely hot key, because each cold key is "most recent" at the moment it is read. It also forgets frequency: a key read 10,000 times yesterday loses to a key read once a second ago.

Implementing LRU in O(1) (a classic interview question)

Combine a hash map (key → node, O(1) lookup) with a doubly linked list (ordered by recency, O(1) move and remove). On get: look up the node, move it to the head. On put: insert/update at the head; if over capacity, remove the tail node and delete its key from the map.

from collections import OrderedDict
class LRUCache:
 def __init__(self, capacity):
 self.capacity = capacity
 self.data = OrderedDict()
 def get(self, key):
 if key not in self.data:
 return None
 self.data.move_to_end(key)
 return self.data[key]
 def put(self, key, value):
 if key in self.data:
 self.data.move_to_end(key)
 self.data[key] = value
 if len(self.data) > self.capacity:
 self.data.popitem(last=False)

OrderedDict is itself a hash map plus a doubly linked list, which is why every operation stays O(1). In an interview, be ready to write the explicit node/list version. For concurrent use, a single lock around the list becomes a bottleneck — production caches (Caffeine) buffer reads in lock-free ring buffers and replay them onto the list in batches.

⚠️ Common mistake

Running a nightly batch job against the same LRU cache your users hit. Every one-time key it reads becomes "most recent" and pushes the real hot set out — the morning starts with a cold cache. Use a scan-resistant policy (LFU, W-TinyLFU) or a separate cache for batch work.

2. LFU — Least Frequently Used

What it is: evict the entry with the lowest access count. Why it exists: when popularity is stable (a product catalogue, reference data), frequency predicts the future better than recency, and LFU is naturally scan-resistant — keys read once during a scan have count 1 and are evicted first.

Example (capacity 3): A read 50 times, B 20 times, C 2 times → insert D → evict C (lowest count), even if C was read a second ago.

  • Cons — cache pollution by old popularity: a key that was hot last week keeps a huge count and never leaves, even if nobody reads it now. Fix: aging / decay — periodically halve all counters, or decay them with time.
  • Cons — new keys are fragile: a new key starts at count 1 and is the first victim, even if it is about to become hot. Fix: give new entries an initial count, or use a small admission window (see W-TinyLFU).
  • Implementation: O(1) LFU uses a map of key → node plus a map of frequency → doubly linked list of keys, tracking the current minimum frequency.

LRU vs. LFU — the difference is what counts as evidence of future use: LRU trusts how recently a key was used (adapts fast, fooled by scans), LFU trusts how often (resists scans, slow to adapt to change without decay).

3. FIFO — First In, First Out

Evict the oldest inserted entry, ignoring reads. Cheap (a queue, no update on read — which also means reads need no lock). Weakness: a key read every second is still evicted just because it was inserted early. Useful when entries have a natural lifetime anyway. Recent research policies (S3-FIFO, SIEVE) show that FIFO queues plus a small "visited" bit can match or beat LRU on real web-cache traces while staying lock-friendly.

4. LIFO and MRU — evict the newest

MRU (Most Recently Used) evicts the entry just used; LIFO evicts the entry just inserted. They sound backwards, but they are optimal for cyclic scans larger than the cache: if a job loops over 1,000 items with room for 900, LRU misses on every single access (each item is evicted just before it is needed again), while MRU keeps 899 items stable and hits most of the time. Rare in application caches; appears in database buffer managers for specific scan patterns.

5. Random replacement

Evict a random entry. No bookkeeping per access at all, and no worst-case pattern for an attacker or a scan to exploit. It performs surprisingly close to LRU on many workloads and is used in some CPU caches and in Redis's allkeys-random / volatile-random. Best when access is roughly uniform, or when you want predictable, low CPU cost.

6. CLOCK (second chance)

An approximation of LRU with cheaper reads. Entries sit in a circular buffer with a reference bit. A read just sets the bit to 1 (no list moves, no lock). To evict, a "clock hand" sweeps: bit 1 → clear it to 0 and move on (a second chance); bit 0 → evict. Used by operating systems for page replacement and by PostgreSQL's buffer manager (clock-sweep, with a usage counter up to 5 instead of one bit).

7. Segmented LRU (SLRU) and 2Q

Both split the cache so one-time keys can't evict proven hot keys.

  • SLRU — a probationary segment and a protected segment, each LRU. New keys enter probation; a second hit promotes them to protected; keys demoted from protected fall back to probation. A scan only churns probation. Memcached uses a segmented LRU per slab class (HOT / WARM / COLD queues).
  • 2Q — a small FIFO for first-time keys (A1in), a "ghost" list remembering keys recently evicted from it (A1out, keys only), and a main LRU (Am). A key reaches the main LRU only if it is requested again while still remembered — proof it is not a one-off.
  • MySQL InnoDB uses the same idea as a midpoint insertion LRU: new pages enter at the 3/8 point ("old" sublist) and move to the "young" sublist only if read again after innodb_old_blocks_time (1 second by default), so a full-table scan can't flush the buffer pool.

8. ARC — Adaptive Replacement Cache

ARC keeps two LRU lists — T1 (seen once recently) and T2 (seen at least twice) — plus two ghost lists of recently evicted keys (B1, B2). A hit in ghost list B1 means "we evicted a recency key too early" → grow T1's share; a hit in B2 means the opposite → grow T2. So ARC self-tunes between recency and frequency with no parameter. Used by ZFS (the ARC is ZFS's main read cache). PostgreSQL 8.0 briefly used ARC and replaced it because of an IBM patent, moving to 2Q and then clock-sweep.

9. W-TinyLFU (Caffeine)

The policy behind Java's Caffeine library, and one of the best-performing general-purpose policies known. It is built from three parts:

  1. Window — a small LRU (~1% of capacity) that every new key enters first, so a burst of new keys gets a chance to prove itself (fixes LFU's "new keys are fragile").
  2. Main — a large SLRU (the rest, split ~20% probation / ~80% protected).
  3. TinyLFU admission filter — a compact frequency sketch (a Count-Min Sketch, a few bits per key, covering keys even after they leave the cache). When a key leaves the window, it is admitted to main only if its estimated frequency is higher than the main cache's eviction victim. Counters are periodically halved (aging), fixing LFU's "old popularity" problem.

Cause → effect: a scan's one-time keys enter the window → they have frequency ~1 → they lose the admission contest against established keys → they are dropped without disturbing the main cache. Caffeine additionally tunes the window size at runtime (hill climbing) for workloads that favour recency.

🧠 Think about it

Why does W-TinyLFU keep frequency counts for keys that are no longer in the cache? (So a key evicted yesterday but popular again today can win admission immediately — the sketch remembers its history cheaply.)

Expiration (TTL) — the freshness side

  • Absolute TTL (expire-after-write) — the entry expires N seconds after it was written, however often it is read. Bounds staleness: SET user:42 … EX 300 means never more than 5 minutes old.
  • Sliding expiration (expire-after-access) — each read resets the timer. Keeps hot entries forever — good for sessions ("log out after 30 minutes of inactivity"), bad for freshness because a constantly read value is never reloaded.
  • Choosing a TTL — from the staleness budget, not from gut feeling: "how wrong may this value be, and for how long?" Add jitter (e.g. 300 s ± 10%) so keys written together don't expire together — see cache avalanche.

How Redis actually removes expired keys

An expired key is not deleted at the exact second it expires. Redis uses two mechanisms together:

  1. Lazy (passive) expiry — when a client reads a key, Redis checks its TTL first; if expired, it deletes it and returns nil. Readers never see an expired value.
  2. Active expiry — about 10 times per second (hz 10), Redis samples 20 keys that have a TTL and deletes the expired ones; if more than 25% of the sample was expired, it repeats immediately.

Consequence: expired-but-unread keys can occupy memory for a while, so memory usage can exceed what "live" keys need. Under maxmemory pressure, eviction may then remove live keys while expired ones still sit in memory — watch the expired_keys and evicted_keys counters in INFO stats.

Redis eviction policies (maxmemory-policy)

Redis evicts only once memory reaches maxmemory. The policy then decides which keys are candidates (all keys, or only keys with a TTL — the "volatile" set) and how to rank them:

Gotcha: volatile-* with no TTL keys behaves like noeviction

If a volatile-* policy finds no keys with a TTL, there is nothing it may evict, and writes fail with OOM command not allowed when used memory > 'maxmemory'. Either put TTLs on cache keys or use an allkeys-* policy. Also leave headroom: replication buffers and copy-on-write during BGSAVE use memory beyond maxmemory.

Redis LFU details: each key stores an 8-bit logarithmic counter (a Morris counter, so 255 represents roughly a million accesses with the default lfu-log-factor 10) and a last-decrement time. The counter decays by one for every lfu-decay-time minutes (default 1) of idleness, and new keys start at 5 so they aren't evicted instantly. OBJECT FREQ <key> shows a key's counter.

Memcached, by contrast, has no policy choice: it uses a segmented LRU per slab class (memory is pre-divided into chunk sizes). Gotcha: eviction happens within a slab class, so a class of small items can evict hot keys while another class has free memory — the slab rebalancer (slab_reassign, slab_automove) moves pages between classes.

redis-cli CONFIG SET maxmemory 4gb
redis-cli CONFIG SET maxmemory-policy allkeys-lfu
redis-cli INFO stats | grep -E "evicted_keys|expired_keys|keyspace_hits|keyspace_misses"
redis-cli OBJECT FREQ user:42
redis-cli --bigkeys
  • maxmemory + maxmemory-policy — eviction only starts once the limit is reached.
  • evicted_keys vs. expired_keys — evictions are memory pressure; expirations are TTLs doing their job.
  • OBJECT FREQ — the logarithmic LFU counter for a key (only under an LFU policy).
  • --bigkeys — finds the largest keys, which distort memory and eviction.

Production Usage

  • Pure cache instance: allkeys-lru by default; allkeys-lfu when batch scans or very stable hot keys exist.
  • Mixed instance (cache + data you can't lose): volatile-lru/volatile-lfu with TTLs on cache keys only — or better, separate instances.
  • Primary store (queues, sessions): noeviction and alerts on memory, so you get errors instead of silent data loss.
  • In-process: Caffeine (W-TinyLFU) on the JVM; size by entries or weight.

Signals to watch

  • Hit ratio — the policy's report card.
  • Eviction rate — sustained evictions with a falling hit ratio = undersized cache.
  • used_memory vs. maxmemory, fragmentation ratio.
  • OOM errors on writes — noeviction or volatile-* with no TTL keys.

🔥 Production insight

A rising eviction rate is often the first sign of a deploy that changed key shapes (e.g. added a field to every key) or forgot TTLs — memory fills with keys nobody will read again, and genuinely hot keys get evicted.

Performance & Scalability

  • Per-read cost: LRU moves a list node (needs a lock under concurrency); CLOCK and FIFO only set a bit or nothing — better for highly concurrent caches.
  • Approximation: Redis samples keys (maxmemory-samples, default 5) instead of keeping a global list — less memory and CPU, slightly less precise.
  • Scan resistance matters more than precision for mixed workloads.
  • Memory overhead: per-entry metadata (pointers, counters) can be significant for small values.

Best Practices

Do

  • Always set maxmemory and an explicit policy.
  • Pick allkeys-lru by default; allkeys-lfu for scans or stable hot sets.
  • Use TTLs with jitter on every cache key.
  • Separate "cache" data from "can't lose" data (different instances or volatile-* + TTLs).
  • Measure hit ratio before and after any policy change.

Avoid

  • Running a cache on noeviction.
  • volatile-* policies when most keys have no TTL.
  • Tuning the policy when the real problem is cache size.

Interview Answer — What Is a Cache Eviction Policy?

An eviction policy is the rule a cache uses to choose which entry to remove when it is full and a new entry must be stored. The common policies rank entries by recency (LRU — least recently used), frequency (LFU — least frequently used), insertion order (FIFO), or pick at random; modern caches such as Caffeine combine recency and frequency (W-TinyLFU).

Eviction exists because an in-memory cache is deliberately much smaller than the data behind it — RAM is expensive, and the whole point is to hold only the hot subset. When memory runs out, the cache must either drop something or refuse the write. The cause → effect chain is: the cache reaches its memory limit → a new key arrives → the policy picks a victim → if it picked a key that is about to be read again, that read becomes a miss and goes to the database. A good policy therefore maximises the hit ratio for a fixed amount of memory by predicting which keys will not be needed soon.

Eviction is separate from expiration (TTL). Eviction vs. expiration — the difference is the trigger: eviction removes keys because of memory pressure, whatever their age; expiration removes keys because they are too old to trust, whatever the memory usage. Production caches use both: a TTL bounds staleness, an eviction policy bounds memory. The comparison table summarises every policy.

Simple interview version

"An eviction policy decides what to drop when the cache is full. LRU drops the entry not used for the longest time and is the usual default because recent use predicts future use; LFU drops the least-used entry and is better when popularity is stable; FIFO and random are cheap but ignore usage. Eviction handles memory, TTL handles freshness, so I set both. In Redis I set maxmemory and a policy like allkeys-lru or allkeys-lfu, because the default noeviction makes writes fail when memory is full."

One important interview follow-up

Q: Does Redis's LRU actually evict the least recently used key?

A: No — it is an approximation. Keeping every key in a global linked list would cost extra memory per key and a list update on every read. Instead, Redis stores a 24-bit last-access clock in each object and, when it needs to evict, samples a few random keys (maxmemory-samples, default 5), keeps the best candidates in a small eviction pool, and evicts the one idle the longest. With 5 samples the result is close to true LRU; raising it to 10 is closer still at more CPU per eviction. The same sampling applies to allkeys-lfu. See Redis eviction policies.

Practice questions

Eviction vs. expiration?

Eviction is triggered by memory pressure regardless of age; expiration is triggered by a TTL regardless of memory.

Why is LRU the usual default?

Temporal locality — recently used keys are likely to be used again — and it's simple, O(1) and adapts quickly.

How do you implement LRU in O(1)?

Hash map (key → node) plus a doubly linked list ordered by recency: move to head on access, evict from tail.

LRU vs. LFU?

LRU trusts recency (adapts fast, fooled by scans); LFU trusts frequency (resists scans, slow to adapt, needs decay).

Why can MRU beat LRU?

For cyclic scans larger than the cache, LRU always evicts the key needed next; MRU keeps part of the cycle resident.

How does Redis expire keys?

Lazily on access plus active sampling ~10 times per second, repeating when more than 25% of a sample is expired.

Is Redis LRU exact?

No: it samples a few keys (maxmemory-samples) using a per-key last-access clock and evicts the best candidate from a pool — approximate, but cheap.

How does W-TinyLFU work?

New keys enter a small LRU window; leaving it, they compete with the main SLRU's victim using frequencies from a Count-Min sketch — one-time scan keys lose and are dropped.

What does InnoDB's midpoint insertion protect against?

Scans: new pages enter the "old" sublist and only move to "young" if read again after a delay, so one scan can't flush hot pages.

After setting volatile-lru, writes start failing with OOM. Why?

Most keys have no TTL, so there are no eviction candidates; volatile-* then behaves like noeviction. Add TTLs or use allkeys-*.

The hit ratio drops from 95% to 60% every night at 2 a.m. Diagnose.

A batch job scans many cold keys and pollutes LRU. Switch to allkeys-lfu / scan-resistant policy or isolate the batch workload.

Redis is at maxmemory with a high eviction rate and a low hit ratio. Next steps?

Check key sizes and TTLs (--bigkeys, keys without TTL), remove waste, then add memory or shard — the working set doesn't fit.

What Should I Remember?

  1. Eviction = memory; expiration = time.
  2. LRU is the default; LFU and W-TinyLFU resist scans.
  3. O(1) LRU = hash map + doubly linked list.
  4. Redis LRU/LFU are sampled approximations; expiry is lazy + active.
  5. Redis default is noeviction — set maxmemory-policy for caches.
  6. If the working set doesn't fit, add memory — no policy will save you.
