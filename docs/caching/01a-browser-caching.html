Browser Caching

How the browser HTTP cache works — freshness, Cache-Control, ETag revalidation and 304, Vary, memory vs disk cache, cache partitioning, cache busting, Service Worker strategies, and header recipes.

What you'll learn

By the end of this page you will be able to:

  • Explain fresh, stale and revalidated responses
  • Use Cache-Control directives correctly — especially no-cache vs. no-store
  • Choose between ETag and Last-Modified, and use Vary safely
  • Ship deploys safely with fingerprinted URLs
  • Pick a Service Worker caching strategy
  • Debug "users still see the old version" problems

What Browser Caching Is For

Browser caching is the browser reusing HTTP responses it already downloaded, under rules the server sets in response headers. It exists because the fastest request is the one never sent — and it is the only cache that removes the network entirely. Its defining constraint: it lives on users' devices, so you cannot purge it. Everything on this page follows from that.

💡 Important

The standard design is a split: content-hashed asset URLs cached for a year, and HTML revalidated on every load. The HTML is the only thing that must be fresh — it points to whatever asset versions are current.

Terms used on this page

  • Fresh — a stored response still within its freshness lifetime (max-age); it can be used without contacting the server.
  • Stale — past its freshness lifetime; it must be revalidated before use (unless a stale-* directive allows serving it).
  • Revalidation — a conditional request asking "has this changed?" using a validator (ETag or Last-Modified).
  • Cache key — what identifies a stored response: the URL (plus method), extended by the headers named in Vary, and in modern browsers partitioned by the top-level site.

Cache-Control directives (response)

DirectiveMeaning

⚠️ Common mistake

Using no-cache to mean "don't cache". It still stores the response — it only forces revalidation. For data that must never touch disk, use no-store.

Validators: ETag vs. Last-Modified

ETag vs. Last-Modified — the difference is precision. Last-Modified is a timestamp with one-second resolution: two changes within the same second look identical, and a file re-deployed with a new modification time but identical bytes looks changed. An ETag is an opaque version identifier chosen by the server — usually a hash of the content — so it changes exactly when the content changes.

  • Strong ETag ("abc123") — byte-for-byte identical. Weak ETag (W/"abc123") — semantically equivalent (e.g. same content, different compression).
  • Gotcha — ETags across servers: if each web server generates ETags from local file metadata (older Apache used the file's inode), the same file gets different ETags on different servers behind a load balancer, so revalidation always "changes" and returns full 200s. Use content-hash ETags.

Vary and the cache key

Vary lists request headers that change the response, so the cache stores one variant per value. Vary: Accept-Encoding keeps gzip and Brotli versions apart (correct and common). Vary: Accept-Language stores per-language variants. Gotcha: Vary: Cookie or Vary: User-Agent creates a variant per user or per browser build, which destroys the hit ratio in shared caches; Vary: * makes a response effectively uncacheable.

Memory cache, disk cache, and other browser layers

  • Memory cache — resources used by the current page/tab (images, scripts, preloads). Very fast, discarded when the tab closes. It may reuse a resource within the same document even when headers would otherwise require revalidation.
  • Disk (HTTP) cache — the persistent cache that follows Cache-Control rules across sessions. It has a size limit and evicts (roughly LRU) when full, so "cached for a year" really means "at most a year".
  • Back/forward cache (bfcache) — keeps an entire page (DOM and JavaScript heap) in memory so Back/Forward restores it instantly. Things that can make a page ineligible include unload event handlers and open connections; historically Cache-Control: no-store on the HTML also blocked it.
  • Service Worker cache — programmatic, see below.
  • Other stores used as caches — localStorage, IndexedDB, and in-memory caches in data libraries (React Query, SWR, Apollo). These are app-managed and ignore HTTP headers.
  • DNS and connection caches — the browser also caches DNS answers and reuses open TCP/TLS connections; see DNS caching.

Cache partitioning (why "shared CDN libraries" stopped helping)

Browsers now partition the HTTP cache by the top-level site (Chrome since version 86, and Safari and Firefox similarly). A copy of jquery.min.js from a public CDN that was cached while visiting site A is not reused on site B. Why: without partitioning, site B could time how fast a resource loads to detect whether you had visited site A (a privacy leak). Consequence: the old argument "load libraries from a public CDN because users already have them cached" no longer holds — self-host and bundle instead.

What the browser does for every request

  1. Build the cache key (URL, plus partition key, plus Vary headers).
  2. No stored response → send the request normally; store the response if its headers allow.
  3. Stored and fresh → use it immediately. DevTools shows 200 (from memory cache) or 200 (from disk cache); no request leaves the device.
  4. Stored but stale, has a validator → send a conditional request with If-None-Match: "abc123" (or If-Modified-Since).
    • Unchanged → server replies 304 Not Modified with headers only → browser refreshes the stored headers and reuses the body.
    • Changed → server replies 200 with the new body → browser replaces the stored copy.
  5. Stored but stale, no validator → full request, as if nothing were stored.

Last-Modified?"} V -->|no| N V -->|yes| C["Conditional request

Freshness: how long a response stays fresh

  • Cache-Control: max-age=N — fresh for N seconds after the response was generated. Takes precedence over Expires.
  • Expires: <date> — HTTP/1.0 absolute expiry. Ignored when max-age is present; fragile because it depends on clocks agreeing.
  • Age — set by shared caches (CDN) to say how long the response has already sat in cache. The browser subtracts it, so a response with max-age=600 and Age: 500 has only 100 seconds of freshness left.
  • Heuristic freshness — if a response has no explicit lifetime but has Last-Modified, browsers may treat it as fresh for a fraction (commonly 10%) of the time since it was last modified. Gotcha: a file last modified 100 days ago may be cached for ~10 days without you ever asking — always send explicit Cache-Control.

🧠 Think about it

A CDN returns a response with max-age=600 and Age: 590. How long will the browser treat it as fresh? (10 seconds — the CDN already used up 590 of the 600.)

Reloads and user actions

  • Normal navigation — follows the rules above.
  • Reload (F5) — the main document is revalidated; browsers differ for subresources, and immutable tells them not to revalidate.
  • Hard reload (Ctrl/Cmd + Shift + R) — bypasses the cache and re-downloads everything.
  • DevTools "Disable cache" — only while DevTools is open; a common reason developers never see caching bugs their users hit.
  • Clear-Site-Data: "cache" — a response header that tells the browser to clear that site's cached data (useful on logout). It only reaches users who make a request to your site, so it is not a remote purge for everyone.

Cache busting with fingerprinted URLs

Because you can't purge browsers, the build tool (Vite, webpack, esbuild) puts a hash of each file's content into its name: app.3f9a1c.js. Cause → effect of a deploy:

  1. You change app.js → the build produces app.8d02be.js.
  2. The HTML now references app.8d02be.js; the HTML itself is served with no-cache, so browsers revalidate it and get the new version.
  3. The new URL has never been cached → the browser downloads it once, then caches it for a year.
  4. The old app.3f9a1c.js is simply never requested again and ages out.

Fingerprint vs. query-string versioning (app.js?v=42) — the difference is reliability: some proxies and CDN configurations ignore or strip query strings in the cache key, so a filename hash is safer. (This site itself uses ?v= on site.css and site-header.js — acceptable for GitHub Pages, and the reason the CLAUDE.md rule says to bump it on every change.)

Gotcha: cached HTML pointing to deleted assets

If the HTML is cached (for example max-age=3600) and your deploy deletes old asset files, users with the old HTML request app.3f9a1c.js and get a 404 — a blank page. Keep old assets available for a while after a deploy, and never give HTML a long max-age.

Header recipes

ResourceHeaderWhy
Fingerprinted JS/CSS/fonts/imagesCache-Control: public, max-age=31536000, immutableContent never changes at that URL.
HTML pagesCache-Control: no-cache + ETagAlways current; cheap 304 when unchanged.
Non-fingerprinted images (user uploads)Cache-Control: public, max-age=86400, stale-while-revalidate=604800A day fresh; a week of instant stale serving while refreshing.
Per-user API responsesCache-Control: private, no-cache + ETagBrowser may reuse after revalidation; CDN must not store.
Sensitive data (banking, tokens)Cache-Control: no-storeNever written to disk.

The recipes in Nginx

location ~* \.[0-9a-f]{6,}\.(js|css|woff2|png|svg)$ {
    add_header Cache-Control "public, max-age=31536000, immutable";
}
location / {
    add_header Cache-Control "no-cache";
    etag on;
}
  • The first location matches filenames containing a hex hash (app.3f9a1c.js) — only those get the one-year immutable policy.
  • Everything else (including HTML) gets no-cache; etag on (Nginx's default for static files) supplies the validator for cheap 304s.

Service Worker caching strategies

A Service Worker is a script that sits between the page and the network and can answer requests from the Cache Storage API. It enables offline support and full control of caching, at the cost of owning freshness yourself (it ignores Cache-Control for what you put in it).

StrategyBehaviourUse for
Cache firstServe from cache; network only on a miss.Fingerprinted static assets, fonts.
Network firstTry the network; fall back to cache when offline.HTML, frequently updated API data.
Stale-while-revalidateServe cache immediately, update it from the network in the background.Avatars, non-critical API data.
Cache only / network onlyOne source, no fallback.Precached app shell / analytics beacons.

Gotcha: a buggy Service Worker can pin users to an old app version indefinitely. Version your caches, delete old ones in the activate event, and have a way to ship an update (a new worker file is checked on navigation, at most every 24 hours for the script itself by default).

Production Usage

Low traffic or high, the browser cache is free capacity: every fresh hit is a request your CDN and origin never see. At scale the decisions are the same but the stakes are higher — a wrong long max-age on HTML can strand millions of users on a broken version with no way to recall it.

Signals to watch

  • CDN/origin requests for static assets per page view — should be near zero for returning users.
  • 304 vs. 200 ratio on HTML — many 304s means validators work.
  • 404s on old asset URLs after deploys — users on stale HTML.
  • Real-user monitoring (RUM) — repeat-visit load times, transfer sizes (transferSize of 0 in the Resource Timing API means served from cache).

🔥 Production insight

Keep old fingerprinted assets deployed for days after a release. Some users have the previous HTML open in a tab or cached; deleting its assets on deploy turns their next navigation into a blank page.

Security gotchas

  • A shared computer's browser cache can expose a previous user's pages — use no-store for sensitive pages and Clear-Site-Data on logout.
  • Responses to authenticated requests must be private (or no-store) so a CDN never serves them to someone else — see CDN security.
  • Never cache secrets in localStorage; any XSS can read it. See Cookies, Sessions & JWT.

Performance

  • Fresh hit: zero network — the biggest possible win.
  • Revalidation (304): one round trip, no body — still pays latency, so don't revalidate fingerprinted assets (immutable).
  • Vary fragmentation lowers hit ratio in every cache down the chain.
  • Partitioning means third-party shared libraries are re-downloaded per site — bundle and self-host.
  • bfcache eligibility makes Back/Forward instant — avoid unload handlers.

Debugging workflow

  1. DevTools → Network, cache enabled: look at the Size column — "(memory cache)", "(disk cache)", or bytes transferred; and the status (200/304).
  2. Read the response headers: Cache-Control, ETag, Age, Vary.
  3. Reproduce outside the browser: curl -I https://example.com/app.js and curl -I -H 'If-None-Match: "abc123"' https://example.com/ (expect 304).
  4. Check Application → Service Workers / Cache Storage if a worker is installed.

Best Practices

Do

  • Always send explicit Cache-Control — otherwise heuristic freshness decides for you.
  • Fingerprint assets + immutable, one year.
  • HTML: no-cache + ETag.
  • Per-user responses: private; sensitive: no-store.
  • Keep old assets available after deploys.

Avoid

  • Long max-age on HTML or un-fingerprinted URLs.
  • Vary: Cookie / User-Agent on cacheable responses.
  • Cache-first Service Worker for HTML without an update path.
  • Secrets in localStorage.

Interview Answer — What Is Browser Caching?

Browser caching is the browser storing copies of HTTP responses — HTML, JavaScript, CSS, images, fonts, API responses — on the user's device and reusing them for later requests instead of downloading them again. What may be stored, for how long, and whether it must be checked with the server first is decided by the server through response headers, mainly Cache-Control, ETag, and Last-Modified.

It exists because the fastest network request is the one never sent. A returning visitor typically needs the same logo, fonts, and JavaScript bundle as last time; without a cache, every page view re-downloads them, costing the user time and data and costing you bandwidth. The cause → effect chain: the server sends Cache-Control: max-age=31536000, immutable for app.3f9a1c.js → the browser stores it → every later page that references that exact URL uses the stored copy with zero network → pages render faster and the origin/CDN serve less traffic.

The price is that a browser cache is private and unpurgeable: it lives on millions of devices you don't control, so you cannot delete a bad cached file remotely. That is why the standard design is split in two: long-lived assets get fingerprinted URLs (a content hash in the filename, so a new version is a new URL) with a one-year TTL, while the HTML that references them is revalidated on every load (no-cache + ETag). See the header recipes.

Simple interview version

"Browser caching lets the browser reuse responses it has already downloaded, controlled by the server's Cache-Control and validator headers. A fresh response within max-age is used with no request at all; a stale one is revalidated with If-None-Match, and the server answers 304 Not Modified with no body if nothing changed. Because I can't purge users' browsers, I give static assets content-hashed filenames with a one-year immutable TTL, and serve the HTML with no-cache so it is revalidated each time and always points to the latest asset URLs. Private data is private or no-store."

One important interview follow-up

Q: Does Cache-Control: no-cache mean the browser doesn't cache the response?

A: No — it's the most misunderstood directive. no-cache means "you may store it, but you must revalidate with the server before every use." The browser keeps the body and sends If-None-Match; if unchanged, the server returns a tiny 304 and the stored body is reused. The directive that forbids storing is no-store. So no-cache is ideal for HTML (always current, but cheap when unchanged), and no-store is for sensitive responses such as bank statements.

Practice questions

What's the difference between a fresh hit and a revalidation?

A fresh hit uses the stored response with no request. A revalidation sends a conditional request; a 304 means "unchanged, reuse your copy".

Why can't you just purge a bad file from users' browsers?

The cache is on millions of devices you don't control. You can only change URLs (fingerprinting) or wait for expiry.

What does immutable add to max-age?

It tells the browser not to revalidate even on reload, saving 304 round trips for content that can never change at that URL.

ETag vs. Last-Modified?

ETag is an exact version identifier (usually a content hash); Last-Modified has one-second resolution and changes on redeploys with identical bytes. Prefer content-hash ETags.

Why is Vary: Cookie bad for caching?

Every distinct cookie value is a separate variant — effectively one cache entry per user — so shared caches almost never hit.

Why don't public CDN copies of jQuery help across sites any more?

Browsers partition the HTTP cache by top-level site to stop timing-based history leaks, so a copy cached on site A isn't reused on site B.

What's heuristic freshness and why is it dangerous?

With no explicit lifetime but a Last-Modified date, browsers may cache for ~10% of the time since modification — days or weeks you never chose. Always send Cache-Control.

Which Service Worker strategy for HTML, and why?

Network-first with cache fallback: users get the latest version online and still work offline. Cache-first HTML can pin users to an old app.

Fingerprinted filenames vs. ?v= query strings?

Filenames are safer: some proxies/CDN configs ignore or strip query strings from the cache key, so a ?v= bump may not bust everything.

After a release, some users see a blank page. Diagnose.

Their cached HTML references asset files the deploy removed → 404 on JS. Restore old assets; make HTML no-cache and keep previous assets for a while.

A shared library computer showed the previous user's account page via Back. Fix?

Mark sensitive pages no-store and send Clear-Site-Data: "cache" on logout.

Your HTML has ETags but users never get 304s behind the load balancer. Why?

Each server generates different ETags (e.g. inode-based), so validators never match. Use content-hash ETags or identical artifacts.

What Should I Remember?

  1. Fresh → used without a request; stale → revalidated (304) or refetched.
  2. no-cache = store but revalidate; no-store = never store.
  3. You can't purge browsers: fingerprint assets (1 year, immutable), revalidate HTML (no-cache + ETag).
  4. private for per-user data; never cache secrets client-side.
  5. Keep Vary minimal; prefer content-hash ETags.
  6. Browser caches are partitioned per site.
