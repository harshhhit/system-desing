Database Caching

The buffer pool and its hit ratio, double buffering with the OS page cache, plan caches, why MySQL removed its query cache, materialized views, ORM caches, and external caches such as Redis and DAX.

Interview Answer — What Is Database Caching?

Database caching covers two different things that are easy to mix up. Inside the database, the engine caches data and index pages in RAM (the buffer pool), caches query plans, and can store precomputed results (materialized views). In front of the database, the application or a proxy caches query results or objects in a separate store — Redis, Memcached, or a purpose-built cache such as DynamoDB Accelerator (DAX).

Both exist because disk and query execution are the expensive parts of a read. A page read from an SSD costs ~100 µs; the same page in the buffer pool costs well under a microsecond to find. A complex join might take 200 ms to execute; its cached result takes 1 ms to fetch from Redis. The cause → effect chain for the buffer pool: the working set (hot tables and indexes) fits in RAM → almost every query is served from memory → disk I/O drops, latency is predictable. When the working set outgrows RAM → pages are evicted and re-read constantly → I/O saturates → latency jumps sharply rather than gradually.

Internal vs. external caching — the difference is consistency. The buffer pool is always consistent: the database itself manages it transactionally, so it never returns stale data. A cache in front of the database (Redis) is a separate copy with no shared transaction, so it can go stale and needs a caching strategy and invalidation. Tune the internal caches first — they are free correctness-wise — and add an external cache when the database is still the bottleneck.

Simple interview version

"Databases cache internally: the buffer pool keeps hot data and index pages in RAM — ideally the whole working set — and it's always consistent. I check its hit ratio before anything else. On top of that, materialized views precompute expensive queries, read replicas spread read load, and for hot reads that are still too slow or too frequent, I add Redis in front using cache-aside with TTLs and invalidation on write. The key difference is that the database's own cache never serves stale data, while an external cache can, so I only add one where some staleness is acceptable."

One important interview follow-up

Q: Why did MySQL remove its built-in query cache if caching is good?

A: Because its invalidation was too coarse and it didn't scale. It cached result sets keyed by the exact SQL text, and any write to a table invalidated every cached result that touched that table. On a write-heavy table the cache was constantly filled and thrown away, and every query had to take a global mutex to check it, which serialised work on multi-core servers. It was deprecated in 5.7.20 and removed in MySQL 8.0. The lesson: a cache that is invalidated more often than it is hit costs more than it saves — result caching belongs in the application, where you choose what to cache and how stale it may be.

1. The buffer pool (buffer cache)

What it is: a region of RAM where the database keeps fixed-size pages (8 KB in PostgreSQL, 16 KB in InnoDB) of tables and indexes. Every read and write goes through it: a needed page is looked up in the pool; on a miss it is read from disk into the pool; modified ("dirty") pages are written back later by checkpoints and background writers, with durability guaranteed by the write-ahead log, not by the pool.

Measuring it

  • PostgreSQL — blks_hit / (blks_hit + blks_read) from pg_stat_database (per table: pg_statio_user_tables). Well-tuned OLTP databases are typically above 99%. Note that blks_read may be served by the OS page cache, so it is not necessarily a disk read.
  • MySQL — compare Innodb_buffer_pool_reads (had to go to disk) with Innodb_buffer_pool_read_requests (logical reads).
  • EXPLAIN (ANALYZE, BUFFERS) in PostgreSQL shows shared hit vs. read per query — see Query Plans and Optimization.

Gotchas

  • Scans flush the cache — a full scan of a huge table could push out hot pages; InnoDB's midpoint insertion and PostgreSQL's small ring buffers for large sequential scans exist to prevent that. Run reports on a replica.
  • Cold after restart or failover — the pool starts empty, so queries are slow until it warms. InnoDB saves and reloads the list of hot pages (innodb_buffer_pool_dump_at_shutdown / load_at_startup, on by default); PostgreSQL has the pg_prewarm extension.
  • Indexes are cached too — an index that fits in memory is what makes lookups fast; unused indexes waste buffer pool space. See Indexing.

2. The OS page cache and double buffering

PostgreSQL reads through the operating system, so a page can sit in shared_buffers and in the OS page cache — two copies (double buffering). That's why PostgreSQL's shared_buffers is kept moderate and effective_cache_size (a planner hint, not an allocation) is set to about the total of both caches. InnoDB avoids double buffering with innodb_flush_method=O_DIRECT and uses a larger buffer pool instead. See OS page cache.

3. Plan cache and prepared statements

Parsing and planning a query costs CPU. Prepared statements let the database reuse a parsed (and sometimes planned) statement: PostgreSQL, after five executions, may switch a prepared statement to a generic plan if it isn't estimated to be worse than custom plans; SQL Server and Oracle keep a shared plan cache keyed by SQL text. Gotchas: a generic or cached plan chosen for one parameter value can be bad for another (parameter sniffing); and connection poolers in transaction mode (PgBouncer) historically broke server-side prepared statements (PgBouncer 1.21+ supports them). See Connection Management and Database Proxies.

4. Query result caches

  • MySQL query cache — removed in 8.0 (see the follow-up above).
  • Oracle result cache — caches results of queries/functions marked for it, invalidated when dependent tables change.
  • Proxy-level result caching — ProxySQL can cache results of queries matching rules for a TTL (the staleness is then up to you).
  • Application-level result caching — the usual answer today: key Redis by a hash of the query and parameters (q:sha1(sql+params)) with a TTL. Hard to invalidate precisely (which cached queries does a write affect?), so prefer caching objects by ID, which the write path knows how to delete.
  • Warehouse result caches — Snowflake, BigQuery, and Redshift return a cached result for an identical query if the underlying data hasn't changed — free and always correct because the engine knows when data changed.

5. Materialized views and summary tables

A materialized view stores the result of a query as a physical table that can be indexed. View vs. materialized view — the difference is when the work happens: a normal view re-runs its query on every read; a materialized view runs it at refresh time and reads are just table scans or index lookups.

  • PostgreSQL — REFRESH MATERIALIZED VIEW sales_daily; recomputes fully and blocks reads; REFRESH … CONCURRENTLY doesn't block reads but needs a unique index. No built-in incremental refresh.
  • Oracle, SQL Server (indexed views), Snowflake, BigQuery — support automatic or incremental maintenance for eligible queries.
  • Summary / rollup tables — the do-it-yourself version, maintained by triggers, batch jobs, or stream processors.

Staleness equals the time since the last refresh — acceptable for dashboards and reports, not for balances. See PostgreSQL Views. The architecture-level version is a CQRS read model: Event Sourcing & CQRS.

6. ORM and data-access caches

  • First-level (session) cache — Hibernate/JPA, Entity Framework, SQLAlchemy keep loaded objects for the duration of a session/transaction; the same row loaded twice is one object and one query.
  • Second-level cache — shared across sessions (Hibernate with Ehcache, Infinispan, or Redis). Only safe if all writes go through the ORM; raw SQL or another service's writes leave it stale.
  • The N+1 problem is not solved by caching — fix it with joins or batch loading (JOIN FETCH, selectinload, DataLoader).

7. External caches in front of the database

  • Redis / Memcached / Valkey (ElastiCache) — the general-purpose choice; you write the caching logic. AWS service details: Amazon ElastiCache. Everything on the in-memory pages applies: strategies, eviction, problems.
  • DynamoDB Accelerator (DAX) — a managed read-through / write-through cache that speaks the DynamoDB API, giving microsecond reads without code changes. Reads are eventually consistent; strongly consistent reads pass through to DynamoDB.
  • Read replicas — not a cache (they hold all data and answer any query), but they offload reads the same way and share the staleness problem: see Replication Lag.
  • Search / analytics copies — Elasticsearch or OpenSearch indexes fed by CDC are "caches" optimised for a different query shape.

What to try, in order

  1. Fix the query and indexes (a missing index is not a caching problem).
  2. Size the buffer pool to hold the working set; confirm with the hit ratio.
  3. Use prepared statements and connection pooling.
  4. Precompute expensive aggregates (materialized views, rollup tables).
  5. Add read replicas for read volume.
  6. Add Redis for hot objects when latency or volume still demands it — and accept the staleness and invalidation work it brings.
