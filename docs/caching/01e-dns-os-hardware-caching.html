DNS, OS & Hardware Caching

DNS caching at every layer and TTL strategy, negative caching, Kubernetes DNS, the OS page cache and fsync, CPU caches and false sharing, and TLS session caches.

What you'll learn

By the end of this page you will be able to:

  • Trace a DNS lookup through every cache on its path
  • Choose DNS TTLs and plan migrations around them
  • Explain how the OS page cache makes Kafka and PostgreSQL fast — and when writes aren't durable
  • Reason about CPU caches: locality, coherence, false sharing
  • Recognise device write caches and protocol-level caches (TLS, ARP)

The Caches Under Everything

These are the caches you rarely configure but always depend on: DNS answers cached along the lookup path, file data cached by the kernel, and memory cached by the CPU. They explain why a DNS change "doesn't propagate", why free says your RAM is full, why Kafka is fast without its own cache, and why an array beats a linked list.

💡 Important

All three share one rule: the cache is controlled by someone other than the data's owner (resolvers, the kernel, the hardware). You influence them — with TTLs, fsync, data layout — but you can't directly invalidate them.

Where These Caches Sit

A lookup stops at the first cache with a valid answer; data on a host passes through CPU, kernel and device caches.

1. DNS caching: the full path

A lookup checks each cache in turn and stops at the first hit:

  1. Browser DNS cache — Chrome keeps its own host cache (inspect it at chrome://net-internals/#dns) and reuses open connections, so a warm page may not need DNS at all.
  2. OS stub resolver cache — systemd-resolved / nscd on Linux, the DNS Client service on Windows, mDNSResponder on macOS. /etc/hosts is consulted before DNS.
  3. Language runtime caches — the JVM caches successful lookups (networkaddress.cache.ttl; 30 seconds by default in modern JVMs without a security manager, but historically "forever" with one — a classic cause of services clinging to old IPs after failover). Some HTTP clients and connection pools resolve once and keep the connection indefinitely.
  4. Recursive resolver cache — your ISP, a public resolver (1.1.1.1, 8.8.8.8), or the cloud resolver (AWS Route 53 Resolver at VPC+2). Shared by all its clients, so popular names are almost always cached.
  5. Authoritative servers — the source of truth (e.g. Route 53 hosted zone). Reached only on a miss everywhere above.

Negative caching

An NXDOMAIN ("does not exist") answer is cached for a time taken from the zone's SOA record (RFC 2308). Gotcha: if a client looks up new.example.com before you create it, that "does not exist" answer is cached and the name appears broken until the negative TTL expires — create records before announcing them.

Choosing TTLs

  • Long (hours–a day) — stable records (MX, NS, rarely changed hosts): fewer queries, faster lookups, slow changes.
  • Short (30–300 s) — records used for failover or load distribution; AWS load balancer DNS names use 60 seconds because their IPs change as they scale.
  • Alias records to AWS resources (Route 53 ALIAS) inherit the target's TTL. See Networking Fundamentals and Load Balancing (DNS-based GSLB).

DNS caching in Kubernetes

Every Pod lookup goes to CoreDNS, which has a cache plugin (default 30 seconds in the standard Corefile). Two well-known issues: with the default ndots:5, a lookup for an external name like api.stripe.com first tries every cluster search domain (several wasted queries) — use a fully-qualified name with a trailing dot or lower ndots; and high DNS volume can hit conntrack races, which NodeLocal DNSCache (a caching agent on every node) mitigates. See Kubernetes Networking Roadmap.

⚠️ Common mistake

Checking a brand-new hostname before creating its record "to see if it works". The NXDOMAIN answer gets negatively cached, and the name stays broken for that resolver until the negative TTL expires.

2. The OS page cache

What it is: the kernel keeps file data it has read or written in otherwise-free RAM, in 4 KB pages. Why it exists: RAM is ~1,000× faster than SSD for small reads, and unused RAM is wasted RAM. The cause → effect chain for a read: a process calls read() on a file → the kernel checks the page cache → hit: copy from RAM, no disk I/O → miss: read from disk into the page cache (usually with read-ahead of the following pages, because sequential reads are likely), then copy to the process.

Writes: the page cache as a write-back cache

A write() normally just copies data into the page cache and marks the page dirty; the kernel flushes dirty pages to disk later (tuned by vm.dirty_ratio, vm.dirty_background_ratio, vm.dirty_expire_centisecs). So a successful write() does not mean the data survives a power loss — that requires fsync() (or O_DSYNC). This is why databases fsync their write-ahead log on commit.

Why system designers care

  • Kafka deliberately has no large internal cache: it writes to the page cache and serves consumers from it, using sendfile (zero-copy) to send pages straight to the socket. Consumers that keep up read from RAM; lagging consumers read from disk and can evict data the up-to-date consumers need. See Kafka Fundamentals.
  • PostgreSQL uses the page cache as its second caching layer — see double buffering.
  • Memory-mapped files (mmap) — used by LMDB, older MongoDB (MMAPv1), and Elasticsearch/Lucene index files: the page cache is the application's cache.
  • Bypassing it — O_DIRECT (InnoDB) skips the page cache when the application manages its own cache better.
  • Containers — page cache used by a container's files is charged to its cgroup memory, which can make memory metrics look alarming; reclaimable cache is not the same as a leak. See Memory Profiling.

Gotcha: free -h shows page cache as buff/cache; the number to watch is available. echo 3 > /proc/sys/vm/drop_caches empties it — useful for cold-cache benchmarks, harmful in production.

🧠 Think about it

Your app writes a payment record with write(), returns 200, and the machine loses power a second later. Is the record on disk? (Probably not — it sat in the page cache as a dirty page. Only fsync (or a database that calls it on commit) makes it durable.)

3. CPU caches

What it is: small, very fast SRAM on the CPU that holds recently used memory in 64-byte cache lines.

LevelTypical sizeApprox. latencyShared by
L1 (data + instruction)32–64 KB each~1 ns (4–5 cycles)one core
L2256 KB–2 MB~3–5 nsone core (sometimes a pair)
L3 (last-level cache)tens to hundreds of MB~10–40 nsall cores on a socket/chiplet
Main memory (RAM)GBs~80–100 nsall sockets (NUMA: local vs. remote)

Consequences for software

  • Locality wins — iterating an array sequentially uses every byte of each cache line and the hardware prefetcher predicts the next lines; chasing pointers through a linked list or a hash map of boxed objects misses constantly. Same algorithmic complexity, often 10× different speed.
  • Cache coherence — when one core writes a line, other cores' copies are invalidated (MESI-style protocols). Shared mutable counters updated by many threads bounce a line between cores; per-core counters summed later scale better.
  • False sharing — two threads writing different variables that happen to sit on the same 64-byte line invalidate each other continuously. Fix by padding/aligning hot per-thread data to separate lines (Java's @Contended).
  • NUMA — on multi-socket servers, memory attached to the other socket is slower; databases and JVMs have NUMA-aware settings.
  • TLB — caches virtual-to-physical page translations; huge pages reduce TLB misses for large heaps (but Redis recommends disabling transparent huge pages because they slow copy-on-write during snapshots).

4. Storage-device caches

SSDs, HDDs, and RAID controllers have DRAM caches. As read caches they are harmless; as write-back caches they acknowledge writes before data reaches durable media, so without power-loss protection (capacitors/battery) an fsync may lie. Cloud block storage (EBS) hides this but has its own performance characteristics. Related: Storage Types.

5. Other protocol-level caches

  • TLS session resumption — servers cache session state (session IDs) or hand clients encrypted session tickets, so a returning client skips part of the handshake; TLS 1.3 adds 0-RTT resumption (with replay risks for non-idempotent requests). Behind a load balancer, ticket keys must be shared across servers or resumption fails.
  • ARP / neighbour cache — maps IP addresses to MAC addresses on a local network; stale entries after an IP moves are why failover tools send gratuitous ARP.
  • Connection reuse — keep-alive and HTTP/2 connection pools are not caches of data, but they cache the expensive result of DNS + TCP + TLS setup; the same staleness risk appears when a pooled connection points at a server that has been replaced.
  • Build and package caches — Docker layer cache, CI dependency caches, Bazel remote cache: keyed by a hash of the inputs, so they never serve stale results.

Implementation: Inspecting These Caches

dig +noall +answer example.com
dig @1.1.1.1 example.com +noall +answer
resolvectl statistics
free -h
grep -E "Dirty|Writeback" /proc/meminfo
perf stat -e cache-references,cache-misses ./my-benchmark
  • dig +noall +answer — the answer and its remaining TTL from your resolver's cache; repeat it and the TTL counts down.
  • dig @1.1.1.1 — ask a different resolver to compare what different caches hold.
  • resolvectl statistics — systemd-resolved's cache size and hit/miss counters.
  • free -h — read available, not free; buff/cache is the reclaimable page cache.
  • Dirty/Writeback in /proc/meminfo — how much written data isn't on disk yet.
  • perf stat -e cache-misses — CPU cache miss counts for a program, to compare data layouts.

Production Usage

  • DNS migrations: lower TTLs at least one old-TTL period ahead, change the record, keep the old target serving until the old TTL has passed, then raise TTLs again.
  • Failover by DNS needs short TTLs and clients that respect them — the JVM setting and connection pools often decide the real failover time.
  • Kubernetes: CoreDNS caching, ndots search-path amplification, and node-local DNS caches matter at scale.
  • Hosts: size RAM so the hot file set stays in the page cache (Kafka, PostgreSQL), and alert on available memory, not free.

Signals to watch

  • DNS query rate, SERVFAIL/NXDOMAIN rates, CoreDNS cache hits.
  • Page cache size, major page faults, disk read IOPS.
  • Dirty bytes and writeback latency during write bursts.

🔥 Production insight

Don't run echo 3 > /proc/sys/vm/drop_caches on a production database or Kafka broker "to free memory". It throws away the hot data those systems rely on, and every read goes to disk until the cache re-warms.

Security

  • DNS cache poisoning — forged answers injected into a resolver cache redirect users; DNSSEC validation and randomized source ports/IDs defend against it.
  • CPU cache side channels (Spectre/Meltdown-class) — timing differences in shared caches can leak data across processes; patched kernels and microcode mitigate them at some performance cost.
  • TLS session ticket keys must be rotated and shared securely across servers; a leaked key exposes resumed sessions.

Performance

  • DNS: warm caches make lookups ~0 ms; cold lookups add tens to hundreds of ms — reuse connections so you look up rarely.
  • Page cache: RAM is ~1,000× faster than SSD for small reads; sequential, recently-written data (logs, Kafka) stays hot.
  • CPU caches: contiguous data structures, fewer pointer hops, per-core counters, and padding against false sharing.

Best Practices

Do

  • Plan TTLs around changes — short for failover records, long for stable ones.
  • Set runtime DNS TTLs explicitly (JVM).
  • Leave RAM for the page cache on data-heavy hosts.
  • Use fsync (or the DB's commit) for anything that must survive a crash.
  • Design hot data structures for locality.

Avoid

  • Relying on DNS alone for instant failover.
  • Dropping caches in production.
  • Treating buff/cache as a leak.
  • Write-back device caches without power-loss protection under databases.

Interview Answer — What Is DNS Caching?

DNS caching is every component on the path of a name lookup — the browser, the operating system, language runtimes, and recursive resolvers such as your ISP's, 8.8.8.8, or the AWS VPC resolver — storing the answer to "what is the IP address of api.example.com?" for the TTL (time to live) the domain's owner set on that DNS record. Negative answers ("this name does not exist") are cached too.

It exists because a full DNS resolution walks several servers (root → .com → the domain's authoritative servers) and can take tens to hundreds of milliseconds, while the answer rarely changes. Without caching, every connection would pay that cost and authoritative servers would receive the internet's entire lookup volume. The cause → effect chain for the gotcha: your record has TTL 3600 → resolvers worldwide cache the old IP for up to an hour → you move the service to a new IP → clients keep connecting to the old IP until their cached copy expires, so a DNS-based migration or failover is only as fast as the TTL (and slower when clients cache longer than they should).

This page also covers the two layers below DNS that every system relies on without configuring directly: the OS page cache (why Kafka and PostgreSQL are fast) and CPU caches (why memory layout matters), plus other protocol-level caches such as TLS session resumption and ARP.

Simple interview version

"DNS answers are cached at every step — browser, OS, runtime, and recursive resolvers — for the TTL on the record, so lookups are fast and authoritative servers aren't overloaded. The consequence is that DNS changes propagate only as caches expire: before a planned migration I lower the TTL to about 60 seconds a day ahead, and I don't rely on DNS alone for instant failover because some clients cache longer than the TTL. Below that, the OS page cache keeps recently used file data in RAM, and CPU caches keep recently used memory close to the cores — which is why sequential access patterns are so much faster."

One important interview follow-up

Q: If I lower a record's TTL to 60 seconds right now, will clients see my change within a minute?

A: No — not the ones that already cached it. Resolvers that fetched the record under the old TTL (say 86,400 seconds) keep that copy until their timer expires, up to a day later. The TTL change itself only takes effect as those old copies expire. So the procedure is: lower the TTL at least one old-TTL period before the change, make the change, and raise it again afterwards. And some clients — long-running JVMs with a misconfigured cache, embedded devices, connection pools that never re-resolve — may ignore TTLs entirely, so keep the old endpoint alive for a while.

Practice questions

List the caches a DNS lookup can hit.

Browser host cache → OS stub resolver → language runtime (e.g. JVM) → recursive resolver → authoritative server on a full miss.

Why does free show almost no free memory on a healthy server?

The kernel uses idle RAM as page cache and reclaims it on demand; watch available.

What is negative DNS caching?

Resolvers cache NXDOMAIN answers for a time from the zone's SOA, so a name looked up before it existed stays "missing" for that period.

Why is Kafka fast without a big internal cache?

It writes to and reads from the OS page cache and uses sendfile zero-copy; consumers that keep up read from RAM.

Why does iterating an array beat a linked list even at the same big-O?

Arrays use whole 64-byte cache lines and prefetching; linked lists chase pointers to scattered memory, missing the cache constantly.

What's the ndots:5 problem in Kubernetes?

Names with fewer than five dots are tried against every search domain first, multiplying DNS queries for external names; use FQDNs with a trailing dot or tune ndots.

Explain false sharing and its fix.

Two threads write different variables on the same cache line, so coherence keeps invalidating each core's copy. Pad or align per-thread data to separate lines.

Why does InnoDB use O_DIRECT?

It manages its own buffer pool and avoids double-caching pages in the OS page cache.

Why must TLS session ticket keys be shared across servers?

So a client resuming on a different server behind the load balancer can still be decrypted; otherwise resumption fails and full handshakes return.

You'll move a site to a new IP tomorrow; the A record TTL is 86,400. Plan it.

Today: lower TTL to 60–300 s. After 24 h: change the record; keep the old server serving for at least the old TTL. Afterwards raise the TTL again.

After a database failover, one service fails for 30 minutes while others recover in a minute. Why?

That service (often JVM-based) or its connection pool cached the old IP longer than the DNS TTL. Configure runtime DNS TTL and pool max-lifetime/validation.

A container is OOM-killed though the app's heap is small. What could memory metrics be including?

Page cache charged to the container's cgroup inflates usage figures; check working-set vs. cache, then real causes (native memory, leaks). See Memory Profiling.

What Should I Remember?

  1. DNS is cached at every hop for the record's TTL; changes propagate only as caches expire.
  2. Lower TTLs one old-TTL period before a change; negative answers are cached too.
  3. The page cache is free RAM doing useful work; write() isn't durable until fsync.
  4. CPU caches reward locality and punish pointer chasing and false sharing.
  5. Device write caches need power-loss protection.
