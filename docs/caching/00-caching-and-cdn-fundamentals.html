Caching & CDN Fundamentals

Caching layers, cache-aside vs write-through vs write-behind, eviction and invalidation, cache stampede, Redis vs Memcached, and CDN edge caching.

What you'll learn

By the end of this page you will be able to:

  • Explain why caching works and what it costs (staleness)
  • Place a cache at the right layer: browser, CDN, proxy, Redis, process
  • Choose a caching strategy: cache-aside, read/write-through, write-behind, write-around
  • Separate eviction from invalidation, and pick a TTL
  • Prevent cache stampedes and handle hot keys
  • Control CDN caching with Cache-Control headers and purge it safely

Why Caching Exists

Every cache trades a little staleness for a lot of speed: reading from memory (nanoseconds–microseconds) instead of making a network round trip to a database or an origin server (single-digit to hundreds of milliseconds) is the single biggest latency win available in most systems, and it removes read load from whatever sits behind it. The cost is that what the cache holds can drift out of sync with the source of truth — caching as a discipline is mostly about managing that drift on purpose instead of by accident.

How to Study This Section

Read this page in the order you would design a cache. Each step exists because the previous step creates a new problem.

  1. Why caching exists — the same data is read far more often than it changes, so copying it closer to the reader removes most database load and network round trips. This unlocks the question of where to put the copy.
  2. Where a cache can live — each layer (browser, CDN, reverse proxy, shared store such as Redis, in-process memory) trades latency against how many users share the copy. A cache closer to the user is faster but harder to invalidate.
  3. Caching strategies — once a layer is chosen, decide which code path writes to the cache. Watch for: cache-aside vs. write-through — the difference is who fills the cache. In cache-aside the application loads data into the cache only after a miss; in write-through every write updates the cache and the database together, so reads rarely miss but every write pays for both.
  4. Eviction, invalidation, and cache stampede — a cache has limited memory and holds copies that can go stale. Watch for: eviction vs. invalidation — the difference is the reason a key is removed. Eviction removes a key because the cache is full (the data may still be correct); invalidation removes a key because the data has changed (the copy is now wrong). A good eviction policy does nothing to prevent stale reads.
  5. Redis vs. Memcached and the CDN — finally, apply the same rules to concrete tools and to edge caching, where Cache-Control headers tell every cache in the chain what it may store and for how long. Then review the interview checklist.
  6. Go deeper in this section — the Caching Roadmap orders every topic; Types of Cache expands "where a cache can live" (with per-type pages for browser, CDN, proxy & gateway, database, and DNS/OS/hardware caching); the in-memory pages expand strategies, eviction policies, and cache problems such as the thundering herd.
  7. Next sections — continue to Load Balancing (how requests that miss the cache are spread across servers) and Consistent Hashing (how keys are spread across many cache nodes).

Caching Strategies — Who Writes, Who Reads, in What Order

StrategyRead pathWrite pathTrade-off
Cache-aside (lazy loading)App checks the cache; on a miss, reads the DB, then populates the cacheApp writes the DB, then invalidates (or updates) the cache keyThe most common strategy. Cache and DB can briefly disagree between the DB write and the invalidation; only data that's actually requested ever gets cached.
Read-throughApp always asks the cache; the cache itself loads from the DB on a missusually paired with write-throughSimpler application code (the cache library owns the miss path), at the cost of coupling the cache to the data-loading logic.
Write-through—App writes to the cache, which synchronously writes to the DBCache and DB never disagree, but every write pays the DB's latency — no write speedup.
Write-behind / write-back—App writes to the cache; the cache asynchronously flushes to the DB laterFastest writes, absorbs write bursts — but a cache crash before the flush loses data, so it needs a durable queue/log behind it.
Write-aroundCache-aside on readApp writes straight to the DB, skipping the cache entirelyKeeps the cache from filling with cold, write-once-read-rarely data; the first read after a write is always a miss.
Default choice

Cache-aside + write-around is what most teams reach for first: it's the simplest to reason about, and it only ever caches data that's actually being read. Reach for write-through or write-behind specifically when the cache and DB must never disagree, or when write latency itself is the bottleneck.

Eviction — What Gets Thrown Out When the Cache Is Full

  • LRU (Least Recently Used) — evicts whatever hasn't been touched in the longest time. The most common choice in caching libraries, and the policy you usually configure in Redis (maxmemory-policy allkeys-lru) — note that Redis’s actual default is noeviction, which rejects writes with an error once maxmemory is reached instead of evicting anything, so a Redis cache must set an eviction policy explicitly; a good general-purpose choice because real traffic is usually Zipfian (a small set of keys accounts for most of the reads).
  • LFU (Least Frequently Used) — evicts by access count instead of recency. Beats LRU when a key is hit constantly but happened to go quiet for an hour; Redis offers this as allkeys-lfu.
  • FIFO — evicts in insertion order regardless of use. Cheap to implement, rarely optimal — a key read every second can still be evicted just because it happens to be the oldest.
  • TTL / expiration — every entry gets a time budget regardless of memory pressure. Used alongside LRU/LFU, not instead of it — TTL is the main tool for bounding freshness, eviction policy is the tool for bounding memory.

Deep dive: In-Memory: Eviction Policies.

Invalidation — the Genuinely Hard Part

"There are only two hard things in Computer Science: cache invalidation and naming things" isn't a joke about implementation effort, it's about correctness: a stale cache doesn't crash — it just quietly serves wrong answers.

  • TTL expiry — the simplest strategy, and the only one that needs zero coordination: bound staleness to "at most N seconds old" and move on. Wrong choice when correctness matters more than a few seconds of staleness (an account balance, an inventory count).
  • Explicit invalidation on write — the write path deletes or updates the cache key. Correct in principle, but every code path that writes that data has to remember to do it — a second service or a one-off backfill script that writes directly to the DB silently breaks the cache.
  • Versioned / namespaced keys — e.g. user:42:v3; bump the version on write instead of deleting. Old readers naturally age out, and there's no race between "delete the key" and "a slow read that started before the write repopulates the old value."
  • Event-driven invalidation — a write publishes an event (a DB change stream, or a message queue — see SQS Overview) and every cache node subscribes and invalidates. Scales to many cache nodes/services without them all knowing about each other directly, at the cost of eventual rather than immediate consistency.
  • Stale-while-revalidate — serve the stale value immediately, kick off a background refresh, the next request gets the fresh value. Trades a bounded amount of staleness for zero-latency cache misses; it's the pattern CDNs use by default (see below).

⚠️ Common mistake

Updating the cache with the new value on write instead of deleting it. Two concurrent writers can apply DB writes in one order and cache writes in the other, leaving the cache permanently wrong. Deleting the key (and letting the next read repopulate it) narrows that race.

Cache Stampede (Thundering Herd)

A hot key expires, and every one of the thousands of requests that would have hit the cache in that instant now misses at the same moment and hammers the database simultaneously — often hard enough to take it down, which is worse than never having had a cache at all.

  • Locking / request coalescing — the first request to miss takes a short-lived lock and recomputes; every other concurrent request for the same key waits on that one result instead of each recomputing it independently.
  • Early / probabilistic recomputation — recompute slightly before the TTL actually expires (with random jitter so not every key refreshes at once), so the cache is never truly empty for that key.
  • TTL jitter — add a small random offset to every TTL so a batch of keys written at the same time (e.g. a cache warm-up after a deploy) doesn't all expire in the same millisecond.
  • Stale-while-revalidate — the same fix as above: keep serving the old value while one request refreshes it in the background.
The "hot key" problem is a different failure mode

A stampede is many requests hitting an empty slot at once. A hot key is one key so popular it saturates a single cache shard/node even while warm (a celebrity's profile, a viral post) — the fix is different: client-side/local caching of that one key, or replicating just that key across shards, not TTL tuning.

CDN: Caching at the Edge

A CDN is a distributed cache sitting in front of your origin server: dozens to hundreds of PoPs (Points of Presence) spread geographically, so a user's request is answered by whichever PoP is nearest instead of crossing the planet to the origin. DNS or anycast routing sends each user to their nearest PoP automatically.

  • Origin pull — the common model: a PoP fetches from your origin on its first miss for a given URL, then caches it for subsequent requests until the TTL expires. Nothing to push, nothing to pre-warm.
  • Origin push — you proactively upload content to the CDN ahead of demand — common for release-day assets (video, game patches) where a stampede on first request would overwhelm the origin.

Cache-Control headers — how the origin tells every cache in the chain what to do

Header valueMeaning
max-age=NFresh for N seconds; any cache (browser, CDN, proxy) may store and reuse it.
s-maxage=NSame as max-age, but only for shared caches (CDN/proxy) — lets you cache longer at the edge than in the user's own browser.
no-cacheMisleadingly named — may be stored, but must be revalidated with the origin (via ETag/If-None-Match) before every use.
no-storeThe real "don't cache this" — never stored anywhere; use it for genuinely sensitive, per-request data.
privateOnly the end user's own browser may cache it — shared caches (CDN) must not.
publicAny cache may store it, even a normally-uncacheable authenticated response.
stale-while-revalidate=NServe the stale copy for up to N more seconds after expiry while refetching in the background — turns every refresh into a zero-latency cache hit.
stale-if-error=NIf the origin is down or erroring, keep serving the stale copy for N seconds instead of surfacing the error — a cheap resilience win for free.

Purging and invalidating edge content

  • Let it expire — the simplest option: set a TTL and don't fight it. Right choice for anything that changes on a schedule rather than on demand.
  • Explicit purge / invalidation API — every major CDN exposes an API to force-evict a URL (or a whole path/tag) immediately; needed when content changes at an unpredictable time (a CMS publish, a bug-fix redeploy of a JS bundle).
  • Cache-busting via the URL itself — bake a content hash or version into the filename (app.a1b2c3.js) and set an effectively infinite TTL. A new deploy is a new URL, so there's never anything to invalidate, and the old URL just harmlessly stays cached forever. This is why build tools fingerprint static assets.

Static vs. dynamic content at the edge

Static assets (JS/CSS/images, fingerprinted per the point above) are the easy, textbook case for a CDN — cache them aggressively, for a very long time. Dynamic, personalized, or authenticated responses (a logged-in user's dashboard, an API response scoped to one account) are harder: either mark them private/no-store and skip the edge entirely, or split the response so the CDN caches a static shell/fragment and an edge function or the client fills in the personalized part after load. Modern CDNs also run edge compute (Cloudflare Workers, Lambda@Edge) to do light request-time logic — auth checks, A/B routing, header rewriting — right at the PoP instead of round-tripping to the origin for it.

Cache-aside in code (Python + Redis)

def get_user(user_id):
    key = f"user:{user_id}"
    cached = redis.get(key)
    if cached is not None:
        return json.loads(cached)
    user = db.fetch_user(user_id)
    redis.set(key, json.dumps(user), ex=300 + random.randint(0, 60))
    return user

def update_user(user_id, fields):
    db.update_user(user_id, fields)
    redis.delete(f"user:{user_id}")
  • redis.get → hit returns immediately; miss falls through to the database.
  • ex=300 + random.randint(0, 60) — a 5-minute TTL with up to 60 s of jitter, so keys loaded together don't expire together.
  • update_user writes the DB first, then deletes the key — the next read repopulates it from the source of truth.

Redis as a cache

redis-cli CONFIG SET maxmemory 2gb
redis-cli CONFIG SET maxmemory-policy allkeys-lru
redis-cli INFO stats | grep -E "keyspace_hits|keyspace_misses|evicted_keys"
  • maxmemory — cap memory, or Redis grows until the host runs out.
  • allkeys-lru — evict instead of the default noeviction (which rejects writes when full).
  • keyspace_hits/keyspace_misses give the hit ratio; evicted_keys rising fast means the cache is too small.

Cache-Control on two kinds of response

Cache-Control: public, max-age=31536000, immutable
Cache-Control: private, no-cache
  • First line — fingerprinted static asset (app.a1b2c3.js): cache for a year everywhere; immutable tells browsers not to revalidate.
  • Second line — a logged-in user's API response: only their browser may store it, and must revalidate before reuse.

🔥 Production insight

Never let the cache become a hard dependency. Wrap cache calls with short timeouts and fall back to the database (with stampede protection) — a Redis outage should make the site slower, not down.

Security

  • Never cache personalized responses in shared caches. A missing private on an authenticated response can serve one user's data to everyone behind that CDN PoP.
  • Include everything that changes the response in the cache key (e.g. language, auth state) — or cache keys mix users' content.
  • Web cache poisoning: if an unkeyed header (like X-Forwarded-Host) influences the response, an attacker can get a malicious variant cached for everyone.
  • Protect Redis: no public exposure, require auth (ACLs), TLS where traffic crosses networks; it often holds sessions and tokens.
  • Use no-store for genuinely sensitive data.

Performance & Scalability

  • Hit ratio is everything: going from 90% to 99% hits cuts database reads 10×.
  • Scale a shared cache by sharding keys across nodes (Redis Cluster hash slots, or consistent hashing on the client).
  • Hot keys saturate one shard — cache them locally or replicate them.
  • Large values cost network time and block single-threaded Redis — cache the fields you need, compress big blobs.
  • Batch reads (MGET, pipelining) instead of N round trips.

Debugging workflow

  1. Which layer answered? curl -I and read Age, Cache-Control and the CDN's hit/miss header (e.g. X-Cache, CF-Cache-Status).
  2. Inspect the key: redis-cli GET user:42, redis-cli TTL user:42.
  3. Compare with the source of truth to confirm staleness vs. a bug.
  4. Check hit ratio and evictions (INFO stats) around the incident time.

Best Practices

Do

  • Start with cache-aside + delete on write — simplest to reason about.
  • Always set a TTL and an eviction policy — every cached value needs a freshness bound and the cache needs a memory bound.
  • Jitter TTLs and coalesce misses on hot keys.
  • Fingerprint static assets and cache them for a year.
  • Treat the cache as optional — timeouts and DB fallback.

Avoid

  • Caching data whose staleness you haven't decided is acceptable.
  • Shared caching of personalized responses.
  • Leaving Redis on noeviction for a cache.
  • In-process caches for data that must be consistent across instances.

Interview Answer — What Is Caching?

Caching is keeping a copy of data in a faster, closer storage layer so that repeated reads can be answered without going back to the slower source of truth — usually a database or an origin server. A cache can live in the browser, at a CDN edge, in a reverse proxy, in a shared store such as Redis, or inside the application process itself.

Caching exists because the same data is read far more often than it changes. Without a cache, every read pays a full network round trip and puts load on the database; with one, most reads are answered from memory in microseconds to a few milliseconds, and the database only sees the misses. The cause → effect chain is: a request checks the cache → on a hit it returns immediately → on a miss it reads the source of truth, returns the result, and stores a copy so the next request becomes a hit.

The price is staleness: the cached copy can drift away from the source of truth. That is why every cache design has to answer three questions — which caching strategy writes the data (cache-aside, write-through, write-behind), which eviction policy frees memory (LRU, LFU) and which TTL bounds freshness, and how a change invalidates the old copy. A CDN is the same idea applied at the network edge: geographically distributed caches that serve static and cacheable responses from the location nearest to the user.

Simple interview version

"Caching stores a copy of frequently read data in a faster layer — browser, CDN, Redis, or process memory — so most reads skip the database or origin. The most common pattern is cache-aside: check the cache, on a miss read the database and populate the cache, and on a write update the database and invalidate the key. Every cache trades some staleness for speed, so I always state the strategy, the eviction policy, the TTL, and how the data gets invalidated."

One important interview follow-up

Q: If a cache makes reads faster, can adding one ever make the system less reliable?

A: Yes. A cache does not crash when it is wrong — it quietly serves stale data if invalidation is missed, for example when a backfill script writes directly to the database. And if a hot key expires, thousands of concurrent requests miss at the same moment and hit the database together — a cache stampede — which can take down a database that was sized for the cache-hit traffic. The database must be protected with request coalescing, TTL jitter, or stale-while-revalidate, and the system must be designed so a cold or failed cache degrades performance instead of availability.

Interview checklist

  • Name the layer: is this a browser-cache, CDN, app-level-cache, or DB-buffer-pool problem? They have different failure modes and different fixes.
  • State the strategy explicitly (cache-aside vs. write-through vs. write-behind) — interviewers will ask what happens if the cache write fails, and the answer depends entirely on which strategy you picked.
  • Always name an eviction policy and a TTL — "cache it" alone isn't a complete answer.
  • Call out cache-stampede risk on any "single hot key" scenario (trending topic, homepage, celebrity profile) and name a mitigation (locking, jitter, stale-while-revalidate).
  • Remember caches trade consistency for speed — be ready to say how stale is acceptable for this specific piece of data, and why.

Practice questions

Why does caching work at all?

Reads vastly outnumber writes and access is skewed (a few keys get most reads), so a small, fast copy answers most requests.

Eviction vs. invalidation?

Eviction removes entries because memory is full; invalidation removes them because the data changed. A good eviction policy doesn't prevent stale reads.

no-cache vs. no-store?

no-cache may be stored but must be revalidated before use; no-store must never be stored.

In cache-aside, why delete the key on write instead of updating it?

Concurrent writers can update the cache out of order, leaving a permanently wrong value. Deleting makes the next read reload from the source of truth.

When would you choose write-behind, and what's the risk?

When write latency or bursty writes are the bottleneck (counters, analytics). Risk: data in the cache but not yet flushed is lost on a crash — needs a durable log/queue.

Redis or Memcached for a leaderboard?

Redis — sorted sets give ranked inserts and range queries natively; Memcached only stores blobs.

How do you prevent a cache stampede on a hot key?

Request coalescing (one recompute, others wait), early probabilistic refresh, TTL jitter, and stale-while-revalidate.

Stampede vs. hot key — why do they need different fixes?

A stampede is many misses on an expired key (fix the refill); a hot key overloads one shard even when warm (fix distribution: local caching or replicating the key).

How do you invalidate caches when many services write the same data?

Publish change events (CDC or a queue) that every cache subscribes to, or use versioned keys; accept eventual consistency within a bounded TTL.

After a Redis restart the database CPU hits 100% and the site falls over. Why, and how do you prevent it next time?

The DB was sized for cache-hit traffic; a cold cache sends every read to it. Prevent with stampede protection, gradual traffic ramp or cache warm-up, DB capacity headroom, and Redis replicas/persistence.

A user saw another user's account page. What happened?

A personalized response was cached by a shared cache (CDN/proxy) — missing private/no-store or a cache key without the user. Purge immediately, fix headers and keys.

You deployed a JS fix but many users still run the old bundle. What do you do?

Purge the CDN path now; long term, fingerprint filenames so every deploy is a new URL with a long TTL and the HTML references the new name.

What Should I Remember?

  1. Caching trades staleness for speed; manage the staleness on purpose.
  2. Layers: browser → CDN → proxy → app/local → Redis → DB buffer pool.
  3. Default strategy: cache-aside + delete on write (+ write-around).
  4. Eviction bounds memory; TTL and invalidation bound staleness.
  5. Protect the DB from stampedes: coalescing, jitter, stale-while-revalidate.
  6. Cache-Control decides what every cache may store; never share personalized responses.
  7. Fingerprinted URLs remove the need to purge.

Quick commands

  • redis-cli INFO stats — hits, misses, evictions
  • redis-cli TTL user:42 — remaining lifetime of a key
  • curl -I https://example.com/app.js — Cache-Control, Age, CDN hit header
