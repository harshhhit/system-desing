In-Memory Caching Strategies

Cache-aside, read-through, write-through, write-behind, write-around and refresh-ahead — who fills the cache, how writes keep it in sync, and why you delete instead of update.

Interview Answer — What Is a Caching Strategy?

A caching strategy (also called a caching pattern) is the rule that decides which component reads from and writes to the cache, and in what order relative to the database. Read strategies decide how a missing value gets into the cache (cache-aside, read-through, refresh-ahead); write strategies decide how a changed value reaches both the cache and the database (write-through, write-behind, write-around).

Strategies exist because an in-memory cache and a database are two separate stores with no shared transaction. Every write therefore creates a window where the two can disagree, and every miss creates a moment where many callers may try to fill the same key. The strategy chooses where that window sits: write-through keeps the cache current at the cost of slower writes; write-behind makes writes fast at the risk of losing data; cache-aside keeps the cache simple and only holds data somebody has actually asked for.

In practice the default for Redis or Memcached in front of a relational database is cache-aside for reads + delete-the-key on write, with a TTL as a safety net. The other strategies are chosen when a specific requirement — write latency, always-warm keys, or a library that owns loading — outweighs that simplicity. The comparison table lists all six side by side.

Simple interview version

"A caching strategy defines who fills the cache and how writes keep it in sync. My default is cache-aside: the app reads the cache, on a miss reads the database and stores the result with a TTL, and on a write it updates the database and then deletes the cache key. Write-through writes cache and database together so the cache is always current but writes are slower; write-behind writes only the cache and flushes to the database asynchronously — fastest, but data can be lost if the cache dies; write-around skips the cache on writes; and refresh-ahead reloads hot keys before they expire."

One important interview follow-up

Q: On a write, should the application update the cached value or delete it?

A: Delete it, in most cases. Updating means two concurrent writers can set the database in order A → B but set the cache in order B → A, leaving the cache permanently holding A while the database holds B — and nothing corrects it until the TTL. Deleting is idempotent: whatever the order, the next read misses and loads the current database value. Deleting also avoids computing a cache value that may never be read. The remaining race (a slow reader re-inserting an old value right after the delete) is small and is handled with a short TTL, delayed double delete, or versioned keys — see invalidate vs. update and stale data.

Terms used on this page

  • Source of truth — the store whose value is correct by definition (here, the database).
  • Cache fill — writing a value into the cache after reading it from the source of truth.
  • Invalidation — removing (or versioning away) a cached value because the source of truth changed. Invalidation vs. eviction — the difference is the reason: invalidation removes a key because it is wrong; eviction (see Eviction Policies) removes a key because the cache is full.

1. Cache-aside (lazy loading)

What it is: the application talks to both the cache and the database; the cache knows nothing about the database. Why it exists: it is the simplest pattern that works with any cache (Redis, Memcached, an in-process map) and any database, and it only caches data that is actually read.

Read path, step by step:

  1. The app calls GET user:42 on Redis.
  2. Hit → return the value. Done.
  3. Miss → the app runs SELECT * FROM users WHERE id = 42.
  4. The app stores the row: SET user:42 <json> EX 300 (5-minute TTL) and returns it.

Write path: the app runs UPDATE users … on the database, then DEL user:42. The next read misses and reloads the new row.

def get_user(user_id):
    key = f"user:{user_id}"
    cached = redis.get(key)
    if cached is not None:
        return json.loads(cached)
    row = db.fetch_one("SELECT * FROM users WHERE id = %s", user_id)
    redis.set(key, json.dumps(row), ex=300)
    return row

def update_user(user_id, fields):
    db.execute("UPDATE users SET ... WHERE id = %s", user_id)
    redis.delete(f"user:{user_id}")
  • Pros: simple; resilient (if Redis is down, reads fall back to the database); the cache holds only requested data.
  • Cons: the first read of every key is a miss (three trips: cache, DB, cache); a stale window exists between the DB write and the delete; every write path must remember to delete; many concurrent misses on one key cause a thundering herd.
  • Use when: read-heavy data, general purpose — this is the default.

2. Read-through

What it is: the application only ever asks the cache; on a miss, the cache (or a cache library) calls a loader function to fetch from the database, stores the result, and returns it. Cache-aside vs. read-through — the difference is who owns the miss path: in cache-aside the application code loads the database; in read-through the cache layer does, through a loader you register once.

users = Caffeine.newBuilder()
    .maximumSize(10_000)
    .expireAfterWrite(Duration.ofMinutes(5))
    .build(id -> userRepository.findById(id));

User u = users.get(42L);
  • Pros: application code is shorter and consistent; a good library coalesces concurrent misses for the same key into one load (Caffeine's LoadingCache does), which prevents a stampede for free.
  • Cons: the cache must know how to load data (coupling); plain Redis and Memcached don't do read-through on their own — you need a library or a provider such as Hazelcast MapLoader, NCache, or DynamoDB Accelerator (DAX), which is a read-through/write-through cache in front of DynamoDB.

3. Write-through

What it is: every write goes to the cache, and the cache layer synchronously writes it to the database before acknowledging. Why it exists: the cache is never stale for keys written through it, and a read right after a write is always a hit.

Write path, step by step: app writes user:42 → cache stores it → cache (or the library) writes the database → both succeed → acknowledge to the app. If the database write fails, the cache entry must be rolled back or removed, otherwise the cache holds a value the database never accepted.

  • Pros: cache and database agree for data written through the cache; reads after writes are fast.
  • Cons: every write pays cache + database latency (no write speedup); the cache fills with data that may never be read (pair it with a TTL or eviction); writes that bypass the cache (a migration, another service) still leave it stale.
  • Use when: data is read soon after it is written and staleness is unacceptable — e.g. a user's own settings page. Usually paired with read-through.

4. Write-behind (write-back)

What it is: the app writes only to the cache, which acknowledges immediately; the cache flushes changes to the database asynchronously, often batched (every N ms or N writes). Why it exists: to absorb write bursts and make writes as fast as memory — e.g. view counters, likes, game scores, IoT readings.

Cause → effect of a crash: app writes views:post:9 = 1001 → cache acknowledges → the cache node crashes before the flush → the database still says 1000 → that write is lost, and the client was told it succeeded. That is why write-behind needs a durable buffer (Redis with AOF persistence and a replica, or a log such as Kafka between cache and database) for anything that matters.

  • Pros: lowest write latency; batching turns 1,000 increments into one UPDATE … SET views = views + 1000; the database is shielded from spikes.
  • Cons: risk of data loss; the database is temporarily behind (other readers of the database see old data); ordering and retries of flushes need care; harder to operate.
  • Use when: high write rates where a small loss window is acceptable, or where a durable log sits behind the cache.

5. Write-around

What it is: writes go straight to the database and skip the cache entirely (no update, often combined with a delete). Reads use cache-aside. Why it exists: to stop the cache filling with data that is written once and rarely read — log records, audit entries, bulk imports.

  • Pros: no cache pollution from write-heavy, read-rarely data.
  • Cons: the first read after a write is always a miss. If an older copy is already cached and you don't delete it, reads are stale until the TTL — so "write-around" in practice usually means "write DB + delete key", which is exactly cache-aside's write path.

6. Refresh-ahead

What it is: the cache reloads a hot key before its TTL expires, in the background, so readers keep hitting a warm value. For example, with a 60-second TTL and a refresh factor of 0.8, a read after second 48 returns the current value immediately and triggers an asynchronous reload. Caffeine's refreshAfterWrite does this; HTTP's stale-while-revalidate is the same idea at the CDN.

  • Pros: hot keys never miss, so no latency spike and no stampede at expiry.
  • Cons: wasted reloads for keys that turn out not to be read again; it predicts what is hot, and a bad prediction spends database capacity for nothing.

Invalidate vs. update on write

The concrete race that makes "update the cache" dangerous:

  1. Writer A sets price = 10 in the DB.
  2. Writer B sets price = 12 in the DB (B's write is the latest).
  3. Writer B sets the cache to 12.
  4. Writer A (delayed by a GC pause) sets the cache to 10.
  5. Result: DB = 12, cache = 10 — wrong until the TTL expires.

With DEL instead, both writers delete the key and the next reader loads 12. The ordering of the two operations also matters: update the database first, then delete the cache. Deleting first opens a window where a reader misses, loads the old row from the database, and re-caches it before the write lands.

This does NOT make cache-aside perfectly consistent

Even "DB first, then delete" has a rare race: a reader misses, reads the old row, stalls; the writer updates the DB and deletes the key; the reader then writes the old row into the cache. Mitigations: a TTL so the error is bounded, a delayed double delete (delete again ~1 second later), versioned values (only write if the version is newer), or Memcached-style leases (Facebook's approach: a miss gets a lease token; a delete invalidates outstanding leases, so the stale fill is rejected). Details: stale data & race conditions.

The dual-write problem and change-data-capture

Writing the database and then deleting the cache is a dual write: two systems, no shared transaction. If the process crashes between the two steps, or the DEL fails on a network blip, the cache stays stale until the TTL. Two ways to close the gap:

  • Retry the delete through a queue (put "invalidate user:42" on a queue and retry until it succeeds).
  • Change-data-capture (CDC) — a process tails the database's replication log (PostgreSQL WAL via Debezium, MySQL binlog) and deletes cache keys for every committed change. The cache is then invalidated for every write, including ones from other services or backfill scripts that don't know about the cache. See WAL vs Binlog.

How to choose

  • Read-heavy, a few seconds of staleness is fine → cache-aside + delete on write + TTL.
  • Using a caching library/provider that supports loaders → read-through (and get stampede protection for free).
  • Users must see their own write immediately → write-through, or cache-aside plus read-your-writes (read the writer's own data from the DB for a few seconds after they write).
  • Extreme write rate, small loss acceptable (counters, metrics) → write-behind with batching.
  • Write-once, read-rarely data → write-around.
  • A small set of very hot keys with predictable reads → add refresh-ahead.
