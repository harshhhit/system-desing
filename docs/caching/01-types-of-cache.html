Types of Cache

Every kind of cache on one page — hardware, OS page cache, browser and Service Worker, DNS, CDN, reverse proxy, API gateway, in-process, distributed, near cache, session, negative cache, and the database's own buffer pool, query cache and materialized views.

Interview Answer — What Types of Cache Are There?

A cache is any smaller, faster store that keeps a copy of data whose source of truth is slower or farther away. "Types of cache" is the list of places such a copy can live along a request's path: in the CPU, in the operating system, in the user's browser or app, in the network (DNS, CDN, reverse proxy, API gateway), in the application (in-process memory or a shared store such as Redis), and inside the database itself.

The types exist because each layer removes a different cost. A browser cache removes the network trip entirely; a CDN removes the long-distance trip to the origin; a reverse proxy removes the application's work; Redis removes the database query; the database buffer pool removes the disk read; the CPU cache removes the RAM read. The cause → effect chain is: the closer to the user a copy lives → the more work it saves per hit → but the more copies exist and the harder it is to invalidate them all when the data changes.

Two axes classify every type: who shares the copy (private to one user or process vs. shared by everyone) and where it runs (local to the process vs. distributed over the network). A real request usually misses through several types in order — browser → CDN → reverse proxy → application cache → database buffer pool → disk — before it reaches the source of truth. The summary table at the end lists every type side by side.

Simple interview version

"Caches exist at every layer: the browser and mobile app cache responses per user; DNS and the CDN cache at the network edge; a reverse proxy or API gateway caches whole responses in front of the app; the application caches objects in its own memory or in a shared store like Redis; and the database keeps hot pages in its buffer pool. The closer a cache is to the user, the more it saves on a hit, but the harder it is to invalidate — so I pick the layer per data type: static assets at the CDN, shared hot objects in Redis, and tiny rarely-changing data in-process."

One important interview follow-up

Q: If I already have Redis, is an in-process cache redundant?

A: Not necessarily — they solve different costs. Redis still costs a network round trip (~0.5–1 ms) and serialization on every read; an in-process cache costs microseconds. For a very hot key (a feature-flag set, a config blob, a celebrity profile) that network trip dominates and can even saturate one Redis shard, so a small in-process cache with a short TTL in front of Redis — a near cache — removes it. The catch is that N application instances now hold N independent copies that go stale independently, so it only suits data that tolerates a few seconds of staleness or has a push-based invalidation channel.

How to classify any cache

Before the list, four distinctions that apply to every type. Naming them lets you describe a new cache in one sentence.

1. Hardware caches

Deep dive: 01e. DNS, OS & Hardware Caching.

Hardware caches are memory built into the CPU and storage devices. You don't configure them in system design, but they explain why in-memory caches are fast and why data layout matters.

CPU caches (L1, L2, L3)

What it is: small SRAM memories on the CPU die that hold recently used 64-byte cache lines from RAM. L1 (~32–64 KB per core, ~1 ns), L2 (~256 KB–2 MB per core, ~4 ns), L3 (tens of MB shared by all cores, ~10–40 ns); RAM is ~80–100 ns. Why it exists: without it the CPU would wait ~100 cycles on every memory access. Consequence for software: a sequential array scan is fast (spatial locality — the next element is already in the cache line), while pointer-chasing through a linked list misses constantly. This is also why multithreaded code suffers from false sharing — two cores writing different variables on the same cache line keep invalidating each other's copy.

TLB (Translation Lookaside Buffer)

A cache of virtual-to-physical page-address translations. Every memory access needs a translation; the TLB avoids walking the page tables each time. Huge pages (2 MB instead of 4 KB) are used by databases and Redis-like systems partly to reduce TLB misses — though Redis specifically recommends disabling transparent huge pages because they slow down its fork-based snapshots.

Disk and controller caches

SSDs and RAID controllers have their own DRAM cache. As a read cache it is harmless; as a write-back cache it acknowledges a write before it reaches durable media — which is why databases depend on battery- or capacitor-backed controllers or on fsync semantics to avoid losing acknowledged writes on power failure.

2. Operating-system caches

Deep dive: 01e. DNS, OS & Hardware Caching.

Page cache (file-system cache)

What it is: the kernel keeps recently read file blocks in otherwise unused RAM, so the second read of a file comes from memory, not disk. Why it matters in system design: Kafka relies on it instead of its own cache (consumers reading recent messages hit the page cache); PostgreSQL deliberately relies on it as a second layer behind shared_buffers (which is why the common guidance is ~25% of RAM for shared_buffers and leave the rest to the OS). Gotcha: free shows this memory as "buff/cache" — it is not a leak; the kernel releases it when applications need memory.

OS DNS resolver cache

The OS (e.g. systemd-resolved, or the macOS/Windows DNS client) caches name → IP answers for the record's TTL, so a process doesn't repeat a DNS lookup on every connection. Language runtimes can add their own layer — the JVM caches successful lookups (networkaddress.cache.ttl), which historically caused services to keep connecting to an old IP after a failover.

3. Client-side caches

Deep dive: 01a. Browser Caching.

Browser HTTP cache

What it is: the browser stores HTTP responses (in a memory cache for the current tab session and a disk cache across sessions) and reuses them according to the response's Cache-Control, ETag, and Last-Modified headers. Why it exists: a hit costs zero network — the fastest request is the one never sent. How it works:

  1. The first response says Cache-Control: max-age=31536000, immutable for app.3f9a1c.js → the browser stores it.
  2. For a year, every page that references that URL uses the stored copy without contacting the server (a fresh hit).
  3. For a response with Cache-Control: no-cache and an ETag, the browser sends If-None-Match every time → the server answers 304 Not Modified with no body if unchanged (a revalidation: a round trip, but no payload).

no-cache vs. no-store — the difference is that no-cache may store but must revalidate before every use, while no-store must not store the response at all (use it for banking pages and anything with secrets). Gotcha: you cannot purge a browser cache remotely — so long-lived assets must use fingerprinted URLs (a content hash in the filename); a new deploy changes the URL instead of trying to invalidate the old one.

Service Worker cache (Cache Storage API)

A programmable cache: a Service Worker script intercepts the page's requests and decides whether to answer from caches.open(...), the network, or both (cache-first, network-first, stale-while-revalidate). It powers offline-capable Progressive Web Apps. Unlike the HTTP cache it ignores Cache-Control — your code owns freshness, so a bug can pin users to an old version of the app.

Application storage as a cache (localStorage, IndexedDB, mobile caches)

Web apps cache API data in localStorage / IndexedDB; mobile apps cache in SQLite, on-disk image caches, or HTTP client caches (OkHttp, URLCache). Front-end data libraries (React Query, SWR, Apollo Client) keep an in-memory response cache with stale-while-revalidate semantics. Limit: this data is on the user's device — never cache secrets there, and assume it may be stale or cleared at any time.

4. Network and edge caches

Deep dives: DNS caching, 01b. CDN Caching, 01c. Reverse Proxy & API Gateway Caching.

DNS caching (recursive resolvers)

What it is: recursive resolvers (your ISP's, 8.8.8.8, 1.1.1.1, Route 53 Resolver in a VPC) cache DNS answers for the record's TTL, and also cache "this name does not exist" answers (negative caching, bounded by the SOA record). Why it matters: DNS TTL decides how fast a DNS-based failover or migration takes effect. Lower the TTL (e.g. 3600 → 60 seconds) before a planned migration, because resolvers that cached the old answer keep it until the old TTL expires. Gotcha: some resolvers and clients ignore low TTLs, so never rely on DNS alone for instant failover.

CDN (edge) cache

What it is: a shared HTTP cache operated in many Points of Presence (PoPs) worldwide — CloudFront, Cloudflare, Fastly, Akamai. It stores responses near users so a hit avoids the long trip to the origin. Layers inside a CDN: edge PoP → regional cache → optional origin shield (one designated PoP that all edges fetch through, so the origin sees one miss per object instead of one per PoP). Controlled by Cache-Control / s-maxage and the cache key (host + path + selected query strings/headers/cookies — every extra item in the cache key lowers the hit ratio). Full detail: CDN: caching at the edge.

Reverse-proxy cache

What it is: a proxy in front of your application servers that stores whole HTTP responses — Varnish, Nginx proxy_cache, Apache Traffic Server. Why it exists: it serves repeated responses without running application code at all, and it can apply micro-caching (caching a dynamic page for 1–5 seconds) which collapses a burst of identical requests into one backend call. Nginx's proxy_cache_lock on additionally makes concurrent misses wait for the first one — built-in stampede protection. Difference from a CDN: same idea, but it lives in your datacenter next to the app, so it saves application work, not geographic distance.

API gateway cache

API gateways (Amazon API Gateway stage caching, Kong's proxy-cache plugin, Apigee) cache responses per method + path + selected parameters for a TTL. Useful for read-heavy public APIs. Gotcha: the cache key must include every parameter that changes the response — especially the caller's identity or tenant, otherwise one user's response is served to another.

Forward-proxy cache

A proxy on the client side of the network (a corporate Squid proxy, historically ISP proxies) that caches for many users behind it. Less relevant today because HTTPS hides responses from it, but it is the reason Cache-Control: private exists.

5. Application caches (the in-memory caches you design)

Deep dives: 02. Strategies, 03. Eviction Policies, 04. Cache Problems.

This is the layer the rest of this section's deep-dive pages focus on: strategies, eviction policies, and problems such as the thundering herd.

In-process (local) cache

What it is: a map inside the application's own memory, with size limits and TTLs — Caffeine or Guava (Java), functools.lru_cache / cachetools (Python), lru-cache (Node.js), MemoryCache (.NET). Why use it: reads cost nanoseconds to microseconds, no network, no serialization. Limits: memory is per-process and lost on restart; with N instances there are N copies that are invalidated independently, so instance A may serve a new value while instance B still serves the old one. Best for small, hot, rarely changing data: configuration, feature flags, country lists, compiled templates.

Distributed (remote) cache

What it is: a separate cache service shared by every application instance over the network — Redis, Memcached, Valkey, Amazon ElastiCache / MemoryDB, Hazelcast. (See Amazon ElastiCache for the managed AWS version.) Why use it: one shared copy (all instances see the same value), capacity beyond one machine's memory via sharding, and the cache survives application deploys. Cost: a network round trip (~0.5–1 ms in the same zone) and serialization per read, plus a new piece of infrastructure that can fail. Distributed cache vs. in-process cache — the difference is one consistent shared copy with a network hop vs. many fast independent copies.

Near cache (two-level / L1 + L2)

What it is: an in-process cache (L1) in front of a distributed cache (L2). A read checks L1 → then L2 → then the database. Why: it removes the network hop for the hottest keys and protects a single Redis shard from a hot key. The hard part is invalidating L1 on every instance: options are a short L1 TTL (seconds), pub/sub invalidation messages, or Redis 6+ client-side caching (the CLIENT TRACKING command — Redis remembers which keys each client read and pushes an invalidation message when they change). Hazelcast and Apache Ignite have a built-in near cache.

Session cache

Storing login sessions in Redis/Memcached so any application instance can serve any user (stateless app servers). Note the change in role: here the cache is effectively the primary store for sessions — evicting a session logs the user out — so it needs a no-eviction or volatile-only eviction policy, replication, and possibly persistence. See Cookies, Sessions & JWT.

Object, full-page, and fragment caches

  • Object cache — caches a domain object (user:42 → serialized JSON). The most common application-cache use.
  • Full-page cache — caches the whole rendered HTML page (WordPress page caches, Varnish). Only works when the page is identical for everyone who hits that key.
  • Fragment cache — caches parts of a page (a product-description block, a sidebar) and assembles them per request (Rails fragment caching, Edge Side Includes at the CDN). Lets a mostly-shared page have a small personalised part.

Memoization and computation caches

Caching the result of a function keyed by its inputs — a pure function's output never goes stale, so memoization has no invalidation problem at all. Extended to expensive computations: rendered thumbnails, ML model inference results, aggregated dashboards, LLM prompt caches. Build systems use the same idea (Bazel remote cache, Docker layer cache, CI dependency caches): the key is a hash of the inputs, so correctness is automatic.

Negative cache

Caching the fact that something does not exist ("user 999 not found") for a short TTL. It prevents repeated lookups for missing keys from reaching the database — the main defence against cache penetration. DNS does the same with NXDOMAIN answers.

6. Data-layer caches (inside the database)

Deep dive: 01d. Database Caching.

Database buffer pool / buffer cache

What it is: the database's own in-memory cache of data and index pages — PostgreSQL shared_buffers, MySQL InnoDB buffer pool (innodb_buffer_pool_size, often 50–75% of RAM on a dedicated server), Oracle buffer cache, MongoDB WiredTiger cache. Why it matters: if the working set (hot tables + indexes) fits in the buffer pool, most queries never touch disk — often the single biggest database performance factor. It uses its own eviction policy (PostgreSQL: clock-sweep; InnoDB: an LRU with a "young/old" midpoint insertion so one large table scan doesn't flush the hot pages). See Indexing.

Query / result cache

Caching the result set of a query keyed by its SQL text. MySQL's built-in query cache was removed in MySQL 8.0 because every write to a table invalidated all cached queries on that table, and the global lock around it hurt concurrency on multi-core servers — a clear example of a cache that cost more than it saved on write-heavy workloads. Today result caching is done in the application (usually Redis, keyed by query + parameters) or in a SQL-aware proxy such as ProxySQL, which can cache the results of queries matching configured rules for a TTL. Note that a connection proxy such as Amazon RDS Proxy pools connections but does not cache results.

Materialized views and precomputed tables

A materialized view stores the result of a query as a table and is refreshed on a schedule or incrementally (REFRESH MATERIALIZED VIEW in PostgreSQL). It is a cache that lives inside the database and can be indexed. Same trade-off as every cache: fast reads, results as stale as the last refresh. Denormalized read models in CQRS are the same idea at the architecture level — see Event Sourcing & CQRS.

ORM caches (first- and second-level)

Hibernate's first-level cache is per session/transaction (the same entity loaded twice in one transaction is one object); its second-level cache is shared across sessions and backed by Ehcache, Infinispan, or Redis. Gotcha: any write that bypasses the ORM (raw SQL, another service) leaves the second-level cache stale.

Read replicas (a cache-like layer)

A read replica is not a cache — it is a full copy that is updated by replication, not by eviction and TTL — but it plays a similar role (offloading reads) and shares the same staleness problem: see Replication Lag. Replica vs. cache — the difference is that a replica holds all data and answers any query, while a cache holds a subset and answers only key lookups it has seen.

This does NOT mean "use every layer"
