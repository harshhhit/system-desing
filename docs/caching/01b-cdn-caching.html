CDN Caching

PoPs, anycast vs DNS routing, tiered caching and origin shield, cache keys, edge TTLs, purge by URL or tag, request collapsing, dynamic content at the edge, and CDN security (cache poisoning and deception).

Interview Answer — What Is CDN Caching?

A CDN (Content Delivery Network) is a globally distributed network of servers, grouped into Points of Presence (PoPs), that sits between users and your origin (your web servers or an S3 bucket). CDN caching is those PoPs storing copies of your HTTP responses so that a user's request is answered by a nearby PoP instead of travelling to the origin. CloudFront, Cloudflare, Fastly, and Akamai are the common examples.

It exists to solve two problems at once: distance and load. A user in Sydney fetching from an origin in Virginia pays ~200 ms per round trip; the nearest PoP is a few milliseconds away. And because one PoP serves thousands of users, one origin fetch can answer thousands of requests. The cause → effect chain: the first Sydney user requests /img/hero.webp → the Sydney PoP misses and fetches it from the origin (possibly through a regional cache or origin shield) → stores it for the TTL from Cache-Control: s-maxage → every later Sydney user gets it from the PoP in milliseconds → the origin sees one request instead of thousands.

Unlike the browser cache, a CDN is a shared cache that you can purge. That makes it powerful and dangerous: a correct cache key and private/no-store on personalised responses are what stop one user's page being served to another. The deep-dive sections below cover architecture and tiers, cache keys, TTLs, invalidation, dynamic content, and security.

Simple interview version

"A CDN caches my responses in edge locations close to users, so most requests never reach my origin. Users are routed to the nearest PoP by anycast or DNS; on a miss the PoP fetches from the origin, often through an origin shield so the origin sees one request per object, and caches it for the TTL set by s-maxage. I keep the cache key minimal to get a high hit ratio, version static asset URLs so I never need to purge them, purge by tag for content that changes unpredictably, and mark personalised responses private so the CDN never shares them. The metric I watch is the hit ratio and origin offload."

One important interview follow-up

Q: Can a CDN help with dynamic, uncacheable API responses?

A: Yes, even with zero caching. The CDN terminates TCP and TLS at a PoP near the user (so handshakes take a few milliseconds instead of hundreds), then forwards the request to the origin over persistent, pre-warmed connections on the provider's optimised backbone. It also absorbs DDoS traffic and runs the WAF at the edge. On top of that, short micro-caching (1–5 seconds) of semi-dynamic responses, request collapsing, and edge compute for personalisation can offload much of "dynamic" traffic. See Dynamic content at the edge.

Terms used on this page

  • Origin — the source of truth the CDN fetches from (an ALB, EC2/Kubernetes ingress, S3 bucket).
  • PoP / edge location — a CDN data centre near users.
  • Cache hit ratio — fraction of requests answered from the CDN. Byte hit ratio / origin offload — fraction of bytes served without the origin, often the number that matters for cost.
  • Cache key — the parts of the request that identify a cached object.

Architecture: routing, tiers, and origin shield

How users reach the nearest PoP

  • Anycast — every PoP announces the same IP address over BGP; the internet's routing delivers packets to the topologically nearest one (Cloudflare's model). Also spreads DDoS traffic across all PoPs.
  • DNS-based (GeoDNS) — the CDN's DNS returns the IP of a nearby PoP based on the resolver's location (CloudFront, Akamai). Gotcha: it locates the resolver, not the user — EDNS Client Subnet exists to pass a hint of the user's network.

Tiered caching and origin shield

Without tiers, each of 400 PoPs misses independently and fetches from the origin — a new object costs up to 400 origin requests. Tiered caching puts a layer between them:

  1. User → edge PoP (small, many). Miss →
  2. Regional / mid-tier cache (larger, fewer — CloudFront's Regional Edge Caches). Miss →
  3. Origin shield — one designated cache location that all traffic funnels through. Miss →
  4. Origin.

Effect: the origin sees roughly one request per object per TTL, the hit ratio rises (a large regional tier holds the long tail edges evict), and a burst of misses collapses at the shield. Trade-off: an extra hop on a full miss, and a shield location should be near the origin.

Pull vs. push

Most CDNs are pull (fetch from the origin on first miss). Push (upload content ahead of time) suits large release-day files. More in the fundamentals page: CDN: caching at the edge.

The cache key: the biggest lever on hit ratio

By default the key is roughly scheme + host + path (+ query string). Everything you add to the key splits one cached object into many:

  • Query strings — /p/42?utm_source=twitter and /p/42?utm_source=email are different objects unless you ignore marketing parameters. Include only parameters that change the response, and normalise their order.
  • Headers — forwarding Accept-Language keys per language (fine); forwarding User-Agent keys per browser build (terrible). Normalise instead, e.g. to a device class.
  • Cookies — keying on the whole cookie header makes every user unique → ~0% hit ratio. Whitelist only the cookie that matters (e.g. currency).

Cache key vs. origin request — the difference is that some data must be forwarded to the origin without being part of the key. CloudFront models this with two separate settings: a cache policy (what's in the key, plus TTLs) and an origin request policy (what's forwarded). Gotcha: if the origin's response depends on a header that is forwarded but not keyed, the CDN will serve one variant to everyone — the root of cache poisoning.

TTLs at the edge

  • Header-driven — the CDN honours Cache-Control: s-maxage (edge only) over max-age. This lets the edge cache for a day while browsers cache for a minute: Cache-Control: public, max-age=60, s-maxage=86400.
  • CDN-specific headers — CDN-Cache-Control (RFC 9213) or Surrogate-Control (Fastly, Akamai) target the CDN only and are usually stripped before reaching the browser.
  • Configured min/default/max — CloudFront cache policies clamp the header's TTL into [min, max] and apply the default (24 hours in the managed CachingOptimized policy) when the origin sends no caching headers. Gotcha: an origin that forgets headers gets cached for a day.
  • Error caching — CDNs briefly cache error responses (CloudFront caches 4xx/5xx for 10 seconds by default) to protect a failing origin. Gotcha: a transient 404 during a deploy can be served for that period.
  • Serving stale — stale-while-revalidate and stale-if-error let the edge keep serving when an object expires or the origin is down: a cheap availability win.

Invalidation and purging

MethodHow it worksTrade-off
Versioned URLsNew content = new URL (app.8d02be.js)Instant, free, no purge needed. Only for assets whose URL you control.
Purge by URL / pathAPI call evicts /products/42 or /products/* everywherePropagation takes seconds to minutes; CloudFront charges per path beyond a monthly free allowance.
Purge by tag (surrogate keys)Origin tags responses (Surrogate-Key: product-42 category-7 on Fastly, Cache-Tag on Cloudflare); one call purges every object with that tagPrecise: purge "everything that shows product 42" when its price changes.
Soft purgeMark stale instead of deleting, so it can still be served stale-while-revalidateAvoids a stampede on the origin right after a purge.
Short TTLLet it expireNo tooling, bounded staleness, lower hit ratio.
Purge-all is a self-inflicted avalanche

Purging the whole CDN empties every PoP at once; the next wave of requests all misses and hits the origin — a cache avalanche at the edge. Prefer targeted tag purges, soft purges, and an origin shield.

Request collapsing (the CDN's thundering-herd fix)

When 10,000 users request a just-expired object at once, the PoP should send one request to the origin and make the others wait for it. This is request collapsing (or coalescing) — Varnish, Fastly, and CloudFront do it for cacheable objects. Gotcha: responses that turn out to be uncacheable can serialize the waiters behind each other; CDNs mark such URLs as pass-through ("hit-for-pass") to avoid it. The application-level version is on Cache Problems.

Dynamic and personalised content at the edge

  • Micro-caching — cache a public but frequently changing page (a news homepage, a stock ticker) for 1–5 seconds. At 5,000 requests/second, a 1-second TTL turns 5,000 origin hits into ~1 per PoP per second.
  • Split static shell + personal data — cache the page shell for everyone; fetch the user-specific part (cart count, name) from an uncached API call.
  • Edge Side Includes (ESI) — the cached page contains placeholders the CDN fills with separately cached fragments, each with its own TTL.
  • Edge compute — CloudFront Functions, Lambda@Edge, Cloudflare Workers, Fastly Compute: run code at the PoP for auth checks, A/B bucketing, header normalisation (to shrink the cache key), redirects, or assembling personalised responses from cached parts.
  • Dynamic acceleration — for truly uncacheable requests: edge TLS termination and backbone routing (see the follow-up above).
  • Video and large files — video is split into small HLS/DASH segments, each a cacheable object; byte-range requests let the CDN cache large files in chunks.

Security at the CDN

  • Serving private data to the wrong user — the most damaging CDN bug. A response for a logged-in user cached without the user in the key is served to everyone. Defence: Cache-Control: private or no-store on personalised responses, and CDN rules that bypass cache when an Authorization header or session cookie is present.
  • Web cache poisoning — an attacker sends a request with an unkeyed header (e.g. X-Forwarded-Host: evil.com) that the origin reflects into the page; the poisoned response is cached and served to every visitor. Defence: don't let unkeyed inputs change responses; strip unknown headers at the edge.
  • Web cache deception — tricking the CDN into caching a private page by making its URL look static (/account/profile.css). Defence: cache by content type/explicit rules, return 404 for unknown paths, and rely on origin Cache-Control.
  • Protecting the origin — restrict the origin to the CDN (CloudFront Origin Access Control for S3, security groups allowing only the CDN's IP ranges, or a secret header), otherwise attackers bypass the CDN's WAF and DDoS protection.
  • Access control for paid content — signed URLs or signed cookies with an expiry, validated at the edge.

Operating a CDN

  • Watch — hit ratio, byte hit ratio (origin offload), origin 5xx rate, edge TTFB per region. Response headers such as X-Cache: Hit from cloudfront, CF-Cache-Status: HIT, and Age show what happened for one request.
  • Low hit ratio checklist — cookies or User-Agent in the key; unnormalised query strings; Vary: Cookie; missing Cache-Control; Set-Cookie on responses (many CDNs won't cache them); TTLs too short.
  • Multi-CDN — large sites use two CDNs with DNS-based traffic steering for resilience and price; the trade-off is duplicated configuration and purges.
