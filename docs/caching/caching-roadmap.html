Interview Answer — What Is a Caching Strategy for a System?

A system's caching strategy is the set of decisions that say where copies of data are kept (browser, CDN, reverse proxy, application memory, a shared store such as Redis, the database's own buffer pool), how each copy is filled and updated (cache-aside, read-through, write-through, write-behind), when a copy is dropped (an eviction policy such as LRU for memory, a TTL for freshness), and what happens when the cache misses on a large scale (the thundering herd, cache penetration, cache avalanche).

It exists because a single cache is easy but a whole system of caches is not. Each layer you add removes load and latency from the layer behind it, and each one also adds a copy that can go stale and a new way to fail. The cause → effect chain is: a popular key is cached → the database sees almost none of its reads → the database is sized for the miss traffic only → so if that key expires or the cache node restarts, the full read traffic lands on a database that was never sized for it. That is why the roadmap below goes from placement, to strategies, to eviction, to failure modes — each step exists because the previous one creates a new problem.

Caching is not a free win: it trades freshness for speed, and in an interview the strong answer names that trade-off explicitly, together with a staleness budget ("a user profile may be up to 60 seconds old; an account balance is never cached").

Simple interview version

"I decide caching layer by layer: static assets at the CDN with long TTLs and versioned URLs, hot read-heavy objects in Redis with cache-aside, and a small in-process cache only for data that is almost never written. For each cache I state the eviction policy — usually LRU or LFU with a maxmemory limit — a TTL that matches how stale the data may be, and how writes invalidate it. Then I protect the database from mass misses: request coalescing for hot keys, TTL jitter against mass expiry, and negative caching or a Bloom filter against requests for keys that don't exist."

One important interview follow-up

Q: Is a higher cache hit ratio always better?

A: No. A hit ratio of 99% is only good if the 1% of misses can be served safely and the hits are fresh enough. You can raise the hit ratio by lengthening TTLs, but that serves staler data; and a very high hit ratio makes the database dependent on the cache, because it is sized for 1% of the load — losing the cache then becomes an outage (see cache avalanche). Track hit ratio together with staleness, eviction rate, and miss-path latency, and make sure the origin survives a cold cache.

Stage 0 — Why Caching Exists & the Vocabulary

Know the words and the numbers before choosing any tool.

  • Cache — a smaller, faster copy of data whose source of truth lives somewhere slower.
  • Hit / miss / hit ratio — a hit answers from the cache; a miss falls through to the source; hit ratio = hits ÷ (hits + misses).
  • Latency ladder — L1 cache ~1 ns, RAM ~100 ns, same-datacenter network round trip ~0.5 ms, SSD read ~0.1 ms, cross-region round trip ~50–150 ms. Caching moves a read up this ladder.
  • Locality — temporal (a key read now will be read again soon) and spatial (neighbours of a key will be read soon). Caches only work because real traffic has locality; typical web traffic is Zipf-shaped, so a small set of keys serves most reads.
  • Staleness — how far the cached copy may lag the source. Every cache design needs a stated staleness budget.
  • Working set — the set of keys actively read in a time window. If the cache is smaller than the working set, it thrashes.

Stage 1 — Types of Cache (Where a Copy Can Live)

One request passes through many caches before it reaches the database.

  • Hardware caches: CPU L1/L2/L3, TLB, disk controller cache
  • Operating-system caches: page cache, DNS resolver cache
  • Client caches: browser HTTP cache, Service Worker cache, mobile app cache
  • Network caches: DNS, CDN edge, reverse proxy, API gateway
  • Application caches: in-process (local), distributed (remote), near cache (two-level)
  • Data-layer caches: database buffer pool, query/result cache, materialized views, ORM second-level cache
  • Classifications: private vs. shared, local vs. distributed, in-memory vs. on-disk, read cache vs. write buffer

Deep dive: 01. Types of Cache — every type on a single page; then per type: browser, CDN, reverse proxy & API gateway, database, DNS, OS & hardware.

Stage 2 — HTTP Caching & the CDN

The caches you don't run yourself, controlled entirely by response headers.

  • Cache-Control: max-age, s-maxage, public vs. private, no-cache vs. no-store, immutable
  • Validation: ETag / If-None-Match, Last-Modified / If-Modified-Since, 304 Not Modified
  • stale-while-revalidate and stale-if-error
  • Cache keys and Vary; cache-busting with fingerprinted file names
  • CDN PoPs, origin shield, purge vs. versioned URLs, static vs. dynamic content at the edge

Deep dive: 01a. Browser Caching, 01b. CDN Caching, 01c. Reverse Proxy & API Gateway Caching; overview in CDN and Cache-Control headers.

Stage 3 — In-Memory Caching Strategies (Read & Write Patterns)

Decide which code path fills the cache and which one keeps it in sync with the database.

  • Read patterns: cache-aside (lazy loading), read-through, refresh-ahead
  • Write patterns: write-through, write-behind (write-back), write-around
  • Invalidate vs. update on write — why deleting the key is the safer default
  • The dual-write problem and how change-data-capture avoids it

Deep dive: 02. In-Memory Caching Strategies.

Stage 4 — Eviction & Expiration Policies

Memory is finite: decide what is dropped when it runs out, and when data is too old to serve.

  • Classic policies: LRU, LFU, FIFO, LIFO/MRU, Random, CLOCK
  • Modern policies: SLRU, 2Q, ARC, W-TinyLFU (Caffeine)
  • Expiration: TTL, sliding expiration, lazy vs. active expiry
  • Redis maxmemory-policy options and its approximated LRU / LFU

Deep dive: 03. In-Memory Eviction Policies.

Stage 5 — Invalidation & Consistency

A stale cache doesn't crash — it silently serves wrong answers.

  • TTL expiry vs. explicit invalidation vs. event-driven invalidation
  • Versioned keys; the read-after-write race in cache-aside
  • Delayed double delete, leases, and read-your-writes for the writer
  • Keeping many layers (local + Redis + CDN) consistent

Deep dive: Invalidation, stale data & race conditions.

Stage 6 — Cache Problems & Failure Modes

What happens when the cache misses at scale — the most-asked caching interview topic.

  • Thundering herd / cache stampede and cache breakdown (one hot key expiring)
  • Cache penetration (requests for keys that don't exist)
  • Cache avalanche (mass expiry or a cache cluster outage)
  • Hot keys, big keys, cold start and cache warming, cache pollution

Deep dive: 04. In-Memory Cache Problems.

Stage 7 — Distributed Caching

One cache node is not enough for memory, throughput, or availability.

  • Redis vs. Memcached; data structures vs. plain key-value
  • Sharding keys with consistent hashing; Redis Cluster hash slots (16,384)
  • Replication and failover (Redis Sentinel, Redis Cluster replicas)
  • Near cache / two-level caching and its invalidation (Redis client-side caching)

Deep dive: Redis vs. Memcached, Consistent Hashing, near cache.

Stage 8 — Operating a Cache

A cache you can't observe is a cache you can't trust.

  • Metrics: hit ratio, eviction rate, expired-keys rate, memory used vs. maxmemory, p99 latency, connections
  • Sizing: working-set size × average value size × overhead, plus headroom
  • Warming a cache before a deploy or failover; protecting the origin with rate limits and circuit breakers
  • Security: no public exposure, AUTH/ACLs, TLS, never cache one user's private data under a shared key

Related: Observability Fundamentals, Rate Limiting.

Stage 9 — Design Practice

Apply every stage above to a concrete interview problem.

  • Cache a user-profile service read 100× more than it is written (cache-aside + TTL + delete on write)
  • Cache a celebrity's timeline (hot key → local cache + key replication)
  • Cache product-page HTML at the CDN with per-user fragments fetched separately
  • Design a rate limiter or session store on Redis (cache as a primary store — and what that changes)
  • Implement an LRU cache in O(1) (hash map + doubly linked list)
