In-Memory Cache Problems

Thundering herd (cache stampede), cache breakdown, penetration, avalanche, hot keys, big keys, stale data races, cold start and pollution — what triggers each and how to fix it.

Interview Answer — What Is the Thundering Herd Problem in Caching?

The thundering herd (also called a cache stampede) happens when a popular cached value disappears — it expires, is evicted, or is invalidated — and many concurrent requests all miss at the same moment and all go to the database to rebuild the same value. Instead of one query, the database receives hundreds or thousands of identical ones.

It matters because a cache changes how the database is sized. Once a key is served from the cache, the database is provisioned only for the misses. The cause → effect chain is: a hot key with 5,000 reads/second expires → for the ~200 ms it takes to rebuild, every request misses → ~1,000 identical queries hit the database at once → database latency climbs, so the rebuild takes even longer → more requests pile up → connection pools exhaust and the database (and every service depending on it) can fall over. A cache meant to protect the database becomes the reason it fails.

The fixes all make sure only one caller rebuilds a key while the others wait or get a slightly stale value: request coalescing (a lock or single-flight per key), serving stale-while-revalidate, refreshing hot keys before they expire (probabilistic early expiration), and adding TTL jitter so many keys don't expire together. The thundering herd is one of a family of cache failure modes — penetration, breakdown, avalanche, hot keys — covered below and summarised in the summary table.

Simple interview version

"A thundering herd is when a hot cache key expires and thousands of concurrent requests miss together and all hit the database to rebuild the same value, which can overload it. I prevent it by letting only one request rebuild the key — a per-key lock or single-flight — while the others wait or get the stale value; by refreshing hot keys early or in the background before they expire; and by adding random jitter to TTLs so keys don't expire at the same moment. Related problems are cache penetration, where requests ask for keys that don't exist, fixed with negative caching or a Bloom filter, and cache avalanche, where many keys or the whole cache fail at once."

One important interview follow-up

Q: Does adding a lock around the cache rebuild fully solve the thundering herd?

A: Not by itself. A lock ensures one rebuild per key, but the waiters still need a plan: if they block, their latency grows and they hold threads and connections; if they poll, they add load to the cache; and if the lock holder crashes, everyone waits until the lock's TTL expires. A local in-process lock only coalesces requests on one instance — with 50 instances you still get 50 database queries, so a distributed lock (Redis SET … NX PX) or stale-while-revalidate is needed for cluster-wide protection. The robust combination is: serve the stale value while one caller refreshes, with a lock that has a short timeout, plus TTL jitter.

Terms used on this page

  • Origin — whatever the cache protects: usually the database, sometimes a downstream service.
  • Miss storm — a sudden spike of cache misses reaching the origin. Every problem on this page is a different cause of a miss storm, and each has a different fix.
  • Request coalescing — merging concurrent requests for the same key into one origin call whose result all of them share.

1. Thundering herd / cache stampede

Definition and cause → effect chain: see the Interview Answer above. The fixes, each with its trade-off:

Fix A — Per-key lock (mutex) with a distributed lock

  1. Request misses on product:7.
  2. It tries SET lock:product:7 <token> NX PX 5000 (set only if absent, expire after 5 s).
  3. Winner → loads the database, SET product:7 … EX 300, then deletes the lock only if the token still matches (a small Lua script, so it never deletes another caller's lock).
  4. Losers → wait briefly (e.g. 50 ms) and read the cache again, or return the stale value if one exists.

Trade-off: correct and simple, but waiters add latency; the lock timeout must exceed the normal rebuild time.

Fix B — Single-flight / in-process request coalescing

Inside one process, concurrent callers for the same key share one in-flight future. Go's golang.org/x/sync/singleflight, Caffeine's LoadingCache (computes each key once), and Nginx's proxy_cache_lock on all do this. No network lock needed, but it only coalesces per instance — N instances still send up to N queries, which is usually acceptable.

Fix C — Stale-while-revalidate (soft TTL + hard TTL)

Store the value with a soft expiry inside the payload (e.g. 5 minutes) and a longer hard TTL in Redis (e.g. 1 hour). After the soft expiry, the first reader triggers a background refresh (guarded by the lock) and every reader, including that one, gets the stale value immediately. Nobody waits, the origin sees one query. Trade-off: readers may see data up to one refresh-duration past its soft expiry. It is the same mechanism as HTTP Cache-Control: stale-while-revalidate.

Fix D — Probabilistic early expiration (XFetch)

Each reader decides, with a probability that rises as expiry approaches, to refresh early. The published XFetch rule: recompute if now − delta × beta × ln(random()) ≥ expiry, where delta is how long the recompute takes and beta ≈ 1 (higher means earlier). Because ln(random()) is negative, the left side jumps ahead of now by a random amount. Effect: one request (usually) refreshes the key slightly before it expires, so the cache is never actually empty — no lock needed.

Fix E — Background refresh of known hot keys

A scheduled job or refresh-ahead policy rewrites known hot keys (home page, top-100 products) before their TTL ends, or the key has no TTL and is updated on every write. Works when the hot set is known in advance.

Default combination

Single-flight in every instance + stale-while-revalidate for hot keys + TTL jitter everywhere. Add a distributed lock only when the per-instance query count is still too high.

2. Cache breakdown (hotspot invalidation)

What it is: a thundering herd on one specific very hot key — a flash-sale product, a celebrity's profile, a trending post — at the moment it expires. The term comes from Chinese engineering literature ("缓存击穿"), where it is taught alongside penetration and avalanche. Breakdown vs. thundering herd — the difference is mostly scope: breakdown names the single-hot-key case; thundering herd is the general mechanism. Fixes are the same as above, plus: don't give the hottest keys a TTL at all — refresh them from the write path or a background job, and use a logical expiry field inside the value to decide when to refresh.

3. Cache penetration (requests for data that doesn't exist)

What it is: requests for keys that exist neither in the cache nor in the database — GET /users/-1, random IDs from a bot, a bug looping on a deleted ID. Why it's a problem: cache-aside only caches found values, so every such request misses the cache, queries the database, finds nothing, caches nothing — and the next identical request does it all again. The cache provides zero protection, and an attacker can deliberately drive database load this way.

  • Negative caching — cache the "not found" result: SET user:999999 "__NULL__" EX 60. Keep the TTL short so a newly created record appears quickly; and delete the negative entry when that record is created. Limit: random IDs are all different, so an attacker can still generate endless unique misses — and fill the cache with null entries.
  • Bloom filter in front of the cache — a compact probabilistic set of every ID that exists (e.g. RedisBloom BF.ADD / BF.EXISTS). If the filter says "definitely not present", reject without touching cache or database. A Bloom filter has no false negatives but some false positives (~1% at ~10 bits per item), so a few non-existent IDs still get through to the normal path. Limit: standard Bloom filters can't delete items (use a Cuckoo filter or rebuild periodically).
  • Input validation — reject malformed IDs (negative, wrong format, out of range) at the API layer before any lookup.
  • Rate limiting per client for repeated misses — see Rate Limiting & Throttling.

4. Cache avalanche (mass expiry or cache outage)

What it is: a large fraction of the cache disappears at once, so misses for many different keys hit the database simultaneously. Two causes:

  1. Synchronized expiry — a warm-up job (or a deploy) writes 1 million keys with the same EX 3600 → exactly one hour later they all expire within the same second → the database sees a million misses.
  2. Cache node or cluster failure — a Redis primary dies, a cluster is restarted, or a network partition cuts the app off from the cache → 100% of traffic becomes misses.

Avalanche vs. thundering herd — the difference is the number of keys: a thundering herd is many requests for one key; an avalanche is misses across many keys at once, so request coalescing per key does not help.

  • TTL jitter — ttl = 3600 + random(0, 360) spreads expiry over time.
  • High availability for the cache — replicas with automatic failover (Redis Sentinel, Redis Cluster, ElastiCache Multi-AZ), and sharding so one node failure loses only 1/N of the keys.
  • Multi-level caching — an in-process L1 cache keeps serving the hottest keys while Redis recovers (see near cache).
  • Protect the origin — circuit breakers, rate limiting, and load shedding on the miss path, so the database degrades gracefully instead of collapsing; serve a default or degraded response when the breaker is open. See Microservice Resilience Patterns.
  • Warm up gradually — after a restart, pre-load the hot set (from a key list or access logs) before sending full traffic.

5. Hot key

What it is: one key read so often that it saturates the single cache node or shard that owns it, even while it is warm. In a sharded cache each key lives on one shard; one key at 500,000 reads/second can exceed one Redis node's CPU or network bandwidth while every other shard is idle. Hot key vs. thundering herd — the difference is that a hot key hurts while it is present; the herd hurts when it is absent.

  • Detect — redis-cli --hotkeys (needs an LFU policy), per-key metrics in the client, or cloud monitoring of per-shard CPU skew.
  • Local cache the hot key — an in-process L1 cache with a TTL of a second or two turns 500,000 Redis reads/s into ~one read per instance per second.
  • Replicate the key — store copies as product:7#0 … product:7#9 on different shards; readers pick a random suffix, writers update all copies.
  • Read replicas — spread reads for that shard across replicas (accepting replication lag).

6. Big key

What it is: a single key holding a very large value — a 10 MB JSON string, a hash or list with millions of elements. Because Redis executes commands on a single main thread, one GET, HGETALL, or DEL on a big key blocks every other client for milliseconds or more; it also skews memory across shards and makes replication and migration slow.

  • Detect — redis-cli --bigkeys or MEMORY USAGE <key>.
  • Split — break it into smaller keys (per page, per field group) or use a hash and read only needed fields with HMGET.
  • Delete safely — UNLINK instead of DEL (frees memory in a background thread); iterate large collections with HSCAN/SSCAN instead of reading them whole.
  • Compress large values (gzip, Snappy) when they must stay whole.

7. Stale data and race conditions (cache–database inconsistency)

What it is: the cache holds a value the database no longer has, and nothing will correct it until the TTL. Causes, step by step:

  • Missed invalidation — a write path (a second service, a migration, a manual SQL fix) updates the database without deleting the cache key.
  • Failed invalidation — the DB write succeeds, the DEL fails (network blip, crash between the two steps) — the dual-write problem.
  • Read–write race in cache-aside — (1) reader misses, reads the old row, is paused; (2) writer updates the DB and deletes the key; (3) reader resumes and caches the old row. The cache is now stale with no pending invalidation.
  • Concurrent updates — two writers updating the cache out of order (why you delete instead of update).
  • Replica lag — the cache is refilled from a read replica that has not yet applied the write, re-caching the old value right after the delete. See Replication Lag.

Fixes, from cheapest: always set a TTL (bounds the damage); delete after the DB commit, never before; delayed double delete (delete again ~0.5–1 s later to catch the race window); versioned values (store a row version and only write the cache if the version is newer — e.g. a Lua script comparing versions); leases (Memcached-style: a miss receives a lease token, a delete invalidates it, so a stale fill is rejected); refill from the primary, not a replica, right after writes; and CDC-based invalidation so every committed change deletes its key.

This does NOT mean caches can be strongly consistent for free

A cache next to a database is eventually consistent unless every read and write goes through one serialization point. For data where any staleness is a bug — balances, inventory at checkout, permissions revoked for security — read from the database (or use write-through with the cache as the only write path), and cache only derived, display-level data.

8. Cold start and cache warming

What it is: an empty cache — after a deploy of a new cache cluster, a restart without persistence, a failover to an empty replica, or a region brought online. Initially every request misses, so the origin sees full traffic: effectively a planned avalanche.

  • Pre-warm — load the known hot set (top keys from access logs or a key dump) before shifting traffic.
  • Shift traffic gradually — weighted routing (1% → 10% → 100%) so the cache fills while the origin copes.
  • Persistence / replicas — Redis RDB/AOF or a warm replica so a restart doesn't start empty.
  • Consistent hashing — adding or removing one node remaps only ~1/N of keys, instead of nearly all of them with hash(key) % N. See Consistent Hashing.

9. Cache pollution and thrashing

Cache pollution — rarely-used data pushes out hot data: a nightly report, a crawler, or a bulk export reads millions of keys once. Thrashing — the working set is larger than the cache, so keys are evicted just before they are needed again; the hit ratio collapses and the eviction rate is high. Fixes: scan-resistant eviction (LFU, W-TinyLFU, segmented LRU — see Eviction Policies); don't cache the results of bulk/background reads (write-around); run batch jobs against a replica, not through the cache; and when thrashing, add memory or shards — no policy can fix a cache that is simply too small.

10. Other operational issues

  • Memory fragmentation — Redis mem_fragmentation_ratio well above 1.5 means RSS is much larger than data size; enable activedefrag or restart a replica and fail over.
  • Serialization cost — large objects serialized with slow formats can cost more CPU than the database query they replace; cache smaller projections, use efficient formats.
  • Connection storms — thousands of app instances each opening many connections to Redis; use connection pools, and a proxy (Twemproxy, Envoy) if needed.
  • Security leaks — a shared cache key that omits the user/tenant ID serves one user's data to another; an internet-exposed Redis without AUTH is a common breach. Include identity in the key for personalised data, enable ACLs and TLS, keep caches on private networks.
  • Cache as a hidden dependency — if the system can't serve traffic without the cache, the cache is part of your availability budget; load-test the origin with the cache disabled so you know the real failure behaviour.
