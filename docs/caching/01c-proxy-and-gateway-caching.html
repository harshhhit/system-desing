Reverse Proxy & API Gateway Caching

Nginx proxy_cache, micro-caching, Varnish grace and bans, API Gateway and Kong response caching, and caching GraphQL — saving application work in front of your servers.

Interview Answer — What Is Reverse-Proxy Caching?

Reverse-proxy caching is a server that sits in front of your application servers — Nginx, Varnish, HAProxy, Envoy, or an API gateway — storing complete HTTP responses and returning them for matching requests without calling the application at all. It is the same idea as a CDN, but it runs inside your own infrastructure, next to the application, rather than in PoPs near users.

It exists to save application work, not network distance. Rendering a product page may take 80 ms of CPU and five database queries; returning a stored copy from the proxy takes under a millisecond. The cause → effect chain: 2,000 users request /products/42 in one second → the first request misses and goes to the app → the proxy stores the response for, say, 10 seconds → the other 1,999 requests are served from the proxy → the app renders that page once per 10 seconds instead of 2,000 times per second.

It fits between the CDN and the application cache: the CDN handles public content near users; the reverse proxy catches what reaches your data centre (including CDN misses and traffic that bypasses the CDN); Redis caches the objects the application uses to build responses. An API gateway cache is the same mechanism configured on a managed gateway, keyed on API parameters.

Simple interview version

"A reverse-proxy cache like Nginx or Varnish sits in front of the app servers and stores full HTTP responses, so repeated requests are answered without running application code. It's most useful for public pages and APIs with many identical requests — even micro-caching a dynamic page for one second collapses a traffic spike into one backend call per second. I configure the cache key carefully, lock concurrent misses so only one request hits the backend, and serve stale content while updating or when the backend errors. API gateways offer the same per-endpoint response caching."

One important interview follow-up

Q: If I already have a CDN, why add a reverse-proxy cache?

A: Often you don't need one — but they cover different gaps. The CDN has many PoPs, each missing independently (unless you use an origin shield), and some traffic never goes through the CDN (internal services, other regions, API clients calling the origin directly). A reverse proxy in front of the app gives one shared cache for all of that, with request collapsing and stale-on-error close to the application, plus features like micro-caching and cache purging under your full control. If the CDN has an origin shield and all traffic passes through it, the proxy cache is often redundant.

Nginx proxy_cache

Nginx stores cached responses as files on disk, with keys and metadata in a shared-memory zone. A typical configuration:

proxy_cache_path /var/cache/nginx levels=1:2 keys_zone=app:100m
                 max_size=10g inactive=60m use_temp_path=off;

server {
  location / {
    proxy_pass http://app_upstream;
    proxy_cache app;
    proxy_cache_key "$scheme$host$request_uri";
    proxy_cache_valid 200 301 10m;
    proxy_cache_valid 404 1m;
    proxy_cache_lock on;
    proxy_cache_use_stale error timeout updating http_500 http_502 http_503;
    proxy_cache_background_update on;
    add_header X-Cache-Status $upstream_cache_status;
  }
}
  • keys_zone=app:100m — shared memory for keys (about 8,000 keys per MB); max_size caps disk; inactive=60m removes entries not accessed for an hour, regardless of freshness.
  • proxy_cache_valid — TTLs per status code, used when the upstream sends no caching headers (upstream Cache-Control/Expires take priority).
  • proxy_cache_lock on — only one request per key goes upstream on a miss; others wait. Built-in stampede protection.
  • proxy_cache_use_stale … updating + proxy_cache_background_update on — stale-while-revalidate: serve the stale copy while one background request refreshes it; also serve stale when the upstream errors.
  • $upstream_cache_status — HIT, MISS, EXPIRED, STALE, UPDATING, BYPASS; expose it in a header or logs to measure hit ratio.

Gotcha: by default Nginx does not cache responses that carry Set-Cookie or Cache-Control: private/no-store, and it only caches GET/HEAD. Use proxy_cache_bypass / proxy_no_cache to skip caching for logged-in users (e.g. when a session cookie is present).

Micro-caching

What it is: caching dynamic pages for a very short time — 1 to 5 seconds. Why it works: for a page receiving 1,000 requests/second, a 1-second TTL means the backend renders it once per second instead of 1,000 times, and users see content at most one second old — invisible for news, listings, scores, or search results. Combined with proxy_cache_lock and use_stale updating, it flattens traffic spikes (a link on a popular site, a TV mention) that would otherwise overload the application. Limit: only for responses that are the same for everyone who shares the key.

Varnish

Varnish is a dedicated HTTP cache (memory-first) configured with VCL (Varnish Configuration Language), which gives request-by-request control over the cache key, TTLs, and bypass rules. Concepts worth knowing:

  • Grace mode — how long past its TTL an object may be served while a fetch refreshes it (Varnish's stale-while-revalidate / stale-if-error).
  • Request coalescing — built in: concurrent misses for the same object wait on one backend fetch.
  • Purge vs. ban — the difference is scope and timing: a purge removes one specific object immediately; a ban is a rule (e.g. "every URL matching ^/products/42") checked lazily against objects when they're next requested — good for invalidating many objects at once.
  • Varnish doesn't terminate TLS itself; it is usually paired with a TLS terminator (Hitch, Nginx, or a load balancer) in front.

API gateway caching

Managed and self-hosted API gateways can cache responses per endpoint:

  • Amazon API Gateway (REST APIs) — per-stage cache with a size you provision (from 0.5 GB), a default TTL of 300 seconds (maximum 3,600), and per-method settings. You choose which path/query parameters and headers form the cache key. Clients can request a fresh response with Cache-Control: max-age=0 only if you allow it (the execute-api:InvalidateCache permission) — otherwise any caller could bypass your cache. Note: HTTP APIs (the newer, cheaper API Gateway type) don't have built-in caching.
  • Kong — the proxy-cache plugin (memory strategy) caches by method, path, and configured parameters/headers.
  • Apigee, Azure API Management — similar response-cache policies with keys and TTLs.
Gotcha: identity must be in the key

If GET /me/orders is cached by path alone, the first caller's orders are returned to every caller. For any user- or tenant-specific endpoint, include the user/tenant identifier (or the authorisation header) in the cache key — or don't cache that endpoint at the gateway at all.

Caching GraphQL and POST APIs

HTTP caches key on URL and generally cache only GET. GraphQL typically sends every query as POST /graphql, so proxies and CDNs can't cache it. Common fixes: persisted queries (the client sends a hash of a pre-registered query via GET /graphql?id=abc&variables=…, which is cacheable), or caching at the resolver/object level in Redis instead. See GraphQL vs REST.

Other proxy caches

  • Envoy has an HTTP cache filter; service meshes generally don't cache by default — caching between internal services is usually done in the calling service (in-process) or in Redis.
  • Forward proxies (Squid) cache on the client side for many users; mostly historical now that HTTPS hides responses from them.
  • Load balancers (AWS ALB/NLB) do not cache — put CloudFront in front of the ALB for response caching. See Load Balancing.

Checklist

  • Cache only responses that are identical for everyone sharing the key; bypass on session cookies or Authorization.
  • Turn on miss locking (proxy_cache_lock, Varnish coalescing) and stale serving (use_stale, grace).
  • Expose the cache status in a header/log and track hit ratio.
  • Plan invalidation: short TTLs, purge/ban APIs, or versioned URLs.
  • With several proxy instances, each has its own cache — hit ratio per instance drops as you scale out; consistent-hash routing of URLs to proxies (or a single shared tier) fixes it.
