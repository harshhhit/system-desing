Interview Answer — What Is AWS?

Amazon Web Services (AWS) is a public cloud platform: it rents computing resources — virtual servers, storage, databases, networks, queues, and hundreds of higher-level managed services — on demand over the internet, billed by usage. Instead of buying servers, racking them in a data centre, and waiting weeks for capacity, a team calls an API (or clicks in the console) and has a server, a database, or a load balancer in minutes, and deletes it when it is no longer needed.

AWS exists because owning infrastructure is slow, expensive up front, and hard to size correctly. Without the cloud, a team must guess peak capacity months ahead: guess too low and the site falls over during a spike; guess too high and money sits in idle hardware. The cause → effect chain AWS changes is: demand rises → an Auto Scaling group launches more EC2 instances → the load balancer starts sending them traffic → demand falls → the extra instances are terminated → the bill falls with them. Capital expense (buying hardware) becomes operating expense (paying per hour, per request, or per GB).

AWS runs in Regions — separate geographic areas — each made of several isolated Availability Zones (AZs). You build reliable systems by spreading a workload across AZs, so one data-centre failure does not take the application down. Security follows the shared responsibility model: AWS secures the physical data centres, hardware, and the virtualisation layer (security of the cloud); you secure what you put in it — IAM permissions, network rules, data encryption, OS patches on EC2 (security in the cloud). In a system design interview, AWS services are the concrete names for concepts found elsewhere on this site: load balancing becomes ELB, a message queue becomes SQS, object storage becomes S3.

Simple interview version

"AWS is Amazon's public cloud: it rents servers, storage, databases and networking on demand, billed by usage, so I don't have to buy and size hardware up front. It runs in Regions, each with multiple isolated Availability Zones, and I get high availability by spreading my workload across AZs. Security is shared — AWS secures the physical infrastructure, and I secure my IAM permissions, network rules, data, and anything I run on EC2. For a typical web app I'd use Route 53 and CloudFront at the edge, an Application Load Balancer, EC2 or containers in private subnets across two AZs, RDS Multi-AZ for the database, S3 for files, and CloudWatch for monitoring."

One important interview follow-up

Q: If AWS is "highly available," is my application automatically highly available once it runs on AWS?

A: No. AWS gives you the building blocks for high availability — multiple Availability Zones, load balancers, Multi-AZ databases, Auto Scaling — but it does not apply them for you. A single EC2 instance in one AZ with its database on the same instance is exactly as fragile as one physical server: if that AZ has an outage or the instance's host fails, the application is down. Some services are regional and multi-AZ by design (S3, DynamoDB, SQS, Lambda), but for EC2, RDS, and anything you deploy yourself, high availability is your design choice: run at least two instances in two AZs behind a load balancer, enable RDS Multi-AZ, and store state outside the instance. This is the shared responsibility model applied to reliability — see Global Infrastructure and the worked example.

How to Study This Section

Read the stages in order. Each stage exists because the previous one creates a new question.

  1. Cloud basics and global infrastructure — learn what renting infrastructure means and where it physically runs. Watch for: Region vs. Availability Zone — the difference is scale and purpose. A Region is a whole geographic area you choose for latency and data-residency reasons; an AZ is one isolated failure domain inside a Region that you spread across for availability.
  2. IAM and shared responsibility — before launching anything, decide who may do what. Watch for: IAM user vs. IAM role — the difference is the credential. A user has long-lived credentials tied to one person or program; a role has no permanent credentials and is assumed, handing out short-lived ones.
  3. Networking — every EC2 instance, database, and load balancer lives in a VPC subnet, so the network comes before the servers. Watch for: security group vs. network ACL.
  4. Compute, storage, databases, messaging — place the workload. For each service, ask the same three questions: what does AWS manage, what do I manage, and how does it survive an AZ failure?
  5. Operate, secure, automate, pay — then judge the whole design with the Well-Architected Framework, and finish with the worked example and interview checklist.
  6. Next sections — for the vendor-neutral theory behind these services continue to Networking Fundamentals, Load Balancing, and Storage Types.

Stage 0 — Cloud Basics: Why Rent Instead of Buy

The vocabulary every other stage uses.

Cloud computing is on-demand access to IT resources over the internet with pay-as-you-go pricing. It exists because the traditional model — buy hardware, wait for delivery, rack it, then run it for years — forces a team to predict demand far in advance and pay for it before earning anything from it.

  • CapEx vs. OpEx — the difference is when and how you pay. Capital expense is a large up-front hardware purchase; operating expense is paying per hour, per request, or per GB as you use it. AWS turns the first into the second.
  • Elasticity: capacity grows and shrinks with demand, automatically if you configure Auto Scaling. This does NOT mean everything scales on its own — an EC2 instance you launched by hand stays exactly one instance until you change it.
  • Service models — IaaS vs. PaaS vs. SaaS: with IaaS (EC2) you manage the OS and everything above it; with PaaS-style managed services (Elastic Beanstalk, RDS, Lambda) AWS manages the OS and runtime and you manage code, data and configuration; SaaS is a finished application you only use. The further up you go, the less you operate — and the less you can customise.
  • Managed vs. self-managed: PostgreSQL on an EC2 instance is self-managed (you patch, back up, and fail over). RDS for PostgreSQL is managed (AWS patches, backs up, and fails over; you still design the schema and tune queries).
  • How you talk to AWS: every action — console click, aws CLI command, SDK call, Terraform run — is ultimately an authenticated HTTPS API call. That is why IAM (Stage 2) governs all of them in exactly the same way.

Stage 1 — Global Infrastructure: Regions, AZs, Edge Locations

Where your resources physically run, and how that decides availability and latency.

  • Region: a separate geographic area (for example ap-south-1, Mumbai, or us-east-1, N. Virginia). Regions are isolated from each other; most resources you create live in exactly one Region and are not copied elsewhere unless you set that up.
  • Availability Zone (AZ): one or more discrete data centres inside a Region, with independent power, cooling and networking, connected to the other AZs by low-latency links (for example ap-south-1a, ap-south-1b). An AZ is the unit of failure you design around.
  • Edge locations: many smaller sites, far more numerous than Regions, used by CloudFront (CDN) and Route 53 (DNS) to answer users from nearby.
  • How to choose a Region: (1) data-residency / compliance rules, (2) latency to your users, (3) whether the services you need are available there, (4) price, which differs between Regions.
  • Global vs. regional vs. zonal services: IAM and Route 53 are global; S3 buckets, SQS queues and DynamoDB tables are regional (already spread across AZs); an EC2 instance and an EBS volume are zonal — they live in one AZ and die with it.
Gotcha: an EBS volume cannot follow an instance to another AZ

Because EBS volumes are zonal, an instance in ap-south-1a cannot attach a volume in ap-south-1b. To move data across AZs you snapshot the volume (snapshots are stored regionally) and create a new volume from the snapshot in the target AZ.

Stage 2 — Account, IAM & the Shared Responsibility Model

Who is allowed to do what — decided before anything is launched.

IAM (Identity and Access Management) is the AWS service that decides whether an API call is allowed. It exists because every action in AWS is an API call, and without a central permission system anyone holding account credentials could delete every resource. IAM evaluates each request against policies: by default everything is denied, an explicit Allow grants access, and an explicit Deny always wins over any Allow.

  • Root user: the email address that created the account; it can do everything, including close the account, and IAM policies cannot restrict it. Enable MFA on it, create no access keys for it, and use it only for the few tasks that require it.
  • IAM user: a long-lived identity with a password and/or access keys. Today the recommended way for humans to sign in is IAM Identity Center (single sign-on) with short-lived credentials rather than one IAM user per person.
  • IAM group: a collection of users that share policies. A group is not an identity — it cannot be assumed or sign in.
  • IAM role: an identity with permissions but no long-lived credentials; a trusted principal (an EC2 instance, a Lambda function, a user from another account, a Kubernetes service account) assumes it and receives temporary credentials from STS (Security Token Service).
  • Policy: a JSON document listing Effect, Action, Resource and optional Condition. For example, "Action": "s3:GetObject" on "Resource": "arn:aws:s3:::my-app-uploads/*" lets the holder read objects from that one bucket only.
  • Least privilege: grant only the actions and resources a job needs. Start narrow and widen on evidence — IAM Access Analyzer can generate a policy from what was actually used.

Why roles instead of access keys on a server: if you paste an access key into an EC2 instance's config file, the key never expires, and anyone who reads the file or the Git history owns those permissions. When you attach a role to the instance (through an instance profile) instead, the SDK fetches temporary credentials from the instance metadata service, and AWS rotates them automatically. The cause → effect chain is: no stored secret → nothing long-lived to leak → a leaked credential stops working within hours.

Shared responsibility model: AWS is responsible for security of the cloud — physical data centres, hardware, network backbone, the hypervisor. You are responsible for security in the cloud — IAM, security groups, encryption settings, and the guest OS and application on EC2. The line moves with the service: on EC2 you patch the OS; on Lambda or RDS, AWS patches it, but the IAM permissions and data are still yours.

Multi-account setup: larger organisations use AWS Organizations to split workloads into separate accounts (for example prod, staging, security), because an account is the strongest isolation boundary AWS has. Service Control Policies (SCPs) set the maximum permissions any identity in a member account can ever have.

Stage 3 — Networking: VPC, Subnets, Security Groups, Route 53, ELB, CloudFront

Every server, database and load balancer lives in a network you define. Theory behind it: Networking Fundamentals.

A VPC (Virtual Private Cloud) is your own logically isolated private network inside a Region, with an IP range you choose in CIDR notation (for example 10.0.0.0/16). It exists so your resources get private IP addresses and only the paths you explicitly open lead in or out. Each Region gives a new account a default VPC with public subnets for quick experiments; production designs usually create their own.

  • Subnet: a slice of the VPC's IP range that lives in exactly one AZ (for example 10.0.1.0/24 in ap-south-1a). To survive an AZ failure, create matching subnets in at least two AZs.
  • Public vs. private subnet — the difference is the route table. A subnet is "public" only because its route table sends 0.0.0.0/0 to an Internet Gateway. A private subnet has no such route, so nothing on the internet can reach its instances directly.
  • NAT Gateway: lets instances in private subnets start outbound connections (for OS updates, calling external APIs) while still blocking inbound ones. It sits in a public subnet and is billed per hour plus per GB processed — a common surprise on the bill.
  • VPC endpoints: let private resources reach AWS services such as S3 or DynamoDB without going through the internet or a NAT Gateway.

  • Route 53: AWS's DNS service — hosts your domain's records and supports routing policies (latency-based, weighted, failover) with health checks.
  • Elastic Load Balancing: the Application Load Balancer (ALB) works at layer 7 (HTTP/HTTPS; routes by path or host header, terminates TLS); the Network Load Balancer (NLB) works at layer 4 (TCP/UDP; very high throughput, static IPs). Concepts: Load Balancing.
  • CloudFront: AWS's CDN; caches content at edge locations close to users. Concepts: Caching & CDN.

Stage 4 — Compute: EC2, Lambda, ECS, EKS, Fargate

Where your code actually runs — and how much of the machine you must look after.

  • EC2 (Elastic Compute Cloud): virtual machines. You choose an AMI (the disk image: OS plus software), an instance type (CPU/memory family and size, for example t3.micro, m7g.large), a subnet and security groups. You own everything from the OS up. An Auto Scaling group keeps a desired number of instances running across AZs, replaces unhealthy ones, and scales on metrics such as CPU. See the EC2 Hosting Checklist.
  • Lambda: serverless functions. You upload code; AWS runs it in response to an event (an HTTP request via API Gateway, a new S3 object, an SQS message) and bills per request and per millisecond of run time. Limits to know: maximum 15 minutes per invocation, and a cold start — extra latency when a new execution environment must be created.
  • ECS (Elastic Container Service): AWS's own container orchestrator — simpler than Kubernetes, deeply integrated with AWS.
  • EKS (Elastic Kubernetes Service): managed Kubernetes — AWS runs the control plane (API server, etcd; see Kubernetes), you run workloads on worker nodes.
  • Fargate: a serverless compute engine for ECS and EKS — you define a task or pod's CPU and memory and AWS runs it with no EC2 instances for you to manage.

Stage 5 — Storage: S3, EBS, EFS

Object, block and file storage — the three shapes from Storage Types, as AWS services.

  • S3 (Simple Storage Service): object storage. You store objects (a file plus metadata) under keys in a bucket, accessed over HTTPS. Designed for 99.999999999% ("eleven nines") durability by storing data redundantly across multiple AZs. Since December 2020, S3 has strong read-after-write consistency for all objects. Storage classes (Standard, Standard-IA, Intelligent-Tiering, Glacier tiers) trade retrieval speed and cost against storage price; lifecycle rules move objects between them automatically.
  • EBS (Elastic Block Store): a network-attached block disk for one EC2 instance, in one AZ. It behaves like a hard drive: you format it with a filesystem. Snapshots back it up incrementally to S3-backed storage.
  • EFS (Elastic File System): a managed NFS file system that many instances, across AZs, can mount at the same time.
S3 vs. EBS vs. EFS — the difference is who can access it and how

EBS: one instance (usually), one AZ, a raw disk — use it for the OS and databases on EC2. EFS: many instances, many AZs, a shared POSIX file system — use it for shared content folders. S3: any client with permission, over HTTP, whole objects — use it for uploads, static assets, backups, logs and data lakes. S3 is NOT a file system: you cannot append to or edit part of an object in place; you rewrite the whole object.

Gotcha: public buckets

Many data leaks are S3 buckets made public by mistake. New buckets have Block Public Access enabled by default — keep it on, and serve public files through CloudFront (with origin access control) or pre-signed URLs instead of making the bucket public.

Stage 6 — Databases: RDS, Aurora, DynamoDB, ElastiCache

Managed data stores — AWS runs the servers, you design the data. Concepts: Database Learning Path.

  • RDS (Relational Database Service): managed PostgreSQL, MySQL, MariaDB, Oracle and SQL Server. AWS handles provisioning, patching, automated backups with point-in-time recovery, and failover.
  • Aurora: AWS's MySQL- and PostgreSQL-compatible engine with a distributed storage layer that keeps six copies of data across three AZs; failover is typically faster than standard RDS, and up to 15 read replicas share the same storage.
  • DynamoDB: a serverless key-value and document database with single-digit-millisecond latency at any scale. You design around access patterns (partition key + optional sort key) rather than joins. Reads are eventually consistent by default; strongly consistent reads are available on request.
  • ElastiCache: managed Redis-compatible (Redis OSS / Valkey) and Memcached caches. Concepts: Caching & CDN. Service deep dive with the official FAQ: Amazon ElastiCache.

RDS Multi-AZ vs. read replica — the difference is purpose

Multi-AZ is for availability: RDS keeps a standby in another AZ, replicated synchronously; if the primary fails, RDS flips the DNS endpoint to the standby, usually within a minute or two. In the classic Multi-AZ instance deployment the standby does NOT serve reads. Read replicas are for read scaling: they replicate asynchronously, serve read traffic, and can lag behind the primary (see Replication Lag). Caveat: the newer Multi-AZ DB cluster deployment (two readable standbys) blurs this line — say which one you mean.

Stage 7 — Messaging & Integration: SQS, SNS, EventBridge, Kinesis

Decoupling services so one slow or failing part does not take down the rest. Concepts: SQS Overview, Kafka Fundamentals.

  • SQS (Simple Queue Service): a managed message queue. Producers send messages; consumers poll, process and delete them. Standard queues give at-least-once delivery with best-effort ordering; FIFO queues give strict ordering per message group and exactly-once processing within a deduplication window. Failed messages move to a dead-letter queue after a set number of receives.
  • SNS (Simple Notification Service): pub/sub. A publisher sends one message to a topic; SNS pushes a copy to every subscriber (SQS queues, Lambda functions, HTTP endpoints, email, SMS).
  • EventBridge: an event bus that routes events by content-matching rules — from your services, from AWS services, and from SaaS partners — and also runs scheduled jobs.
  • Kinesis Data Streams: an ordered, replayable stream split into shards, for high-volume real-time data such as clickstreams — AWS's closest managed equivalent to a Kafka topic (Amazon MSK is managed Kafka itself).
SQS vs. SNS — the difference is pull-to-one vs. push-to-many

In SQS, each message is processed by one consumer, which pulls it when ready. In SNS, each message is pushed to all subscribers immediately. The common "fan-out" pattern combines them: publish once to an SNS topic that has several SQS queues subscribed, so each downstream service gets its own durable copy and can process it at its own pace.

Stage 8 — Observability & Governance: CloudWatch, CloudTrail, Config

Seeing what the system does and who changed it. Concepts: Observability Fundamentals.

  • CloudWatch: metrics (CPU, request count, queue depth), logs (CloudWatch Logs), alarms that act on metric thresholds (notify via SNS, trigger Auto Scaling), and dashboards.
  • CloudTrail: an audit log of API calls in your account — who did what, from where, and when.
  • AWS Config: records resource configuration over time and evaluates it against rules ("every S3 bucket must block public access").
  • X-Ray: distributed tracing across services.
CloudWatch vs. CloudTrail — the difference is performance vs. audit

CloudWatch answers "how is my system behaving?" (latency is up, CPU is at 90%). CloudTrail answers "who changed my system?" (user X deleted security group Y at 14:02). When an incident starts right after a change, you need both: CloudWatch shows when behaviour changed, CloudTrail shows what changed.

Stage 9 — Security Services: KMS, Secrets Manager, WAF, Shield, GuardDuty

Protecting data and traffic beyond IAM. Concepts: Application Security Fundamentals.

  • KMS (Key Management Service): creates and controls encryption keys; S3, EBS, RDS and most other services encrypt data at rest with KMS keys. Access to the key is itself governed by IAM and key policies — so encryption also becomes an access control.
  • Secrets Manager vs. SSM Parameter Store — the difference is rotation and cost. Secrets Manager stores secrets such as database passwords and can rotate them automatically, at a per-secret monthly price; Parameter Store holds configuration and secrets (SecureString) with no built-in rotation and a free standard tier.
  • WAF (Web Application Firewall): filters HTTP requests at CloudFront, ALB or API Gateway — SQL injection patterns, bad bots, and rate-based rules (see Rate Limiting).
  • Shield: DDoS protection. Shield Standard is automatic and free for all customers; Shield Advanced is a paid add-on with response-team support and cost protection.
  • GuardDuty: threat detection that analyses CloudTrail, VPC flow logs and DNS logs for suspicious activity, such as credentials used from an unusual location.
  • ACM (Certificate Manager): free public TLS certificates for ALB and CloudFront, renewed automatically.

Stage 10 — Infrastructure as Code & Deployment

Creating environments from files instead of console clicks. Concepts: CI/CD & Deployment Strategies.

Infrastructure as Code (IaC) means describing resources (VPCs, instances, buckets) in version-controlled files that a tool turns into real infrastructure. It exists because console clicks are not repeatable: staging and production drift apart, nobody can review the change, and a lost Region cannot be rebuilt quickly.

  • CloudFormation: AWS's native IaC — YAML/JSON templates deployed as stacks; AWS tracks state and rolls back failed updates.
  • CDK (Cloud Development Kit): write infrastructure in TypeScript, Python, Java and others; it synthesises CloudFormation templates.
  • Terraform: a third-party, multi-cloud IaC tool (HCL language) that keeps its own state file — very common in industry.
  • Deploy tooling: CodePipeline / CodeBuild / CodeDeploy, or GitHub Actions authenticating to AWS through an OIDC role (no stored access keys — the same reason as roles in Stage 2).

Stage 11 — Cost: Pricing Models, Budgets, Data Transfer

Pay-as-you-go also means pay-for-what-you-forgot.

  • Pricing models: On-Demand, Savings Plans and Reserved Instances (commitment for a discount), Spot (deep discount, can be interrupted). Match the model to the workload: a steady baseline on a commitment, peaks on On-Demand, interruptible batch on Spot.
  • Data transfer: data coming into AWS is generally free; data going out to the internet is billed per GB, and traffic between AZs is billed too. Chatty cross-AZ designs and NAT Gateway traffic are the classic hidden costs.
  • Guard rails: set an AWS Budgets alert on day one, tag resources by project/owner, and use Cost Explorer to find what is spending.
  • Free Tier: AWS offers free usage for new accounts, but its terms change (in 2025 AWS moved new accounts to a credit-based free plan) — always check the current Free Tier page and never assume a service is free. A forgotten NAT Gateway, Elastic IP, or large instance keeps billing after the tutorial ends.

Stage 12 — The Well-Architected Framework

AWS's own checklist for judging a design — useful as an interview structure too.

The AWS Well-Architected Framework is a set of design principles and review questions grouped into six pillars. It exists so a design can be reviewed systematically instead of by gut feeling; the free Well-Architected Tool in the console walks through the questions for a workload.

  1. Operational Excellence — run and improve the system: IaC, small reversible changes, runbooks, learning from failures.
  2. Security — least-privilege identity, traceability, encryption in transit and at rest, protection at every layer.
  3. Reliability — recover from failure automatically: multiple AZs, health checks, backups that are actually tested.
  4. Performance Efficiency — right resource types and sizes, use managed services, measure and experiment.
  5. Cost Optimization — pay only for what delivers value: right-sizing, pricing models, turning off idle resources.
  6. Sustainability — reduce the environmental impact of the workload: higher utilisation, efficient instance types (for example Graviton), less wasted data.

Worked Example — A 3-Tier Web App on AWS

This ties every stage together. Follow one HTTPS request from a user to the database and back, and note which stage each hop belongs to.

  1. The user's browser resolves app.example.com through Route 53 (Stage 3), which returns the address of a CloudFront distribution.
  2. CloudFront serves static files (JS, CSS, images) from an edge cache, fetched from an S3 bucket (Stage 5) that is private and reachable only through CloudFront. WAF on CloudFront filters malicious requests (Stage 9).
  3. API requests (/api/*) go on to an Application Load Balancer in public subnets in two AZs; it terminates TLS with an ACM certificate.
  4. The ALB forwards to application servers — an EC2 Auto Scaling group or ECS on Fargate tasks (Stage 4) — in private subnets in both AZs. Their security group allows the app port only from the ALB's security group.
  5. The application reads its database password from Secrets Manager using the task's or instance's IAM role (Stages 2 and 9) — no keys in code.
  6. It queries RDS PostgreSQL Multi-AZ (Stage 6) in private subnets, checking ElastiCache first for hot reads.
  7. Slow work (sending email, resizing an uploaded image) is put on an SQS queue (Stage 7) and handled by a Lambda function or worker, so the user's request returns quickly.
  8. CloudWatch collects metrics and logs and alarms on error rate; CloudTrail records every configuration change (Stage 8). The whole stack is defined in Terraform or CDK (Stage 10).

What happens when AZ a fails: the ALB's health checks mark targets in AZ a unhealthy → it sends all traffic to AZ b → the Auto Scaling group launches replacement capacity in AZ b → RDS Multi-AZ promotes the standby in AZ b and updates its DNS endpoint → the application reconnects. Users see a short blip, not an outage. This only works because every tier was deployed in two AZs from the start.

Hands-on Labs — Build It Yourself

Reading is not enough for AWS; each lab below practises one or more stages. Set a budget alert first (Stage 11) and delete everything when done.

  1. Secure the account: enable MFA on root, create an admin identity through IAM Identity Center, set a $5 AWS Budgets alert.
  2. Static site: host a static site in a private S3 bucket behind CloudFront with an ACM certificate.
  3. Custom VPC: build a VPC with public and private subnets in two AZs; launch an EC2 instance in the private subnet and connect to it with Session Manager (no SSH port, no public IP).
  4. Load-balanced app: put two EC2 instances (or an Auto Scaling group) behind an ALB; stop one and watch traffic shift.
  5. Serverless API: API Gateway → Lambda → DynamoDB, with the Lambda's IAM role limited to one table.
  6. Queue worker: S3 upload → event → SQS → Lambda that processes the file, with a dead-letter queue.
  7. IaC rebuild: recreate lab 4 with Terraform or CDK, destroy it, and recreate it in one command.

Certification Path

Certifications are optional, but their exam guides are a good syllabus for what to learn next.

  • AWS Certified Cloud Practitioner — foundational: cloud concepts, core services, billing, shared responsibility (Stages 0–2, 11).
  • AWS Certified Solutions Architect – Associate — the most useful one for system design: choosing and combining services for resilient, secure, cost-effective designs (all stages).
  • Developer – Associate or SysOps Administrator / CloudOps Engineer – Associate — depending on whether you build applications or operate infrastructure.
  • Professional / Specialty exams (Solutions Architect – Professional, DevOps Engineer – Professional, Security – Specialty) come after hands-on experience.

Exam names and content are revised from time to time — check the official AWS Certification page for the current list.

Interview Checklist

  • Name the Region choice and why (users' location, compliance), and deploy every stateful and stateless tier across at least two AZs.
  • Put application servers and databases in private subnets; only the load balancer (and NAT Gateway) sits in public subnets.
  • Use IAM roles, never long-lived access keys, for anything running inside AWS; apply least privilege.
  • Say which compute model and why (EC2 vs. containers vs. Lambda), including what you manage and how it scales.
  • Separate storage by shape: S3 for objects, EBS for a single server's disk, EFS for a shared file system, RDS/DynamoDB for records.
  • Distinguish RDS Multi-AZ (availability) from read replicas (read scaling), and name the consistency trade-off of each.
  • Decouple slow or failure-prone work with SQS/SNS, and mention dead-letter queues.
  • Mention observability (CloudWatch metrics, logs, alarms; CloudTrail for audit), encryption with KMS, and secrets in Secrets Manager.
  • Call out cost drivers — NAT Gateway, cross-AZ and internet egress, idle instances — and a pricing model that fits the load.
