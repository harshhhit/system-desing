Amazon ElastiCache

AWS's managed Valkey, Redis OSS and Memcached service, following the User Guide's main chapters — serverless vs node-based, engines, caching strategies, Multi-AZ, durability, Global Datastore, scaling, data tiering, security, monitoring — plus the full official FAQ.

This page follows the main chapters of the Amazon ElastiCache User Guide and ends with the official ElastiCache FAQs (jump to the FAQ), with the caching concepts cross-linked to this site's Caching section. AWS changes limits, versions and prices often, so check the linked docs before quoting a number.

Interview Answer — What Is Amazon ElastiCache?

Amazon ElastiCache is AWS's fully managed, in-memory data store and cache service. It runs three open-source-compatible engines — Valkey, Redis OSS, and Memcached — and AWS handles the hardware, patching, monitoring, failure detection, node replacement, and backups. You use it in one of two ways: ElastiCache Serverless, where you just create a cache by name and it scales automatically, or a node-based cluster, where you choose the node type, number of nodes/shards, and where they are placed across Availability Zones.

It exists because running Redis or Memcached yourself at production quality is real work: replicas and automatic failover across AZs, resharding without downtime, patching, backups, TLS, and monitoring. ElastiCache turns that into configuration. The cause → effect chain for a typical app: an application on EC2, ECS, EKS, or Lambda checks ElastiCache before RDS/Aurora/DynamoDB → hot reads come back in microseconds from memory → the database only handles misses and writes → you can run a smaller database and still give users faster responses.

ElastiCache vs. running Redis on EC2 — the difference is who owns operations. On EC2 you control every setting but you build HA, failover, backups, and scaling yourself. With ElastiCache, AWS does those, and in return some things are restricted (for example, some admin commands are disabled and configuration goes through parameter groups). ElastiCache is still a cache first: unless you enable the newer durability feature, treat the data as something you can rebuild from the source of truth.

Simple interview version

"ElastiCache is AWS's managed in-memory cache running Valkey, Redis OSS, or Memcached. I put it in front of RDS, Aurora, or DynamoDB for microsecond reads using lazy loading with TTLs. Serverless is the default when I don't want to size anything — it scales automatically and bills per GB and per ECPU; node-based clusters give me control over node types, shards, and replicas. For HA I use Valkey or Redis OSS with Multi-AZ and automatic failover, cluster mode for sharding, and Global Datastore for cross-Region reads and disaster recovery. It runs inside my VPC, secured with security groups, TLS, encryption at rest, and IAM or RBAC authentication."

One important interview follow-up

Q: If ElastiCache fails over to a replica, is any data lost?

A: Possibly, with standard replication. Valkey/Redis OSS replication is asynchronous, so writes acknowledged by the primary but not yet copied to the replica are lost when the replica is promoted. The Redis-style append-only file (AOF) doesn't fix this in a managed failover because it lives on the failed node's local disk. If you need zero data loss, the options are to treat ElastiCache as a cache that can be rebuilt from the database, or to use ElastiCache durability with synchronous writes, which persists each write to a Multi-AZ transactional log before acknowledging (at single-digit-millisecond write latency). Amazon MemoryDB is the related AWS service built as a durable, Redis-compatible primary database.

1. What is ElastiCache — the two deployment options

ElastiCache Serverless

  • What it is: create a highly available cache in under a minute by giving it a name; no instances, nodes, or clusters to configure. ElastiCache continuously watches memory, compute, and network use and scales up and out to match — the FAQ describes scaling up while scale-out starts in parallel, with no downtime.
  • Endpoint: one endpoint that hides the cluster design. All serverless caches run Multi-AZ.
  • Connection types: VPC, or (for Valkey 9.0 and later) a public endpoint reachable over the internet without a VPC — every connection must use IAM authentication and TLS 1.3.
  • Engines (per the user guide): Valkey 7.2 and later, Memcached 1.6.22 and later, Redis OSS 7.1.
  • Billing: per GB of data stored and per ECPU (ElastiCache Processing Unit — a measure of the compute and data transferred by your requests), with no node-hour charges. Valkey serverless has a lower minimum storage charge (100 MB) than Redis OSS.
  • Use when: traffic is unpredictable or spiky, or you want zero capacity planning.

Node-based (self-designed) clusters

  • What it is: you pick the node type (e.g. cache.r7g.large), how many nodes/shards, and which AZs they live in. AWS still manages hardware, monitoring, node replacement, and patching; you choose when to apply engine patches.
  • Options only here: single-AZ or Multi-AZ, cluster mode enabled or disabled, data tiering, Global Datastore, reserved nodes, durability (Valkey 9.0).
  • Billing: per node-hour, with reserved nodes for 1- or 3-year discounts.
  • Use when: load is steady and predictable (reserved nodes are cheaper), or you need a feature only node-based clusters offer.

Serverless vs. node-based — the difference is who sizes the cache: with serverless, ElastiCache sizes and scales it and you pay per use; with node-based, you size it, you pay per node-hour, and you are responsible for having enough capacity.

2. How it works, related services, and use cases

ElastiCache sits between your application and its data store. The application (on EC2, ECS, EKS, Lambda, or EMR) connects to the cache endpoint inside your VPC using a normal Valkey/Redis or Memcached client library — no AWS-specific SDK is needed for data operations. The AWS SDK/CLI/console are only used to create and manage the cache.

  • Related services: it is used as a caching layer in front of Amazon RDS, Aurora, DocumentDB, and DynamoDB; CloudWatch receives its metrics; S3 stores backups; KMS encrypts data at rest; IAM controls management and (optionally) data access.
  • Use cases in the guide and FAQ: database query caching, session stores, leaderboards (sorted sets), real-time analytics and counters, rate limiting, pub/sub messaging, geospatial queries, and — in newer Valkey versions — vector search for generative-AI workloads (semantic caching, retrieval), full-text search, and Bloom filters.
  • Getting started paths in the guide: create a Valkey/Redis OSS/Memcached serverless cache, a Python tutorial, and connecting Lambda to ElastiCache inside a VPC (Lambda must be attached to the VPC's subnets and allowed by the cache's security group).

4. Comparing Valkey, Memcached, and Redis OSS

Choose Memcached (per the guide) if you need the simplest model, want large multi-core/multi-threaded nodes, need to scale out and in by adding and removing nodes, and are caching simple objects. Choose Valkey or Redis OSS if you need rich data types, replication and automatic failover, backups, pub/sub, sorted sets, geospatial indexes, encryption and compliance features, or the newer Valkey capabilities. Valkey is the open-source, Linux Foundation-governed fork of Redis; ElastiCache for Valkey is priced lower than Redis OSS (the FAQ says 20% lower node-based and up to 33% lower serverless).

You can upgrade, not downgrade

After a cache is created you can move to a newer engine version but not back to an older one — downgrading means creating a new cache. Test new versions on a separate cluster first. (Moving from Redis OSS to Valkey is supported in place; see the Valkey FAQ.)

5. Best practices and caching strategies (from the guide)

The guide describes the same strategies covered in In-Memory Caching Strategies, in AWS's terms:

  • Lazy loading (cache-aside) — load into the cache only on a miss. Advantages: only requested data is cached; a node failure isn't fatal (a replacement empty node just causes more misses). Disadvantages: a miss penalty of three trips (cache, database, cache write) and stale data, because nothing updates the cache when the database changes.
  • Write-through — update the cache whenever you write the database. Advantages: cache data is never stale; users tolerate write latency better than read latency. Disadvantages: missing data on a new or replaced node until it is written again (combine with lazy loading), and cache churn — most written data is never read.
  • Adding TTL — give every write a time to live (seconds or milliseconds for Valkey/Redis OSS, seconds for Memcached). Combining lazy loading + write-through + TTL gets the benefits of each while keeping data from getting too stale and the cache from filling with unused data.
  • Read replicas — read from replicas instead of the primary to scale reads (with serverless, reads from replicas are made through a separate reader port; replica reads can be slightly behind the primary).

The guide's lazy-loading pseudocode, as a runnable shape:

def get_customer(customer_id):
    record = cache.get(customer_id)
    if record is None:
        record = db.query("SELECT * FROM Customers WHERE id = %s", customer_id)
        cache.set(customer_id, record, ex=300)
    return record

Other best practices in the guide and Well-Architected Lens: reserve memory for replication and background saves (the reserved-memory-percent parameter), size so that DatabaseMemoryUsagePercentage stays below eviction thresholds, use connection pooling, handle failover in clients (retry with backoff and reconnect to the primary endpoint), and avoid long-running commands such as KEYS in production. For failure modes such as stampedes, see Cache Problems.

6. High availability: replication groups and Multi-AZ

  1. Each Valkey/Redis OSS shard has a primary and up to five read replicas, placed in different AZs.
  2. With Multi-AZ with automatic failover enabled, ElastiCache detects a failed primary and promotes a replica.
  3. It updates the DNS record of the primary endpoint to point at the promoted replica, so clients using the endpoint reconnect to the new primary.
  4. A replacement node is provisioned in the background (the FAQ says a new healthy node joins within about six minutes).

Multi-AZ is required for the 99.99% availability SLA on node-based clusters; serverless caches are always Multi-AZ. Memcached has no replication: a failed node is replaced empty, and the keys it held are simply misses (which lazy loading tolerates). Gotcha: replication is asynchronous, so a failover can lose the most recent writes — see the follow-up and Replication Lag. Read replicas must be in the same Region as the primary; cross-Region copies need Global Datastore.

7. Durability

For node-based Valkey clusters (Valkey 9.0, cluster mode enabled), durability persists data in a distributed Multi-AZ transactional log, so data survives even if all cache nodes fail, and replicas recover without slowing the primary. Two write modes:

  • Synchronous writes — persisted across two AZs before responding: zero data loss, single-digit-millisecond write latency. For applications that can't tolerate losing a write.
  • Asynchronous writes — respond first, persist afterwards: microsecond latency, with up to about 10 seconds of possible data loss. Suitable for most workloads.

Durability vs. AOF — the difference is where the log lives: Redis-style AOF writes to the local disk of a single node in one AZ, so a node loss or failover can still lose data or become inconsistent; the ElastiCache transactional log is stored across AZs, independently of the nodes.

8. Replication across Regions: Global Datastore

  • A node-based feature: one primary cluster (reads and writes) in one Region replicates to up to two secondary Regions (reads only), typically in under a second.
  • Uses: low-latency local reads for users in other Regions, and cross-Region disaster recovery.
  • Failover is manual: you promote a secondary to primary; it typically completes in under a minute. AWS gives no SLA for RPO/RTO, but typical RPO is under a second and RTO under a minute after promotion.
  • Security: cross-Region traffic is encrypted in transit; each cluster can use its own customer-managed KMS key for encryption at rest.

9. Snapshot and restore

  • Supported for Valkey, Redis OSS, and serverless Memcached (not node-based Memcached). Backups are stored in S3.
  • Manual snapshots, or automatic daily backups kept for up to 35 days. One free snapshot is included per active cache.
  • Deleting a cache keeps its manual snapshots (and you can take a final snapshot); automatic snapshots are deleted.
  • Snapshots can be exported to an S3 bucket and shared with another account in the same Region to warm-start a cluster there. Valkey can restore Redis OSS backups (both use the RDB format).
  • Gotcha: on node-based clusters, taking a snapshot of a busy primary uses extra memory (fork and copy-on-write) — take backups from a replica and keep reserved-memory-percent headroom.

10. Scaling ElastiCache

  • Serverless — automatic, based on memory, compute, and network; you can set maximum limits for data and ECPUs to cap cost.
  • Vertical (node-based) — change to a larger or smaller node type; for Valkey/Redis OSS with replicas this is done online.
  • Horizontal, reads — add read replicas (up to five per shard).
  • Horizontal, writes and memory — cluster mode enabled: add or remove shards with online resharding (hash slots move between shards while the cluster keeps serving). Auto Scaling policies can adjust shards or replicas based on CloudWatch metrics.
  • Memcached — add/remove nodes; with Auto Discovery clients learn the new node list, but because keys are distributed by the client's hashing, changing the node count remaps some keys (misses until they refill).
  • Modifying cluster mode — a cluster-mode-disabled cluster can be moved to cluster mode enabled (via a compatible transition step), which requires cluster-aware clients.

11. Data tiering

On R6gd nodes (Valkey 7.2+ / Redis OSS 6.2+), data tiering adds local NVMe SSD to memory. When memory is full, ElastiCache automatically moves the least recently used items to SSD; when such an item is read, it is moved back into memory asynchronously. Keys and hot values stay in RAM. Designed for workloads that regularly access up to about 20% of the dataset: SSD reads add roughly 300 µs of latency, while in-memory items see no penalty. AWS cites nearly 5× more total capacity per node and over 60% savings versus memory-only nodes. Nearly all commands work unchanged, with a few documented feature limitations. It is an applied example of the LRU idea across two storage tiers.

12. Parameter groups and maintenance

  • Parameter groups hold engine settings. Default groups can't be edited — create a custom group to change values such as maxmemory-policy, timeout, notify-keyspace-events, or reserved-memory-percent. Some changes apply immediately; others need a node reboot.
  • Gotcha — the eviction policy default: ElastiCache's default parameter group for Valkey/Redis OSS uses volatile-lru (not open-source Redis's noeviction), so only keys with a TTL are evicted; if most keys have no TTL, writes fail with OOM errors when memory fills. For a pure cache, set allkeys-lru or allkeys-lfu. See Redis eviction policies.
  • Maintenance windows — a weekly window when AWS may apply patches and service updates; with Multi-AZ, updates are applied to replicas first and then fail over. Service updates can also be applied on demand.
  • Engine versions and upgrading — node-based Memcached and Valkey/Redis OSS major/minor upgrades are applied when you choose (security patches may be applied in the maintenance window).

13. Security

  • Network — caches live in your VPC (except Valkey serverless public endpoints). Security groups and network ACLs decide who can connect. ElastiCache can automatically set up the connection between an EC2 instance and a cache.
  • Encryption in transit — TLS between clients and nodes, and between primary and replicas; AWS issues and renews the certificates.
  • Encryption at rest — AWS KMS (AWS-managed or customer-managed keys) for data synced to disk, swap, and backups in S3.
  • Authentication — the Valkey/Redis AUTH token, Role-Based Access Control (RBAC) with users and user groups that restrict commands and key patterns, or IAM authentication (short-lived tokens from IAM identities). IAM policies separately control who can manage caches via the API.
  • Compliance — SOC 1/2/3, ISO, MTCS, C5, PCI DSS, HIPAA (with a BAA), and FedRAMP.

General principles: Application Security Fundamentals.

14. Logging and monitoring

  • CloudWatch metrics — host-level (CPUUtilization, FreeableMemory, NetworkBytesIn/Out, SwapUsage) and engine-level (EngineCPUUtilization — the engine's single main thread, the one to alarm on for Valkey/Redis OSS; DatabaseMemoryUsagePercentage; CacheHits, CacheMisses, CacheHitRate; Evictions; CurrConnections; ReplicationLag). Serverless caches report usage such as BytesUsedForCache and ElastiCacheProcessingUnits.
  • Events — failovers, node replacements, and scaling events, delivered through Amazon SNS.
  • Log delivery — Valkey/Redis OSS slow log and engine log to CloudWatch Logs or Kinesis Data Firehose.
  • CloudTrail — records ElastiCache API calls (who created, modified, or deleted a cache).

What to watch and why: Operating a cache and Observability Fundamentals.

15. Pricing and quotas

  • Serverless — per GB-hour of data stored plus per ECPU; no node charges.
  • Node-based — per node-hour by node type; reserved nodes for 1 or 3 years (All, Partial, or No Upfront) with size flexibility within a node family and Region. Redis OSS reservations apply to Valkey nodes in the same family.
  • Other charges — backup storage beyond the free snapshot, cross-Region data transfer (Global Datastore), and cross-AZ data transfer between your application and cache nodes in other AZs.
  • Quotas — nodes per cluster, shards per cluster, clusters per Region, and parameter/subnet groups have default limits (some raisable). See the Quotas chapter.

16. Online migration

To move from a self-managed Valkey/Redis OSS server (for example on EC2) into ElastiCache, online migration makes the ElastiCache cluster replicate from your source while it keeps serving traffic; you verify progress, then complete the migration and point the application at ElastiCache. The alternative is restoring an RDB snapshot from S3 (point-in-time, simpler, but writes after the snapshot are not included).

Frequently Asked Questions (from the AWS ElastiCache FAQ)

Summarised from the official FAQ page, grouped as AWS groups them.

General

Q: What is Amazon ElastiCache?

A serverless, fully managed caching service for Valkey, Memcached, and Redis OSS with microsecond latency and up to a 99.99% availability SLA. AWS handles the management work, and there's no upfront investment.

Q: What is caching and how does it help my applications?

Caching keeps frequently accessed data (such as database query results or computation results) in memory, improving latency and throughput for read-heavy workloads such as social networking, gaming, and media sharing.

Q: What deployment options do I have?

Serverless (no infrastructure management, instant scaling, pay per use) and node-based (fine-grained control over node types and placement, suited to fixed, predictable capacity).

Q: What does ElastiCache manage on my behalf?

Hardware provisioning, software patching, setup and configuration, monitoring, failure recovery, and backups. It publishes CloudWatch metrics so you can set alarms.

Q: How does ElastiCache interact with other AWS services?

It is commonly a caching layer in front of RDS, Aurora, DocumentDB, and DynamoDB, reducing database load with microsecond reads, and serves applications on EC2 and EMR.

Q: How am I billed?

Serverless: per GB of data stored and per ECPU consumed, no node-hour charges. Node-based: per node-hour, with optional reserved-node discounts. Cross-Region data transfer and backup storage in S3 beyond the free allowance are billed separately.

Q: How do I select the right node type?

You don't need to get it exactly right — you can add or remove nodes later. Consider the total memory needed for your target hit rate and the number of nodes needed for fault tolerance; the docs include sizing guidance.

Q: Can a cluster span multiple AZs?

Yes. When creating a cluster or adding nodes, you can specify how many nodes go in each AZ, or choose to spread nodes across the zones in your cache subnet group.

Performance

Q: What are the performance benefits?

Microsecond latency and scaling to billions of operations per second. AWS cites up to 80× faster reads and up to 55% cost savings when paired with RDS for MySQL, and up to 310 TiB per cluster (982 TiB with data tiering).

Q: Does a failover affect latency between my application and the cache?

Cross-AZ latency is negligible because AZs are connected with low-latency links. For best results, run your application tier redundantly in the same AZs as your cache nodes.

Scalability and serverless

Q: What is ElastiCache Serverless?

The most automated option: zero infrastructure management, instant scaling, pay-per-use billing, and a 99.99% availability SLA. See Serverless above for supported engine versions (the user guide lists Valkey 7.2+, Memcached 1.6.22+, Redis OSS 7.1).

Q: How do I migrate an existing workload to Serverless?

Change your application's endpoint to the serverless cache endpoint; to bring existing data, create the serverless cache from a backup in S3.

Q: How does Serverless scale?

It continuously monitors memory, compute, and network use and scales instantly without downtime, scaling up while it starts scaling out in parallel.

Q: How do I scale a node-based cluster?

Horizontally by adding shards or nodes, or vertically by changing to a larger node type. Valkey and Redis OSS support online resharding and online vertical scaling using read replicas.

Reliability

Q: What is durability for ElastiCache?

A feature that lets ElastiCache act as a persistent data store with microsecond reads by storing data in a Multi-AZ transactional log, with synchronous (zero data loss) or asynchronous (microsecond latency) writes — useful for knowledge bases, AI workflows, and leaderboards. See Durability.

Q: Synchronous vs. asynchronous writes — which should I choose?

Synchronous writes persist across two AZs before responding: zero data loss, single-digit-millisecond write latency — for applications that cannot lose data. Asynchronous writes respond first: microsecond latency with up to 10 seconds of potential loss — right for most workloads.

Q: How is durability different from Valkey/Redis OSS AOF?

ElastiCache durability uses a Multi-AZ transactional log; AOF is stored on a single node's local disk in one AZ, and AOF plus replication can lead to unbounded data loss and consistency problems during failover.

Q: What does it mean to run a node as a read replica?

A replica is a live, read-only copy of a primary kept in sync by replication, used to offload reads. You can create up to five per primary. Valkey and Redis OSS only — not Memcached.

Q: When would I use a read replica?

To scale reads beyond one node's capacity, to keep serving reads when the primary is unavailable, and for data protection — a replica can be promoted if the primary or its AZ fails.

Q: Can a read replica be in another Region?

No — replicas must be in an AZ of the same Region. For cross-Region replication, use Global Datastore.

Q: What happens during failover and how long does it take?

ElastiCache flips the DNS record of the cache endpoint to the read replica, which is promoted to primary. A new healthy node joins within about six minutes. Global Datastore cross-Region failovers complete in under a minute.

Q: What is Backup and Restore?

Snapshots stored in S3 for recovery, supported for Valkey, Redis OSS, and serverless Memcached. One free snapshot per active cache; manual or daily automatic backups with up to 35 days' retention.

Q: Can I use a snapshot from one account to warm-start a cluster in another?

Yes — copy the snapshot to an authorised S3 bucket in the same Region and grant the other account permission on that bucket.

Q: What happens to snapshots if I delete my cache?

Manual snapshots are kept, and you can take a final snapshot when deleting. Automatic snapshots are not kept.

Q: Can I restore a Redis OSS backup to Valkey?

Yes — ElastiCache for Valkey restores backups from any version of ElastiCache for Redis OSS, since both use the RDB file format.

Q: What is Global Datastore?

A node-based feature providing fully managed, secure cross-Region replication in under a second, for low-latency local reads and disaster recovery.

Q: How many Regions can I replicate to?

Up to two secondary Regions per Global Datastore.

Q: Does Global Datastore fail over automatically if the primary Region is degraded?

No — you manually promote a secondary cluster to primary; it usually completes in under a minute.

Q: What RPO and RTO can I expect with Global Datastore?

There's no SLA, but RPO is typically under one second and RTO typically under one minute after you start the promotion.

Q: How is my data secured with Global Datastore?

Cross-Region traffic is encrypted in transit, and each primary and secondary cache can use its own customer-managed KMS key for encryption at rest.

Availability / Multi-AZ

Q: What is Multi-AZ for ElastiCache?

A high-availability configuration that replicates data across AZs and fails over automatically. All serverless caches run Multi-AZ; node-based Valkey and Redis OSS with Multi-AZ support up to five read replicas.

Q: What are the benefits of Multi-AZ and when should I use it?

Higher availability and less administration: if the primary fails, the impact is limited to the time automatic failover takes. It makes the cache eligible for the 99.99% availability SLA — use it for production.

Security and compliance

Q: What security controls exist?

Encryption at rest (AWS KMS), encryption in transit (TLS), IAM authentication, VPC security groups for network control, and role-based access control for fine-grained permissions. Public endpoints rely on IAM policies.

Q: How do I control access to ElastiCache?

At two layers: network (VPC security groups and network ACLs) and identity (IAM authentication and Valkey/Redis OSS RBAC, which restricts users and commands).

Q: What are public endpoints?

A public endpoint lets you connect to an ElastiCache Serverless for Valkey cache (Valkey 9 and later) over the internet without a VPC. Every connection requires IAM authentication and TLS.

Q: Which compliance programs are supported?

SOC 1, SOC 2, SOC 3, ISO, MTCS, C5, PCI DSS, HIPAA, and FedRAMP, at no extra cost. Processing health data (PHI) requires a Business Associate Agreement with AWS.

Q: What does encryption at rest provide?

Protection for data during disk sync, swap operations, and backups stored in S3, using AWS-managed or customer-managed KMS keys.

Q: What does encryption in transit provide?

TLS for traffic between clients and ElastiCache and between primary and replica nodes; AWS manages certificate issuance and renewal.

Cost-effectiveness

Q: What is data tiering?

Using lower-cost NVMe SSDs alongside memory on R6gd nodes, for workloads that regularly access up to 20% of their data. It gives nearly 5× more capacity and over 60% savings; supported for Valkey 7.2+ and Redis OSS 6.2+.

Q: How does data tiering work?

When memory is fully used, the least recently used items move automatically to SSD; when accessed, they move back to memory asynchronously.

Q: What performance can I expect with data tiering?

About 300 µs of extra latency for items read from SSD, and no penalty for items in memory; steady-state latency is close to in-memory levels when about 20% or less of the data is accessed frequently.

Q: Which features work with data tiering?

All Valkey and Redis OSS commands, and most ElastiCache features; the docs list the few that aren't supported.

Q: What are reserved nodes?

A pricing option with a significant discount for a one- or three-year commitment, as All Upfront, Partial Upfront, or No Upfront. Not applicable to serverless.

Q: What happens to my Redis OSS reserved nodes if I upgrade to Valkey?

They apply automatically to Valkey nodes in the same family and Region. Because Valkey is 20% cheaper, the same reservation covers more capacity — for example five reserved nodes cover six Valkey nodes.

Q: Does size flexibility apply to reserved nodes?

Yes — within a node family and Region, the discount applies across all sizes automatically.

Valkey engine

Q: Why use ElastiCache for Valkey?

A fully managed experience on open-source Valkey with a 99.99% availability SLA and lower prices: serverless up to 33% cheaper with a 100 MB minimum storage charge (90% lower than Redis OSS), and node-based 20% cheaper, with faster scaling and better memory efficiency.

Q: How is Valkey different from Redis OSS on ElastiCache?

Faster scaling, about 20% better memory efficiency, and lower pricing (up to 33% serverless, 20% node-based). Valkey is governed by the Linux Foundation, avoiding single-vendor lock-in.

Q: How do I upgrade from Redis OSS to Valkey?

In place, without downtime. Clusters on Redis OSS versions before 5.0.6 may see a 30–60 second failover during DNS propagation. Rolling back to Redis OSS 7.1 is possible with data preserved.

Q: How can I migrate from self-managed Valkey or Redis OSS?

Either online migration (continuous replication with minimal disruption) or restoring a snapshot (a simpler point-in-time migration). See Online migration.

Q: Do reserved-node discounts carry across all node sizes when I upgrade to Valkey?

Yes — Redis OSS reservations apply to Valkey nodes in the same family and Region, and size flexibility spreads the discount across all sizes; because Valkey is cheaper, they cover more capacity.

Memcached engine

Q: I use Memcached today. How do I migrate?

ElastiCache is protocol-compatible with Memcached (get, set, incr, decr behave the same). Point your application at the ElastiCache endpoints; Auto Discovery lets clients detect added or removed nodes without restarts.

Q: Can I control when my Memcached engine is upgraded?

Yes — ElastiCache doesn't apply major or minor engine upgrades automatically. You choose the version at creation and upgrade when you want; security patches may be applied in the maintenance window.

Q: How do I choose the Memcached version?

Pick any supported version when creating the cluster; to upgrade, modify the cluster's engine version and apply immediately or in the next maintenance window.

Q: Can I test a new version before upgrading?

Yes — create a new cluster on the new version and point a development or staging application at it first.

Redis OSS engine

Q: Will AWS keep supporting ElastiCache for Redis OSS?

Yes, including version 7.1. Older versions follow the normal end-of-life process with advance notice; check the docs for currently supported versions.

Interview checklist

  • Say which engine and why: Valkey/Redis OSS for data structures, HA, and backups; Memcached for the simplest multi-threaded object cache.
  • Say serverless vs. node-based and why (unpredictable traffic vs. steady load and reserved-node savings).
  • State the caching strategy (lazy loading + TTL, write-through where freshness matters) and the eviction policy (allkeys-lru rather than the default volatile-lru for a pure cache).
  • Mention Multi-AZ with automatic failover, cluster mode for sharding, and Global Datastore for multi-Region.
  • Name the data-loss caveat of asynchronous replication, and durability/MemoryDB when the cache must be a primary store.
  • Security: private subnets, security groups from the app tier only, TLS, encryption at rest, RBAC or IAM auth.
  • Monitoring: EngineCPUUtilization, DatabaseMemoryUsagePercentage, Evictions, CacheHitRate, ReplicationLag.
