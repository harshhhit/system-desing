SQS Overview

What you'll learn

By the end of this page you will be able to:

  • Explain what SQS is and why queues decouple services
  • Walk one message through send, receive, visibility timeout, delete and DLQ
  • Choose between Standard and FIFO queues
  • Write an idempotent consumer with long polling and batching
  • Scale consumers on queue depth and debug stuck or duplicated messages

What SQS Is and Why It Exists

Producer → SQS API → Storage Layer → Message replicated to AZ1 + AZ2 + AZ3 → Consumer retrieves message from healthy AZ.

A message queue lets one service hand work to another without waiting for it. Amazon SQS is AWS's fully managed version: no brokers to run, storage replicated across Availability Zones, and throughput that scales without provisioning. Use it whenever a request can be acknowledged now and processed later — emails, image processing, order fulfilment, webhooks.

💡 Important

Receiving a message does not remove it. Only an explicit delete does. Everything about SQS reliability — and its duplicates — follows from that one rule.

Core Concepts

TermMeaning
Producer / consumerThe service that sends messages / the one that receives, processes and deletes them.
Visibility timeoutHow long a received message stays hidden from other consumers (default 30 s, up to 12 hours).
Receipt handleThe token from one receive that you must use to delete (or extend) that message.
Retention periodHow long an unprocessed message is kept (default 4 days, 1 minute–14 days).
Dead-letter queue (DLQ)Where messages go after maxReceiveCount failed receives.
Long pollingA receive that waits up to 20 s for messages instead of returning empty.
Delay queue / message timerHides new messages for up to 15 minutes before first delivery.

Standard vs. FIFO queues

StandardFIFO
DeliveryAt-least-once (occasional duplicates)Exactly-once processing within a 5-minute deduplication window
OrderingBest-effortStrict, per message group ID
ThroughputNearly unlimited300 API calls/s per action (3,000 messages/s with batches of 10); high-throughput mode raises this substantially
Use whenOrder doesn't matter and consumers are idempotentOrder per entity matters (per-account ledger updates) or duplicates are costly

Standard vs. FIFO — the difference is the trade between throughput and guarantees. FIFO's ordering is per message group, so parallelism comes from having many groups (e.g. one per customer), not from one global order.

⚠️ Common mistake

Choosing FIFO "to get exactly-once" and then writing a non-idempotent consumer. Deduplication only covers the 5-minute window and the queue; a consumer that crashes after charging a card but before deleting the message will still process it again.

The Life of One SQS Message, Step by Step

The one-line flow at the top of this page compresses the whole lifecycle. Spelled out, each step causes the next:

  1. Send. The producer calls SendMessage. SQS stores the message redundantly across Availability Zones and returns a message ID. The producer is now done — it does not know or care which consumer will handle the message, or when.
  2. Wait in the queue. The message stays in the queue until a consumer receives it or the queue's retention period expires (4 days by default, configurable from 1 minute to 14 days). A message that is never processed within the retention period is deleted — a queue is a buffer, not permanent storage.
  3. Receive. A consumer calls ReceiveMessage. With long polling (a wait time of up to 20 seconds) the call waits for a message to arrive instead of returning empty immediately, which cuts empty responses and cost.
  4. Invisible while processing. Receiving a message does not remove it. It starts the visibility timeout (30 seconds by default), during which other consumers cannot receive that message.
  5. Delete on success. When processing succeeds, the consumer calls DeleteMessage with the receipt handle. Only this call removes the message from the queue.
  6. Reappear on failure. If the consumer crashes or is too slow, the visibility timeout expires → the message becomes visible again → another consumer receives it. This is exactly why delivery is at-least-once and consumers must be idempotent.
  7. Dead-letter after repeated failure. Each receive increments the message's receive count. Once it exceeds the maxReceiveCount in the queue's redrive policy, SQS moves the message to the dead-letter queue, where it can be inspected and replayed instead of blocking the queue.

Visibility timeout vs. retention period — the difference is scope: the visibility timeout is a short per-receive lock that decides who may process a message right now, while the retention period is the overall lifetime that decides how long the message may exist at all. Setting the visibility timeout shorter than your real processing time does NOT lose messages, but it does cause duplicate processing, because the message reappears while the first consumer is still working on it.

🧠 Think about it

A job usually takes 20 s but sometimes 90 s, and the visibility timeout is 30 s. What happens on the slow runs? (The message reappears at 30 s and a second consumer starts the same job — set the timeout above the worst case, or extend it with ChangeMessageVisibility while working.)

Implementation

Create a queue with a DLQ

aws sqs create-queue --queue-name orders-dlq
aws sqs create-queue --queue-name orders --attributes '{"VisibilityTimeout":"120","ReceiveMessageWaitTimeSeconds":"20","RedrivePolicy":"{\"deadLetterTargetArn\":\"arn:aws:sqs:us-east-1:123456789012:orders-dlq\",\"maxReceiveCount\":\"5\"}"}'
aws sqs send-message --queue-url https://sqs.us-east-1.amazonaws.com/123456789012/orders --message-body '{"order_id":42}'
  • VisibilityTimeout 120 — above the slowest normal processing time.
  • ReceiveMessageWaitTimeSeconds 20 — long polling by default for every consumer.
  • RedrivePolicy … maxReceiveCount 5 — after 5 failed receives the message moves to orders-dlq.

An idempotent consumer (Python, boto3)

while True:
    resp = sqs.receive_message(QueueUrl=URL, MaxNumberOfMessages=10, WaitTimeSeconds=20)
    for m in resp.get("Messages", []):
        order = json.loads(m["Body"])
        if not already_processed(order["order_id"]):
            fulfil(order)
            mark_processed(order["order_id"])
        sqs.delete_message(QueueUrl=URL, ReceiptHandle=m["ReceiptHandle"])
  • MaxNumberOfMessages=10, WaitTimeSeconds=20 — batch up to 10 per call and long-poll: fewer, cheaper API calls.
  • already_processed / mark_processed — an idempotency record (e.g. a unique constraint on order_id) so a redelivered message does nothing twice.
  • delete_message only after success — if fulfil throws, the message reappears after the visibility timeout and is retried, then dead-lettered.

🔥 Production insight

Alert on the age of the oldest message, not just on depth. A depth of 10,000 is fine if consumers clear it in seconds; an age of 30 minutes means users are waiting for their emails or orders, whatever the depth.

Security

  • IAM least privilege — producers get sqs:SendMessage only; consumers get ReceiveMessage, DeleteMessage, ChangeMessageVisibility on that queue only.
  • Queue policies control cross-account and service access (e.g. allow only a specific SNS topic or S3 bucket to send).
  • Encryption at rest with SSE-SQS or SSE-KMS; HTTPS in transit; VPC endpoints to keep traffic off the internet.
  • Treat message bodies as untrusted input — validate before acting; never put secrets in messages.

Performance & Scalability

  • Throughput scales with consumers: Standard queues accept nearly unlimited rates; your consumers are the bottleneck.
  • Batching (10 messages per send/receive/delete) cuts API calls and cost ~10×.
  • Long polling removes empty receives.
  • Large payloads belong in S3 with a pointer in the message (the SQS Extended Client does this).
  • Downstream limits: scaling consumers can overload the database they write to — cap concurrency (Lambda reserved concurrency, worker counts).

Debugging workflow

  1. aws sqs get-queue-attributes --queue-url $URL --attribute-names All — depth, in-flight, timeouts, redrive policy.
  2. Check consumer logs and error rates; is the downstream (DB, API) healthy?
  3. Peek at the DLQ: aws sqs receive-message --queue-url $DLQ_URL --max-number-of-messages 10.
  4. After fixing, redrive: aws sqs start-message-move-task --source-arn $DLQ_ARN.

Best Practices

Do

  • Make every consumer idempotent — duplicates will happen.
  • Delete only after success; extend visibility for long jobs.
  • Always attach a DLQ with a sensible maxReceiveCount.
  • Long-poll and batch.
  • Scale on age of oldest message and depth.

Avoid

  • Visibility timeouts shorter than processing time.
  • Large payloads in messages — store in S3.
  • Assuming order on Standard queues.
  • Unbounded consumer scaling that overwhelms downstream systems.

Interview Answer — What Is Amazon SQS?

Amazon SQS (Simple Queue Service) is a fully managed message queue from AWS: a producer sends a message to a queue over an HTTPS API, SQS stores it durably, and a consumer polls the queue, processes the message, and deletes it. As the one-line flow above shows, every message is stored redundantly across multiple Availability Zones, so a consumer can still receive it if one AZ fails.

SQS exists to decouple services. Without a queue, a service that calls another directly must wait for it and fails when it is down or overloaded. With a queue in between, the cause → effect chain is: the producer writes a message and returns immediately → the message waits safely in SQS → consumers process it at their own pace, and more consumers can be added when the backlog grows → if a consumer crashes mid-processing, the message becomes visible again and is retried. See SQS Use Cases for the patterns this enables.

Three mechanisms make this work. The visibility timeout hides a received message from other consumers while one consumer works on it; if the consumer does not delete it before the timeout, it reappears for another attempt. A dead-letter queue (DLQ) receives messages that have failed a configured number of times, so one bad message does not block processing forever. And SQS offers two queue types: Standard (nearly unlimited throughput, at-least-once delivery, best-effort ordering) and FIFO (strict ordering within a message group and deduplication, with lower throughput).

Simple interview version

"SQS is AWS's fully managed message queue. Producers send messages, SQS stores them redundantly across Availability Zones, and consumers poll, process, and delete them. It decouples services and absorbs traffic spikes, because the producer doesn't wait for the consumer. A visibility timeout hides a message while it's being processed and makes it reappear if the consumer fails, and a dead-letter queue catches messages that keep failing. Standard queues give high throughput with at-least-once delivery; FIFO queues give strict ordering and deduplication."

One important interview follow-up

Q: Does SQS guarantee that each message is processed exactly once?

A: No. A Standard queue guarantees at-least-once delivery: a message can occasionally be delivered more than once, and it is redelivered whenever a consumer does not delete it before the visibility timeout expires — for example if the consumer crashed after doing the work but before deleting the message. FIFO queues deduplicate messages sent with the same deduplication ID within a 5-minute window, but that prevents duplicate sends, not duplicate processing after a consumer failure. So consumers must be idempotent — processing the same message twice must have the same effect as processing it once, for example by recording the message or order ID and skipping IDs already handled.

Practice questions

Why put a queue between two services?

The producer returns immediately and doesn't fail when the consumer is slow or down; the queue buffers spikes and consumers scale independently.

What does the visibility timeout do?

Hides a received message from other consumers while one works on it; if it isn't deleted in time, it reappears for another attempt.

What's a dead-letter queue for?

Isolating messages that failed maxReceiveCount times, so they stop retrying forever and can be inspected and replayed.

Standard vs. FIFO — when do you choose FIFO?

When order per entity matters or duplicates are costly, and throughput fits FIFO limits; parallelise with many message group IDs.

Visibility timeout vs. retention period?

Visibility is a short per-receive lock (who processes now); retention is the message's whole lifetime in the queue.

How do you make a consumer idempotent?

Record a processed key (order ID or message deduplication ID) atomically with the side effect — e.g. a unique constraint — and skip if it already exists.

Does SQS guarantee exactly-once?

No. Standard is at-least-once; FIFO deduplicates within 5 minutes, but end-to-end exactly-once still requires idempotent consumers.

How would you autoscale consumers?

Target a backlog per consumer (visible messages ÷ consumers) and an age-of-oldest-message ceiling; cap max consumers by downstream capacity.

How does a poison message affect a FIFO queue?

It blocks its message group (later messages in that group wait) until it's dead-lettered — so set maxReceiveCount and a DLQ.

Customers get two confirmation emails for one order. Why?

The consumer sent the email but crashed or timed out before deleting; the message reappeared. Make sending idempotent (record sent per order) and size the visibility timeout correctly.

Black Friday: the queue holds 2 million messages and the oldest is 40 minutes old. What do you do?

Scale consumers within downstream limits, batch operations, check for a slow dependency, prioritise critical work (separate queues), and keep an eye on retention.

The DLQ suddenly has 5,000 messages. Next steps?

Inspect samples for a common error, correlate with deploys/outages, fix the cause, then redrive from the DLQ in a controlled way.

What Should I Remember?

  1. SQS decouples producers and consumers; receive ≠ delete.
  2. Visibility timeout hides in-flight messages; expiry means redelivery.
  3. Standard = at-least-once, best-effort order; FIFO = ordered per group, deduplicated, lower throughput.
  4. Consumers must be idempotent; delete only after success.
  5. DLQ + maxReceiveCount isolate poison messages.
  6. Long-poll, batch, and scale on age of oldest message.
