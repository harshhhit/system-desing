Event Sourcing & CQRS

Storing state as immutable events, snapshotting, splitting write and read models, projections and materialized views, and when this is (and isn't) worth the complexity.

Event sourcing: store what happened, not just the current state

A conventional model stores current state and overwrites it on every update — an orders row's status column just becomes "shipped", and whatever it was before is gone. Event sourcing instead stores the full sequence of immutable events that led there — OrderPlaced, PaymentReceived, OrderShipped — and derives current state by replaying them in order. The event log is the source of truth; any "current state" view is just a cache of it.

GainCost
Full audit trail for free — every change is already an explicit, timestamped record of what happened and (with metadata) whyReplaying the full history to get current state gets expensive as the log grows
Time travel — reconstruct state as of any point in the past by replaying only up to that pointEvent schemas change over time; old events must still be readable ("upcasting" old event shapes to new ones)
Natural fit for a Kafka-style log (see Kafka Fundamentals) as the storage/transport mechanismDebugging "what's the current state" requires replaying, not just reading a row — a real shift in mental model
Snapshotting

To avoid replaying an entity's entire history on every read, periodically persist a snapshot of its current state alongside the event log. Reads then replay only the events since the last snapshot — the log stays the source of truth, the snapshot is just a cached checkpoint.

CQRS: separate the write model from the read model

CQRS (Command Query Responsibility Segregation) is a distinct idea that's often paired with event sourcing but doesn't require it: instead of one model serving both writes (commands) and reads (queries), split them into two. The write side is optimized for validating and recording changes correctly; the read side is optimized — independently — for however queries actually need the data shaped, including multiple different read models for different consumers of the same data.

  • A normalized write model doesn't have to be denormalized for read performance, and a read model doesn't have to fit the write side's schema at all — they can even live in entirely different databases (a relational write store, a search-optimized read store).
  • This directly addresses the same "how do I choose the database" trade-off in How to Choose the Database — CQRS lets you pick a different, purpose-fit answer for reads than for writes instead of one compromise database.

How they combine

  1. A command arrives, is validated, and — instead of updating a row — appends a new event to that entity's event log.
  2. The write side acknowledges once the event is durably appended (this is the source of truth being updated).
  3. One or more projections — separate processes subscribed to the event stream — consume each new event and update a read-optimized materialized view (a denormalized table, a search index, a cache).
  4. Queries read from the materialized view, never from replaying the event log directly.
The read side is eventually consistent

Between step 2 and step 3 there's a real (usually small) window where the write has committed but the read-side projection hasn't caught up yet — a user can write something and, for a moment, not see it reflected in a query. Any system built this way has to decide explicitly how to handle that gap (read-your-writes tricks, UI optimism, or simply accepting the lag) rather than assume the read side is always current.

When this is worth the complexity

  • Reach for it when an audit trail is a real requirement (financial ledgers, compliance-heavy domains), when read and write access patterns genuinely diverge enough that one schema can't serve both well, or when the domain is naturally event-shaped (order fulfillment, workflow/state-machine-heavy processes).
  • Skip it for straightforward CRUD domains — event sourcing and CQRS add real operational and cognitive overhead (event schema versioning, projection lag, replay tooling), and most systems don't need either. This is one of the more commonly over-applied patterns in system design interviews; being able to say "this doesn't need it" is as valuable as knowing how it works.

Interview checklist

  • Keep the two ideas distinct: event sourcing is about how state is stored (as events, not current state); CQRS is about splitting write and read models. They're commonly combined but are independent decisions.
  • Always mention the read side's eventual consistency explicitly when proposing this — it's the detail interviewers probe for.
  • Bring up snapshotting the moment "replay the whole history" comes up as a cost.
  • Be ready to argue against using it for a simple CRUD-shaped problem — knowing the trade-off cuts both ways is part of a strong answer.
