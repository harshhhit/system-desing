The core difference from SQS: a log, not a queue

SQS Overview covers a classic queue: a message is delivered, and once a consumer acknowledges it, it's gone. Kafka is built on a different primitive — an append-only, durable, ordered log. Consuming a message doesn't remove it; every consumer tracks its own position (offset) in the log and can replay from any earlier point. That one structural difference drives almost everything else below.

Topics and partitions

  • A topic is a named stream (e.g. orders), split into some number of partitions — independent, ordered logs that together make up the topic.
  • Kafka guarantees order within a partition only, never across the whole topic — a core interview point: "Kafka preserves order" is only true per-partition.
  • A producer picks a partition per message, usually by hashing a key (e.g. order_id) — the same key always lands on the same partition, which is what gives you ordering guarantees for all events about one entity.
  • Partition count sets the ceiling on consumer parallelism (see below) and is chosen up front — increasing it later changes which partition a given key hashes to, breaking per-key ordering for keys already in flight.

Consumer groups and offsets

  • Consumers belong to a consumer group; Kafka assigns each partition in a topic to exactly one consumer within that group — so a group with as many consumers as partitions gets full parallelism, and extra consumers beyond that sit idle.
  • Multiple independent groups can each consume the same topic from scratch — this is Kafka's fan-out: unlike an SQS queue (where one message goes to one consumer, full stop), N independent services can each read every event, at their own pace, without competing.
  • Each consumer tracks an offset — its position in a partition — and periodically commits it (to Kafka itself, in practice) so that a restart resumes from the last committed point instead of the beginning.
  • Rebalancing — when a consumer joins or leaves a group, partitions are reassigned among the survivors; this pauses consumption briefly and is a real operational concern at scale (frequent restarts causing frequent rebalances).
Delivery semanticsHow it's achieved
At-most-onceCommit the offset before processing — a crash after commit but before processing finishes loses the message
At-least-onceCommit the offset after processing succeeds — a crash after processing but before commit reprocesses the message (so processing must be idempotent)
Exactly-onceKafka's idempotent producer (dedupes retried sends) + transactional writes (an offset commit and a downstream write succeed or fail together) — real, but adds meaningful complexity and is usually scoped to Kafka-to-Kafka pipelines

Retention

  • Time/size-based retention — the default: keep every message for N days (or up to N gigabytes per partition), then delete the oldest. A new consumer group can still replay the last N days of history — something an SQS queue, which deletes on ack, simply can't offer.
  • Log compaction — an alternative retention mode: instead of deleting by age, Kafka keeps only the latest message per key, deleting older ones. Turns a topic into something closer to a changelog of a key-value store — the basis for rebuilding state (see Event Sourcing & CQRS) or for Kafka Streams' internal state stores.

Replication

  • Each partition has a leader broker (handles all reads/writes for it) and some number of follower replicas that copy its log.
  • The ISR (in-sync replica) set is the subset of followers caught up closely enough with the leader to be eligible to take over if it fails — a follower that falls too far behind drops out of the ISR.
  • acks controls the producer's durability trade-off: acks=0 (fire and forget, fastest, can silently lose messages), acks=1 (wait for the leader only), acks=all (wait for the full ISR — safest, since a fully-committed message survives even a leader failure).

Interview checklist

  • State the log-vs-queue distinction first — most of Kafka's other properties (replay, fan-out, per-partition order) follow directly from it.
  • Be precise about ordering: per-partition only, driven by the producer's partition key — not "Kafka guarantees order."
  • Know how partition count caps parallel consumption within one group, and how multiple groups get independent full copies of the stream.
  • Name a delivery-semantics choice (at-least-once is the common default) and note that it requires idempotent consumers.
  • Justify Kafka vs. SQS by the actual requirement — replay/fan-out/throughput vs. simple managed task queueing — not by familiarity.
