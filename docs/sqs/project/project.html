Multiprotocol Messaging Starter: Project Guide

Awesome—here’s a complete, Docker-based Django + Kafka + RabbitMQ project that implements retries and DLQs end-to-end. I’ve packaged it for you:

Download the project (ZIP)

Interview Answer — What Are Retries and Dead-Letter Queues?

A retry is re-attempting the processing of a message that failed, on the assumption that the failure was temporary — a timeout, a database briefly unavailable. A dead-letter queue (DLQ) is a separate queue or topic where a message is moved after it has failed a maximum number of attempts, so it stops being retried and can be inspected, fixed, and replayed later.

They exist because consumers fail in two different ways. A transient failure succeeds if tried again, so retries recover it automatically. A permanent failure — a malformed message, a bug, a missing record — fails every time; without a limit, that "poison message" is retried forever, wasting workers and, in ordered systems, blocking every message behind it. The cause → effect chain in this project is: the worker fails to process a message on orders → it republishes the message to orders.retry with an attempt count → after MAX_RETRIES attempts it is published to orders.dlq → the main flow keeps moving and the failed order is preserved for investigation (see how retries & DLQs work here).

This project implements the same pattern on two brokers so you can compare them: RabbitMQ (a queue broker speaking AMQP, with native dead-letter exchanges) and Kafka (a log, where retries and DLQs are built with extra topics). A production version adds exponential backoff between attempts — RabbitMQ message TTL with a dead-letter exchange, or delayed-retry topics in Kafka — and a replayer that moves fixed messages from the DLQ back to the main queue.

Simple interview version

"When a consumer fails to process a message, I retry it a limited number of times, ideally with exponential backoff, because many failures are transient. If it still fails after the maximum attempts, I move it to a dead-letter queue so the poison message doesn't block or waste the workers, and I alert on the DLQ and replay messages once the cause is fixed. RabbitMQ supports this natively with dead-letter exchanges; in Kafka I build it with retry and DLQ topics."

One important interview follow-up

Q: Once failing messages go to the DLQ, is the problem handled?

A: No — a DLQ only parks the problem. If nobody monitors it, failed orders silently pile up and customers are never served. A DLQ needs an alert on its depth or age, a way to inspect why each message failed (store the error and attempt count with it), and a replay path to send messages back to the main queue once the bug or dependency is fixed. Replays and retries also mean the same message can be processed more than once, so the consumer must be idempotent.

What’s inside

  • Django API (DRF) to publish orders to Kafka and/or RabbitMQ
  • Kafka worker that consumes, retries via a retry topic, and finally dead-letters
  • RabbitMQ worker that consumes, retries via a retry queue, and finally dead-letters
  • Kafka UI for browsing topics
  • RabbitMQ Management UI for browsing queues
  • docker-compose.yml to run everything locally

Quick start

  1. Unzip and cd multiprotocol-messaging-starter

  2. Run:

    docker compose up --build

  3. Open:

    • Django API: http://localhost:8000
    • Kafka UI: http://localhost:8080
    • RabbitMQ UI: http://localhost:15672 (guest/guest)

Send test messages

Success-ish (random failures are simulated in workers):

curl -X POST http://localhost:8000/api/orders \
  -H "Content-Type: application/json" \
  -d '{"order_id": 1}'

Force a failure (to exercise retries & DLQ):

curl -X POST http://localhost:8000/api/orders \
  -H "Content-Type: application/json" \
  -d '{"order_id": 2, "should_fail": true}'

How retries & DLQs work here

  • Kafka: orders → (on failure) orders.retry → (exceeds MAX_RETRIES) orders.dlq
  • RabbitMQ: orders → (on failure) orders.retry → (exceeds MAX_RETRIES) orders.dlq

You can inspect messages moving through these topics/queues using the UIs above.

Tweak it

  • Turn brokers on/off for the API in docker-compose.yml (USE_KAFKA, USE_RABBIT)
  • Set retry caps via MAX_RETRIES env variables for each worker
  • Add persistence (DB) in workers, implement exponential backoff (RabbitMQ TTL + DLX; Kafka delayed-retry pattern), or build a DLQ “replayer” service

If you want, I can add exponential backoff with RabbitMQ TTL/DLX and Kafka delayed retries, or wire in Postgres to store processed orders.
