Microservice Resilience Patterns

Circuit breaker, retries with backoff and idempotency, bulkhead isolation, the saga pattern, API gateway, and service mesh.

The problem these patterns all address

In a monolith, a failing function call is a stack trace. In a microservice architecture, a failing call is a network call to another process that might be slow, down, or overloaded — and if nothing contains that failure, it doesn't stay local: a caller that keeps retrying a dead dependency, or keeps waiting on a slow one, consumes its own threads/connections and starts failing too, which then does the same thing to its callers. This is a cascading failure, and every pattern on this page exists to stop one service's bad day from becoming the whole system's bad day.

Circuit breaker

Named for the electrical version: after enough failures calling a dependency, stop calling it entirely for a while, instead of continuing to hammer something that's clearly down.

  • Closed — normal state, requests pass through; failures are counted.
  • Open — once failures cross a threshold, the breaker trips: calls fail immediately (or return a fallback) without hitting the network at all, for a cooldown period.
  • Half-open — after the cooldown, let a small number of trial requests through; if they succeed, close the breaker again, if they fail, reopen it.

The payoff is twofold: it stops wasting the caller's own resources (threads, connections) on calls almost certain to fail, and it gives the struggling dependency room to recover instead of being kept down by continued load.

Retries with backoff

  • Exponential backoff — wait longer between each retry (1s, 2s, 4s, 8s…) instead of retrying immediately, so a struggling dependency isn't hit with the same request rate that may have contributed to it struggling in the first place.
  • Jitter — add randomness to each wait so that many clients retrying after the same failure (e.g. after a dependency blips) don't all retry in lockstep and recreate the exact spike that just happened — the same self-inflicted thundering herd covered in Rate Limiting & Throttling.
  • Retries require idempotency — retrying a call that already partially succeeded (e.g. "charge the card" succeeded but the response was lost) must be safe to repeat. This is usually solved with an idempotency key the caller generates once and sends on every retry, so the server can recognize and dedupe a repeat.
  • Retries and circuit breakers work together, not against each other: the breaker stops retries from ever reaching a dependency it's already given up on.

Bulkhead isolation

Named for a ship's watertight compartments — a hull breach floods one compartment, not the whole ship. Applied to services: give each dependency its own resource pool (a thread pool, a connection pool) instead of sharing one pool across every downstream call. If one dependency goes slow and every call to it hangs, it only exhausts its own pool — calls to every other, healthy dependency keep working on their own separate pool instead of queuing behind the stuck one.

Saga pattern — distributed "transactions" without 2PC

A single-database transaction can just roll back on failure. A business operation spanning multiple services (place an order → reserve inventory → charge payment → schedule shipping) has no single database to wrap a transaction around, and a blocking two-phase-commit across services doesn't scale and couples their availability together. A saga instead breaks the operation into a sequence of local transactions, each with a compensating transaction that undoes it if a later step fails (e.g. "release the inventory reservation" compensates "reserve inventory").

API gateway

A single entry point in front of a microservice fleet that terminates external requests and handles cross-cutting concerns once instead of duplicating them in every service: authentication, rate limiting (see Rate Limiting & Throttling), request routing to the right backend service, and sometimes response aggregation across several services into one client-facing response. It's the same "coarse enforcement point" idea as the edge/gateway tier in the rate-limiting note, generalized beyond just limits.

Service mesh

Instead of building retries, circuit breaking, mTLS, and observability into every service's application code, a service mesh runs a small proxy (sidecar) alongside every service instance and routes all its network traffic through that proxy. The proxies handle these concerns uniformly at the infrastructure layer — the same client-side load-balancing idea from Load Balancing, generalized into a dedicated process next to every caller rather than logic embedded in each application. The trade-off is operational: another moving part (the mesh control plane) and another hop (proxy → proxy) added to every call.

Interview checklist

  • Match the pattern to the failure mode: circuit breaker for "dependency is down," bulkhead for "one slow dependency shouldn't starve resources needed by others," retries+backoff for "transient failure," saga for "multi-service operation with no shared transaction."
  • Any retry story needs an idempotency answer — interviewers will ask "what if this request actually succeeded and the response was just lost."
  • For a saga, pick choreography vs. orchestration explicitly and name the trade-off (implicit-but-decoupled vs. explicit-but-centralized), and always describe the compensating transaction for at least one failure path.
  • API gateway and service mesh solve overlapping concerns at different layers (edge vs. every internal hop) — know which one a given cross-cutting concern actually belongs to.
