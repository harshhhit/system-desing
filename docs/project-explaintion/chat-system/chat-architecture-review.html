Chat Architecture Review: Postgres + PubNub

A design review of a chat app that stores messages in Postgres and uses PubNub for live delivery — plus a learning guide and references for every pattern it names: scoped tokens, transactional outbox, N+1 fan-out, idempotency keys, cursor pagination.

Interview Answer — What Is a "Database as Source of Truth + Pub/Sub for Delivery" Chat Architecture?

This is a chat design where every message is first saved in a database (here, PostgreSQL) and a hosted publish/subscribe service (here, PubNub) is used only to push a notification of that change to the clients that are online. The database is the source of truth — the one copy of chat data that every other view is derived from. The pub/sub service is a delivery channel — a pipe that carries "something changed" events and holds no data you would be upset to lose.

It exists because the two jobs have opposite requirements. Storing messages needs durability, transactions, querying and history. Delivering messages in real time needs thousands of long-lived connections and very low latency. Running your own WebSocket servers to do the second job means managing connection state, sticky sessions, and horizontal fan-out; renting that from PubNub (or Ably, Pusher, etc.) lets a small team skip it. Splitting the jobs means an outage in the delivery channel degrades the app to "not live" instead of "data lost".

The design is only as good as the seams between the two systems. The five fixes on this page are all seam problems: who may subscribe to which channel (per-user tokens), what happens if the database write succeeds but the publish fails (transactional outbox), how much work one send does (N+1 queries and background jobs), what happens when a client retries (idempotency keys), and how clients page through a list that keeps changing (cursor pagination).

Simple interview version

"I save every message to Postgres first — that's the source of truth — and only after the commit do I publish a small event to PubNub so online clients update instantly. PubNub is just the delivery pipe, so if it goes down nobody loses messages; they just stop getting live updates until they reconnect and re-fetch from the API. To make that safe I give each user a scoped PubNub token, write the publish event into an outbox table in the same transaction, dedupe client retries with a client-generated message ID and a unique constraint, and page message history with a cursor instead of an offset."

One important interview follow-up

Q: If you write to the database first and then publish, aren't you guaranteed that every saved message reaches the clients?

A: No. Writing first only guarantees the opposite direction — clients never see an event for a message that wasn't saved. The database commit and the PubNub publish are two separate systems, so the process can crash, time out, or get a 5xx from PubNub in the gap between them; the message is then saved but no live event is ever sent. This is called the dual-write problem. You close it with the transactional outbox (save the event in the same database transaction as the message, and have a separate relay publish it with retries), and you back it up by having clients re-fetch from the API on reconnect. See Pattern 2 — Transactional Outbox below.

The Review

Yes, the basic design is sound. Saving to Postgres and using PubNub only to push live updates is a common approach for apps at your scale, and it means you don't have to run your own WebSocket servers. The problems are in the details of how it's built, not in the overall design.

What's done well

  • The database is the only real copy of chat data. If PubNub goes down, no messages are lost; users just stop getting live updates.
  • PubNub is only used to deliver updates. Chat history isn't split between two systems.
  • The database is written before anything is published, so clients never receive an event for a message that wasn't saved.

What I'd fix

  1. Clients don't get their own PubNub tokens. This is the most important one, and it's the gap from my last answer. The backend should give each user a token limited to their own chat:{id} and user:{id}:notifications channels. The grantAccessToken function for this already exists but nothing calls it.
  2. Live updates can be lost without anyone knowing. If publishing fails after the database write, the error is only logged. The usual fixes are:
    • the transactional outbox pattern (saving the event in the database and publishing it separately), or at least
    • having clients re-fetch from the API when they reconnect, which covers any updates they missed.
  3. Sending a message is slow. One send runs roughly 8–10 database/cache calls in sequence, plus one unread-count query per recipient (apps/chat-api/src/services/message.service.ts#L525-L527, i.e. message.service.ts:525-527). In a group chat of 200 people, that's 200 extra queries. The fix is to calculate the counts in one grouped query, or move the notifications to a background job.
  4. Retries can create duplicate messages. If a phone loses its connection and resends, the same message is saved twice. The usual fix is for the client to send its own message ID, with a unique constraint on it in the database.
  5. Paging by offset breaks in a busy chat. Message lists use page/skip, so new messages arriving while someone scrolls cause skipped or repeated messages. Chat apps normally page by position instead ("messages before ID X"), called cursor pagination.

  • Run your own WebSocket servers (Socket.IO with a Redis adapter, or like Slack). This costs nothing per message but you have to run and scale it.
  • Use another hosted service such as Ably, Stream or Sendbird. Stream and Sendbird also store the messages for you.
  • Stay on PubNub. For your app, I'd keep it and fix items 1–4.

I can start with item 1, having the backend issue per-user PubNub tokens, if you want.

Pattern Learning Guide — Every Pattern in This Review

The review names a pattern for each fix but does not teach it. This section takes each one in turn: what it is, why it exists (what breaks without it), how it works step by step, a concrete example from this chat app, the common gotcha, and where to learn it properly. Related notes already on this site are linked alongside the external references.

Pattern map — at a glance

Suggested learning order

  1. Pattern 0 first — every other fix only makes sense once "source of truth vs. delivery channel" is clear.
  2. Pattern 4 (idempotency) and Pattern 5 (cursor pagination) next — they are small, self-contained, and you can implement each in an afternoon.
  3. Pattern 1 (scoped tokens) — the highest-impact fix in the review, and it builds on basic token authentication.
  4. Pattern 2 (outbox) — the deepest one; it needs idempotency (Pattern 4) on the consumer side, which is why that comes first.
  5. Pattern 3 (N+1 / background jobs) — a performance fix; reuses the queue/worker ideas from Pattern 2.
  6. Pattern 6 — read last, once you know what each option would have to do for you.

Pattern 0 — Source of Truth + Pub/Sub Delivery Channel

What it is. One system (PostgreSQL) holds the authoritative data; a second system (PubNub) only broadcasts change notifications. Clients render from the API, and use pub/sub events as a hint that something changed.

Why it exists. If chat history lived partly in PubNub's history and partly in Postgres, you would have two systems that can disagree, and no rule for which one wins. Making the database the only source of truth means there is always a single answer to "what messages are in this chat?".

How it works, cause → effect.

  1. Client calls POST /chats/{id}/messages.
  2. API inserts the row into Postgres and commits.
  3. After commit, API publishes a small event to channel chat:{id}.
  4. Every subscribed client receives the event and appends the message (or re-fetches).
  5. If step 3 fails, the data is still correct in Postgres — only the "live" part is missing, which is exactly the gap Pattern 2 closes.

Source of truth vs. delivery channel — the difference is that losing the source of truth loses data, while losing the delivery channel only loses timeliness. This does NOT mean the delivery channel can be ignored: a lost event looks to the user like a missing message until they refresh.

Learn it:

  • On this site: Pub/Sub and PubNub · Event Sourcing & CQRS (read models derived from one source of truth)
  • ByteByteGo — Design A Chat System (storage vs. chat-server split)
  • PubNub — Publish/Subscribe basics
  • Azure Architecture Center — Publisher-Subscriber pattern
  • Book: Designing Data-Intensive Applications (Martin Kleppmann), Chapter 11 "Stream Processing" — "systems of record vs. derived data".

Pattern 1 — Per-User Scoped Access Tokens (Least Privilege)

What it is. Instead of every client sharing one key that can subscribe to anything, the backend issues each logged-in user a short-lived token that grants access to only that user's channels — here, the chat:{id} channels they are a member of and user:{id}:notifications.

Why it exists. A client-side key ships inside the app, so anyone can extract it. Without per-user grants, an attacker who knows (or guesses) a chat ID can subscribe to chat:123 and read someone else's conversation, or publish fake events into it. Your API's authorization checks don't help, because the client is talking to PubNub directly, not to your API.

How it works, cause → effect.

  1. User logs in to your API (normal session/JWT).
  2. Client asks your API for a PubNub token.
  3. API looks up which chats the user belongs to and calls PubNub's Access Manager (grantToken, wrapped by the existing grantAccessToken function) with read on those channels and a TTL (e.g. 60 minutes). This call uses the secret key, which only the server holds.
  4. Client initializes PubNub with that token; PubNub rejects subscribe/publish on any channel not in the grant.
  5. Before the TTL runs out — or when the user joins/leaves a chat — the client requests a fresh token.
// server — sketch
const token = await pubnub.grantToken({
  ttl: 60,                           // minutes
  authorized_uuid: user.id,
  resources: {
    channels: {
      [`user:${user.id}:notifications`]: { read: true },
      ...Object.fromEntries(user.chatIds.map(id => [`chat:${id}`, { read: true }]))
    }
  }
});

Gotcha. Granting on a wildcard or pattern such as chat:* defeats the purpose. Also, a token is a snapshot: removing a user from a chat does NOT revoke access until the token expires or you call revokeToken — keep TTLs short.

Learn it:

  • On this site: Authentication Schemes: An Introduction · Cookies, Sessions & JWT · Application Security Fundamentals
  • PubNub — Access Control and JavaScript Access Manager API
  • Ably — Token authentication (same pattern in another provider, well explained)
  • OWASP — Authorization Cheat Sheet (least privilege, deny by default)
  • OWASP API Security Top 10 — Broken Object Level Authorization (what happens without it)

Pattern 2 — Transactional Outbox (and Reconnect Catch-Up)

What it is. A way to reliably "save data and publish an event" when the database and the message broker are different systems. You write the event into an outbox table in the same transaction as the message; a separate relay process reads the outbox and publishes to PubNub, retrying until it succeeds.

Why it exists — the dual-write problem. You cannot commit to Postgres and PubNub atomically. With "insert, then publish":

  1. Insert commits.
  2. Process crashes, deploy restarts the pod, or PubNub returns an error.
  3. The error is only logged, so nothing retries.
  4. Recipients never get the live event; the message only appears after a manual refresh. Nobody is alerted.

How the outbox fixes it.

BEGIN;
  INSERT INTO messages (id, chat_id, sender_id, body) VALUES (...);
  INSERT INTO outbox (id, channel, payload, created_at)
       VALUES (gen_random_uuid(), 'chat:42', '{"type":"message.created","id":"..."}', now());
COMMIT;

-- relay worker, in a loop
SELECT * FROM outbox WHERE published_at IS NULL
 ORDER BY created_at LIMIT 100
 FOR UPDATE SKIP LOCKED;
-- publish each to PubNub, then:
UPDATE outbox SET published_at = now() WHERE id = ANY($1);

Both rows commit or neither does, so "message saved but event forgotten" can no longer happen. The relay can be a polling publisher (the loop above) or transaction log tailing (e.g. Debezium reading Postgres's WAL).

Gotcha — it is at-least-once, not exactly-once. If the relay publishes and then crashes before marking the row, it will publish again. Clients must de-duplicate by message ID (see Pattern 4). This does NOT remove the need for reconnect catch-up either: an event published while a phone was offline is still missed by that phone.

Reconnect catch-up (the cheaper fallback). On every (re)connect, the client calls GET /chats/{id}/messages?after={lastSeenId} and merges the result. This covers both lost publishes and time spent offline, and it is worth doing even with an outbox.

Learn it:

Pattern 3 — Avoid N+1 Queries; Move Fan-Out to a Background Job

What it is. An N+1 query is running one query to get a list, then one more query per item in that list. Here the list is "recipients of this message" and the per-item query is "unread count for this recipient". Fan-out is the work of delivering one message to many recipients.

Why it exists. Latency adds up in sequence: 8–10 calls before the response, plus 200 unread-count queries in a 200-person group, all while the sender waits for "sent". It also multiplies database load by group size, so the busiest chats hurt the most.

Fix A — one grouped query.

-- instead of 200 × "SELECT count(*) ... WHERE user_id = $1"
SELECT m.user_id, count(msg.id) AS unread
  FROM chat_members m
  JOIN messages msg
    ON msg.chat_id = m.chat_id
   AND msg.id > m.last_read_message_id
 WHERE m.chat_id = $1
 GROUP BY m.user_id;

Better still, keep a denormalized unread_count column on chat_members and increment it for all members in one UPDATE ... WHERE chat_id = $1 AND user_id <> $sender.

Fix B — background job. The request path only saves the message (and outbox row) and returns. A worker picks up a "message.created" job and does the unread counts, per-user notifications, and push notifications off the critical path. Cause → effect: the sender's latency no longer depends on group size; spikes are absorbed by the queue instead of the database.

Gotcha. Moving work to a background job does NOT make it cheaper — it only moves it off the user's request. You still want Fix A inside the job. And background jobs retry, so they must be idempotent (Pattern 4).

Learn it:

  • On this site: Query Plans and Optimization · Indexing · SQS Overview · SQS Use Cases

  • PostgreSQL — GROUP BY and HAVING
  • Azure Architecture Center — Queue-Based Load Leveling and Background jobs guidance
  • BullMQ docs (Redis-backed job queue for a Node/TypeScript API like chat-api)
  • Fan-out on write vs. on read: ByteByteGo's "Design a News Feed System" chapter covers the same trade-off for feeds.

Pattern 4 — Idempotency Key + Unique Constraint

What it is. An operation is idempotent if doing it twice has the same effect as doing it once. An idempotency key is an ID the client generates once per logical action and sends with every retry of it, so the server can recognize repeats.

Why it exists. Mobile networks drop responses, not just requests. Cause → effect: the phone sends the message → the server saves it → the response is lost on a flaky connection → the phone assumes failure and resends → the server saves it again → the chat shows the message twice.

How it works.

  1. Client generates client_message_id (a UUID) when the user presses Send, and stores it with the pending message.
  2. Every retry sends the same client_message_id.
  3. The database enforces uniqueness, so the second insert cannot create a row.
  4. On conflict, the server returns the already-saved message, so the client sees success either way.
ALTER TABLE messages ADD COLUMN client_message_id uuid;
CREATE UNIQUE INDEX messages_sender_client_id_uq
    ON messages (sender_id, client_message_id);

INSERT INTO messages (chat_id, sender_id, client_message_id, body)
VALUES ($1, $2, $3, $4)
ON CONFLICT (sender_id, client_message_id) DO NOTHING
RETURNING *;
-- if no row returned, SELECT the existing one and return it

Gotcha. Checking "does it exist?" in application code and then inserting is NOT enough — two concurrent retries can both pass the check. The unique constraint is what makes it safe. The same client ID also lets the client match the live PubNub event to its own optimistic "sending…" bubble instead of showing it twice.

Learn it:

  • On this site: Microservice Resilience Patterns · Queue Methods · Transactions and Concurrency
  • AWS Builders' Library — Making retries safe with idempotent APIs
  • Stripe — Designing robust and predictable APIs with idempotency and Stripe API — Idempotent requests
  • microservices.io — Idempotent Consumer (the consumer side of Pattern 2)
  • Enterprise Integration Patterns — Idempotent Receiver
  • PostgreSQL — INSERT ... ON CONFLICT

Pattern 5 — Cursor (Keyset) Pagination

What it is. Paging by a cursor — "give me 50 messages older than message X" — instead of by an offset — "skip 100 rows, give me the next 50".

Why it exists — offset vs. cursor, the difference is that an offset counts positions from the newest message, and positions shift every time a new message arrives; a cursor names a fixed message, which doesn't move.

Cause → effect with offsets.

  1. User loads page 1 (newest 50, skip=0).
  2. 3 new messages arrive.
  3. User scrolls up; client requests skip=50.
  4. Everything shifted down by 3, so the first 3 messages of the new page are ones the user already saw → repeated messages. (Deletions cause the opposite: skipped messages.)
  5. Also, OFFSET 10000 makes Postgres read and discard 10,000 rows, so deep scrolling gets slower.
-- offset (current)
SELECT * FROM messages WHERE chat_id = $1
 ORDER BY created_at DESC LIMIT 50 OFFSET $2;

-- cursor / keyset (fix)
SELECT * FROM messages
 WHERE chat_id = $1
   AND (created_at, id) < ($2, $3)      -- the last message the client has
 ORDER BY created_at DESC, id DESC
 LIMIT 50;

CREATE INDEX messages_chat_cursor_idx ON messages (chat_id, created_at DESC, id DESC);

The API returns a nextCursor (often base64 of created_at|id) and the client sends it back as ?before=. The same shape with > gives ?after= for reconnect catch-up (Pattern 2).

Gotcha. The cursor must be unique — created_at alone can tie, so add id as a tie-breaker. Cursor pagination does NOT support "jump to page 37"; for chat that's fine because users scroll, they don't jump.

Learn it:

  • On this site: Indexing · API Planning · GraphQL vs REST (GraphQL "connections" are cursor pagination)
  • Use The Index, Luke — "We need tool support for keyset pagination" (no-offset) and Paging Through Results
  • Slack Engineering — Evolving API Pagination at Slack
  • Stripe API — Pagination (starting_after / ending_before)
  • GraphQL — Pagination
