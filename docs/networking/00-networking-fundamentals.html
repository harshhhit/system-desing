Why this layer matters for system design

Every "should we cache this," "how many round trips does this take," and "why is this API slow from one region and fast from another" question ultimately comes down to what's happening below the application layer — how a connection gets established, how a name becomes an address, and how much of that has to happen again for every single request. This page is the plumbing that Client-Server Model, End to End and Caching & CDN Fundamentals both sit on top of.

The TCP handshake

  1. SYN — client sends a synchronize packet with an initial sequence number, proposing a connection.
  2. SYN-ACK — server acknowledges and sends its own sequence number back.
  3. ACK — client acknowledges the server's number; the connection is now open.

That's one full round trip before a single byte of actual data (or TLS negotiation) can begin — the reason connection reuse (HTTP keep-alive, connection pooling to a database — see Connection Management and Database Proxies) matters so much: paying the handshake cost once and reusing the connection for many requests is far cheaper than paying it per request. Closing a connection (FIN/ACK from each side, four steps) has its own smaller cost, and a server holding many connections in that teardown state is a real resource-exhaustion concern under high request-per-second load.

DNS resolution, end to end

Turning example.com into an IP address before a TCP handshake can even start:

  1. Check the browser's own DNS cache, then the OS cache — if the name was resolved recently and its TTL hasn't expired, stop here.
  2. Query a recursive resolver (the ISP's, or a public one like 8.8.8.8/1.1.1.1) which does the rest of the walk on the client's behalf.
  3. Resolver asks a root server — "who handles .com?" — gets back the TLD server's address.
  4. Resolver asks the TLD server — "who handles example.com?" — gets back the domain's authoritative name server.
  5. Resolver asks the authoritative server for the actual A/AAAA record, caches the answer for its TTL, and returns it to the client.

Every one of those hops is a full round trip the first time (a "cold" lookup can add tens to hundreds of milliseconds), which is why DNS caching and short-but-not-too-short TTLs matter, and why CDN/GSLB routing (see Load Balancing) exploits this same lookup to return a different, nearer IP depending on where the query came from.

The TLS handshake

HTTPS is HTTP over a TCP connection that's had TLS negotiated on top of it first — so a fresh HTTPS request pays for the TCP handshake and the TLS handshake before any HTTP request/response happens.

  • ClientHello — client sends the TLS versions and cipher suites it supports, plus a random value.
  • ServerHello + certificate — server picks a cipher suite, sends its certificate (proving identity, signed by a CA the client trusts) and its own random value.
  • Key exchange — both sides derive the same shared symmetric session key without ever sending it over the wire (Diffie-Hellman in practice), which then encrypts everything else in the session — symmetric crypto is far cheaper than the asymmetric crypto used just to set that key up.
  • Finished — both sides confirm the handshake succeeded; encrypted application data (the actual HTTP request) can now flow.

TLS 1.3 cut this from two round trips to one (and offers a "0-RTT" resumption mode for returning clients) — one of the concrete reasons upgrading matters, not just a version-number bump. Session resumption (a session ticket/ID from a previous connection) skips the full handshake on reconnect entirely, which is why a client that closes and reopens connections to the same host repeatedly is far more expensive than one that keeps a connection alive.

WebSockets vs. gRPC vs. plain HTTP

Pick by direction of data flow, then by audience

If only the client ever initiates, plain HTTP is enough. If the server needs to push without being asked, that's WebSockets (browser-facing) or gRPC streaming (service-to-service). If it's internal microservice traffic where every caller controls their own client, gRPC's schema and binary framing usually win over hand-rolled JSON HTTP.

Interview checklist

  • Separate the three costs of "a fresh HTTPS request to a new host": DNS lookup, TCP handshake, TLS handshake — and know that connection reuse and session resumption are how real systems avoid paying them repeatedly.
  • Justify TCP vs. UDP by whether ordered, guaranteed delivery is actually required, not by default.
  • If the design streams or pushes data to a client, name WebSockets/gRPC explicitly and say why plain request/response polling doesn't fit.
  • Know that HTTP/2 fixed application-level head-of-line blocking but not the TCP-level one — and that's specifically what HTTP/3 (QUIC) fixes.
  • DNS and CDN routing are the same trick — the first lookup can point a client at a different, nearer server depending on where the query originated.
