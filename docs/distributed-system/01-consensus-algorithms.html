Consensus Algorithms: Raft & Paxos

Quorums, Paxos's prepare/accept phases, Raft's leader election and log replication, split-brain, and how etcd/ZooKeeper use this in practice.

Interview Answer — What Is a Consensus Algorithm?

A consensus algorithm is a protocol that lets a group of nodes agree on a single value — who the leader is, what the next entry in a shared log is, whether a write is committed — even when some nodes crash or messages are delayed or lost. Paxos and Raft are the two best-known consensus algorithms; Raft is used by etcd, Consul, and CockroachDB.

Consensus exists because replicating data across machines is only useful if every replica applies the same changes in the same order. Without it, a crashed node or a network partition leaves the cluster unable to answer "which value is actually true?", and two halves of a cluster can each accept conflicting writes — split-brain. Every distributed lock, leader election, and replicated database log depends on solving this.

Both algorithms rely on a majority quorum: a value is committed only once ⌊N/2⌋ + 1 of N nodes accept it. Any two majorities overlap in at least one node, so a later majority can never "forget" a committed value. In Raft, the cause → effect chain for a write is: the client sends the write to the leader → the leader appends it to its log and replicates it to followers → once a majority have stored it, the entry is committed and applied → if the leader dies, followers time out, hold an election, and only a node with an up-to-date log can win. As a consequence, an N-node cluster tolerates ⌊(N−1)/2⌋ failures — 3 nodes tolerate 1, 5 tolerate 2.

Simple interview version

"A consensus algorithm lets a cluster of nodes agree on one value, or one ordered log of values, even when some nodes fail. Raft and Paxos both do it with majority quorums: a write is committed only after a majority of nodes accept it, and because any two majorities overlap, a committed value can't be lost. Raft elects a leader that handles all writes and replicates them to followers. A cluster of N nodes survives ⌊(N−1)/2⌋ failures, which is why clusters like etcd run with 3 or 5 nodes."

One important interview follow-up

Q: Would a 4-node cluster be more fault-tolerant than a 3-node cluster?

A: No. A 4-node cluster needs a majority of 3, so it still tolerates only 1 failure — the same as 3 nodes — while adding one more machine that must acknowledge writes. It is also worse in a partition: a 2–2 split leaves neither side with a majority, so the whole cluster stops accepting writes. This is why consensus clusters use odd sizes (3, 5, 7); going from 3 to 5 is what raises fault tolerance from 1 failure to 2.

Why consensus is a hard problem

Consensus means getting a set of nodes to agree on a single value — "who's the leader," "what's the next entry in this log," "did this write commit" — even though nodes can crash, restart, and messages can be delayed or lost. It's the foundation underneath leader election, distributed locks, and any "replicated log" a cluster uses to stay consistent. Without it, a network partition or a crashed node leaves the question "which answer is actually true?" unanswerable — which is exactly the failure mode called split-brain, covered below.

Quorums — the mechanism both algorithms are built on

Instead of requiring every node to agree (impossible to guarantee once nodes can fail), consensus algorithms require a majority — ⌊N/2⌋ + 1 out of N nodes — to agree before a value is considered committed.

  • Any two majorities out of the same N nodes must overlap by at least one node — that overlap is what guarantees a new majority can't "forget" what a previous majority already agreed on.
  • This generalizes to the read/write quorum model from replicated databases (W + R > N guarantees every read overlaps the last write) — see CAP Theorem Questions for the read side of this same idea.
  • Because a majority is required, a cluster of N nodes tolerates ⌊(N-1)/2⌋ failures — 5 nodes tolerate 2 failures, which is why odd cluster sizes (3, 5, 7) are the norm: an even-sized cluster pays for an extra node without tolerating an extra failure.

Paxos

The original proof that consensus is solvable despite failures — correct, but notoriously difficult to reason about and implement (its own author called explaining it a fight).

  • Roles: proposers (suggest values), acceptors (vote on them), learners (find out what was decided). A node commonly plays more than one role.
  • Phase 1 — Prepare/Promise: a proposer asks acceptors to promise not to accept any proposal older than this one; a majority of promises lets it proceed.
  • Phase 2 — Accept/Accepted: the proposer sends the actual value; if a majority accepts it, it's chosen.
  • Multi-Paxos — running the full two-phase protocol per value is expensive, so real systems elect a stable leader/distinguished proposer and skip straight to phase 2 for a whole stream of values, only falling back to phase 1 on leader change. This is the version actually used in production (e.g. inside Google's Chubby, and conceptually inside ZooKeeper's Zab).

Raft

Designed specifically to be understandable — same guarantees as Multi-Paxos, decomposed into three separable sub-problems.

  • Leader election — time is divided into terms; nodes start as followers, and if a follower doesn't hear from a leader within a randomized election timeout, it becomes a candidate and requests votes. The randomization is deliberate — it makes two nodes becoming candidates at the exact same moment (a split vote) unlikely, so elections converge quickly.
  • Log replication — once elected, the leader is the only node that accepts writes; it appends each entry to its own log, replicates it to followers, and considers the entry committed once a majority have stored it — only then is it applied and acknowledged to the client.
  • Safety — a candidate can only win an election if its log is at least as up-to-date as a majority of the cluster's, which guarantees a new leader can never "lose" a previously committed entry.

The practical difference is smaller than it looks

Both provide the same guarantee (linearizable agreement via majority quorum) and both end up with a stable leader in real deployments — Raft just makes that leader concept explicit and mandatory from the start instead of arriving at it as an optimization. For an interview, knowing why a leader + majority quorum gives safety matters more than reciting either algorithm's message sequence from memory.

Split-brain — and how quorum prevents it

A network partition splits a cluster into two groups, each of which can still talk to itself. If both groups kept accepting writes independently as if they were the whole cluster, you'd get two diverging, inconsistent copies of the data — that's split-brain.

  • Quorum-based consensus prevents this by construction: only the partition that contains a majority of nodes can elect a leader or commit a write. The minority partition can see that it doesn't have a majority and correctly refuses to accept writes, rather than guessing.
  • This is a direct, deliberate availability trade for consistency — the minority side becomes unavailable rather than risk serving/accepting inconsistent data, which is the CP choice in CAP terms.
  • It's also why a 2-node cluster can't safely tolerate any failure: if the link between them drops, neither side has a majority of 2, so the whole cluster stops accepting writes — a concrete reason minimum viable consensus clusters are sized 3, not 2.

Where this shows up in real systems

  • etcd (Raft) — the source of truth for the entire Kubernetes control plane; see etcd Deep Dive and Leader Election: HA for Controller Manager & Scheduler for how kube-controller-manager and kube-scheduler themselves use a Raft-backed lease in etcd to elect a single active instance.
  • ZooKeeper (Zab, a Paxos-family protocol) — historically the coordination service behind Kafka (partition leader election, cluster metadata) before Kafka's own KRaft mode replaced it.
  • Distributed databases — Spanner and CockroachDB use Paxos/Raft respectively per data shard to agree on the order of writes within that shard; see Replication & Distributed Data Roadmap for how this fits into the broader replication picture.

Interview checklist

  • State the core mechanism in one sentence: majority quorum + overlapping majorities is what makes agreement safe despite failures.
  • Know the failure-tolerance math: an N-node cluster tolerates ⌊(N-1)/2⌋ failures, and explain why odd sizes are chosen.
  • Explain split-brain and why quorum prevents it, not just that it does — the minority partition can detect it lacks a majority and self-refuses.
  • Be ready to name a real system (etcd/Raft is the easiest, given it's already covered in the Kubernetes section) and say specifically what it uses consensus for (leader election vs. a replicated log of configuration/state).
