Consistent Hashing

Why mod-N hashing breaks on resize, the hash ring, virtual nodes, rebalancing cost, and where this shows up in databases, caches, load balancers, and CDNs.

The problem: naive hashing doesn't survive a resize

The obvious way to shard N keys across M servers is server = hash(key) % M. It's simple and spreads load evenly — right up until M changes. Add or remove a single server and hash(key) % M gives a different answer for almost every key, not just the keys that "belong" to the changed server — going from 4 servers to 5 remaps roughly (M-1)/M, i.e. about 80%, of all keys. For a cache, that's a near-total cache wipe (a stampede — see Caching & CDN Fundamentals) every time you scale. For a sharded database, it means moving nearly all the data on every resize.

Consistent hashing: the ring

  1. Hash both the servers and the keys onto the same circular space (e.g. a 32- or 64-bit integer range, wrapping back to 0 — a "ring").
  2. Each key belongs to the first server found walking clockwise from that key's position on the ring.
  3. Adding a server only takes over the slice of the ring between it and the next server clockwise — every other key on the ring is untouched.
  4. Removing a server hands its slice to the next server clockwise — again, nothing else on the ring moves.

The result: a resize moves roughly 1/M of the keys instead of nearly all of them — the exact problem mod-N hashing has.

Virtual nodes — fixing uneven distribution

With only a handful of physical servers hashed to a handful of points on the ring, the slices between them can be very uneven by chance — one server might own 5% of the ring, another 40%. Virtual nodes fix this: each physical server is hashed onto the ring not once but many times (e.g. 100–200 points, each representing the same physical server under a different virtual identity).

  • More points per server means the law of large numbers smooths out the slice sizes — load balances far more evenly across physical servers.
  • When a server joins or leaves, its virtual points are scattered around the whole ring, so the keys it picks up or gives away are spread across many other servers roughly evenly, rather than dumping the entire load onto whichever single physical neighbor happens to be next on the ring.
  • Virtual nodes also make it easy to give a more powerful server proportionally more of the ring — just assign it more virtual points, the same idea as weighted load balancing (see Load Balancing).

Rebalancing cost, compared

SchemeKeys remapped on a resizeLoad distribution
Mod-N hashing (hash(key) % M)Nearly all keys — (M-1)/MEven, but only while M never changes
Consistent hashing, no virtual nodes~1/M of keysCan be uneven — a server's slice size depends on the luck of its single hash position
Consistent hashing with virtual nodesStill ~1/M, but spread across many servers instead of one neighborEven — smoothed by having many points per server

Where this shows up in real systems

  • Distributed data stores — DynamoDB and Cassandra both partition data around a consistent-hash ring so nodes can be added or removed without a full data reshuffle; see Partitioning for the general sharding picture this slots into.
  • Cache client sharding — a Memcached client library hashes keys across a pool of cache servers this way, so losing one server only invalidates its share of the cache instead of scrambling every key's server assignment (see Caching & CDN Fundamentals).
  • Load balancers — the "IP hash / consistent hashing" algorithm in Load Balancing is this same ring, used to keep a client pinned to the same backend without a sticky-session cookie, while still surviving backend pool changes gracefully.
  • CDN routing — request routing to edge nodes/PoPs uses the same principle so that adding or removing an edge node doesn't invalidate every cache key's assignment across the whole network at once.

Interview checklist

  • Lead with the concrete failure of mod-N hashing (~80%+ of keys remapped on one resize) — that's the motivating problem, not an aside.
  • State the ring mechanism and the ~1/M rebalancing result in one breath — that's the actual answer to "why consistent hashing."
  • Always mention virtual nodes explicitly — "consistent hashing" without virtual nodes is a common half-answer; the even-distribution property specifically depends on them.
  • Be ready to name where it's used: sharded databases, cache client routing, load-balancer session affinity, CDN edge routing — the same idea, four different layers.
