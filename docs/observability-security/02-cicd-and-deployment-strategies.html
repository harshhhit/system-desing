CI/CD & Deployment Strategies

CI vs CD vs continuous deployment, a typical pipeline, blue-green vs canary vs rolling deploys, the testing pyramid, feature flags, and rollback strategy.

What you'll learn

By the end of this page you will be able to:

  • Distinguish CI, continuous delivery and continuous deployment precisely
  • Describe the stages of a typical pipeline and why each exists
  • Choose between recreate, rolling, blue-green and canary
  • Justify the shape of the testing pyramid
  • Use feature flags to separate deploy from release
  • Plan a rollback that survives database migrations

Why CI/CD Exists

CI/CD is an automated pipeline that takes every code change from commit to a production-ready (or production-deployed) release. It exists because manual, infrequent releases are risky: large batches of changes are hard to test and hard to debug when they break, and hand-run deploy steps are easy to get wrong. Small, frequent, automated releases make each change easy to verify and easy to undo.

💡 Important

Build the artifact once. The exact image that passed tests in staging is the one promoted to production — rebuilding per environment means production runs something that was never tested.

CI, CD, and Continuous Deployment — Three Different Promises

  • Continuous Integration (CI) — every code change is automatically built and tested as soon as it's pushed, so integration problems (two people's changes conflicting, a break nobody noticed) surface in minutes, not at the end of a long-lived branch.
  • Continuous Delivery (CD) — every change that passes CI is automatically packaged into a deployable artifact and is always in a releasable state — but a human still decides when to actually ship it.
  • Continuous Deployment — the same pipeline, minus the manual gate: every change that passes all checks deploys to production automatically. The distinction between this and continuous delivery is entirely about whether a human clicks "deploy," not about the pipeline itself.
TermMeaning
ArtifactThe versioned, immutable output of the build (usually a container image tagged with the commit SHA).
EnvironmentA place the artifact runs: dev, staging, production.
Deploy vs. releaseDeploy = new code is running; release = users get the new behaviour. Feature flags separate them.
Blast radiusHow many users a bad change can affect before it is stopped.

A Typical Pipeline

flowchart LR C["git push"] --> B["Build
immutable image:sha"] B --> T["Test
unit → integration"] T --> Q["Security / quality gates"] Q --> S["Deploy to staging
+ smoke / e2e"] S --> G{"Manual approval?
(delivery: yes,
deployment: no)"} G --> P["Deploy to prod
rolling · blue-green · canary"] P --> V["Verify: SLO metrics
auto-rollback on breach"]

One artifact flows left to right; any failed stage stops it.

  1. Build — compile/bundle the code, produce a versioned, immutable artifact (a container image is the common case today).
  2. Test — run the automated test suite (see the testing pyramid below) against the build; fail fast and stop the pipeline on the first failure rather than deploying anyway.
  3. Security/quality gates — dependency vulnerability scanning, static analysis, license checks — automated versions of the checks in Application Security Fundamentals's "vulnerable/outdated components" row.
  4. Deploy — push the artifact to an environment using one of the strategies below, typically staging first, then production.
  5. Verify — automated smoke tests and/or a monitored rollout window (see Observability Fundamentals) before calling the deploy complete.

Deployment Strategies

StrategyHow it worksRollback speedCost / complexity
RecreateStop the old version entirely, then start the new oneSlow — redeploy the old version from scratchSimplest, but guarantees downtime during the swap
RollingReplace instances a few at a time, waiting for each batch to become healthy before moving to the nextModerate — roll forward with the old version, same gradual processNo extra infrastructure needed; both versions briefly serve traffic side by side, so both must be compatible with the current data/API contract
Blue-greenDeploy the new version ("green") fully, alongside the still-running old version ("blue"); flip the load balancer/router to green all at once once it's verifiedFast — flip the router back to blueNeeds double the running capacity during the switch, but the cutover itself is instant and the rollback is just as instant
CanaryRoute a small percentage of real traffic to the new version, watch its error rate/latency, then progressively increase the percentage if it looks healthyFast — route the canary's traffic slice back to the old versionMost operationally involved (needs traffic-splitting and close monitoring), but limits the blast radius of a bad deploy to a small slice of real users instead of all of them
These aren't mutually exclusive

A canary deploy is commonly done as a rolling or blue-green deploy with an extra "watch a small slice first" gate in front of it — they answer different questions (how do old/new versions coexist during rollout vs. how much real traffic sees the new version before it's trusted) and often combine.

A canary rollout, step by step

  1. Deploy the new version next to the old; route 5% of traffic to it.
  2. Compare the canary's error rate and p99 latency against the old version over a fixed window.
  3. Healthy → 25% → 50% → 100%, re-checking at each step.
  4. Unhealthy at any step → route the slice back to the old version; only 5–25% of users were exposed, briefly.

🧠 Think about it

During a rolling deploy, v1 and v2 serve traffic at the same time. What breaks if v2 starts writing a new JSON field that v1's code rejects? (v1 instances fail on records v2 wrote — so every change must be compatible with the previous version in both directions.)

The Testing Pyramid

  • Unit tests — the base of the pyramid: fast, isolated, test one function/class in isolation from the network and other services. Should be the large majority of the suite because they're cheap to run and pinpoint failures precisely.
  • Integration tests — verify that a service correctly talks to its real (or realistically faked) dependencies — a database, a queue. Fewer than unit tests; slower, but catch the class of bug unit tests structurally can't (a wrong SQL query that's syntactically valid, a wire-format mismatch).
  • End-to-end tests — drive the whole system through a real user-facing flow. The fewest of the three — slow, often flaky, expensive to maintain — reserved for the handful of flows that matter most (checkout, login), not exhaustive coverage.
  • Contract testing — for microservices specifically: instead of a slow, brittle e2e test spanning every service, each consumer and provider of an API independently verify against a shared contract (e.g. Pact) that their expectations still match, without either side needing the other actually running.

Feature Flags

Decouple deploying code from releasing a feature: ship the new code path behind a flag that's off by default, deploy it safely (it has zero behavioral effect while off), then flip the flag on — for everyone at once, for a percentage (a form of canarying at the feature level rather than the infrastructure level), or for specific users. This also makes "rollback" instant and cheap for a bad feature specifically: flip the flag off, no redeploy needed at all.

Rollback Strategy

  • Decide the rollback mechanism before deploying, not while an incident is already happening — for infrastructure-level issues that's redeploying the previous artifact (fast with blue-green, slower with recreate); for a bad feature specifically, a feature flag flip is faster than either.
  • Database migrations complicate rollback the most: a migration that's already run and been written to by the new code often can't simply be reversed once real writes have happened — favor backward-compatible, additive migrations (add a column, don't rename/drop one in the same release) so the previous code version can still run against the new schema if a rollback is needed.

Expand and contract, for a column rename

  1. Release 1 (expand): add full_name; code writes both name and full_name, reads name. Backfill old rows.
  2. Release 2: code reads full_name, still writes both. Rolling back to release 1 is safe.
  3. Release 3 (contract): stop writing name; a later migration drops it once no running version uses it.

⚠️ Common mistake

Shipping a destructive migration (drop/rename) in the same release as the code that needs it. The moment the migration runs, the previous version can no longer start — so "instant rollback" no longer exists.

Implementation

A minimal pipeline (GitHub Actions)

name: ci
on: [push]
jobs:
  build-test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: make test
      - run: docker build -t registry.example.com/api:${{ github.sha }} .
      - run: docker push registry.example.com/api:${{ github.sha }}
  • on: [push] — every push triggers CI.
  • make test before docker build — fail fast; nothing is published if tests fail.
  • Tag :${{ github.sha }} — the immutable artifact; deploys reference this exact tag, never latest.

Rolling update settings (Kubernetes)

spec:
  replicas: 6
  strategy:
    type: RollingUpdate
    rollingUpdate:
      maxUnavailable: 1
      maxSurge: 1
  • maxUnavailable: 1 — at most one Pod below the desired count during the rollout (capacity stays ≥ 5/6).
  • maxSurge: 1 — at most one extra Pod above the desired count, so the rollout needs little spare capacity.
  • A new Pod only counts as available once its readiness probe passes — that is the "wait for each batch to become healthy" step.
kubectl rollout status deployment/api
kubectl rollout undo deployment/api
  • rollout status — waits and reports whether the rollout completed.
  • rollout undo — rolls back to the previous ReplicaSet (the previous artifact).

Signals to watch

  • Deploy frequency and lead time (commit → production) — how fast changes flow.
  • Change failure rate — % of deploys causing incidents or rollbacks.
  • Time to restore — how fast a bad change is undone.
  • During a rollout: error rate and p99 of new vs. old version, side by side.

🔥 Production insight

Annotate dashboards with deploy events. The first question in most incidents is "what changed?" — a vertical line on the latency graph at 15:08 labelled "api v2.41" answers it in seconds.

Security of the Pipeline

  • The pipeline can deploy to production, so it is a production credential. Least-privilege CI tokens, short-lived cloud credentials (OIDC) instead of long-lived keys in CI secrets.
  • Supply chain: pin dependency and action versions, sign images, verify signatures at deploy time — the "software/data integrity failures" category in OWASP Top 10.
  • Scan in the pipeline: dependencies, container images, committed secrets.
  • Protect the main branch: required reviews and passing checks before merge.

Best Practices

Do

  • Build once, promote the same artifact — what you tested is what you ship.
  • Keep changes small and frequent — small diffs are easy to verify and to revert.
  • Plan the rollback before the deploy — and make migrations backward-compatible.
  • Gate production on SLO metrics, not just on tests passing.
  • Use feature flags for risky behaviour changes — and remove stale flags.

Avoid

  • Deploying latest — you can't tell what's running or roll back to it.
  • Big-bang releases of many changes at once.
  • An inverted pyramid of slow, flaky e2e tests.
  • Long-lived CI credentials with broad production access.

Interview Answer — What Is CI/CD?

CI/CD is an automated pipeline that takes every code change from commit to a production-ready (or production-deployed) release. Continuous Integration (CI) builds and tests every change as soon as it is pushed. Continuous Delivery (CD) additionally packages every passing change into a deployable artifact, so the code is always releasable and a human decides when to ship. Continuous Deployment removes that manual gate, so every change that passes all checks goes to production automatically.

It exists because manual, infrequent releases are risky: large batches of changes are hard to test and hard to debug when they break, and hand-run deploy steps are easy to get wrong. With a pipeline, the cause → effect chain is: a developer pushes a change → the pipeline builds one immutable artifact (typically a container image) → tests and security scans run and stop the pipeline on the first failure → the same artifact is deployed to staging, then production → automated checks verify the rollout.

How the new version replaces the old one is the deployment strategy: rolling (replace instances in batches), blue-green (run the full new version beside the old and switch traffic at once), or canary (send a small share of real traffic to the new version and increase it while metrics stay healthy). Feature flags add a second layer by separating deploying code from releasing a feature.

Simple interview version

"CI means every change is automatically built and tested on push. Continuous delivery means every passing change is packaged into an artifact that's always ready to release, and continuous deployment goes further and ships it to production automatically. The pipeline builds one immutable artifact, tests and scans it, deploys it with a strategy like rolling, blue-green, or canary, and verifies it with monitoring. Feature flags let me deploy code dark and turn features on separately, and I plan the rollback before I deploy."

One important interview follow-up

Q: With blue-green deployment, can I always roll back instantly by switching traffic back to blue?

A: Only for the application code. Switching the router back is instant, but if the release ran a database migration — dropped a column, renamed a field, changed a format — and green has already written real data in the new shape, the old blue version may no longer work against that database. That is why schema changes should be backward-compatible and additive (the expand-and-contract pattern: add the new column, deploy code that handles both, remove the old column in a later release), so both versions can run against the same schema. See Rollback strategy above.

Interview checklist

  • Distinguish CI (build+test on every change) from CD (always releasable) from continuous deployment (auto-ships) precisely — these get conflated constantly, and being precise is a cheap, clear signal.
  • Pick a deployment strategy by the actual constraint: zero extra infrastructure → rolling; instant, safe cutover → blue-green; minimizing blast radius of an unknown-risk change → canary.
  • Know the testing pyramid's shape (many unit, fewer integration, fewest e2e) and be ready to justify why that shape, not just name the layers.
  • If the design involves a schema change, mention backward-compatible migrations specifically — it's the detail that makes a rollback plan actually credible.

Practice questions

Continuous delivery vs. continuous deployment?

Same pipeline; delivery keeps every change releasable but a human approves production, deployment ships automatically when checks pass.

Why should the pipeline build one immutable artifact?

So the exact thing tested is the thing deployed, and rollback means redeploying a known previous artifact.

Why is the testing pyramid shaped that way?

Unit tests are fast, cheap and precise, so most coverage goes there; integration tests catch wiring bugs; e2e tests are slow and flaky, so keep only the critical flows.

When would you pick blue-green over canary?

Blue-green when you want an instant, all-at-once cutover and rollback and can afford double capacity; canary when the change's risk is unknown and you want to limit blast radius with real traffic.

What constraint does a rolling deploy put on your code?

Old and new versions serve traffic simultaneously, so APIs, message formats and schema must be compatible across both versions.

How do feature flags change rollback?

A bad feature is turned off by flipping the flag — no redeploy. Deploy and release become separate decisions.

Why can't blue-green always roll back instantly?

Destructive migrations plus new-shape writes mean the old version may not run against the database any more. Use expand-and-contract migrations.

How would you automate canary analysis?

Compare the canary's SLIs (error ratio, p99) against the baseline over fixed windows with thresholds; promote on pass, auto-rollback on breach, and require enough traffic for the comparison to be meaningful.

What makes a CI/CD pipeline a security risk, and how do you reduce it?

It holds credentials that can deploy to production and executes third-party code. Use short-lived OIDC credentials, least privilege, pinned/signed dependencies and images, and protected branches.

Error rate doubles 3 minutes after a deploy. What do you do first?

Roll back (or flip the flag) immediately to restore service, then investigate with the deploy diff, traces and logs. Restore first, debug second.

You need to rename a heavily used column with zero downtime. Plan it.

Expand: add the new column and dual-write, backfill. Switch reads to the new column. Contract: stop writing the old one, drop it in a later release once no version uses it. Each step is independently rollback-safe.

Deploys pass staging but fail in production regularly. What do you investigate?

Whether the same artifact digest is promoted, config/secret drift between environments, production-only dependencies or data volume, and whether staging tests cover the failing paths.

What Should I Remember?

  1. CI = build + test every change; continuous delivery = always releasable; continuous deployment = ships automatically.
  2. Build one immutable artifact and promote it through environments.
  3. Rolling (no extra infra), blue-green (instant switch), canary (small blast radius) — and they combine.
  4. Many unit tests, fewer integration, fewest e2e; contract tests between services.
  5. Feature flags separate deploy from release and make feature rollback instant.
  6. Migrations decide whether rollback is real — expand and contract.
