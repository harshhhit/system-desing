CI, CD, and continuous deployment — three different promises

  • Continuous Integration (CI) — every code change is automatically built and tested as soon as it's pushed, so integration problems (two people's changes conflicting, a break nobody noticed) surface in minutes, not at the end of a long-lived branch.
  • Continuous Delivery (CD) — every change that passes CI is automatically packaged into a deployable artifact and is always in a releasable state — but a human still decides when to actually ship it.
  • Continuous Deployment — the same pipeline, minus the manual gate: every change that passes all checks deploys to production automatically. The distinction between this and continuous delivery is entirely about whether a human clicks "deploy," not about the pipeline itself.

A typical pipeline

  1. Build — compile/bundle the code, produce a versioned, immutable artifact (a container image is the common case today).
  2. Test — run the automated test suite (see the testing pyramid below) against the build; fail fast and stop the pipeline on the first failure rather than deploying anyway.
  3. Security/quality gates — dependency vulnerability scanning, static analysis, license checks — automated versions of the checks in Application Security Fundamentals's "vulnerable/outdated components" row.
  4. Deploy — push the artifact to an environment using one of the strategies below, typically staging first, then production.
  5. Verify — automated smoke tests and/or a monitored rollout window (see Observability Fundamentals) before calling the deploy complete.

Deployment strategies

StrategyHow it worksRollback speedCost / complexity
RecreateStop the old version entirely, then start the new oneSlow — redeploy the old version from scratchSimplest, but guarantees downtime during the swap
RollingReplace instances a few at a time, waiting for each batch to become healthy before moving to the nextModerate — roll forward with the old version, same gradual processNo extra infrastructure needed; both versions briefly serve traffic side by side, so both must be compatible with the current data/API contract
Blue-greenDeploy the new version ("green") fully, alongside the still-running old version ("blue"); flip the load balancer/router to green all at once once it's verifiedFast — flip the router back to blueNeeds double the running capacity during the switch, but the cutover itself is instant and the rollback is just as instant
CanaryRoute a small percentage of real traffic to the new version, watch its error rate/latency, then progressively increase the percentage if it looks healthyFast — route the canary's traffic slice back to the old versionMost operationally involved (needs traffic-splitting and close monitoring), but limits the blast radius of a bad deploy to a small slice of real users instead of all of them
These aren't mutually exclusive

A canary deploy is commonly done as a rolling or blue-green deploy with an extra "watch a small slice first" gate in front of it — they answer different questions (how do old/new versions coexist during rollout vs. how much real traffic sees the new version before it's trusted) and often combine.

The testing pyramid

  • Unit tests — the base of the pyramid: fast, isolated, test one function/class in isolation from the network and other services. Should be the large majority of the suite because they're cheap to run and pinpoint failures precisely.
  • Integration tests — verify that a service correctly talks to its real (or realistically faked) dependencies — a database, a queue. Fewer than unit tests; slower, but catch the class of bug unit tests structurally can't (a wrong SQL query that's syntactically valid, a wire-format mismatch).
  • End-to-end tests — drive the whole system through a real user-facing flow. The fewest of the three — slow, often flaky, expensive to maintain — reserved for the handful of flows that matter most (checkout, login), not exhaustive coverage.
  • Contract testing — for microservices specifically: instead of a slow, brittle e2e test spanning every service, each consumer and provider of an API independently verify against a shared contract (e.g. Pact) that their expectations still match, without either side needing the other actually running.

Feature flags

Decouple deploying code from releasing a feature: ship the new code path behind a flag that's off by default, deploy it safely (it has zero behavioral effect while off), then flip the flag on — for everyone at once, for a percentage (a form of canarying at the feature level rather than the infrastructure level), or for specific users. This also makes "rollback" instant and cheap for a bad feature specifically: flip the flag off, no redeploy needed at all.

Rollback strategy

  • Decide the rollback mechanism before deploying, not while an incident is already happening — for infrastructure-level issues that's redeploying the previous artifact (fast with blue-green, slower with recreate); for a bad feature specifically, a feature flag flip is faster than either.
  • Database migrations complicate rollback the most: a migration that's already run and been written to by the new code often can't simply be reversed once real writes have happened — favor backward-compatible, additive migrations (add a column, don't rename/drop one in the same release) so the previous code version can still run against the new schema if a rollback is needed.

Interview checklist

  • Distinguish CI (build+test on every change) from CD (always releasable) from continuous deployment (auto-ships) precisely — these get conflated constantly, and being precise is a cheap, clear signal.
  • Pick a deployment strategy by the actual constraint: zero extra infrastructure → rolling; instant, safe cutover → blue-green; minimizing blast radius of an unknown-risk change → canary.
  • Know the testing pyramid's shape (many unit, fewer integration, fewest e2e) and be ready to justify why that shape, not just name the layers.
  • If the design involves a schema change, mention backward-compatible migrations specifically — it's the detail that makes a rollback plan actually credible.
