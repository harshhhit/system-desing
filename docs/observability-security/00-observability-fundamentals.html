Observability vs. monitoring

Monitoring answers questions you already thought to ask ahead of time ("is CPU above 80%?"). Observability is about being able to answer questions you didn't anticipate — "why did this specific user's request take 4 seconds at 3:12pm?" — by having enough raw signal recorded to investigate after the fact, not just a dashboard that was pre-built for a known failure mode. This page covers the general, cross-service version; Observability, Capacity, and Operations in the Database section covers the same pillars scoped specifically to a database.

The three pillars

PillarWhat it capturesBest for
MetricsNumeric time series — counters (only go up, e.g. total requests), gauges (go up or down, e.g. current memory), histograms (a distribution, e.g. latency buckets)Trends, dashboards, alerting thresholds — cheap to store, low cardinality
LogsDiscrete, timestamped events, ideally structured (JSON key/value, not free-text) rather than a printed sentence"What exactly happened on this one request/entity" — the detail metrics intentionally throw away
TracesThe path a single request took across every service it touched, broken into timed spans (one span per hop/operation)"Where did the time actually go" across a multi-service call — the thing neither metrics nor logs alone can answer

The three are complementary, not substitutes: a metric's spike tells you something is wrong and roughly when; a trace for a slow request from that window shows which service in the chain was slow; a log from that specific span shows why (the exact error, the exact query). Losing any one pillar leaves a real gap the other two can't fill.

Metrics in practice: the Prometheus/Grafana model

  • Pull-based scraping — Prometheus polls each service's /metrics HTTP endpoint on an interval, rather than services pushing metrics out — simpler service discovery, and a service that's down is visible as "scrape failed" rather than silently missing data.
  • Cardinality — every unique combination of metric name + label values (e.g. http_requests{status="500", path="/api/x", user_id="42"}) is a separate time series. Putting a high-cardinality value like a raw user ID in a label can multiply storage and query cost by orders of magnitude — a very common real-world Prometheus mistake, and a strong interview signal to mention.
  • Grafana queries Prometheus (or other backends) to render dashboards — it's a visualization layer, not a separate data store.

Logs: make them structured, and correlate them

  • Structured logging — emit JSON key/value fields instead of a formatted sentence, so logs are queryable/filterable (by status=500, by user_id) instead of requiring regex over free text.
  • Log levels — DEBUG/INFO/WARN/ERROR, tunable per-environment so production doesn't pay the volume cost of debug-level logging by default.
  • Correlation / request IDs — generate one ID at the edge (the API gateway, see Microservice Resilience Patterns) and thread it through every downstream call and every log line for that request, so a single request's logs can be reassembled across every service it touched — the low-tech precursor to full distributed tracing below.
  • Centralized aggregation (e.g. the ELK stack, or Grafana Loki) — ships every service's logs to one searchable place, since SSH-ing into individual instances to grep a log file doesn't scale past a handful of servers.

Distributed tracing

  • A single incoming request gets a trace ID; each hop/operation within it (a service call, a DB query) is a span with its own start/end time and a reference to its parent span — together they reconstruct the full call tree with per-hop timing.
  • Context propagation — the trace ID and current span ID travel with the request across process/service boundaries (typically an HTTP header, standardized as W3C traceparent), which is why every service in a traced system has to participate — one un-instrumented hop breaks the chain.
  • Sampling — tracing every single request in a high-traffic system is often too expensive to store; systems sample a percentage (or always trace slow/error requests specifically — "tail-based" sampling) to keep cost bounded while still catching the interesting cases.

SLI, SLO, SLA, and error budgets

  • SLI (Service Level Indicator) — the actual measured metric, e.g. "% of requests under 200ms."
  • SLO (Service Level Objective) — the internal target for that SLI, e.g. "99.9% of requests under 200ms, measured over 30 days."
  • SLA (Service Level Agreement) — an SLO turned into an external, often contractual, promise to customers — usually looser than the internal SLO, leaving margin.
  • Error budget — 100% − SLO is the amount of "badness" allowed before the SLO is breached (0.1% for a 99.9% SLO). It's a deliberate tool: once the budget for the period is spent, teams pause new feature risk and prioritize reliability work until it recovers — a concrete way to balance velocity against reliability instead of arguing about it abstractly every time.

Alerting

  • Alert on symptoms, not causes — page on "error rate is elevated" or "latency SLO is at risk," not on every individual possible cause ("disk is at 85%"); causes are for the dashboard/runbook you check once paged, not a separate page of their own.
  • Alert fatigue — too many low-value or flapping alerts trains responders to ignore pages, which is worse than having no alert at all; every alert should be actionable and rare enough to stay meaningful.
  • Tie alerts back to the SLO/error-budget framing above where possible — "we're burning error budget too fast" is a more durable alerting philosophy than a pile of ad hoc thresholds accumulated over time.

Interview checklist

  • Name all three pillars and, more importantly, say what each is for — interviewers listen for whether you know why you'd reach for a trace instead of a log, not just that both exist.
  • Bring up cardinality unprompted if metrics/labels come up — it's the detail that separates real Prometheus experience from a surface-level answer.
  • Mention correlation IDs / trace context propagation specifically when a design spans multiple services — "how do you debug a slow request across five services" is a very common follow-up.
  • Frame reliability targets as SLI → SLO → SLA, and use error budget language to justify a "pause features, fix reliability" call rather than treating uptime as a vague aspiration.
  • Justify alerting design around symptoms/actionability, not "alert on everything that could go wrong."
