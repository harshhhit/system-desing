Observability Fundamentals

The three pillars (metrics, logs, traces), Prometheus/Grafana, structured logging and correlation IDs, distributed tracing, SLI/SLO/SLA and error budgets, and alerting.

What you'll learn

By the end of this page you will be able to:

  • Explain observability vs. monitoring
  • Say what metrics, logs and traces are each for
  • Avoid the metric-cardinality trap in Prometheus
  • Propagate correlation IDs and trace context across services
  • Define SLIs, SLOs, SLAs and use an error budget
  • Design alerts on symptoms that stay actionable

What Observability Is For

Observability is the ability to understand what a running system is doing — and why — from the signals it emits, without shipping new code to investigate. It exists because modern systems fail in ways nobody predicted: in a system split across many services, a single slow request can have its cause three hops away, and without recorded signals you cannot reconstruct what happened after the fact.

💡 Important

You cannot secure, deploy safely, or fix what you cannot see. Every later page in this section — security and CI/CD — leans on the signals defined here.

How to Study This Section

This section covers running software in production: seeing what it does, keeping attackers out, and changing it without breaking it. Read the pages in this order, because each one relies on the one before:

  1. 00. Observability Fundamentals (this page) — metrics, logs and traces, then SLOs and alerting. Unlocks: a way to detect and explain problems, which both later pages depend on. Watch for: SLO vs. SLA — the difference is that an SLO is an internal reliability target, while an SLA is an external promise to customers, often with penalties, and is usually set looser than the SLO so the team is warned before the contract is breached.
  2. 01. Application Security Fundamentals — the OWASP Top 10, encryption and secrets management. Unlocks: designing out the common attack paths, and knowing which security events are worth logging and alerting on. Watch for: encryption in transit vs. at rest — the difference is that TLS protects data moving across a network, while at-rest encryption protects stored data if disks or backups are stolen; having one does NOT give you the other.
  3. 02. CI/CD & Deployment Strategies — automated build, test and release, plus canary and blue-green rollouts and rollback. Unlocks: shipping often with less risk, because a bad release is detected by the metrics and alerts from step 1 and reversed before it spends the error budget. Watch for: continuous delivery vs. continuous deployment — the difference is that with continuous delivery every change is ready to release but a human approves production, while with continuous deployment every change that passes the pipeline goes to production automatically.

Observability vs. Monitoring

Monitoring answers questions you already thought to ask ahead of time ("is CPU above 80%?"). Observability is about being able to answer questions you didn't anticipate — "why did this specific user's request take 4 seconds at 3:12pm?" — by having enough raw signal recorded to investigate after the fact, not just a dashboard that was pre-built for a known failure mode. This page covers the general, cross-service version; Observability, Capacity, and Operations in the Database section covers the same pillars scoped specifically to a database.

The Three Pillars

PillarWhat it capturesBest for
MetricsNumeric time series — counters (only go up, e.g. total requests), gauges (go up or down, e.g. current memory), histograms (a distribution, e.g. latency buckets)Trends, dashboards, alerting thresholds — cheap to store, low cardinality
LogsDiscrete, timestamped events, ideally structured (JSON key/value, not free-text) rather than a printed sentence"What exactly happened on this one request/entity" — the detail metrics intentionally throw away
TracesThe path a single request took across every service it touched, broken into timed spans (one span per hop/operation)"Where did the time actually go" across a multi-service call — the thing neither metrics nor logs alone can answer

The three are complementary, not substitutes: a metric's spike tells you something is wrong and roughly when; a trace for a slow request from that window shows which service in the chain was slow; a log from that specific span shows why (the exact error, the exact query). Losing any one pillar leaves a real gap the other two can't fill.

What to measure first

For any request-serving service, start with the four "golden signals": latency (p50/p95/p99, successful and failed requests separately), traffic (requests per second), errors (rate of failed requests) and saturation (how full the most constrained resource is — CPU, memory, connection pool, queue depth). The RED method (Rate, Errors, Duration) is the same idea for services; USE (Utilization, Saturation, Errors) is its counterpart for resources like disks and CPUs.

⚠️ Common mistake

Watching only the average latency. An average of 120 ms can hide a p99 of 4 s — the 1 in 100 requests that users actually complain about. Use histograms and track percentiles.

Metrics in Practice: the Prometheus/Grafana Model

  • Pull-based scraping — Prometheus polls each service's /metrics HTTP endpoint on an interval, rather than services pushing metrics out — simpler service discovery, and a service that's down is visible as "scrape failed" rather than silently missing data.
  • Cardinality — every unique combination of metric name + label values (e.g. http_requests{status="500", path="/api/x", user_id="42"}) is a separate time series. Putting a high-cardinality value like a raw user ID in a label can multiply storage and query cost by orders of magnitude — a very common real-world Prometheus mistake, and a strong interview signal to mention.
  • Grafana queries Prometheus (or other backends) to render dashboards — it's a visualization layer, not a separate data store.

Logs: Make Them Structured, and Correlate Them

  • Structured logging — emit JSON key/value fields instead of a formatted sentence, so logs are queryable/filterable (by status=500, by user_id) instead of requiring regex over free text.
  • Log levels — DEBUG/INFO/WARN/ERROR, tunable per-environment so production doesn't pay the volume cost of debug-level logging by default.
  • Correlation / request IDs — generate one ID at the edge (the API gateway, see Microservice Resilience Patterns) and thread it through every downstream call and every log line for that request, so a single request's logs can be reassembled across every service it touched — the low-tech precursor to full distributed tracing below.
  • Centralized aggregation (e.g. the ELK stack, or Grafana Loki) — ships every service's logs to one searchable place, since SSH-ing into individual instances to grep a log file doesn't scale past a handful of servers.

Distributed Tracing

  • A single incoming request gets a trace ID; each hop/operation within it (a service call, a DB query) is a span with its own start/end time and a reference to its parent span — together they reconstruct the full call tree with per-hop timing.
  • Context propagation — the trace ID and current span ID travel with the request across process/service boundaries (typically an HTTP header, standardized as W3C traceparent), which is why every service in a traced system has to participate — one un-instrumented hop breaks the chain.
  • Sampling — tracing every single request in a high-traffic system is often too expensive to store; systems sample a percentage (or always trace slow/error requests specifically — "tail-based" sampling) to keep cost bounded while still catching the interesting cases.
  1. Edge: the gateway receives a request with no traceparent, starts a trace and a root span.
  2. Hop: it calls Service A with traceparent: 00-<trace-id>-<span-id>-01; A creates a child span with that parent.
  3. Deeper: A's database query and its call to Service B become child spans of A's span, each with timings.
  4. Export: each service sends finished spans to the trace backend, which stitches them into one tree by trace ID.
  5. Correlate: every log line written during the request includes the same trace ID, so you can jump from a slow span to its logs.

SLI, SLO, SLA, and Error Budgets

  • SLI (Service Level Indicator) — the actual measured metric, e.g. "% of requests under 200ms."
  • SLO (Service Level Objective) — the internal target for that SLI, e.g. "99.9% of requests under 200ms, measured over 30 days."
  • SLA (Service Level Agreement) — an SLO turned into an external, often contractual, promise to customers — usually looser than the internal SLO, leaving margin.
  • Error budget — 100% − SLO is the amount of "badness" allowed before the SLO is breached (0.1% for a 99.9% SLO). It's a deliberate tool: once the budget for the period is spent, teams pause new feature risk and prioritize reliability work until it recovers — a concrete way to balance velocity against reliability instead of arguing about it abstractly every time.

Worked example: a 99.9% availability SLO over 30 days allows 0.1% × 43,200 minutes ≈ 43 minutes of failure. A bad deploy that causes 20 minutes of errors spends almost half the month's budget.

🧠 Think about it

Why not set the SLO to 100%? (Every extra nine costs exponentially more, users can't tell 99.99% from 100% because their own network is less reliable, and a 100% target leaves zero budget for deploying anything.)

Alerting

  • Alert on symptoms, not causes — page on "error rate is elevated" or "latency SLO is at risk," not on every individual possible cause ("disk is at 85%"); causes are for the dashboard/runbook you check once paged, not a separate page of their own.
  • Alert fatigue — too many low-value or flapping alerts trains responders to ignore pages, which is worse than having no alert at all; every alert should be actionable and rare enough to stay meaningful.
  • Tie alerts back to the SLO/error-budget framing above where possible — "we're burning error budget too fast" is a more durable alerting philosophy than a pile of ad hoc thresholds accumulated over time.

Implementation

Prometheus scrape config

scrape_configs:
  - job_name: api
    scrape_interval: 15s
    metrics_path: /metrics
    static_configs:
      - targets: ["api-1:8000", "api-2:8000"]
  • scrape_interval: 15s — how often Prometheus pulls; also the finest resolution of your graphs.
  • targets — static here; in Kubernetes or EC2 you use service discovery so new instances are scraped automatically.
  • Each target gets an up series: up == 0 means the scrape failed — the pull model's built-in "this service is down" signal.

PromQL you'll actually use

sum(rate(http_requests_total{job="api"}[5m])) by (status)
sum(rate(http_requests_total{job="api",status=~"5.."}[5m])) / sum(rate(http_requests_total{job="api"}[5m]))
histogram_quantile(0.99, sum(rate(http_request_duration_seconds_bucket{job="api"}[5m])) by (le))
  • rate(counter[5m]) — per-second increase of a counter over 5 minutes; counters only make sense through rate/increase.
  • The second line is the error ratio (5xx ÷ all) — the usual SLI for availability.
  • histogram_quantile(0.99, … by (le)) — p99 latency from histogram buckets; le (bucket upper bound) must survive the aggregation.

A structured log line

{"ts":"2026-10-04T15:12:03Z","level":"error","service":"checkout","trace_id":"4bf92f3577b34da6a3ce929d0e0e4736","user_id":"42","route":"/api/orders","status":500,"duration_ms":4012,"msg":"payment provider timeout"}

Every field is filterable; trace_id links it to the trace; user_id lives here (high cardinality is fine in logs), not in a metric label.

An alert rule on a symptom

groups:
  - name: api-slo
    rules:
      - alert: HighErrorRate
        expr: sum(rate(http_requests_total{job="api",status=~"5.."}[5m])) / sum(rate(http_requests_total{job="api"}[5m])) > 0.02
        for: 10m
        labels: { severity: page }
        annotations:
          summary: "API 5xx ratio above 2% for 10 minutes"
          runbook: "https://wiki.example.com/runbooks/api-errors"
  • expr — the user-facing symptom (error ratio), not a cause like CPU.
  • for: 10m — must hold for 10 minutes before firing; filters out blips that would cause alert fatigue.
  • runbook — every paging alert should link to what to check first.

🔥 Production insight

Observability systems fail too — usually exactly during the incident, when log volume spikes. Watch your pipeline's own health (dropped logs, scrape duration, ingestion lag) and keep at least one signal path that doesn't depend on the system being observed.

Security

  • Never log secrets or sensitive personal data — passwords, tokens, full card numbers, session cookies. Logs are copied widely and kept long; redact at the logger.
  • /metrics endpoints can leak internals (versions, hostnames, business counts) — expose them only on an internal port/network.
  • Restrict access to log and trace backends — they contain request details for every user.
  • Log security-relevant events (failed logins, permission denials, admin actions) so attacks are detectable — see Application Security Fundamentals.

Performance & Scalability

  • Cardinality is the main cost lever for metrics: series count = product of label value counts. Keep labels to bounded sets (status class, route template, region).
  • Log volume drives storage and ingestion cost; structured logs at the right level, plus sampling for high-volume success paths.
  • Tracing overhead is small per span but storage isn't — hence sampling.
  • Instrumentation on the hot path should be non-blocking: buffer and export asynchronously so a slow log/trace backend never slows requests.

Debugging workflow: from alert to root cause

  1. Metric: what changed and when? Error ratio, latency percentiles, traffic, saturation — and which service/route.
  2. Correlate: deploys, config changes, traffic shifts in that window.
  3. Trace: open slow/failed traces from the window; find the span where time or errors concentrate.
  4. Log: filter logs by that trace ID / service / time for the exact error.
  5. Fix and confirm: roll back or patch; watch the SLI return to normal and the burn rate drop.

Best Practices

Do

  • Instrument the golden signals for every service — consistent dashboards make any service debuggable by anyone.
  • Use histograms for latency and look at p95/p99.
  • Propagate one trace/correlation ID end to end and log it on every line.
  • Define SLOs with the product and alert on burn rate.
  • Attach a runbook to every paging alert.

Avoid

  • Unbounded label values in metrics.
  • Free-text logs that need regex to query.
  • Paging on causes (CPU, disk) that don't affect users yet — make them tickets or dashboard panels.
  • Logging secrets or personal data.

Interview Answer — What Is Observability?

Observability is the ability to understand what a running system is doing — and why — from the signals it emits, without shipping new code to investigate. Those signals are the three pillars: metrics (numeric time series such as request rate and latency), logs (structured, timestamped events), and traces (the timed path of one request across every service it touched).

It exists because modern systems fail in ways nobody predicted. Monitoring vs. observability — the difference is that monitoring checks conditions you decided on in advance ("is CPU above 80%?"), while observability lets you answer a question you did not anticipate ("why did this user's checkout take 4 seconds at 3:12pm?"). In a system split across many services, a single slow request can have its cause three hops away, and without recorded signals you cannot reconstruct what happened after the fact.

The pillars work as a chain: a metric spike tells you something is wrong and when → a trace from that window shows which service in the call chain was slow → the log from that span shows the exact error or query. A correlation ID / trace ID propagated through every hop is what ties the three together. Reliability targets are then expressed as SLIs (what you measure), SLOs (the internal target), and SLAs (the external promise), and alerts fire on user-facing symptoms such as burning error budget too fast.

Simple interview version

"Observability is being able to explain what a system is doing from the signals it emits — metrics, logs, and traces. Metrics tell me something is wrong and when, traces show which service in the request path was slow, and structured logs tied together by a correlation ID show exactly why. I define reliability as SLIs and SLOs with an error budget, and I alert on user-facing symptoms like error rate or latency, not on every possible cause."

One important interview follow-up

Q: Why not add the user ID as a label on every metric, so we can see each user's latency?

A: Because every unique combination of metric name and label values is a separate time series. A user_id label with a million users turns one metric into a million series — this is the cardinality problem — and it can exhaust Prometheus's memory and make queries unusably slow. Metrics should carry low-cardinality labels such as status code, route, and region; per-user or per-request detail belongs in logs and traces, which are designed to hold high-cardinality data. See Metrics in practice above.

Interview checklist

  • Name all three pillars and, more importantly, say what each is for — interviewers listen for whether you know why you'd reach for a trace instead of a log, not just that both exist.
  • Bring up cardinality unprompted if metrics/labels come up — it's the detail that separates real Prometheus experience from a surface-level answer.
  • Mention correlation IDs / trace context propagation specifically when a design spans multiple services — "how do you debug a slow request across five services" is a very common follow-up.
  • Frame reliability targets as SLI → SLO → SLA, and use error budget language to justify a "pause features, fix reliability" call rather than treating uptime as a vague aspiration.
  • Justify alerting design around symptoms/actionability, not "alert on everything that could go wrong."

Practice questions

What is each of metrics, logs and traces best at?

Metrics: cheap trends and alerting ("something is wrong, when"). Traces: where time went across services ("which hop"). Logs: exact detail of one event ("why").

SLI vs. SLO vs. SLA?

SLI is the measurement, SLO the internal target, SLA the external (often contractual) promise — usually looser than the SLO.

Why prefer percentiles over averages for latency?

Averages hide the tail: a fine mean can coexist with a terrible p99 that a meaningful share of users experience.

Why does Prometheus pull instead of services pushing?

Service discovery decides what should exist; a target that is down shows as a failed scrape (up == 0) instead of silently missing data, and services don't need to know where the monitoring lives.

How does a trace stay connected across five services?

Context propagation: each hop passes the trace ID and parent span ID (W3C traceparent) to the next; every service must participate, or the chain breaks there.

What is an error budget used for?

It's 100% − SLO. While budget remains, teams ship; when it's spent, they pause risky changes and prioritise reliability — turning reliability vs. velocity into a measurable decision.

Why is a user_id metric label dangerous?

Each label value combination is a new time series; a million users means a million series, exhausting memory and slowing queries. Put user-level detail in logs and traces.

Head-based vs. tail-based trace sampling?

Head-based decides at the start (cheap, but may drop the interesting slow request); tail-based decides after the trace completes, keeping slow/error traces, at the cost of buffering spans.

Why alert on symptoms rather than causes?

Symptoms (error rate, SLO burn) map to user pain and catch causes you didn't predict; cause alerts multiply, flap and fire without user impact, producing alert fatigue.

Checkout p99 jumped from 300 ms to 4 s at 15:10. Walk through your investigation.

Confirm in metrics which route/service and exact start time → check deploys/config changes then → open slow traces from 15:10 to find the slow span (e.g. payment API call) → read that span's logs via trace ID for the error/timeout → roll back or mitigate, confirm p99 recovers.

Your Prometheus server keeps getting OOM-killed after a release. What do you suspect?

The release added a high-cardinality label. Find the metrics with the most series, drop or relabel the label, and move that detail to logs.

The team gets 40 pages a week and has started ignoring them. What do you change?

Audit alerts: delete non-actionable ones, turn cause alerts into dashboard panels or tickets, add for: durations, and replace thresholds with SLO burn-rate alerts that each have an owner and runbook.

What Should I Remember?

  1. Monitoring answers known questions; observability lets you answer new ones.
  2. Metric (something's wrong, when) → trace (which service) → log (why), tied by a trace/correlation ID.
  3. Golden signals: latency, traffic, errors, saturation — latency as percentiles.
  4. Cardinality kills metric systems; high-cardinality detail belongs in logs and traces.
  5. SLI → SLO → SLA; error budget = 100% − SLO, and it drives feature-vs-reliability calls.
  6. Alert on symptoms, rarely, with runbooks.
