Scope of this page

This covers general, system-wide application security — the things that apply regardless of which database or framework sits underneath. Database Security and Access Control covers the same territory specifically for the data layer (row-level security, least-privilege DB roles, encryption of data at rest); Authentication Schemes: An Introduction and Secure Password Hashing Process cover authentication in depth. This page is the layer above both: the classes of vulnerability and the controls that apply to the application as a whole.

OWASP Top 10 — the categories that recur in almost every interview

CategoryWhat it isCore mitigation
Broken access controlA user can act on data/resources they shouldn't be able to — e.g. changing an ID in a URL to view another user's recordEnforce authorization server-side on every request, never trust a client-supplied ID alone; default-deny
Cryptographic failuresSensitive data transmitted or stored without proper encryption, or with weak/outdated algorithmsTLS everywhere in transit, strong at-rest encryption for sensitive fields, never roll your own crypto
InjectionUntrusted input is concatenated into a command interpreter (SQL, shell, LDAP) and executed as codeParameterized queries/prepared statements, never string-concatenate user input into a query
Insecure designA missing security control at the design stage — no amount of careful coding fixes a flaw baked into the architectureThreat modeling before implementation, not just code review after
Security misconfigurationDefault credentials left in place, verbose error messages leaking internals, unnecessary features/ports enabledHardened, minimal defaults; automated config scanning; no debug mode in production
Vulnerable/outdated componentsA known CVE in a dependency the app pulls in, unpatchedDependency scanning (e.g. Dependabot/Snyk) and a real patching cadence
Identification & authentication failuresWeak password policy, no rate limiting on login, session tokens that don't expire or rotateSee Secure Password Hashing Process and Rate Limiting & Throttling (apply it to auth endpoints specifically)
Software/data integrity failuresTrusting a package registry, CI pipeline, or auto-update mechanism without verifying integrity — supply-chain riskSigned packages/commits, pinned dependency versions, verified CI/CD pipeline permissions
Logging & monitoring failuresAn attack goes unnoticed because nothing logged the signal, or nobody was alerted on itSee Observability Fundamentals — security logging is a specific case of the general problem
Server-side request forgery (SSRF)The server is tricked into making a request to an attacker-chosen internal URL (e.g. a cloud metadata endpoint) on the attacker's behalfAllowlist outbound destinations for any server-side "fetch a URL" feature; never let user input fully control the target host
XSS didn't disappear — it's folded into "injection" conceptually

Cross-site scripting (unescaped user input rendered as executable script in another user's browser) is the classic example of injection targeting the browser instead of a database. The fix is the same shape as SQL injection's: never trust unescaped user input in an executable context — escape/encode output, and use a Content-Security-Policy header as defense in depth.

Encryption: in transit vs. at rest

  • In transit — TLS on every network hop, not just the public-facing edge; internal service-to-service traffic inside a "trusted" network is still worth encrypting (assume the network itself isn't a trust boundary) — this is part of what a service mesh's mTLS (see Microservice Resilience Patterns) automates.
  • At rest — disk/volume-level encryption as a baseline, plus field-level encryption for specifically sensitive data (payment details, health records) so even a database dump or backup isn't readable without the key.
  • Encryption without key management is theater — where the key lives, who can access it, and how it's rotated matters as much as the algorithm.

Secrets management

  • Never commit secrets (API keys, DB passwords, private keys) to source control — this is the single most common real-world security incident, and the easiest to prevent structurally.
  • Use a dedicated secrets store (HashiCorp Vault, AWS Secrets Manager, or — inside a cluster — a Kubernetes Secret, see ConfigMap & Secret for why Base64-encoded isn't the same as encrypted) rather than environment variables baked into an image or config file checked into a repo.
  • Rotate secrets on a schedule and immediately on suspected compromise — a secrets store that supports easy rotation is worth more than one that's merely "not in git."

Threat modeling, briefly

Before writing code, walk through: what are we protecting (assets), who might attack it and why (threat actors), how could they get in (attack surface — every input, every trust boundary crossed), and what's the impact if they succeed. A lightweight framework like STRIDE (Spoofing, Tampering, Repudiation, Information disclosure, Denial of service, Elevation of privilege) gives a checklist to walk a design against rather than relying on remembering to think of everything. This is "insecure design" from the table above addressed at the source — before implementation, not after.

Interview checklist

  • When asked to design something with user data, proactively name at least: input validation/parameterized queries, TLS in transit, authZ enforced server-side per-request, and secrets kept out of source control — these four come up constantly and are cheap to state.
  • Distinguish authentication (who are you) from authorization (what can you do) explicitly when a "broken access control" scenario comes up — most real incidents are authorization failures, not authentication ones.
  • If the design fetches a user-supplied URL server-side, flag SSRF and name an allowlist mitigation — a strong, specific signal.
  • Tie security logging back to Observability Fundamentals — an attack nobody logged or alerted on is functionally the same as no security control at all.
